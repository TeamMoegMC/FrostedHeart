# Data-driven natural deposits

- Status: Current source and functional verification; full-pack visual review found unresolved terrain-design issues.
- Last verified: 2026-11-04 (production verification remains 2026-10-24; subsequent work is the separate fixed sample below).
- Scope: `frostedheart:deposit` and the companion pack's hydrothermal configuration. This is a basin/fissure feature, not a general geology simulator.
- Code anchors: `DepositConfig`, `DepositFeature.place`, `DepositPlan.sampleColumn`, `DepositWriter.write`, `FHFeatures.DEPOSIT`.

## Entry and ownership

The mod registers one ordinary Minecraft `Feature<DepositConfig>`. The pack registers one configured/placed feature, `the_winter_rescue:deposits/main`, and attaches it through one `forge:add_features` biome modifier at `vegetal_decoration` (step 9), before freezing in `top_layer_modification` (step 10). Its placement list is empty. Do not add biome/count/height/in-square placement filters: the callback must run in each intersecting chunk, including portions outside the biome that selected the deposit.

The 2026-10-24 scheduling correction avoids a FeatureSorter cycle: snowy_shrubland already declares FH freezing before ADD modifiers append deposits; frozen_peaks instead receives FH freezing in MODIFY, after ADD. Putting both in step 10 imposed freeze → deposit and deposit → freeze. Deposits now run in step 9 in both cases. The current source loads in the full installed pack. Its late excavation still conflicts with floor decorations as described under client inspection below.

The tag `the_winter_rescue:deposit_generation` includes `minecraft:is_overworld`, `the_winter_rescue:all_twr`, and explicit biome IDs missing from that older tag. The exporter reads the existing normal preset to cover all its possible biomes; it never regenerates the climate table. Minecraft collects neighboring biomes and deduplicates the placed feature before decoration. Multiple profiles share this entry.

No new Mixin, BiomeSource, ChunkGenerator, world manager, saved-region data, ticking block, or heat source is part of this feature. Actual biome IDs, temperature/freezing behavior and biome-mining recipes still follow the existing biome source. A body can extend across a biome boundary. The thermal biome's ordinary features supply background detail independently of the large body; a small fragment is not guaranteed a large body or a successful feature at every point.

## Candidate placement

Units are blocks. Defaults belong to the pack JSON, not hardcoded mineral tables:

| Field | Initial value / contract |
|---|---|
| `dimension` | `minecraft:overworld` |
| `placement.cell_size` | 512; divisible by 16 |
| `placement.jitter` | 80 independently on X/Z |
| `placement.anchor_y` | inclusive -24..0 |
| `placement.chance` | 1.0, per candidate cell; matching biome and terrain checks still apply |
| `placement.salt` | 48151623; changing it relocates candidates |
| Maximum horizontal radius | 160 including transition, backing and details |
| Cell margin | `cell_size/2-jitter >= 176` |

`floorDiv` handles negative coordinates. World seed, salt and cell coordinates determine the first candidate, height, probability and independent geometry streams. The caller's random sequence and map iteration order do not select a body. An empty profile map, failed probability or conservative chunk bounds reject before cache/biome/base-height work. Bounds include the full allowed center area plus `MAX_RADIUS`; this prevents a chunk near a backup candidate from being skipped. The one-cell lookup is valid because every possible full envelope stays at least 16 blocks inside its cell.

A cold cell tries the original seeded candidate first, then the four corners of the allowed center area (`cell center +/- jitter` on X/Z). With zero jitter there is only one candidate. The first candidate with a matching registered biome/profile and suitable terrain wins; there is still at most one body per cell. Each candidate uses native `getNoiseBiome` at its own quart X/Y/Z and the current generator's RandomState sampler. All attempts share the sampled anchor Y, profile probability value and geometry seed. A profile's chance is therefore not rerolled by the backup points. The center is not moved after its biome is selected.

The cold-path upper bound is five biome queries and, when all five candidates match profiles but fail late, 25 `OCEAN_FLOOR_WG` base-height probes. A successful candidate stops the search; a fully rejected cell is also memoized. Probes use immutable base terrain, not distant loaded chunks. This bounded search raises the chance of finding suitable ground inside a thermal region; it does not identify connected biome components or guarantee a body in every thermal region. The change from 0.75 to 1.0 removes the extra random rejection of otherwise suitable cells. The current native climate probe found 811 roof-supported selections across eight seeds / 32,768 cells, versus the former 260. This is a selection count, not successful final decoration or discovery coverage.

Each decoded `DepositConfig` owns 64 atomic memo slots. Entries include world seed, cell, build bounds, generator identity and RandomState identity. Generator and RandomState keys are weak references. Plans retain geometry and immutable material configuration; they retain no level, chunk, terrain callback or generated flag. Races/eviction can recompute a candidate without moving it. Every intersecting chunk still writes its portion. A new decoded config owns a new cache; ordinary `/reload` is not promised to rebuild frozen worldgen registries in 1.20.1.

## Shape and material schema

`profiles` maps biome registry IDs to objects with `chance`, `shape`, `materials`, `ores`, and `ore_chance`. `Range` objects contain inclusive integer `min/max`. Materials use Minecraft BlockState JSON and `#namespace:block_tag` references. Each ore entry has `host`, `state`, and positive `weight`. The codec prepares cumulative weights by host tag once. Tag membership remains Minecraft's current binding, rather than a premature copy made before tags load.

| Shape field | Hydrothermal value |
|---|---|
| `length` / `width` | 160..224 / 64..96 |
| `height` | 40..56 total vertical envelope |
| `pool_depth` | 6..10 |
| `water_offset` | -6 relative to anchor Y |
| `bend` | 0.18 of half-width, 0..0.35 supported |
| `roughness` | 2 blocks per horizontal axis, maximum 2 |
| `terraces` | 2, supported range 0..3 |
| `ore_chance` | 0.16 in the coherent mineral mask; separate from material weights |

The codec rejects sizes that cannot contain the pools, terrace headroom or full radius. Length >=96, width >=48, height 32..56 and pool depth 3..12 are the supported family. The envelope check is `hypot(length.max/2,width.max/2)+25+ceil(sqrt(2)*roughness)<=160`. The 25-block allowance covers transition, lining diagonal and details. This conservative bound is intentionally larger than the visible cave.

The immutable plan has four main fissure segments, a separate four-segment dry route, zero to two short branches and two to three chamber sections. Width, bend, depth, chamber proportions and roof vary by seed; this is not a placed template. Two coherent 2D fields at a fixed 24-block scale perturb the outline. No per-voxel climate or 3D octave field is evaluated. An outer smoothstep reduces alteration/mineral influence to zero without cutting at biome borders.

Columns return one open interval `[floor,roof)`, a water level, a route flag and alteration/mineral masks. Multiple independent cave floors at the same X/Z are outside this feature's scope. The dry route raises its floor above the shared main water level and retains headroom; terrace basins have their own rims and levels.

## Writing and fluid behavior

`DepositWriter` samples a 20x20 geometric halo for 16x16 current-chunk writes. Six primitive arrays use about 8.5 KiB including array headers on this JVM, excluding the existing worldgen API's allocations. The maximum tested vertical scan is 56+16=72 blocks, or 18,432 candidate positions per fully covered chunk. No neighboring terrain is read for geometry. Reads use the current chunk; changed states use normal `WorldGenLevel.setBlock`, preserving the existing worldgen heightmap, postprocessing and FH observer path.

A two-block dilation builds backing even in preexisting air. Inner sediment/ore skin is added inside that backing. The hydrothermal profile's `materials.lining` uses the existing `minecraft:tuff` block. This feature registers no block or item and adds no material to the global protection tags. Tuff keeps its ordinary tags and replacement behavior; backing placed by this feature can be modified by later generation that targets tuff.

On 2026-10-24 the user requested removal of the dedicated lining block. Its registration, resources and tag additions were deleted, and the authored profile, exported production configuration and GameTest fixtures were changed to vanilla tuff. A fresh Forge acceptance with the current materials ran 600.28 seconds / 393,600 ticks with water 24,946 → 24,946. This proves the tested exposed basin's fluid behavior; it does not validate every full-pack feature interaction or the terrain's visual design. The older saved reports using the dedicated material remain historical.

Protection precedes carving. Bedrock, block entities, protected states and unrelated non-carvable blocks survive. Existing water/air are explicitly handled; existing lava is not silently replaced. The `deposit_carvable` tag includes natural ores/debris so carving does not leave floating ore; the narrower `deposit_host` and per-ore host tags control mineralization. Static basalt columns do not emit particles or heat. Mineral pockets share global 4x3x4 cells along the fissure and continue across chunk boundaries.

Water follows normal physics and existing thermal/freezing rules. No temperature field, replenishment tick, virtual heat, or forced water tick loop maintains it. Worldgen uses normal postprocessing. The GameTest deliberately schedules source-water ticks to challenge an exposed basin; that is test code only.

Late decoration reduces overwrites by earlier features, but this is not a generic structure-avoidance system. Structures made of otherwise carvable stone can intersect the body; block-entity/protected-state preservation does not preserve an entire building footprint. Third-party features that ignore protection tags, including later neighboring writes, remain a compatibility boundary. A blocked basin/route is not an uninterrupted successful site. Layout determinism does not imply that every final block placed by other features is independent of generation order.

## Authoring and verification

The pack's authored source is `Scripts/worldgen/deposits/placement.json` plus `profiles/*.json`. Run `python Scripts/worldgen/deposits/export_deposits.py --write`, then `--check`. An optional `--registry <block-registry.json>` checks block IDs against the actual Forge registry emitted by the acceptance test. Real Codec/tag loading validates the registered resources. `normal.json`, noise settings and notebooks are not rewritten.

The 2026-10-24 background correction restores the thermal biome's original feature IDs and their generation steps: `cave/diorite`, lava and hydrothermal lakes, `cave/hydrothermal_delta`, existing ores and `cave/hydrothermal_magma`, `cave/calcite_strip`, vines and springs. Calcite and vines return to 30 and 75 attempts; geodes return to the original 1.4-attempt expectation. The reduced `deposits/background_calcite` wrapper was removed. These ordinary biome features run regardless of whether a large deposit was selected. Existing lava/magma entries are restored original content; this correction adds no heat source mechanism or new material.

`cave/hydrothermal_delta` now uses 40 fixed attempts per chunk, square X/Z sampling, the original starting height range, and a downward scan of at most 32 blocks to a sturdy floor. It no longer uses `count_on_every_layer` followed by `height_range`: the latter discarded each discovered surface Y. Vanilla `DeltaFeature` requires a solid target with air above, so placing it at an unrelated height defeated its ground test. Scans in the delta, lake, magma, calcite and vine entries now recognize both `minecraft:air` and `minecraft:cave_air`. This includes air produced by carvers and the large deposit itself.

Restoring visual detail also restores its generation work. Historical timing/mineral results from the reduced-background configuration do not establish performance or balance of this correction. It affects newly decorated chunks; existing saved chunks are not retroactively decorated. Changing candidate selection while generating more of an old cell can create a transition at the boundary between old and new chunks.

Adding a material/scale variant uses another profile and existing tags/blocks. It adds neither a Java subclass nor another global placement callback. Completely different terrain families should be considered separately instead of adding switches indefinitely.

Focused Forge acceptance lives in `DepositGameTests`. The pack's `prepare_acceptance.py` stages immutable legacy data and current dependency graphs into the gameTest resource set. It also supplies test-only preset/dimensions for an old/new/core comparison and an ordinary-biome control. The ordinary fixture keeps the production profiles so it exercises actual non-matching biome queries. FH's existing `SeedSetable` initializes all comparison dimensions to seed 0 and rebuilds their RandomStates; candidate/cache tests exercise seeds 0..7 with a test-only cell chance of 0.75 to retain accepted and rejected probability samples, then restore seed 0. Native FULL generation uses the current production placement configuration.

Use `Scripts/worldgen/deposits/acceptance.gradle` as an init script for a long test when other work shares the build directory. It snapshots compiled runtime directories once, avoiding class deletion during another compilation. It does not copy/recompile source checkouts or compare path-sensitive hashes. Default fluid acceptance requires both 600 wall-clock seconds and 12,000 ticks. `-PdepositFluidSeconds=0` is an iteration smoke test only. The measured cache allocation bound covers the memo and 64 geometry payloads; shared decoded profiles and Minecraft registry objects are accounted separately.

Evidence and numerical conclusions belong in the companion pack's `Scripts/worldgen/deposits/results/` and the linked development diary. Fixed-biome tests use the vanilla 1.20.1 noise settings and real FH/Forge features, not the pack's complete custom noise router or every installed pack mod. They establish local correctness/cost comparisons; actual world-weighted frequency, all structure combinations and client transparency/render costs require the complete pack/client and are not inferred from server plots.

`DepositClimateEvidence` separately reads the actual normal preset and pack NoiseRouter to check native climate selection and base-height support. Its saved historical sample covers eight seeds / 32,768 cells: 290 centers selected the thermal biome, 260 passed build/roof checks under the former one-point placement. The current five-point run queries 161,632 biomes: 877 cells encounter the thermal biome and 811 pass build/roof checks. Its biome histogram counts queries, while `thermal_selected` and `roof_accepted` count cells. The probe uses the native ParameterList operation and production plan geometry, without generating surfaces or features, and does not turn the fixed-biome benchmark into a full-pack benchmark.

## Client inspection and current design limitations

The opt-in `DepositClientValidation` source is in `src/gametest`, and `Scripts/worldgen/deposits/visual_acceptance.gradle` packages only that driver into a separate validation JAR. The normal production JAR includes no driver or GameTest fixtures. `run_visual_validation.py` creates an isolated game directory using all 61 installed mods and current pack data; it does not open the user's saved world. `review_saved_terrain.py` reads the original and new Anvil files for comparison.

At seed `-4191132991717996371`, two 8×8 FULL samples match the original save's thermal biome volume exactly. Restored calcite and vines are visible and more abundant. The large body at `(-1335,-10,-269)` was also generated and inspected over 20×20 FULL chunks. Only 1,067 of its 2,030 geometric interior quart samples are thermal (52.56%). The original visited point's first cell still has no selected body, and the second visited patch is outside the selected body's main cavity. A selected cell is therefore not equivalent to a recognizable body at an arbitrary point in that biome.

`hydrothermal_magma` uses single-layer disks (radius 2–4, 50–100 attempts/chunk) on the old underwater floor. Step-9 excavation removes neighboring rock while `DepositWriter` preserves magma, which is absent from `deposit_carvable`. The full-pack inspection finds 1,557 magma blocks in geometric air cells and screenshots show suspended slabs. The fixed `waterY+3` route also forms long, level promenades; a two-block outline warp does not change that large-scale organization. These are unresolved design/integration findings even though the functional GameTest gates pass.

The actual sampled route has 1,257 intended columns, 1,219 clear columns, and one connected clear component. A 3×3 check restricted to the intended footprint has several components; this is distinct from the clean geometry test and excludes potentially usable ground outside that footprint. Its strict air/sturdy-floor predicate is not collision-based pathfinding and is not a requirement that natural terrain remain an empty, perfectly dry road.

The review's raw JSON, framebuffer PNGs, saved-block sections, new native probe and functional results are under the pack's `Scripts/worldgen/deposits/results/2026-10-24-visual-review/`. An early-body decoration-order experiment changes only the isolated runtime's biome modifier to step 2; production data remains at step 9. At the same pool camera, magma in geometric air drops from 1,557 blocks to zero. Clean-route columns drop to 861, mainly because floor cells become water/bubble columns. The user explicitly accepts this natural decoration of the shoreline; it does not justify extra route protection blocks or filters. Recommendations and visual acceptance are kept separate from implemented behavior in that review. The 600-second functional checks above apply to production step 9, not the experimental step 2 ordering.

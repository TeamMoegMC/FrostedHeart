# TWR 城镇玩法现状、建设路径与自给能力分析

> 分析对象：The Winter Rescue（TWR）整合包当前仓库与 FrostedHeart 城镇实现  
> 分析日期：2026-08-09  
> FrostedHeart：`master` / `8776ed035`  
> TheWinterRescue：`1.20` / `05df2b2b`

## 1. 结论摘要

当前城镇玩法已经具备住宅、居民、仓库、狩猎、矿业和热网等核心结构，但还不是一个能够独立运行的完整生产社会。

按“长期不从城镇之外补充物资”的严格口径：

- **能量端只能阶段性自给，不能依靠城镇矿场永久自给。**城镇可以开采煤、泥炭和原木，并通过玩家工业线加工成能量塔燃料；但矿场统一消耗每区块 1000 单位、当前不恢复的 `ORE` 储量。
- **按当前仓库实际代码，食物端不能仅靠狩猎自给。**没有专用换算配方的物品统一按 1 单位计算；每个满产猎人每天约产出 3.454 单位食物，却要消耗 6.5 单位食物，即使全体居民都是满产猎人也只能覆盖约 53.1%。
- **开发组说明这不是最终设计。**开发组在用户提供的聊天截图中明确表示，默认食物单位应为“饱食度＋饱和度”，但“只是还没写”。按通常的实际饱和点解释，熟肉将显著增加食物资源量，30 人口理论上约 4 名满级猎人即可供餐；该结果目前只是未落地规则的情景推演，不能当作当前游戏行为。
- **烹饪的作用取决于采用哪套口径。**当前代码下，生肉和熟肉都是 1 单位，烹饪只提高营养恢复；开发组预期口径下，熟肉还会显著增加可供给的食物资源量。成熟城镇可用 Create 机械风扇批量烟熏，把持续烹饪燃料消耗降为 0。
- **把玩家外围工业和农业计入城镇后，可以建立资源闭环。**推荐使用自动树场生产锯末压块作为长期燃料，以自动胡萝卜、马铃薯、南瓜或畜牧场补足食物。
- **当前只能确认“生产闭环＋手动搬运”可行，不能确认完整自动物流闭环。**FrostedHeart 中已有仓库接口相关代码，但在当前 TheWinterRescue 仓库中未找到其生存可获得配方、任务或战利品入口。
- 对当前可运行版本的高人口城镇而言，**食物是主要扩张瓶颈，能源是可以通过加工和基础设施解决的工程问题**；若开发组预期的食物单位规则落地，食物瓶颈很可能转为狩猎与烹饪吞吐量问题。

## 2. 分析目标与口径

### 2.1 本文回答的问题

1. 当前版本城镇玩法实际包含什么内容。
2. 如何建设当前机制允许的最高发展程度城镇。
3. 城镇维持能量塔需要哪些燃料、居民和加工设施。
4. 城镇居民食物是否能依靠狩猎闭环。
5. 能量与食物能否做到短期自给、长期自给和全自动自给。
6. 推荐的发展顺序、产能目标和可计算的游戏时间。

### 2.2 “自给”的四层判定

本文不把“仓库里暂时有库存”直接称为自给，而将其分成四层：

| 层级 | 判定标准 |
|---|---|
| 收支平衡 | 日产量不低于日消耗量 |
| 供应闭环 | 原料和加工链都能在基地内部完成 |
| 长期可再生 | 不依赖不可恢复矿藏、遗迹战利品或持续外出采集 |
| 自动闭环 | 生产、入库、加工、送入能量塔及居民结算均不需玩家搬运 |

文中“城镇自身”仅指 FrostedHeart 的城镇建筑和居民工作系统；“城镇＋外围工业”还包括玩家建设的 Create、沉浸工程、木炭坑、农场和物流设备。

### 2.3 统一计算假设

- 一个 Minecraft 日为 24000 tick，即现实时间 20 分钟。
- 能量塔保持普通模式连续运行，不使用过载。
- “初期”表示没有能量塔效率研究；燃料效率系数为 `0.7`。
- “满研究”表示完成两级燃烧效率研究和一级热能产率研究；燃料效率系数为 `0.9`，热能产率系数为 `1.2`。
- “满级矿工”按最大生产力 `2.0` 计算，日产总矿物 7 单位。
- “满级猎人”按最大生产力 `2.5` 计算。
- 食物结论分成“当前代码口径”和“开发组预期口径”；前者用于判断当前可玩版本，后者仅用于评估尚未实现的设计影响。
- 所有结果都是长期平均值；带随机掉落的生产线在单日可能波动。
- 计算的是城镇处于活动、区块加载且正常执行 tick 的游戏日，不等于离线现实时间。

## 3. 分析流程

### 3.1 固定版本与证据范围

首先记录两个仓库的分支和提交号，避免后续代码更新使结论失去版本边界。证据优先级如下：

1. FrostedHeart Java 运行逻辑；
2. FrostedHeart 默认配置和数据包；
3. TheWinterRescue KubeJS 覆盖、追加配方和研究配置；
4. 开发组的直接说明，用于确定预期设计，但在对应实现提交前不替代运行逻辑；
5. 语言文件、任务文字和更新日志，仅用于解释玩法意图，不替代运行逻辑。

当代码与开发组说明不一致时，本文同时记录“当前实际行为”和“预期行为”，所有自给结论都标明使用哪套口径。开发组说明只能证明预期方向；代码、数据或游戏内实测才能证明功能已经落地。

### 3.2 枚举城镇正式入口

从 `content/town` 目录和城镇 README 枚举现有建筑与职责：

- `HouseBuilding`：居民住房和每日食物结算；
- `WarehouseBuilding`：虚拟资源和容量；
- `HuntingBaseBuilding`：居民狩猎与战利品生产；
- `MineBaseBuilding`：分配矿工、汇总矿点并进行开采；
- `MineBuilding`：记录矿点位置和生物群系资源权重。

当前没有独立的城镇农场、林场、厨房或燃料加工建筑。因此农业和工业加工都属于玩家外围系统，而不是居民工作系统。

参考：[城镇系统 README](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/town/README.md)

### 3.3 追踪每日结算链

分析按以下链路进行：

1. 城镇 tick 选择可工作的建筑；
2. 住宅按居民数消耗食物并计算满足度、营养和温度效果；
3. 狩猎所按居民生产力决定战利品表投掷次数；
4. 矿场按居民生产力申请开采量，再按矿点权重分配产物；
5. 产出进入城镇虚拟仓库，受仓库容量限制；
6. 能量塔独立按 tick 消耗实体燃料，并在 T2 阶段向热网供热。

### 3.4 建立量化模型

分别建立四个模型：

- 能量塔基础燃料消耗；
- T2 热网负载引起的附加消耗；
- 矿工对各种燃料原料的日产量；
- 居民食物消耗与猎人食物日产量。

然后用同一组人口与建筑数量进行收支比较。对于尚未实现但足以改变结论的开发计划，另建条件式模型，并显式列出公式解释、未定义物品和配置是否同步调整等未知项。

### 3.5 审计可再生性与物流

最后再检查：

- 原料是否使用可恢复的地形资源；
- 配方中间物是否真的能被能量塔接受；
- 仓库能否把虚拟库存自动送入加工设备和能量塔；
- 是否存在能够让数字变绿、但不符合正常玩法意图的漏洞路径。

这一步用于区分“短期能运行”“长期能自给”和“完全自动化”。

## 4. 当前城镇玩法现状

### 4.1 已形成的玩法循环

当前可正常形成的主循环是：

1. 在能量塔有效范围内建设并扫描住宅；
2. 接纳居民并分配住房；
3. 建设仓库以扩大虚拟资源容量；
4. 建设狩猎所，安排居民生产食物和副产物；
5. 建设矿井基站并连接不同生物群系矿点；
6. 将矿产或狩猎产物手动取出，用于玩家工业和生存；
7. 从玩家生产系统补充食物和能量塔燃料。

居民具有健康、精神、力量、智力、年龄和职业熟练度。狩猎与采矿生产力会随属性和熟练度提高，因此成熟居民显著强于刚招募居民。

### 4.2 建筑规模的最优方向

住宅和狩猎所都按建筑端点消耗热量，而不是按建筑面积或居民人数直接增加每 tick 热耗：

- 每座接入热网的住宅消耗 1 热量/tick；
- 每座接入热网的狩猎所默认消耗 1 热量/tick；
- 矿井基站不消耗该热网负载。

因此，在扫描上限、床位和空间评分允许范围内，最优方向是：

- 少建小住宅，多建大住宅；
- 建设一座足够大的狩猎所，而不是多座小狩猎所；
- 矿点必须放在不同区块，以增加独立矿藏储量；
- 仓库留出产物波动和多日食物缓冲空间。

参考：[HouseBlockEntity.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/town/buildings/house/HouseBlockEntity.java#L155)、[HuntingBaseBlockEntity.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/town/buildings/hunting/HuntingBaseBlockEntity.java#L127)

### 4.3 当前缺少的关键职责

- 没有居民农业建筑，无法让居民种植主粮；
- 没有居民林业建筑，森林矿点产出的原木仍按不可恢复矿藏计算；
- 没有城镇内部燃料加工建筑；
- 当前整合包中没有确认仓库接口的生存获取入口；
- 因此城镇资源与玩家机器之间仍需要玩家参与搬运。

## 5. 能量塔模型

### 5.1 能量塔认可的燃料

当前能量塔配方包含：

| 最终燃料 | 配方时长 |
|---|---:|
| 泥炭 | 500 |
| 木炭 | 1000 |
| 煤 | 1600 |
| 锯末压块 | 1600 |
| 煤压块 | 1800 |
| 木炭压块 | 1800 |
| 焦煤 | 3200 |

实际得到的燃料进度为：

```text
单件有效燃料进度 = 配方时长 × E
E = 0.7 + generator_effi 研究加成
```

两级效率研究各提供 10%，因此：

```text
初期 E = 0.7
满研究 E = 0.9
```

参考：[GeneratorData.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/climate/block/generator/GeneratorData.java#L170)、[coal.json](FrostedHeart/src/main/resources/data/frostedheart/recipes/generator/coal.json)、[coal_coke.json](FrostedHeart/src/main/resources/data/frostedheart/recipes/generator/coal_coke.json)、[b_coal.json](TheWinterRescue/kubejs/data/the_winter_rescue/recipes/generator/b_coal.json)

### 5.2 T1 基础消耗

普通运行时，能量塔每 tick 固定消耗 1 点燃料进度。因此：

```text
T1 每日燃料进度需求 = 24000
```

该基础消耗与连接了多少城镇建筑无关；即使没有热网负载，只要能量塔保持运行，就持续消耗燃料。

满研究时的 T1 日需求为：

| 燃料 | 每游戏日需求 |
|---|---:|
| 泥炭 | 53.33 |
| 木炭 | 26.67 |
| 煤 | 16.67 |
| 煤压块/木炭压块 | 14.81 |
| 锯末压块 | 16.67 |
| 焦煤 | 8.33 |

参考：[GeneratorData.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/climate/block/generator/GeneratorData.java#L300)

### 5.3 T2 蒸汽机制

T2 会先执行与 T1 相同的固体燃料逻辑，再处理蒸汽和热网。因此，**蒸汽不会替代固体燃料**。

默认参数：

- 蒸汽输入速率：144 mB/tick；
- 每 60 tick 增加 1% 蒸汽等级；
- 充至 100% 需要 6000 tick，即现实 5 分钟；
- 总蒸汽输入量为 864000 mB，即 864 桶；
- 内置罐只有 5000 mB，必须在启动阶段持续泵入蒸汽。

蒸汽等级达到 100% 后，代码直接停止继续抽取，不会在正常运行中自然衰减；但能量塔仍持续消耗固体燃料。

参考：[T2GeneratorLogic.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/climate/block/generator/t2/T2GeneratorLogic.java#L128)、[FHConfig.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/infrastructure/config/FHConfig.java#L366)

### 5.4 T2 热网附加消耗

满蒸汽时，T2 每 tick 最多维持 25 热量。热网消耗的热量会按以下近似关系转化为额外燃料进度：

```text
每日燃料进度需求 D(k, H)
  = 24000 + 24000 × k × 8 / (25 × H)

k = 每 tick 总热网负载
H = 1 + generator_heat 研究加成
```

一级热能研究为 20%，所以满研究 `H = 1.2`。

典型场景：

| 场景 | 初期每日进度 | 满研究每日进度 |
|---|---:|---:|
| T1，无热网附加负载 | 24000 | 24000 |
| T2，一住宅＋一狩猎所 | 39360 | 36800 |
| T2，两住宅＋一狩猎所 | 47040 | 43200 |

两种 T2 场景的满研究燃料需求：

| 燃料 | 一住宅＋一狩猎所 | 两住宅＋一狩猎所 |
|---|---:|---:|
| 泥炭 | 81.78 | 96.00 |
| 木炭 | 40.89 | 48.00 |
| 煤 | 25.56 | 30.00 |
| 煤压块/木炭压块 | 22.72 | 26.67 |
| 锯末压块 | 25.56 | 30.00 |
| 焦煤 | 12.78 | 15.00 |

参考：[GeneratorData.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/climate/block/generator/GeneratorData.java#L311)

## 6. 城镇矿业与燃料路线

### 6.1 矿工日产量

标准矿工日产总产物 3.5 单位，满级矿工最大生产力为 2.0，因此：

```text
满级矿工日产总产物 = 3.5 × 2.0 = 7
```

参考：[FHConfig.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/infrastructure/config/FHConfig.java#L846)

矿场先计算全部矿工请求的总产量，再按连接矿点的权重和区块分配产物。因此矿点权重决定其中有多少比例能变成燃料原料。

参考：[MineBaseBuilding.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/town/buildings/mine/MineBaseBuilding.java#L162)

### 6.2 主要矿点产能

| 矿点 | 燃料原料权重 | 满级矿工日产燃料原料 |
|---|---:|---:|
| 没有专属配方的群系回退 | 煤 1 / 总权重 2 | 3.5 煤 |
| 化石矿床 | 煤 8 / 总权重 24 | 2.333 煤 |
| 毁坏沼泽 | 泥炭 12 / 总权重 32 | 2.625 泥炭 |
| 冻结/毁坏森林 | 原木 15 / 总权重 27 | 3.889 原木 |
| 松林 | 原木 12 / 总权重 26 | 3.231 原木 |

参考：[MineBuilding.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/town/buildings/mine/MineBuilding.java#L55)、[biome_mine.js](TheWinterRescue/kubejs/server_scripts/src/recipes_types/frostedheart/biome_mine.js)

### 6.3 路线 A：直接烧煤

回退矿点一名满级矿工日产 3.5 煤。

满研究时：

| 场景 | 需求煤/日 | 满级矿工数 |
|---|---:|---:|
| T1 | 16.67 | 5 |
| T2，两热网端点 | 25.56 | 8 |
| T2，三热网端点 | 30.00 | 9 |

优点是没有加工链；缺点是居民占用多、矿藏消耗快。

### 6.4 路线 B：煤转焦煤

如果按一煤加工成一焦煤计算，燃料时长由 1600 提高到 3200，等效翻倍。

满研究时：

| 场景 | 需求焦煤/日 | 回退矿点满级矿工数 |
|---|---:|---:|
| T1 | 8.33 | 3 |
| T2，两热网端点 | 12.78 | 4 |
| T2，三热网端点 | 15.00 | 5 |

焦煤路线结构简单，适合作为煤压块工业线完成前的过渡方案。

### 6.5 路线 C：煤转煤压块

当前加工链为：

```text
煤
→ Create 磨粉：平均 1.5 煤粉
→ 石灰水混合：1.5 含石灰煤
→ 清洗：1.5 湿煤粉
→ 压制：3 湿煤压块
→ 烘干：3 煤压块
```

所以长期平均：

```text
1 煤 ≈ 3 煤压块
原始配方时长：1600 → 3 × 1800 = 5400
```

参考：[milling.js](TheWinterRescue/kubejs/server_scripts/src/recipes_types/create/milling.js#L61)、[mixing.js](TheWinterRescue/kubejs/server_scripts/src/recipes_types/create/mixing.js#L25)、[compacting.js](TheWinterRescue/kubejs/server_scripts/src/recipes_types/create/compacting.js#L14)、[smoking.js](TheWinterRescue/kubejs/server_scripts/src/recipes_types/minecraft/smoking.js#L14)

回退矿点一名满级矿工每天的期望产量为：

```text
3.5 煤 × 3 = 10.5 煤压块/日
```

所需满级矿工：

| 场景 | 初期 | 满研究 |
|---|---:|---:|
| T1 | 2 | 2 |
| T2，两热网端点 | 3 | 3 |
| T2，三热网端点 | 4 | 3 |

这是当前最节省城镇居民的矿产燃料路线。不过该结果只计算能量塔燃料余额，没有扣除磨粉、混合、压制等设备自身的机械动力和其他原料成本。

### 6.6 路线 D：泥炭

毁坏沼泽一名满级矿工仅产 2.625 泥炭/日，而满研究 T1 需要 53.33 泥炭/日，三端点 T2 需要 96 泥炭/日：

| 场景 | 满级矿工数 |
|---|---:|
| T1 | 21 |
| T2，三热网端点 | 37 |

泥炭适合应急、点火或消耗零散库存，不适合高等级城镇主供能。

### 6.7 路线 E：原木、木炭与锯末压块

直接木炭路线的能量密度不高：9 原木合成一个原木堆，木炭战利品表平均得到 6.4 木炭，相当于每原木约 0.711 木炭。

更适合长期运行的是：

```text
自动树场
→ 原木磨粉，平均 4 锯末/原木
→ 4 锯末＋25 mB 杂酚油
→ 浸油锯末压块
→ 烘干
→ 锯末压块
```

每原木期望得到约 1 个最终锯末压块。木炭坑配置为每处理一原木产生 200 mB 杂酚油，因此少量原木进入木炭坑即可为大量锯末压块提供杂酚油。

参考：[charcoal.json](TheWinterRescue/kubejs/data/charcoal_pit/loot_tables/blocks/charcoal.json)、[compacting.js](TheWinterRescue/kubejs/server_scripts/src/recipes_types/create/compacting.js#L27)、[charcoal_pit-common.toml](TheWinterRescue/config/charcoal_pit-common.toml)

满研究 T2 的长期树场目标：

| 热网场景 | 锯末压块需求 | 连同杂酚油原木的建议总量 |
|---|---:|---:|
| 一住宅＋一狩猎所 | 25.56/日 | 约 29 原木/日 |
| 两住宅＋一狩猎所 | 30.00/日 | 约 34 原木/日 |

换算成现实时间只需要约 1.5～1.7 原木/分钟。自动树场可以把这条路线变成真正的可再生能源闭环。

### 6.8 中间压块不能直接烧

能量塔只识别最终配方中的燃料。以下物品虽然可能是普通炉子的燃料，但当前没有能量塔配方：

- 湿煤压块；
- 绑定煤压块、绑定木炭压块；
- 浸油煤压块、浸油木炭压块、浸油锯末压块；
- 稻草压块。

因此生产线必须完成最终烘干步骤。

### 6.9 每种供能方案需要的居民数

本节的“居民数”专指为能量塔供应原料的矿工数，不包含猎人和其他居民。计算公式为：

```text
所需矿工数
= ceil(能量塔每日燃料进度需求
       / (单名矿工每日原料产量 × 加工产率 × 最终燃料配方时长 × 燃烧效率))
```

口径：

- 表中的“初/满”分别表示没有能量塔研究、完成全部相关能量塔研究；
- 主表人数按满级矿工生产力 `2.0`、日产总产物 7 单位计算；
- “标准工”按生产力 `1.0`、日产总产物 3.5 单位计算；
- 人数向上取整，不能用小数居民；
- T2 两端点表示一住宅＋一狩猎所，三端点表示两住宅＋一狩猎所；
- 只计算塔的持续燃料，烹饪和其他工业机器的能源在后文单列。

| 供能路线 | T1 初/满 | T2 两端点 初/满 | T2 三端点 初/满 | 三端点满研究、标准工 | 闭环条件 |
|---|---:|---:|---:|---:|---|
| 回退矿点煤直烧 | 7 / 5 | 11 / 8 | 12 / 9 | 18 | 无加工副料；矿藏有限 |
| 化石矿床煤直烧 | 10 / 8 | 16 / 11 | 18 / 13 | 26 | 专属煤矿权重反而低于回退矿点；矿藏有限 |
| 回退煤→焦煤 | 4 / 3 | 6 / 4 | 6 / 5 | 9 | 焦炉加工；矿藏有限 |
| 化石煤→焦煤 | 5 / 4 | 8 / 6 | 9 / 7 | 13 | 焦炉加工；矿藏有限 |
| 回退煤→煤压块 | 2 / 2 | 3 / 3 | 4 / 3 | 6 | 还需石灰水和完整加工线；矿藏有限 |
| 化石煤→煤压块 | 3 / 3 | 5 / 4 | 6 / 4 | 8 | 还需石灰水和完整加工线；矿藏有限 |
| 毁坏沼泽泥炭直烧 | 27 / 21 | 43 / 32 | 52 / 37 | 74 | 无加工副料；人数过高且矿藏有限 |
| 森林原木→木炭 | 13 / 10 | 21 / 15 | 25 / 18 | 35 | 木炭坑；城镇矿出的原木仍消耗有限矿藏 |
| 森林原木→蜂蜜/黏合木炭压块 | 4 / 3 | 7 / 5 | 8 / 6 | 11 | 另需可持续蜂蜜或食物黏合剂；矿藏有限 |
| 森林原木→锯末压块闭环 | 6 / 5 | 10 / 8 | 12 / 9 | 17 | 约八份锯末木材配一份木炭坑木材，自产杂酚油；矿藏有限 |
| 松林原木→木炭 | 15 / 12 | 25 / 18 | 30 / 21 | 42 | 木炭坑；矿藏有限 |
| 松林原木→蜂蜜/黏合木炭压块 | 5 / 4 | 8 / 6 | 9 / 7 | 13 | 另需可持续蜂蜜或食物黏合剂；矿藏有限 |
| 松林原木→锯末压块闭环 | 8 / 6 | 12 / 9 | 14 / 10 | 20 | 自产杂酚油；矿藏有限 |

#### 如何解读人数表

- **中期最低居民数是回退煤矿＋煤压块：**满研究 T1 需要 2 名满级矿工，T2 两端点和三端点都需要 3 名。
- **不做复杂加工时，焦煤明显优于直烧煤：**三端点 T2 从 9 名降至 5 名满级矿工。
- **泥炭不能承担成熟城镇主能源：**满研究三端点 T2 需要 37 名满级矿工，已经超过 30 人算例的总人口。
- **城镇矿场的木材路线并不自动可再生：**`MineBaseBuilding` 对森林和松林矿点仍然提取 `ORE` 储量，所以表中木材路线只是阶段性维持。
- **工人熟练度非常重要：**回退煤压块路线在满研究三端点 T2 下需要 3 名满级矿工，却需要 6 名标准矿工。发展路径应先预留冗余岗位，等矿工成长后再转岗。

#### 煤压块副原料

煤压块路线平均每 1 煤产生 1.5 煤粉，每份煤粉需要 100 mB 石灰水；1 生石灰可制 1000 mB 石灰水。因此：

```text
每煤需要约 0.15 生石灰
满研究三端点 T2：
8.89 煤/日 × 0.15 ≈ 1.33 生石灰/日
```

当前城镇矿点没有稳定产出熔剂/生石灰的居民路线，所以“3 名矿工维持煤压块 T2”仍要求玩家从外围提供约 1.33 生石灰/日。它是低居民数路线，但不是纯城镇物料闭环。

#### 木炭压块副原料

蜂蜜木炭压块路线中，每木炭平均磨得 1.25 木炭粉，每 2 木炭粉和 250 mB 蜂蜜产出 3 个木炭压块。满研究三端点 T2 约需：

```text
26.67 木炭压块/日
≈ 14.22 木炭/日
≈ 20 原木/日
≈ 2.22 桶蜂蜜/日
```

如果蜂蜜来自自动蜂场，这条路线只占用表中的伐料矿工；如果蜂蜜或黏合剂还依赖居民食物产线，就必须把相应食物缺口另行计入，不能只看 6 名矿工。

### 6.10 自动树场方案的居民数

自动树场不属于 FrostedHeart 居民工作系统，所以从“专职供能居民”角度为 **0 人**。它消耗的是机器、区块加载和玩家工业维护能力：

| 自动树场路线 | T1 居民数 | T2 两端点居民数 | T2 三端点居民数 | 满研究三端点持续原料 |
|---|---:|---:|---:|---|
| 原木→木炭直烧 | 0 | 0 | 0 | 约 67.5 原木/日 |
| 原木→蜂蜜木炭压块 | 0 | 0 | 0 | 约 20 原木＋2.22 桶蜂蜜/日 |
| 原木→锯末压块、自供杂酚油 | 0 | 0 | 0 | 约 32 原木/日 |

三种方案都能用可再生设施长期运行：

- 有稳定蜂蜜自动化时，木炭压块的原木效率最高；
- 只希望依靠木材闭环时，锯末压块更稳，不需要持续输入蜂蜜、黏合剂或生石灰；
- 直接木炭结构最简单，但原木消耗约为蜂蜜木炭压块的 3.4 倍。

这里的 0 人不表示没有成本，只表示不占用城镇居民岗位；在仓库接口正式可获得之前，仍可能需要玩家搬运最终燃料。

## 7. 矿场储量与可持续时间

每个独立矿场区块的 `ORE` 储量为 1000，恢复量配置为 0，而且代码注释明确当前尚未应用矿石恢复值。

参考：[FHConfig.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/infrastructure/config/FHConfig.java#L970)、[TerrainResourceData.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/town/terrainresource/TerrainResourceData.java#L158)

若有 `M` 名满级矿工，一个矿区块的寿命为：

```text
矿区块寿命（游戏日） = 1000 / (7 × M)
```

| 满级矿工数 | 单区块游戏日 | 现实活动时间 |
|---:|---:|---:|
| 2 | 71.4 日 | 23.8 小时 |
| 3 | 47.6 日 | 15.9 小时 |
| 4 | 35.7 日 | 11.9 小时 |
| 5 | 28.6 日 | 9.5 小时 |
| 9 | 15.9 日 | 5.3 小时 |

必须把矿点放在不同区块；同一区块内的多个矿点共享同一份 1000 储量。连接 `C` 个不同区块，在权重相近时可把总持续时间近似扩大为 `C` 倍。

这说明煤压块路线能让城镇稳定运行几十个游戏日，但仍是“消耗矿区”的阶段性自给，不是永久自给。

## 8. 食物模型

### 8.1 居民消耗

每名居民每天需要 6.5 食物资源：

```text
每日食物需求 = 6.5 × 居民人数 N
```

参考：[FHConfig.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/infrastructure/config/FHConfig.java#L524)、[HouseBuilding.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/town/buildings/house/HouseBuilding.java#L270)

仓库消耗会从 `RESIDENT_FOOD_LEVEL` 的多个等级中由高到低取食物。**当前代码**在找不到单独资源量配方时直接返回 1；当前数据中也没有覆盖居民食物换算量的有效配方。因此在当前可运行实现里，生牛肉、熟牛肉、胡萝卜、烤马铃薯、南瓜派和蛋糕在“填饱人数”的维度都只抵 1 单位。

开发组后来补充说明：默认值预期应取物品的“饱食度＋饱和度”，只是尚未实现。该说明确定了设计方向，却没有改变当前仓库的运行事实，也没有给出非原版可食物品的兜底方式以及“饱和度”究竟指实际恢复点数还是 `saturationModifier`。本文因此保留当前模型，并在 8.5 节单列预期规则情景。

证据：[开发组关于食物单位的聊天截图](evidence/developer-food-unit-explanation.png)

住宅同时进行两套互不等价的计算：

1. **食物满足度**：只看被消耗的食物资源单位数，决定缺粮惩罚；
2. **营养质量**：读取 `frostedheart:diet_override` 配方，把四类营养值相加后除以 4，再与每食物单位 7000 的基准比较，决定健康和精神恢复倍率。

```text
营养质量 Q
= clamp((食物配方四项营养总和 / 4) / 7000, 0, 1)

营养恢复倍率 R
= 0.5 + 0.5 × Q
```

营养类别是否均衡不会单独影响城镇居民；当前城镇模型只使用四项营养的总和。最低恢复倍率为 0.5，所以低营养食物在数量充足时不会造成缺粮惩罚，但居民从低健康、低精神状态恢复得更慢。

参考：[TeamTownResourceHolder.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/town/resource/TeamTownResourceHolder.java#L161)、[HouseBuilding.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/town/buildings/house/HouseBuilding.java#L285)、[HouseDailyModel.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/content/town/buildings/house/HouseDailyModel.java)

### 8.2 当前代码下的狩猎平均食物产量

狩猎战利品表总权重为 19。可计入居民食物的条目包括牛肉、猪肉、鸡肉、骨头和羊肉：

```text
每次投掷的期望食物件数
= (4×2 + 3×2 + 2×2 + 3×1 + 1×1.5) / 19
= 22.5 / 19
≈ 1.18421
```

标准猎人每天期望投掷 `7/6` 次；满级猎人的最大生产力为 2.5：

```text
满级猎人每日投掷次数 = 7/6 × 2.5 = 2.91667
满级猎人每日食物产量 = 2.91667 × 1.18421 ≈ 3.45395
```

参考：[hunting.json](FrostedHeart/src/main/resources/data/frostedheart/loot_tables/town/hunting.json)、[FHConfig.java](FrostedHeart/src/main/java/com/teammoeg/frostedheart/infrastructure/config/FHConfig.java#L727)

### 8.3 烹饪对狩猎食物的影响

当前 TWR 保留了原版牛肉、猪肉、鸡肉和羊肉的 1:1 烧炼、烟熏或营火烹饪。生肉和对应熟肉都在居民食物标签中，且都没有特殊资源换算量，因此按**当前代码**：

```text
1 生肉 → 1 熟肉
居民食物单位：1 → 1
```

烹饪不会改变当前代码口径下的狩猎日产食物 3.45395，也不会改变外部食物缺口；它改变的是营养质量。开发组预期规则下的资源量变化见 8.5 节。

| 食物 | 配方营养总和 | 城镇营养质量 Q | 恢复倍率 R |
|---|---:|---:|---:|
| 生牛肉/生猪肉/生羊肉 | 12000 | 42.86% | 71.43% |
| 生鸡肉 | 4000 | 14.29% | 57.14% |
| 熟牛肉/熟猪肉/熟鸡肉/熟羊肉 | 24000 | 85.71% | 92.86% |
| 骨头 | 4000 | 14.29% | 57.14% |

如果狩猎产生的肉全部烧熟，但骨头仍作为食物进入仓库，则按战利品权重计算：

| 狩猎饮食状态 | 平均每食物单位营养 | 营养质量 | 恢复倍率 |
|---|---:|---:|---:|
| 生肉＋骨头 | 2377.78 | 33.97% | 66.98% |
| 熟肉＋骨头 | 5333.33 | 76.19% | 88.10% |

烹饪使这套狩猎饮食的居民恢复倍率相对提高约 31.5%，有助于居民恢复健康和精神、间接维持工作生产力。它在当前代码下不会修复食物数量赤字；在开发组预期规则下则会同时提高食物资源量。

参考：[生牛肉营养配方](FrostedHeart/src/generated/resources/data/frostedheart/recipes/diet_value/minecraft/beef.json)、[熟牛肉营养配方](FrostedHeart/src/generated/resources/data/frostedheart/recipes/diet_value/minecraft/cooked_beef.json)、[生鸡肉营养配方](FrostedHeart/src/generated/resources/data/frostedheart/recipes/diet_value/minecraft/chicken.json)、[熟鸡肉营养配方](FrostedHeart/src/generated/resources/data/frostedheart/recipes/diet_value/minecraft/cooked_chicken.json)

#### 烹饪的能源成本

每名满级猎人每天约得到 2.993 件肉和 0.461 件骨头。27 名满级猎人每天约有 80.82 件肉需要加工。

**推荐方案是 Create 机械动力批量烟熏。**机械风扇可以处理 `minecraft:smoking` 类型的配方；TWR 不但保留原版肉类烟熏配方，还在脚本中为黑麦面包和多种肉类等补充了烟熏配方。以持续火源配合机械风扇时，不需要逐件投入煤、木炭或木材，因此在本文的物资收支模型中：

```text
81 件肉/日的机械动力烟熏燃料消耗 = 0
新增能源矿工 = 0
成熟 30 人城镇仍为 3 名能源矿工＋27 名猎人
```

这里的“0 燃料”是指 **0 持续消耗的燃料物品**，并不是整套设备没有成本。它仍需要机械风扇、传动机构、旋转动力和有效的烟熏热源；若旋转动力来自风车或其他不消耗燃料的动力源，则烹饪线不会侵蚀能量塔的燃料闭环。按当前代码，机械烟熏只改变加工成本和营养质量，不改变 `1 生肉 → 1 熟肉 → 1 城镇食物单位`；按开发组预期规则，它还会提高食物资源量。

参考：[TWR 新增烟熏配方脚本](TheWinterRescue/kubejs/server_scripts/src/recipes_types/minecraft/smoking.js)

以下煤耗只适用于普通烟熏炉，是没有建成机械烟熏线时的备用对照。

若使用保留原版燃烧参数的烟熏炉：

```text
1 煤可支持约 16 次、每次 100 tick 的烟熏
80.82 / 16 ≈ 5.05 煤/游戏日
```

这部分没有包含在前文的能量塔燃料表中。若煤压块线仍以矿煤为唯一原料，则满研究、三热网端点 T2 的 30 人城镇会从约 3 名满级能源矿工提高到约 4 名：

```text
能量塔所需原煤 ≈ 26.67 压块 / 3 ≈ 8.89 煤/日
烟熏所需原煤 ≈ 5.05 煤/日
合计 ≈ 13.94 煤/日
13.94 / 3.5 ≈ 3.98 名满级矿工
```

因此，普通烟熏炉会把该特定配置推高到 4 名能源矿工，但这不是最高程度城镇的推荐人数。建成 Create 机械动力烟熏线后，烹饪不再增加持续煤耗，恢复为原先 3 名能源矿工的配置。

### 8.4 当前实现下狩猎无法自给的数学证明

每个满级猎人每天：

```text
产出 3.45395
消耗 6.5
净缺口 3.04605
```

即使所有居民都做猎人：

```text
最大内部覆盖率 = 3.45395 / 6.5 ≈ 53.14%
```

设猎人生产力之和为 `ΣS_hunter`，则外部食物最低需求为：

```text
外部食物需求
= 6.5 × N - 1.18421 × 7/6 × ΣS_hunter
= 6.5 × N - 1.38158 × ΣS_hunter
```

其中每名满级猎人的 `S = 2.5`。

### 8.5 开发组预期的“饱食度＋饱和度”情景

开发组提供的是目标规则说明，不是已经提交的实现。为了评估其影响，本文采用 Minecraft 通常意义上的实际饱和恢复点数进行情景计算：

```text
实际饱和点 = 2 × 饱食度 × saturationModifier
预期食物单位 U = 饱食度 + 实际饱和点
```

原版狩猎肉对应为：

| 食物 | 饱食度 | 实际饱和点 | 情景食物单位 U |
|---|---:|---:|---:|
| 生牛肉/生猪肉 | 3 | 1.8 | 4.8 |
| 熟牛肉/熟猪肉 | 8 | 12.8 | 20.8 |
| 生鸡肉/生羊肉 | 2 | 1.2 | 3.2 |
| 熟鸡肉 | 6 | 7.2 | 13.2 |
| 熟羊肉 | 6 | 9.6 | 15.6 |

骨头虽然在当前居民食物标签中，却没有原版食物属性。为便于和现状比较，主算例暂时让骨头保留当前的 1 单位兜底；如果未来实现把无食物属性物品计为 0，结果只会略微下降。

按狩猎权重计算：

```text
生肉＋骨头：每次投掷约 4.62105 单位
熟肉＋骨头：每次投掷约 19.49474 单位

满级猎人每日生食产量 = 4.62105 × 2.91667 ≈ 13.47807
满级猎人每日熟食产量 = 19.49474 × 2.91667 ≈ 56.85965
```

因此，在居民消耗仍为 6.5 单位/日的前提下：

| 预期规则情景 | 单名满级猎人日产 | 可覆盖居民数 | 30 人口最低满级猎人数 |
|---|---:|---:|---:|
| 肉类不烹饪 | 13.478 | 2.07 | 15 |
| 肉类全部烹饪 | 56.860 | 8.75 | 4 |

若骨头改为 0 单位，生食和熟食日产分别约为 13.018、56.399，30 人口所需猎人数仍分别为 15 和 4。也就是说，只要开发组确实按“饱食度＋实际饱和点”落地并保持每日消耗 6.5 不变，**食物侧将从当前必然亏损变为可以仅靠狩猎自给，烹饪也会成为约 4.22 倍的资源增值步骤。**

这个结论仍有三项实现前不确定性：

1. “饱和度”是否指实际饱和恢复点，还是仅指 `saturationModifier`；
2. 骨头、锯末和模组食物等没有原版食物属性的标签物品如何换算；
3. 食物单位提高后，`foodConsumptionPerResidentDay = 6.5` 是否会同步重调。

在代码和数据配方真正落地前，本节只能用于设计评估，不能替代 8.4 节的当前版本结论。

### 8.7 当前代码下的外围农作物与烹饪路线

食物标签中包含胡萝卜、马铃薯、南瓜、面包、肉类、鱼类等物品。

参考：[town_resource_resident_food_level_1.json](FrostedHeart/src/main/resources/data/frostedheart/tags/items/town_resource_resident_food_level_1.json)

以下表格仍按当前“普通物品每件 1 单位”的代码计算。不同烹饪路线必须同时比较“最终食物件数”和“营养质量”，不能只看玩家食用时的饱食度：

| 路线 | 最终食物单位 | 营养质量 | 恢复倍率 | 评价 |
|---|---:|---:|---:|---|
| 1 胡萝卜直接入库 | 1 | 85.71% | 92.86% | 无加工、综合最稳 |
| 1 马铃薯直接入库 | 1 | 57.14% | 78.57% | 能吃，但恢复较慢 |
| 1 马铃薯→1烤马铃薯 | 1 | 85.71% | 92.86% | 数量不变，营养提高 |
| 1 南瓜直接入库 | 1 | 57.14% | 78.57% | 自动化简单 |
| 1 南瓜＋糖＋鸡蛋→1南瓜派 | 1 | 100% | 100% | 数量不变，营养最佳 |
| 1 小麦→平均1.5面粉→约1.875压缩饼干 | 约 1.875 | 78.57% | 89.29% | 需要磨粉、植物油和加热压制 |
| 1 黑麦→平均1.5黑麦粉→约2.25生黑麦面包 | 约 2.25 | 71.43% | 85.71% | 另需糖；烤熟不再提高城镇营养 |

其中小麦和黑麦的结果是长期平均值：磨粉配方固定产出 1 面粉，并有 25% 概率额外产出 2 面粉；压缩饼干配方以 4 小麦粉和植物油产出 5 饼干；含糖黑麦配方以 2 黑麦粉产出 3 生黑麦面包。

参考：[milling.js](TheWinterRescue/kubejs/server_scripts/src/recipes_types/create/milling.js#L85)、[compacting.js](TheWinterRescue/kubejs/server_scripts/src/recipes_types/create/compacting.js#L68)、[mixing.js](TheWinterRescue/kubejs/server_scripts/src/recipes_types/create/mixing.js#L29)

当前代码口径下的推荐优先级：

1. **胡萝卜**：不消耗烹饪燃料，单件营养恢复已经等于熟肉和烤马铃薯；
2. **黑麦→生黑麦面包**：按主作物件数计算的扩产倍率最高，适合解决纯数量缺口；住宅会接受生面包，烘烤只改善玩家食用体验，不改善当前城镇营养值；
3. **小麦→压缩饼干**：数量倍率和营养质量兼顾，但工业链更长；
4. **马铃薯→烤马铃薯**：农场简单，必须使用可再生热源才不会侵蚀能量闭环；
5. **南瓜→南瓜派**：适合作为提高平均营养质量的混合食物，不会提高每个南瓜对应的食物单位数；
6. **自动畜牧或捕鱼**：熟肉、熟鱼营养较高，但同样要计算烹饪吞吐量和热源。

不推荐把以下常见菜肴投入城镇仓库：

- 甜菜汤把多份本来就能入库的甜菜合成 1 件食物；
- 蘑菇煲把两份可分别入库的蘑菇合成 1 件食物；
- 兔肉煲会把兔肉、胡萝卜、马铃薯和蘑菇等多件合格食物合成 1 件；
- 蛋糕营养质量虽然达到 100%，但多个原料最终只得到 1 个城镇食物单位。

这些菜肴对玩家饱食度可能很好，但对当前“每件通常只算 1 单位”的城镇系统反而会降低供餐数量。开发组预期规则落地后，必须按最终物品的饱食度和饱和度重新比较，不能沿用这份排序。
当前整合包还移除了原版蘑菇煲和兔肉煲的常规无序合成配方；上面的比较用于说明即使从战利品、其他配方或未来恢复的配方获得，也不应把多件可入库原料压缩成一件菜肴后再供应城镇。

### 8.8 不应计入正常自给的漏洞路径

当前食物标签还包含骨头和锯末：

- 骨头可以通过刷怪系统大量生产；
- 锯末可以与可再生树场共线生产；
- 两者都能增加食物满足度，但营养质量不符合正常食物设计目标。

另外，当前住宅每日工作逻辑只对可工作的住宅执行食物结算；利用无效或低温住宅跳过结算属于实现漏洞。

本文的正常自给结论排除这些路径。

## 9. 最高发展程度城镇的推荐结构

以下以 30 人口为统一目标，实际建筑数量应服从扫描上限和房屋评分。主方案按当前可运行代码配置；开发组预期食物规则尚未落地，因此只在居民分工后给出条件式调整。

### 9.1 核心建筑

- T2 能量塔 1 座；
- 尽可能少而大的住宅，理想目标 1～2 座；
- 大型狩猎所 1 座，提供约 27 个工作位；
- 矿井基站 1 座；
- 至少 3 个分处不同区块的燃料矿点，建议继续预留轮换矿区；
- 能容纳多日食物和燃料缓冲的仓库；
- 完整煤压块加工线；
- 能处理约 81 件狩猎肉/日的 Create 机械动力批量烟熏线；
- 自动树场及锯末压块线；
- 当前代码下，产能不低于 122 合格食物/日的自动农场。

### 9.2 居民分工

成熟、满研究、三热网端点情景：

| 职业 | 人数 | 作用 |
|---|---:|---|
| 满级矿工 | 3 | 维持煤压块 T2；机械动力烟熏不增加持续煤耗 |
| 满级猎人 | 27 | 提供约 93.26 食物/日及皮革、骨头等副产物 |
| 外围玩家工业 | 不占居民 | 补约 101.74 食物/日，处理燃料并维持物流 |

若未建成机械烟熏线而用普通烟熏炉烧煤，才需要把能源矿工临时提高到约 4 人；此时只有 26 名猎人，狩猎日产约 89.80，外部食物缺口约 105.20/日。默认推荐配置不采用这条路线。

当自动树场和锯末压块线完全接管能量塔、烹饪采用机械动力烟熏后，矿工可转为其他矿产生产；但当前居民职业系统中没有林业岗位，树场仍由玩家工业负责。

如果开发组预期的“饱食度＋实际饱和点”规则按 8.5 节假设落地，30 人口可以改为约 **3 名能源矿工＋4 名满级猎人＋23 名自由岗位居民**。4 名猎人把肉全部烹饪后，情景日产约 227.44 单位，能够覆盖 195 单位需求；在正式实现前不要按这套低猎人数配置当前存档。

### 9.3 资源缓冲

建议库存不低于：

- 5 个游戏日的能量塔最终燃料；
- 3 个游戏日的居民合格食物；
- 一次完整 T2 启动所需的 864 桶蒸汽生产能力；
- 至少一个备用矿区块或一条可独立启动的木材燃料线。

对当前代码下的 30 人口城镇，3 日总食物需求为 585 单位，尚未扣除期间狩猎产出。若只准备外部补充部分，3 名矿工＋27 名猎人的三日外部食物约为 306 件。

## 10. 推荐发展路径与时间

静态仓库可以精确计算消耗、生产率、启动时间和矿区寿命，但不能精确预测玩家收集材料、完成任务、寻找群系和搭建结构所需的现实小时。因此下面把时间分为“可由代码计算的运行时间”和“条件式阶段目标”。

### 阶段 1：建立能运行的 T1 城镇

目标：

- 一座合格住宅；
- 一座仓库；
- 一座狩猎所；
- T1 连续运行；
- 至少 3～5 个游戏日的煤或焦煤库存。

时间含义：

- 5 个游戏日等于现实活动时间 100 分钟；
- 满研究 T1 的 5 日库存约为 84 煤、42 焦煤或 75 最终煤压块；
- 初期实际需求更高，应至少增加约 30% 余量。

### 阶段 2：建设矿业与煤压块加工

目标：

- 连接至少 2～3 个不同区块的矿点；
- 培养 2～4 名主力矿工；
- 完成磨粉、石灰水处理、清洗、压制和烘干；
- 用最终煤压块替代直接烧煤。

达到满产后：

- 两名满级矿工可维持 T1；
- 三名满级矿工可维持满研究、三端点 T2；
- 三名矿工对一个矿区块的理论消耗寿命约 47.6 游戏日，即 15.9 小时活动时间。

### 阶段 3：升级 T2 与压缩热网端点

目标：

- 完成 T2 结构；
- 完成两级燃烧效率研究和一级热能研究；
- 把住宅与狩猎所整合为尽量少的热网端点；
- 建立持续 5 分钟、总量 864 桶的蒸汽输入能力。

启动时间：

- 纯充汽时间固定约 5 分钟；
- 还需要约 6000 点基础燃料进度，初期约 5.36 煤或 2.68 焦煤，另有少量建立热网储能的附加消耗。

### 阶段 4：解决食物硬缺口

当前代码下的目标：

- 30 人口、3 矿工、27 猎人时，外围农场稳定提供至少 101.74 食物/日；
- 建议工程目标为 122 食物/日；
- 保持至少 306 件外部食物的三日缓冲。
- 建立约 81 件狩猎肉/日的 Create 机械动力批量烟熏吞吐量；持续燃料物品消耗按 0 计。
- 普通烟熏炉仅作为备用：若使用煤烟熏，额外准备约 5.05 煤/日，并把能源岗位从 3 名提高到约 4 名。

达到这一阶段后，城镇可以在玩家定期搬运的条件下长期维持人口和能量塔。

如果开发组预期食物单位规则已经在玩家所用版本中实装，应先在仓库或住宅界面实测熟肉的资源换算值，再改用 8.5 节的低猎人数方案；只有聊天说明而没有代码或游戏内数值变化时，仍按上述当前方案建设。

### 阶段 5：转入可再生能源

目标：

- 自动树场每游戏日稳定生产约 29～34 原木；
- 锯末压块线接管 T2 主燃料；
- 矿煤只作应急储备和工业原料；
- 食物农场与树场均按至少 20% 余量运行。

达到这一阶段后，“城镇＋外围工业”可以做到资源意义上的长期自给。

### 阶段 6：自动化审计

检查：

- 树场是否能自动送入锯末加工；
- 最终压块是否能自动送入能量塔；
- 农场物品是否能自动转换并进入城镇虚拟仓库；
- 灰烬输出是否会堵塞能量塔输出槽；
- 仓库接口是否在实际整合包版本中可获得。

在仓库接口获得路径未确认前，最多只能称为“资源自给、定期人工搬运”，不能称为完全自动自给。

## 11. 自给能力最终判定

### 11.1 当前可运行实现

| 范围 | 能量塔 | 食物 | 总体结论 |
|---|---|---|---|
| 纯城镇系统，短期 | 矿产加工后可平衡 | 狩猎不能平衡 | 部分自给 |
| 纯城镇系统，长期 | 矿藏不恢复，不能永久平衡 | 当前代码最高仅覆盖约 53.1% | 不能自给 |
| 城镇＋玩家工业，手动搬运 | 树场＋锯末压块可再生 | 自动农场可补足 | 可以自给 |
| 城镇＋玩家工业，全自动 | 机器侧可以自动化 | 农场侧可以自动化 | 仓库最后一公里尚未证实 |

当前版本最终判断：

> 当前城镇不是一个独立自给系统。能量问题有多条可行工程路线，其中煤压块适合中期、树场与锯末压块适合长期；食物问题必须由城镇外农业补足。对高人口城镇而言，食物吞吐量和入库物流比能量塔燃料更接近真正的扩张上限。

### 11.2 开发组预期规则落地后的条件式判断

若默认食物单位确实实现为“饱食度＋实际饱和点”，每日消耗仍为 6.5，且狩猎肉可正常机械烟熏，则食物侧可以仅靠居民狩猎自给：30 人口约需 4 名满级猎人。此时纯城镇系统长期仍会被不可恢复的矿场 `ORE` 储量阻断，但“食物必须依靠外围农业”的结论将失效；接入可再生树场燃料后，城镇＋外围工业可以在物资生产上形成闭环。

这只是条件式结果。开发组同时说明该规则“还没写”，所以不能据此宣称当前整合包已经实现食物自给。

## 12. 结论的适用范围与复核点

本文结论适用于文首列出的两个提交。以下变化会使部分结果失效，需要重新计算：

- 修改 `foodConsumptionPerResidentDay`；
- 实装或调整默认食物单位的“饱食度＋饱和度”算法；
- 明确其中“饱和度”的计算方式，以及无原版食物属性物品的兜底值；

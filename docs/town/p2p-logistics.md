# P2P 物流终端

> 状态：Current（实现、自动化与 H01 游戏内反馈已核对）
> 最近验证：2026-08-26
> 范围：三类终端、路线牌配对、运力预约、缓存、过滤、传输、同步和生命周期
> 代码锚点：`P2PTerminalBlockEntity`、`FreightRouteCardItem`、`P2PBindingState`、
> `P2PDirectedBinding`、`P2PItemTransfer`、`P2PTerminalBuffer`、`P2PItemFilter`、
> `P2PTerminalMenu`、`TeamTown#bindOrRebindP2PTerminals`、`TownTransportSnapshot`

P2P 物流是城镇运力的同维度点对点物品传输设备。连接、设置速率、两端红石事实和过滤摘要由城镇状态持有；终端方块实体
只持有本地库存、过滤器和运行时预算。它不复用 `content.robotics.logistics` 的频道或机器人网络。

## 设备与注册 ID

| 设备 | 注册 ID | 行为 |
|---|---|---|
| 发货终端 | `frostedheart:shipping_terminal` | 从明确连接面的相邻物品能力主动取货并向一个目标推送 |
| 收货终端 | `frostedheart:receiving_terminal` | 接受多个来源，并把物品插入明确连接面的相邻物品能力 |
| 双向物流终端 | `frostedheart:bidirectional_logistics_terminal` | 不主动扫描相邻容器；六个面都向外部物流暴露同一组 4 格待发送和 4 格已接收受限能力 |
| 货运路线牌 | `frostedheart:freight_route_card` | 仅保存第一个待选端点；第二次选点时绑定未连接的端点，或解绑已经互联的同一对端点 |

终端第一次被有效操作时归属玩家队伍；所属队伍成员都可以配对、改绑、解绑、改速率和编辑过滤器。服务端在每次菜单命令
中复核菜单、方块实体、八格交互距离、队伍、维度和端点角色。授权成功后的视觉刷新会重新读取已解析城镇的当前
`P2PBindingState`；打开菜单、调整速率或编辑过滤器不会先把已绑定终端写成 `UNBOUND`。

三类终端均可按玩家视线放置为上下东南西北六向。角色图形所在面是正面；发货端和收货端只与正面反方向的相邻物品能力
主动交互。该容器连接面保留货运站铆接外框，中央开口连边框严格为 `6x6` 像素：发货端使用蓝色边框的
`frostedheart:block/shipping_terminal_port`，收货端使用橙色边框的 `frostedheart:block/receiving_terminal_port`。
其余非功能面使用带信封标识的 `frostedheart:block/transport_station` 材质，不存在固定的世界顶面。双向端没有专用容器面；
除角色正面外的五面均使用货运站材质，且 `P2PTerminalBlockEntity#getCapability` 对六个方向和无方向查询都返回同一受限缓存
能力。这里的“所有面可交互”不表示它会主动扫描或搬运相邻容器。

## 配对与拓扑

路线牌先后右击两个兼容终端即可绑定，点击顺序不决定方向。第一次选择后，路线牌切换为带青绿色标记的待选材质，tooltip
显示所选终端类型、完整坐标和完成绑定提示；成功绑定、解除或清空选择后立即清除物品状态并恢复常规模型。路线牌不保存
已完成连接的 ID，空白路线牌的普通右键不会解除连接。若玩家重新选择当前已经互联的同一对终端，第二次选点会解除该连接。
发货端只能拥有一个目标；收货端
可以接收多个发货端；双向端
只能拥有一个对端。两个双向端绑定时形成同一稳定连接 ID 下的两条相反有向连接和两条独立预约。发货-发货、收货-收货、
自环和跨维度配对会被拒绝。

同一发送端的新成功绑定覆盖旧连接；双向连接任一端改绑或解绑会同时清理另一端关系。改绑先完整评估候选绑定和预约，失败
时保留旧连接、旧速率和旧预约。初次绑定失败保持未绑定，路线牌也不保存未生效目标。路线牌对空气或无关方块右击只清除
尚未完成的第一个端点选择；没有待选端点时不产生效果。终端 GUI 仍可逐条解除连接。

首版没有频道、广播或内建中继。玩家可以用箱子、漏斗或其他外部物流串联多个独立路段，也可以由此形成外部闭环；每段
P2P 仍独立过滤、调度和计费。相同有向端点对不会重复登记，后成功的连接覆盖旧连接。

## 运力与速率

一条有向连接只由发送端的 `TransportEndpointId(GlobalPos)` 创建一条 `P2P_DIRECT_LINK` 预约。定义：

```text
D = |x_sender - x_receiver| + |y_sender - y_receiver| + |z_sender - z_receiver|  blocks
F = 1 + k_p2p * D
C_reserved = R * F
```

`R` 是设置速率，单位 `items/s`；`D` 是同维度曼哈顿距离；`C_reserved` 是城镇运力。源码默认 `R = 20 items/s`、最大
`1280 items/s`、`k_p2p = 0.05 / block`。运行时配置键位于
`FHConfig.SERVER.TOWN.TRANSPORT_CONSUMERS`：`defaultRateItemsPerSecond`、`minimumRateItemsPerSecond`、
`maximumRateItemsPerSecond` 和 `p2pDistanceCostPerBlock`。

初次绑定和改绑属于玩家准入，容量不足会原子拒绝；玩家主动上调速率同样如此。全镇后来因事实变化出现短缺时，各活动预约
按 `TownTransportSummary.effectiveRateScale` 等比例降低有效速率。连接距离在生命周期内固定，只在绑定、改绑或加载恢复时
从双方 `GlobalPos` 重新派生。

任一端收到红石信号时，对应有向连接进入 `REDSTONE_PAUSED`：保留设置速率和距离，实际传输及预约占用均为 0。发送端和
接收端红石事实分别持久化，任一端卸载后另一端的信号变化仍不会误恢复预约。解除全部红石后直接恢复已接受预约，即使此时
会形成城镇短缺。绑定发生时已供电的端点会作为暂停事实参与同一个准入事务。

## 缓存与过滤

双向端共有八个真实槽位：四格待发送、四格已接收。外部物品能力只能向待发送插入、从已接收提取；P2P 只从待发送取货、
向已接收送货。双向端仅作为接收方时锁定待发送，仅作为发送方时锁定已接收；双向端互联时两组都不锁定。非空槽不会阻止
绑定；锁定后自动化和 P2P 不可访问该组槽位，但玩家仍可手动取出遗留物品，不能放入。

每套过滤器有九个幽灵槽。空过滤无条件放行；默认白名单和精确模式，精确模式比较物品及数据/NBT但忽略数量。可独立切换
黑名单和只比较物品种类的模糊模式。发送方与接收方过滤必须同时通过；双向端的发送和接收过滤完全独立。相关终端页面同步
显示完整方向和单位，并把当前打开的方块写作“本终端”，例如发货端看到“本终端->收货终端，20物品/秒”，收货端看到
“发货终端->本终端，20物品/秒”；同时显示对端坐标、加载状态和过滤摘要且可逐条解除。双向互联分别列明两个方向的速率，
收货端列表按稳定顺序包含全部来源。

## 菜单与调速

发货/收货端由 `P2PEndpointTerminalScreen` 显示，双向端由 `P2PBidirectionalTerminalScreen` 显示；二者共享服务端权威的
`P2PTerminalMenu` 命令校验，但不是同一个具体 Screen。菜单标题分别使用三类终端的完整名称。顶层只有“终端”和“过滤”
两页：发货端直接编辑发送过滤，收货端直接编辑接收过滤；双向端过滤页再以“输入过滤/输出过滤”切换，其中输入过滤对应
待发货方向的发送过滤，输出过滤对应已接收方向的接收过滤。

双向端缓存以两组四格槽显示并标注“待发货”“已接收”。三类终端的相关终端记录都以正常字号显示方向与单位；某个本地化
方向超过 152 像素时，拆成“来源 ->”和“目标，速率”两条语义行，坐标跟随在该记录的全部方向行之后。端点记录高 32
像素，双向记录高 46 像素；双向端的解绑按钮位于坐标行右侧，不占用英文方向文字区域。悬停连接记录可查看对端过滤摘要，
解绑按钮仍可逐条操作。其他受控长文本仍在各自容器内保底适配。运力行显示
`townRemainingCapacity / townTotalCapacity`，不会省略分母。

客户端菜单同步槽以 `null` 作为首包前哨值；首个服务端菜单快照到达前，界面从客户端已有终端 BlockState 构造临时视图，
不会先显示硬编码的“未配对”。服务端授权路径同样保留权威连接事实，不会在打开界面或提交速率时发出一帧错误的未配对
方块状态。标题和右上状态按自然字号互相避让；中文“收货端无可用容器”等正常状态文本不再因固定 46 像素栏宽而缩小，
仅在单条状态本身超过整个标题栏可用宽度时才进行保底缩放。

拥有出站方向且已经绑定的终端可以输入速率并点击应用，也可以悬停速率框直接滚轮提交。`TransportRateScroll` 与仓库接口
共用步长：无修饰键 `1`、Shift `8`、Ctrl `16`、Shift+Ctrl `64 items/s`；`ScrollTracker` 累积高精度滚轮输入，结果限制在
`0..maximumRateItemsPerSecond`。服务端仍通过 `P2PTerminalBlockEntity#setTransportRate` 和城镇准入事务验证权限、距离、
配置上限与可用运力，客户端滚轮不绕过拒绝回退合同。

## 传输与故障边界

发送方主动推送，按来源 slot 升序选择第一个同时通过双方过滤的物品。目标先模拟接收，再提交来源提取和目标插入；目标
实际未接受的余量立即还给发送方。若来源在模拟后变化或出现非常规能力行为，终端使用不可见恢复堆栈阻止后续传输，优先
把余量还回来源；正常保存、卸载和拆除路径会保存或掉落该堆栈。

调度由 `TransportTransferBudget` 统一实现，且只限制发送方：

- 设置速率决定最短运行间隔：`1..32 items/s` 为 20 tick，`33..64` 为 10 tick，
  `65..128` 为 5 tick，`129..640` 为 2 tick，`641..1280` 为 1 tick。状态机初始化或重置后的首次运行也先等待该基础间隔。
- 实际可用速率只生成传输额度，不改变频率上限。额度桶最多保存一秒实际运力，向上取整到完整物品并限制在 64；
  任何一次运行最多搬运 64 件。
- 正常状态下小数余量跨秒顺延，例如 `17.25 items/s` 连续四秒产生 `17`、`17`、`17`、`18` 件完整额度。
- 一次真实传输尝试搬运零件时记录失败，运行间隔倍增并封顶 80 tick；搬运至少 1 件时记录成功，间隔向上取整减半，
  直到恢复设置速率对应的最短间隔。
- 降频后的首次成功会清空剩余整数和小数额度；降频期间溢出的运力直接丢弃，不进行追赶。
- 红石暂停、未绑定、预约无效、对端区块未加载或实际速率为零时不记录失败，也不访问外部物品能力。对端未加载时会清空
  当前额度，并按当前运行间隔安排下一次探测，而不是在其余 tick 反复检查对端。

P2P 终端只在已到期且拥有至少 1 件完整额度后才解析源端和目标端物品处理器。一次真实发送不再先执行独立的需求预扫描；
`P2PItemTransfer#move` 同时完成模拟、提交和结果统计。源能力缺失、接收容器不可用、目标能力缺失或恢复堆栈无法归还时，
在发送端记录零搬运失败。

多个到期发送端可以在同一个服务器 tick 内依次运行；较早发送端可能耗尽目标容量，使较晚发送端发生一次零搬运失败。
不再使用接收端每 tick 单发送方的轮询，也不再按接收端来源数量放大发送速率；每个发送端只使用自己的实际速率。

接收端现有的 `receiverContainerProbeTicks == 20` 仅用于复核相邻容器能力是否存在，不参与发送端调度状态。端点区块或
维度未加载、相邻容器消失或物品能力暂时不可用时，只暂停搬运并保留连接与预约，且不强制加载区块。已加载的收货终端没有
可用相邻物品能力时，收货端及其已加载发送端稳定显示“收货端无可用容器”；发货端自己的来源容器缺失只按无货可发处理，
不显示该故障。发送端无法加载对端时显示“对端未加载”，且在等待下一次实际探测期间保持该状态，不再使用笼统的
“目标不可用”。容器事实由邻居变化立即刷新，
并以最多 20 tick 的周期复核能力恢复。端点位置在已加载状态下被替换、角色不符或队伍关系改变时自动解绑。拆除双向端会
掉落八格缓存和恢复堆栈；普通区块卸载不掉落。

保证范围止于完整服务端调用、正常保存/停服和区块生命周期。实现不写发送方恢复日志，也不声称 JVM、进程或机器在来源
提取与目标插入之间硬崩溃时仍能严格恢复。

## 持久化与同步

`TeamTownData` 持久化 `P2PBindingState` 和 `P2PFilterSummaryState`。有向绑定上限、过滤摘要上限和 transport snapshot 预约
上限分别独立校验，当前均为 4096 条；它们不是同一个共享计数器。snapshot 的 4096 是仓库与 P2P 合计预约上限，新绑定
不能令该总数溢出。`TownTransportSnapshot` 在全量和增量同步中携带绑定、
过滤摘要、P2P 距离系数和派生预约。镇长印章使用稳定排序展示每条发送方预约，双向连接因此显示两个方向而不重复计费。

自动化锚点包括 `P2PBindingStateTest`、`TeamTownP2PBindingTest`、`P2PItemTransferTest`、`TransportTransferBudgetTest`、
`P2PTerminalBufferTest`、`P2PTerminalResourcesTest`、`P2PTerminalScreenTest` 和 `TownTransportSnapshotTest`。`H01` 的七轮游戏内反馈覆盖了方块外观、
GUI scale、中英文布局、配对、调速、低速状态和容器可用性，并已完成对应返修。多人并发、重启、区块生命周期和真实外部
物流组合仍属于发布回归重点；它们不扩大上文明确限定的硬崩溃保证范围。

# TWR 城镇临界自循环数值模型设计

> 状态：首轮可运行模型，不是最终平衡表。本文对应 `Scripts/town_model/` 与
> `Scripts/town_sim.py`。参考参数集中在
> `Scripts/town_model/scenarios/reference.toml`，每个量均注明游戏单位或来源。

## 1. 结论先行

城镇平衡不能由“人口 × 每日定额”或“加热体积 × 温差”单独决定。可玩的临界态至少同时受四类量约束：

1. **库存状态**：燃料值、食物能量、营养、原料、居民健康与精神、热场和室内温度。
2. **流量与功率**：热源功率、散热、热网输送、SWE 分配、食物/燃料生产和消费。
3. **空间几何**：球形热场的总量、重叠、建筑体素覆盖、建筑围护面积与体积。
4. **时间与风险**：热惯性、热源爬升、预报提前量、库存天数、连续低温、恢复时间和失败概率。

原先提出的“每日每立方米升高一度消耗多少燃料”适合作为**模拟输出**，不适合作为独立配置：它把首次升温所需热容与持续维持所需散热混在一起，也隐藏了球体表面积、建筑覆盖和寒潮持续时间。

同样，“标准工人数”不能同时代表人口。模型明确区分：

- `SWE`：标准工人当量，决定生产能力；
- `FCE`：食物消费者当量，决定食物需求；
- 床位与受热建筑容量：决定可容纳人口；
- 实际居民数：连接以上三者，但不与其中任何一个直接相等。

## 2. 从代码确认的现状

`current_compat` 只用于复刻与量化现状，不代表推荐设计。

- `WorldTemperature.block` 并不是环境温度加热场温度。自然温度低于热场值时，结果为
  `min(nature + heat * 2, heat)`；热场值更接近有传热过程的温度上限。
- `ChunkHeatData` 在多个热区重叠时取最大值，不累加。因此重复覆盖会重复付出运行成本，却不增加最终温度。
- T2 塔本体和加热器都通过 `SphereHeatArea` 产生球形空间热场。热力网络的有效城镇用途应是把塔的能量输送给加热器，而不是直接供给普通城镇方块。
- 当前加热器仍是 `4 heat/t` 的网络消费者；满级加热器半径为 16 方块。
- 当前住宅仍保留 `1 heat/t` 的旧网络端点；狩猎基地默认也保留 `1 heat/t` 端点。它们既扫描球形热场中的 `WorldTemperature.block`，又额外叠加最低 24°C 的网络温度修正。这是新旧模型并存，不应作为目标平衡依据。
- 当前住宅若温度低于 0°C 或高于 50°C，会被整个跳过日结算。居民不会吃饭、不会受到低温健康/精神影响，又不一定被视为无家可归，形成“寒冷免费静止”漏洞。
- 住宅在合法温度范围内只有恢复倍率变化，没有随低温产生的直接损伤；狩猎温度主要是二元开关；矿场目前不检查温度。
- 建筑扫描器已经保存内部空气体素和外接盒，因此未来可以从真实 `OccupiedVolume` 导入覆盖几何；当前没有围护面积、材料保温或热惯性。
- 当前食物标签物品若没有专门资源配方，默认只换算为 1 食物资源。以默认狩猎期望计算，标准工人约产生 `7/6 × 1.5 = 1.75` 食物资源/日，远低于每居民 6.5/日的现有消费。

`town_sim.py audit` 会针对上述关键源码公式做漂移检查。它不是 Java 解析器，而是故意只锁定少量会改变兼容模型结论的事实。

## 3. 目标热学模型

### 3.1 单位

- 空间：方块、方块²、方块³；
- 时间：游戏小时和游戏日，默认热学步长 0.25 游戏小时；
- 温度：°C；
- 能量库存：燃料值 `FV`；
- 功率：`FV/游戏小时`。

这些是游戏单位，不声称与现实焦耳一一对应。

### 3.2 球形热场

每个塔或加热器拥有半径、设定温度、实际温度、最大功率、效率、基础消耗和超载模式。目标模型按下式逐步结算：

```text
C_field · V · dT_field/dt
    = P_delivered
    - [U_field · A + L_field · V] · max(T_field - T_ambient, 0)
```

- `C_field · V` 是启动和预热所需热容；
- `U_field · A` 是球体边界稳态损失；
- `L_field · V` 是没有明确围护结构的体积泄漏；
- `P_delivered` 受热源最大功率、燃料、超载、热网容量、效率和端点优先级限制。

球形热场重叠处仍取最高实际温度；各热源仍独立耗能，因此重叠率是显式浪费指标。该设定匹配当前游戏语义，也让玩家有动力提高“有效建筑体积/总热场体积”。

### 3.3 建筑室温

建筑使用整数方块盒体。模拟器逐体素记录它处于哪些球形热场中，预先压缩成覆盖位掩码比例；运行时在每组体素上取最高热场温度，再求建筑等效环境温度。

```text
G_building = U_building · A_envelope + L_building · V
T_inside(t+dt) = T_env + [T_inside(t)-T_env] · exp(-G_building·dt/(C_building·V))
```

这样可以同时表达：

- 建筑只覆盖球体一部分时的真实平均效果；
- 紧凑建筑较低的表面积/体积比；
- 保温与换气；
- 预热提前量和寒潮过后的恢复时间。

建筑永远不从热力网络直接取热。热网只向配置为 `networked=true` 的球形加热器分配功率。

## 4. 居民、食物与生产

食物拆成两个库存：

- `food_energy`：能否吃饱；
- `nutrition`：健康和精神恢复质量。

FCE 的基础能量需求按日结算；住宅低于舒适温度时，根据累计舒适缺口增加调温代谢需求。目标模型中住宅无论冷热都继续消耗和结算，低温影响依次为：

1. 舒适度和精神恢复下降；
2. 工作产能连续下降；
3. 低于生存阈值产生健康损伤；
4. 食物/燃料长期断供后才可能死亡。

关键产业采用有向流程图。每个流程声明输入、输出、SWE 份额、每座建筑最大 SWE、温度对应的建筑种类和优先级。参考场景只展开用于验证闭环的泥炭、林业、生物质压块、狩猎、温室、焦炭扩张和普通工业；它不是对 TWR 全配方网的复制。

动态劳动力奖励以**类别总额**分配，再按该类别流程的基础份额拆分。不能给每条燃料流程各加一次完整奖励，否则把一个流程拆成三条就会凭空获得三倍调度权重。

## 5. 玩家策略

- `none`：只运行基础热源，不根据预报超载或卸载工业。
- `forecast`：只读取玩家可见的分类预报与转折，默认观察未来 120 小时；检测到指定寒潮级别后预热、超载、启用外围热源、提高燃料/食物劳动力，并在库存危险时停非关键工业。
- `conservative`：对较弱寒潮也提前响应，维持更高库存目标，因此通常消耗更多燃料或牺牲非关键产能。

模拟器不会把完整未来温度数组直接交给策略。`forecast` 和 `conservative` 只看到由当前 `WeatherForecast.getTemperatureLevel` 阈值生成的等级。

## 6. 主要输入与派生输出

### 应暴露的设计参数

| 子系统 | 参数 |
|---|---|
| 气候 | 基线、局地偏移、事件持续时间、寒/暖幅度分布、轨道数、预报长度 |
| 热源 | 半径、设温、最大功率、效率、基础消耗、爬升与超载代价 |
| 热场 | `U_field`、`L_field`、`C_field` |
| 热网 | 容量、效率、端点优先级；首版不模拟管线路径损失 |
| 建筑 | 体素/盒体、容量、围护 `U`、泄漏 `L`、热容 `C`、舒适/工作/生存阈值 |
| 人口 | FCE、SWE、基础食物、低温代谢、健康/精神响应 |
| 产业 | 流程输入输出、每建筑吞吐、SWE 份额、库存容量、可再生上限 |
| 控制 | 储备目标、寒潮触发级别、预热长度、卸载优先级 |

### 应由模拟器计算的指标

- 正常和寒潮期间的热功率余量；
- 燃料/食物净产能余量与库存天数；
- 舒适、工作、生存阈值以下的度时；
- 球形热场覆盖率、总热场体积和重叠浪费；
- FCE/SWE 依赖比、床位/人口、有效体积/床；
- 缺货、危险低温、停工、死亡和不可恢复崩溃概率；
- 最低库存、最低健康、连续压力天数及恢复时间；
- 无干预与预报策略的风险差值、保守策略的额外成本；
- 参数敏感度和布局 Pareto 前沿。

不要把上述派生量重复暴露成配置，否则可能同时配置出互相矛盾的“单位燃料耗能”和 `U/L/C`。

## 7. 参考场景的首轮校准

参考场景将普通模式的热功率压在约 24%–25% 余量附近，超载峰值留给寒潮。120 日确定性设计寒潮的结果如下；这是模拟器验收数据，不是正式玩法承诺。

| 人口 | 策略 | 死亡 | 显著压力日 | 最低健康 | 正常功率余量 | 正常燃料余量 | 正常食物余量 |
|---:|---|---:|---:|---:|---:|---:|---:|
| 8 | 无干预 | 0 | 4 | 87.1 | 24.9% | 21.5% | 20.8% |
| 8 | 预报 | 0 | 0 | 100 | 24.9% | 19.5% | 21.2% |
| 24 | 无干预 | 0 | 4 | 87.1 | 24.9% | 23.6% | 26.9% |
| 24 | 预报 | 0 | 0 | 100 | 24.9% | 22.3% | 27.4% |
| 48 | 无干预 | 0 | 4 | 86.8 | 23.9% | 24.9% | 15.7% |
| 48 | 预报 | 0 | 0 | 100 | 23.9% | 23.8% | 16.0% |

固定种子 `24120` 的 8 人、120 日、每策略 100 场随机基准给出了第一组概率数据：

| 策略 | 生存率 | 不可恢复崩溃率 | 缺货或危险低温率 | 软压力触发率 | 平均燃料消耗 |
|---|---:|---:|---:|---:|---:|
| 无干预 | 76% | 24% | 97% | 100% | 10.18M FV |
| 预报 | 99% | 1% | 3% | 80% | 14.99M FV |
| 保守 | 99% | 1% | 4% | 60% | 17.16M FV |

这组数据中，预报策略通过了 95% 生存目标，并将缺货或危险低温风险相对无干预降低 94 个百分点；保守策略相对预报多消耗约 14.4% 燃料。它同时暴露出软压力触发率 80%，高于目标上限 70%，因此不能把首轮参数宣称为全部验收通过。需要用完整 8/24/48 人、每组合 1000 种子结果继续校准以下未完成目标：

- 24 人食物正常余量仍略高于 25%；
- 显著软压力率对寒潮幅度分布和 110°C·h 报告阈值敏感，8 人 100 场结果仍偏高；
- 保守策略在 8 人 100 场随机序列中已付出 14.4% 的额外燃料，但 24/48 人是否稳定达到 10% 仍需完整样本确认；
- 参考随机气候目前限定寒潮幅度为 8–55°C，并用四次幂分布使高级寒潮稀有。游戏进度若允许 T6–T10，必须建立按章节/年份变化的气候场景，不能把 −90°C 直接作为每轮事件的均匀抽样上限。

## 8. 使用方法

```bash
# 核对兼容模型依赖的 Java 事实
conda run -n standard python Scripts/town_sim.py audit

# 确定性设计寒潮
conda run -n standard python Scripts/town_sim.py simulate --design \
  --profiles target_rc --policies none,forecast,conservative

# 8/24/48 人、每组合 1000 个固定种子；默认最多 8 个进程
conda run -n standard python Scripts/town_sim.py simulate \
  --profiles current_compat,target_rc --runs 1000 --workers 8

# 参数化布局搜索与设计寒潮复核
conda run -n standard python Scripts/town_sim.py optimize-layout --population 24

# 目标模型敏感度
conda run -n standard python Scripts/town_sim.py sensitivity \
  --profile target_rc --policy forecast --population 24
```

默认输出位于忽略版本控制的 `build/town-sim/`，包括：

- `summary.json`：组合聚合结果；
- `runs.csv`：每个种子的完整摘要；
- `timeseries.csv`：代表种子的逐时序列；
- `report.html`：嵌入 PNG 的自包含报告；
- 布局和敏感度命令各自输出 JSON/CSV/HTML。

若运行环境禁止创建子进程，蒙特卡洛会发出警告并自动退回串行执行。环境依赖记录在 `Scripts/town_model/environment.yml`。

## 9. 已知边界

- 随机气候保留了“三轨道、最强负事件加最强正事件”的结构，但不是 `WorldClimate` 的逐字节重放；阶段化寒潮权重仍需从实际进度设计确定。
- 居民目前按平均健康、精神、SWE/FCE 聚合；`current_compat` 没有逐人复刻年龄、属性、熟练度和分配历史。
- 首版使用参数化盒体，不从存档导入任意形状建筑；覆盖位掩码数据结构已经允许以后接入 `OccupiedVolume`。
- 热网首版只有容量、效率和优先级，没有管道长度与路径损失，因为当前实现没有稳定的距离损失语义。
- 关键流程图不是完整配方导入。任何正式改动 TWR 配方或 KubeJS 前，仍需在两仓库中重新核对注册名与实际吞吐。
- 参考 TOML 的 `U/L/C` 是为产生可调张力建立的首轮游戏系数，不应解释为现实建筑物性。

# TTL 缓存后主服务器 tick 占用实测（2026-11-13）

- Status: `Current`，只对应下述 32 建筑自然世界与当前缓存实现。
- Last verified: `2026-11-13 UTC`
- Scope: `共享 section 服务及 TownConnectivity 对服务器主线程的直接 CPU/墙钟开销；完整服 tick 作背景对照`
- Code anchors: `TownSectionSnapshots.service/copySection`、`TownConnectivity.tick`、`TownPathCacheMixin`、`TownPathProbe`、`SectionSnapshotCache`

## 主要结果

按 20 TPS 的 **50 ms tick 预算**计算，实际取样/重算阶段：

- 主线程直接 CPU 平均约 0.70～0.73 ms/tick，五轮加权均值约 0.711 ms/tick（约 1.4% 预算）。
- CPU p95 为 1.31～1.52 ms，约 **2.6%～3.0%** 预算；观察到的最大 CPU 为 1.84 ms，约 3.7%。
- 无复制的空闲/尾段 CPU p95 约 0.04～0.08 ms，约 0.08%～0.16% 预算。
- 墙钟 p95 约 3.43～5.35 ms，约 6.9%～10.7% 预算；最大墙钟 32.32 ms，不能把 CPU 百分比当成实际延迟上限。
- 单个 section 复制 CPU 平均约 0.478 ms，逐轮 p95 约 0.83～0.84 ms；每维度每 tick 最多两个。

这里的百分比是占 **50 ms 预算**，不是占当前整服 CPU 耗时的百分比；也不是纯净原版服与整合包的对比。
结论仅覆盖当前一个城镇、一个活跃维度；多个活跃维度各有自己的两 section 预算。

## 环境与采样

使用同一客户端 JVM 和已有自然世界 `town-path-natural-20261113`：32 栋真实房屋，海岸/森林/冻峰自然地形，
其中一个入口已在前次封路测试封闭；图保持 13 条见证路、最大工作组件 8 栋。没有居民负载，所有搜索都扩展 72104 个节点。
221 个测试区块先完成加载，测量请求未触及缺失区块。缓存配置为 100/20/40 tick，容量 1024 section，维度预算 2/tick。

1 个逻辑 CPU、Java 17.0.21.0.3，配置堆上限 4 GiB（运行时最大 4,151,836,672 B）；
llvmpipe 软件渲染和集成服务器共用单核，1280×720、视距 6、VSync 关闭。没有使用 FPS 推算服务器开销。

依次测空闲前对照、两组清缓存/立即重算、显式缩短脏 TTL 后重算、两段刷新尾窗和空闲后对照。
空闲窗口 200 客户端 tick，尾窗 80 tick；搜索窗口直到主线程应用结果。全部阶段保留实际样本数，不假定窗口严格等于十秒。
“脏 TTL”阶段通过开发命令 markAllDirty，等待 25 tick 后重算，不改变实际地形；不是流体/红石密集写入压力测试。

## 怎样理解“占用原版 tick”

计时在主服务器线程进行：共享服务和该城镇 tick 两段区间按同一游戏 tick 累加；ThreadMXBean 给出实际线程 CPU，
System.nanoTime 给出这些区间的墙钟。因此后台 BFS 的等待时间不算主线程执行时间，也不把整轮十秒都算成一次 tick 卡住。
单次 copySection 又单独计时；缓存回收、排队、结果提交等仍包含在整段主线程指标中。

完整服务端 tick 记录 Forge ServerTick START→END。初始空闲对照的 CPU p95 为 11.14 ms，后对照降至 2.63 ms；
相应墙钟 p95 从 50.14 ms 降至 6.99 ms，存在明显预热/背景负载漂移。因此不能简单相减两个 p95，
也不能说“启用寻路反而让整服变快”。直接插桩的 feature 时间才是主要依据。
后半部分活跃阶段整服 CPU 平均约 2.98～3.11 ms，墙钟 p95 约 9.2～11.0 ms，作为背景数值保留在 CSV。

限制：直接 feature 区间不单独归因世界方块写入中的脏标记回调；这部分包含在完整服 tick 中，但没有独立拆分。
没有测试大量方块写入、多城镇/多维度竞争或多人专用服务器，也没有测纯净原版基线。
探针本身有少量计时开销；每轮只有约 188～202 个主线程样本，p95 是本轮经验值，最大值不是硬上限。

## 与缓存前的关系

本次每轮复制 249～262 个 section；之前同世界封入口后的无共享缓存基线为 1240 次，且扩展点同为 72104。
这支持“缓存消除了同轮重复取样”的观察。旧基线与本次不是同一 JVM，不能直接把所有耗时变化作为严格 A/B 优化收益。
新的周期重算约 9.4～10.1 秒，但本报告重点是主线程每 tick 成本，不是后台完成延迟；1200 tick 调度间隔仍保留。

## 最终架构与保留能力

维度协调者批量接管输入、推进就绪结构阶段和合并公共计量；区域独立计算、发布和继续下一次计算。共享池保留多核。真实传热/结构依赖仍保持等待，旧的Page等待全部源窗口的流程不参与SHARED_GRID。

局部结构更新只替换涉及的不可变查询Page，按父模板和相关Page身份检查候选。无关提交不会令整个维度的查询提案失效；普通数值提交只交换本区域帧。读者、候选和保存继续持有实际借用的数据，最后释放者决定归还占用。

粗细任务共用领取、取消、提交和释放规则。选择粗档的数值构建直接建立粗布局/最低传热模型，跳过细网格编译、细pairwise算子、PCG投影、父细布局拼接和细系数复制。细构建中途转粗会释放细工作空间引用，继续从持有的父快照构建。通用几何、材料身份与相变记录仍须捕获，不能把全部构建成本称为固定64节点。

`RegionalAirRuntime`内两处时间合并直接降档入口已删除；总J、符号、目标与时间范围仍由同一Store/Claim持有。2026-10-23晚间核对原验收JAR时确认，`RegionalWorkQueue.offer`仍会对aggregated输入直接降粗，质量控制仍会阻止其细档恢复；此前“全链路不再直接要求空间降档”的概括不准确。实际源码规则及后续存储优化状态见[运行时控制](thermal-runtime-control.md)与[存储计划](../../diary/2026-10-29_23-38-00_thermal-development-history.md)。本页下面的既有运行数据保留为当时结果，不能替代后续复测。

主要删除包括全维度`RegionalDirectory.Preparation/samePage/ownersByBrick`、重复区域帧数组、全局目录身份失效、`compacted_source_input`强制转粗与其无消费者传递标记、未使用内部API和重复状态。共享几何的全局盘点仍存在；本轮合并其调用，没有新造逐对象全局所有权框架。查询仍使用短发布monitor，结构构建与数值求解在锁外。

## 实测条件

- Intel i7-12800HX，16物理核/24逻辑处理器，可见内存约15.74GiB；Windows，JDK17。
- 热工作池4线程；JVM最大堆6GiB，即6442450944B。
- 热内存准入目标512MiB；整池CPU软额度1000ms/墙钟秒，跨线程累计，约相当于平均一个CPU核心的额度。瞬时可以多核并行。
- 真正的Forge服务器，实际房间、篝火、方块变化、源开关、原版保存与区块卸载；2→8→16→32基地，每基地最多8个火源，100个FakePlayer温度消费者按每20tick一次查询。
- 每阶段2400tick（20TPS时120秒），每窗口12000次消费者查询；后半段有240次真实世界变化。撤源阶段保留建筑，每基地留1个火源，再实际卸载/重载并继续运行。
- 最大约6994个原版加载区块。开启JFR及详细区域PROFILE日志；日志、GC和I/O也会影响观测。

## 尖峰与代价

32基地窗口有一次2834ms的服务器tick。JFR对应的结构协调轮持续约2896ms，但实际记录到热线程在`TerminalConsoleAppender → PrintStream → FileOutputStream.write`写2.2KiB详细PROFILE日志时阻塞约2860ms；同一时段原版区域文件写9.1KiB耗时约3040ms。其余热线程在空队列等待，机器CPU约1.56%，没有对应的长GC停顿。这是实测I/O/诊断输出停顿，不能解释成连续占用CPU计算2.9秒，也不能从指标中删除。

生产默认不启用逐区域PROFILE日志；仍保留现有日志和JFR能力，没有静默丢弃观察数据或增加异步日志框架。本记录不保证任意磁盘/终端输出环境无停顿。完整栈与重叠事件见[阻塞分析](../../build/thermal-scattered-20261023-regional-r4-temporal-512m-1000cpu-6g-blocking.txt)。

粗档的空间和时间精度低于细档。小场景真实切档验证记录降粗最大跳变约1.475°C、恢复约0.00435°C、checkpoint采样差约0.097°C；这些不是全世界误差上界。压力下允许其他区域降粗；模式恢复使用既有退避，撤压不会立即恢复全部细档。

## 为什么停止继续扩展优化

在尚未移除时间/空间耦合的早期对照中，128MiB/250ms每秒下16基地出现2400次存档回退，32基地4968次；不能用这组额度作百人分散服务器的资源承诺。512MiB/1000ms每秒在当时使正常32基地基本恢复，但撤源仍触发大量`compacted_source_input`空间降档。最终完整负载采用512MiB/1000ms每秒；旧数据不能精确代表最终源码在默认额度下的分散性能。

移除RegionalAirRuntime内两处时间/空间精度耦合后，该轮撤源工作线程分配从同配置前批约12.58GB降到2.99GB，重载后从约12.11GB降到2.16GB；对应服务器处理P99从60.8/71.3ms降到15.7/12.5ms。该轮满足代表负载的推进、正常精度、重载服务和所有权检查；这不是所有残留时间条件均已删除的证明。没有据此增加调度层或全局逐对象记账。

这不是“维度整批完成”与当前方案在全部场景的严格架构A/B胜负证明。当前选择的依据是保留区域独立服务目标，删除有代码和日志证据的全局重复工作与无必要精度耦合。

## 配置建议

在实际服务器的`config/frostedheart-common.toml`既有`["Thermal Runtime"]`中合并这些键，重启生效；不重复创建同名小节：

```toml
continuousAirNativeCheckpoint = true
continuousAirOverloadProtection = true
thermalMemoryTargetMiB = 512
continuousAirCpuBudgetMsPerSecond = 1000
```

2026-10-25退役旧后端后，区域共享网格是唯一正式运行时，旧`continuousAir`和`continuousAirBackend`不再参与选择。当前源码默认额度为128MiB和1000ms活动时间/墙钟秒，旧128MiB/250配置属于活动时间修正前的历史记录。较小或集中的基地可先采用当前默认；较大分散部署需在当前产物下观察样本年龄、回退、活动费用和堆后选额度。上方512MiB来自旧分散试验，并非百人服必须值或当前默认；本页按日期列出的旧结果只证明各自的产物。

2026-10-24当前实现又在默认128MiB/250ms每秒下完成12000tick双基地、256源、100温度消费者及三轮真实卸载/重载。32基地的新旧性能对照仍使用512MiB/1000ms每秒；本批没有证明更低热目标能提供同等32基地细档服务。512MiB是全热系统软准入目标，不是启动时固定分配的堆，当前32基地整轮峰值登记约269.86MiB；完成/保存等路径可超过软目标，64MiB压力测量已单独披露。

最新同机条件为i7-12800HX、16GiB物理内存、5GiB测试JVM堆和768MiB Gradle。大场景末段曾观测到约301MiB可用物理内存，结束该JVM后恢复；不能只根据热目标估计整机内存。正式服务器不需要Gradle，仍须给Minecraft区块、原生内存、其他模组和操作系统留余量。较大分散部署建议优先规划32GiB物理内存；这是一项部署余量建议，尚未实测32GiB或100真实联网玩家，不把它写成硬件保证。堆大小按整包实际峰值与GC调整，本轮只验证了所列5GiB测试配置。

本轮`assemble/reobfJar`已通过，可安装产物是`build/libs/frostedheart-1.20.1-0.7.7.jar`，使用主JAR而非sources/deobf附件。打包内容核对包含新运行时，不包含GameTest夹具；完整结果见[开发日记](../../diary/2026-10-29_23-38-00_thermal-development-history.md)。

6GiB堆是本机约7000加载区块的验证条件，不能据此承诺6GiB足以支持整个整合包100个真实联网玩家。玩家移动和区块生成、实体AI、网络及其他系统应另留余量。当前没有测量这些完整连接负载，不给未测硬件作保证。

## 能量塔：作物温度存在几十摄氏度的确定性差异

旧 `WorldTemperature.heat` 读取 `ChunkHeatData.getAdditionTemperatureAtBlock`，取命中热区中的最大正热值 `H`，不累加多个热区。旧方块/作物入口调用 `BlockTemperatureModel.applyHeat`。

令 `N` 为该消费者的自然方块温度，`m` 为 `blockHeatApplicationMultiplier`（默认 2），忽略示例中不会触发的绝对零度下限：

```text
旧：N > H 时 T = N；否则 T = min(N + m * H, H)
新：T = max(P, N + H)
```

`N/P/T` 单位为 °C。`H` 是旧热区控制值；当前实现把它当摄氏温差使用。`P` 为当前选择的 live/dormant/natural 温度。当前路径是 `GeneratorData.publishGameplayHeat → FLOOR_FROM_NATURAL → ThermalAnalyticFieldIndex.compose`。旧公式类仍在，不能据其存在认定当前作物仍调用旧公式。

下面取 `H=30`、`m=2`、`P=N`，也就是没有额外物理升温时的确切公式结果：

| 自然方块温度 N | 旧版结果 | 当前结果 | 当前减旧版 |
|---:|---:|---:|---:|
| −60°C | 0°C | −30°C | −30°C |
| −40°C | 20°C | −10°C | −30°C |
| −20°C | 30°C | 10°C | −20°C |
| 0°C | 30°C | 30°C | 0°C |
| 20°C | 30°C | 50°C | +20°C |
| 40°C | 40°C | 70°C | +30°C |

实际物理温场较热时，新结果还可能高于这列。以上不是整座基地的温度测量，但已构成不等价的公式反例。

小麦配方仍要求 `min_grow=5`、`max_grow=30`、`min_survive=-5`。`N=-40,H=30` 的示例中，旧温度 20°C 适合生长，当前保底 −10°C 已低于存活下限；有无额外物理升温会决定当前世界的最终结果。这已经能改变农业生存和科技阶段收益。

旧空气入口使用 `naturalAir + H`。在没有额外物理变化时，当前塔的 `max(P,naturalAir+H)` 可以与这部分对应，但不包含旧玩家之后的粒子修正、昼夜、风寒、衣物和显示步骤。当前物理升温还可叠加到塔的保底之上。

## 方块环境与空气环境不再是原来的关系

默认海平面以上，自然方块温度只接受 `0.5 * climate`，自然空气接受 `1.0 * climate`。两条自然公式本身保留。

当前 `WorldTemperature.block` 和作物入口在读到有效温场后，使用已发布的空气温度替代自然方块背景，而后应用解析场。旧方块入口始终使用自然方块公式再应用旧热区曲线。

因此，相同气候下，即使作物的配方和阈值不改，有无物理空气覆盖也可能改变它所使用的气候影响比例。例如 `D=-10,B=0,A=0,climate=-20` 时，自然方块为 −20°C、自然空气为 −30°C；一个实际读到 −30°C 空气的当前方块查询，与旧 −20°C 方块查询不同。实际热场还受 Section 中心背景采样、热源和历史温度影响，这个例子不是现场测量。

## 玩家显示、天气与身体计算

旧链路为：

```text
WorldTemperature.air（包含旧热区和 0.3°C 高斯扰动）
→ 减 37 → 加局部粒子温度
→ 昼夜/天空光/雨雪/接触修正
→ ENV_TEMPERATURE 属性
→ 风寒公式、部位末端偏移和衣物换热
→ 装备/代谢/调节/部位传热
→ getTotalFeelTemp（0.2 新值 + 0.8 旧值）→ HUD
```

当前链路为：

```text
naturalAir（无随机扰动）/live/dormant → 解析场
→ ENV_TEMPERATURE 属性与 Sauna（用于身体边界）
→ 按瓦/焦耳积分身体
→ sampledAir + 已采样辐射的固定折算 → getDisplayTemperatureC → 温度球
```

当前温度球使用属性和 Sauna 修正前的采样空气，加上既有 `RadiantEquivalentTemperature` 的 `q * 0.8 / 6.0` 辐射折算增温；风、衣物和身体状态不参与这个固定参考。服务端直接同步最终球读数，客户端不计算辐射。`getEnvTemp()`、`getTotalFeelTemp()`和呼气粒子仍读取空气；天气预报当前读数改读独立气候包的 `WorldClimate.getTemp(ChunkPos)` 基准，身体与伤害不消费温度球合成值。显示合同见[玩家温度](player-temperature.md#player-facing-values)。下列无辐射例子的当前读数不受此次显示修订影响。

旧昼夜修正为 `sin(dayTime * π / 12000) * dayNightTempAmplitude`，天空光低于 5 时固定取负振幅，默认幅度 10°C。当前玩家链路没有这项修正。

旧代码在实际降雨且玩家暴露时执行 `envtemp -= snowTempModifier`，雷暴再减 `blizzardTempModifier`，同时把昼夜振幅乘 0.2。默认值分别是 −5 和 −10，因此旧执行结果是加 5°C、再加 10°C，与旧注释“降温”相反。这里记录真实执行，不能把注释意图当成旧版数值。

`tempSkyLightThreshold`、`snowTempModifier`、`blizzardTempModifier`、`dayNightTempAmplitude`、`heatExchangeTimeConstant`、`heatExchangeTempConstant` 当前仍注册为配置，但没有当前玩家公式的消费点。恢复相同配置文件不能恢复这些行为。

当前 `PlayerThermalModel` 使用全身热容量 `245000 J/K`、`GAMEPLAY_TIME_SCALE=8`、空气换热倍率 `0.1`、水 `0.51`、细雪 `0.116`、Wet `0.03`。2026-11-05后续定标把基础代谢改为32W、御寒改为30/45/60W、御寒食物折算改为2800J/exhaustion，并取消`temperatureChangeRate`对普通身体时间的影响。下列表格保留定标前0.0824、30.625W及倍率仍控制身体的调查样本；新的结果以[数值报告](thermal-gameplay-balance.md)的后续定标记录为准。

确定性例子固定以下输入：默认配置、普通难度、初始各部位 37°C、更新间隔 20 ticks、无局部粒子热贡献、无风/雨/接触/装备/辐射、`dayTime=0`、天空光至少 5、噪声取 0、尚未触发体温调节。表内数值为公式求值，忽略 float 舍入末位：

| 输入空气 | 旧 HUD 的首个未平滑历史值 | 当前 HUD 原始值 | 旧核心第一秒温变 | 当前核心第一秒温变 |
|---:|---:|---:|---:|---:|
| −50°C | −4.4505°C | −50°C | −0.00309505°C | −0.00239386°C |
| −20°C | 14.1945°C | −20°C | −0.00123055°C | −0.00112489°C |
| 0°C | 26.6245°C | 0°C | +0.00001245°C | −0.00031650°C |
| 20°C | 39.0545°C | 20°C | +0.00125545°C | +0.00044545°C |

旧显示示例按旧实际算法计算：它把已减 37 的数值代入风寒式，再对手脚额外减 5，最后加回 37 并按部位面积加权。这解释了为什么旧体感数字和物理空气温度能差很多。HUD 最终还会按原显示代码取整/换算。

以上第一秒差异不能外推成长期失温时间；后续调节、内传热和伤害会改变轨迹。它们足以说明当前系统不是旧公式的相同实现。

旧身体基础代谢 `1/1000 °C/更新` 与当前 `30.625 W * 8 s / 245000 J/K` 相符。但环境换热和调节并未因此等价：旧版按各核心部位换热后的偏移触发调节并强制混合核心部位，当前按更新前加权核心温度选择功率，再做有限的守恒传热。

旧身体更新没有读取 `tempSpeed`；旧食物处理会读取它。定标前的新身体时间乘 `tempSpeed`，因此伴生整合包的`temperatureChangeRate=0.5`会额外减半普通身体生理步长。后续定标已移除此乘法，保留热食/冷食和提示的旧作用范围；源码默认1与整合包0.5不再改变普通身体更新速度。

2026-11-05进一步核对Git历史：该配置在模组`b72982c40`（2021-10-28，`config temp rate`）首次加入时默认0.5；整合包`8abd3951`（2024-02-09，`update for rc1`）将0.5写入默认服务端配置。模组`48ee9230c`（2025-02-10，`resolve duplicate files`）把源码默认改为1，更新间隔仍为20tick；整合包继续覆盖为0.5。提交没有说明选择1的具体平衡依据。新身体模型`2ac2973ce`（2026-08-30）明确把该倍率用于生理时间，这是配置作用范围变化的来源。源码默认与整合包覆盖的历史差异，不代表两档均已获得当前玩法平衡资格。

## 生存难度：优先核对热量平衡与完整时间过程

对用户实际目标，比“公式不同”更直接的检查是身体在危险温度下究竟继续降温还是开始恢复。

以下是定标前调查所用的确定性计算：普通难度、食物充足、干燥、无风、无衣物/装备/辐射/接触热源、所有部位初始 33.5°C、空气 −80°C、旧局部粒子与昼夜修正均取零、更新间隔 20 ticks、当时源码默认身体参数。

| 该条件下的计算 | 结果 |
|---|---:|
| 旧模型核心本次温变 | −0.00060955°C，继续降温 |
| 当前空气换热导纳 | 1.23334250 W/K |
| 当前身体失热 | 139.9844 W |
| 当前基础产热加最强御寒 | 30.625 + 122.5 = 153.125 W |
| 当前净功率 | +13.1406 W |
| 当前核心本次温变 | +0.00042907°C，开始回温 |

定标前的`temperatureChangeRate=0.5`会降低速度，但不会改变这个净功率方向。该调查不是实际服务器死亡测试，也没有包含食物消耗后失去御寒、持续风雪、伤害/治疗或真实世界背景。后续定标的同条件导纳约1.49677W/K、失热169.88395W、基础及最强御寒合计92W，净功率约−77.88395W，已恢复继续降温的方向；生存时间仍须由完整有限食物回放核实。

时间倍率和热容量主要控制升降温快慢，不能单独修复稳定热量平衡。应先核对环境失热、基础与御寒产热、衣物保护、装备和热源收益的相对量级，再校准到达危险体温及恢复所需时间；最后核对饥饿、口渴和燃料代价。不能只匹配开局第一秒。

## 热源与装备不能仅凭原配方仍在认定兼容

旧 `TemperatureThreadingPool.submitPlayerData` 确实写回粒子结果的 `blockTemp/windStrengh`，旧 `TemperatureUpdate` 实际提交这些工作。它不是旧版从未使用的无效模块。当前 `player/unused` 按用户要求保留源码，但已不参与当前身体查询。

旧 `block_temperature` 数据仍含篝火 500、燃烧熔炉 200、岩浆 1000 等参数；它们是旧局部采样参数，不代表旁边玩家直接处在该温度。当前这些数据的正式消费者是缓存/注册和提示界面，没有当前供热/辐射运行时的读取点。

当前篝火使用默认 `8000 W`，其中 80% 注入空气、20% 直接辐射；能量塔/喷泉/散热器分别使用 `10000/2000/4000 W * level`。静态辐射只处理岩浆及 `frostedheart:thermal/static_fire_radiators`，默认标签列普通火和灵魂火。因此燃烧熔炉、火把、灯、第三方 `block_temp` 配方等没有凭保留配方自动接入同等供热。伴生包仍提供 `charcoal_pit:log_pile` 的 `temperature=300` 配方，也没有由该配方注册当前热源的路径。

旧喷泉向指定柱形范围写 `(int) lastTemp * 15` 的常值热区；当前改为 `2000 W * level` 的点位物理源。喷泉原有 `lastTemp * 25` 玩家属性加值仍在；保留该加值不能还原已经替换的柱形热区及身体算法。

装备也有独立变化。例如暖贴和煤手炉原来加有效温度 20，再由默认 `1000 * 10` 的身体公式积分，即目标部位每次更新增加约 0.002°C 的加热贡献。当前暖贴最大可用功率为躯干 `110 W`、煤手炉为手部 `12 W` 或躯干 `110 W`。2026-11-08起，实际装备热量受每部位37°C回暖需求限制，叠加装备共用该需求；以下仅是冷态最大贡献的比较。默认时间倍率下，暖贴在忽略同秒散热和内传热时的躯干贡献为：

```text
110 W * 8 s / (245000 J/K * 0.45) = 0.00798186°C
```

这约为旧贡献的四倍，不是两种单位写法等价。总身体变化还要加环境、调节和内部传热，不能把上式当实测完整升温。当前按用户选择保留冷态供热能力，并让普通取暖装备在普通环境趋于舒适体温；背心扣除其他主动设备后补热，有限热库保留未传出的余热。当前合同见[玩家装备供热](player-temperature.md#equipment-food-and-effects)，不能再把这条最大功率算式解释为正常体温下仍持续全功率加热。

## 接触、伤害、食物和旧存档

- 普通水：旧版把环境钳到 0–100°C 后按全身水中状态放大交换 6 倍；当前水边界钳到 0–35°C，按各部位浸没高度建立换热路径。半身入水和旧版不等价。
- 细雪/着火/岩浆：旧版以环境替换和倍率处理；当前分别使用接触导热、着火 1200 W 等输入。温度边界数字相似不保证相同伤害与恢复曲线。
- 直接伤害：主要阈值仍是 ±100/150/200/250，但当前着火/岩浆跳过该温度附加伤害；旧版不跳过。旧 `<-150` 分支的 `nextFloat()<5` 实为必定伤害，当前为 50%。旧源码与注释意图须区分。
- 食物：旧版从核心偏移计算结果后把五个部位设为同一个值；当前对每个部位加相同温差并各自限幅。部位本来不等温时结果不同；过冷食物伤害的符号也修正了。
- 身体存档：旧部位保存 `temp`，当前 `BodyPartData.load` 只有新 schema 的 `energy_j` 才恢复身体能量，否则置零。因此旧人物的冷热偏移在首次读入时恢复到 37°C，衣物仍读入；用户明确要求保留重置，不做旧温度兼容，此项不作为缺陷。
- 材料存档及相变：当前材料 H/分支与休眠冷却是新状态。生成数据从旧 41 份相变配方变为当前 74 份（含状态展开，不能把文件数解释为新增 33 种玩法）。例如薄冰的 −20/9°C 阈值仍在，但当前材料存在时要满足真实能量端点。没有材料记录时才按环境阈值走后备分支。

## 按游玩结果校准的边界与顺序

| 需要保持的体验 | 应对照的结果 |
|---|---|
| 旧冷区仍然危险 | 相同装备、食物、动作和天气下，是否持续失温；到轻度异常、实际伤害和死亡的游戏时间 |
| 原有防护仍有价值 | 无衣、初级衣物、完整防寒装备在同场景下的保护差距与可停留时间 |
| 原有取暖仍然必要且有效 | 篝火/机器所需数量、距离与房间条件；点火后的止跌和恢复时间；熄火后的危险恢复 |
| 生存资源压力大致相当 | 御寒食物、散热用水、装备燃料和世界热源燃料的单位游戏时间消耗 |
| 原有农业阶段保持 | 同气候、同塔等级、同房屋条件下，作物是否存活、能否生长及所需供暖投入 |
| 新机制正常发挥作用 | 允许传播延迟、蓄热和浸没差异，不用额外恒温覆盖掩盖身体与环境计算 |

1. 以用户确认的旧版本、实际部署配置和配方为结果基准，选择少量能区分安全、需要防护和不可长期停留的代表场景。固定初始身体、生命、食物、水量、装备、动作与气候；分别记录裸装、衣物和热源的结果。
2. 保留当前机制，先校准空气/接触失热与基础/御寒产热的比例，防止旧危险环境因身体御寒过强而变成可持续保温。随后调整时间尺度，使危险发生和恢复速度接近旧体验。
3. 校准衣物、设备、辐射和房间供暖相对于失热的收益，并核对食物、水和燃料消耗。旧配方未接入当前运行时属于功能缺口，需要实现有效输入；不能靠提高别的热源补偿。
4. 作物以存活、生长和所需塔等级判定；新温度合成只要能保持这些结果，不必退回旧热区曲线。显示可以继续使用真实空气，不能拿显示数字接近代替身体结果校准。
5. 不恢复旧随机概率笔误、旧天气符号问题或旧内部调度。旧人物体温按用户明确要求重置，无需增加旧温度兼容。
6. 完成统一修改和闭合复查后，再统一运行重点场景；将结果偏差明确报告，不通过临时调难度、无限食物或缩短观察窗口让场景通过。诊断用固定食物条件与最终有限资源场景要分别记录。

当前没有完成上述结果校准，尚不能确认旧危险区域、供暖阶段和生存资源压力已保持。旧新版每点温度相差不超过 0.1°C 不作为这次游玩等效的单独判据；此前新热模拟内部性能优化的精度约束仍属于其自己的验收范围。

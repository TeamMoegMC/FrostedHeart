# 研究内容简报模板

- Status: `Current`（作者填写模板，非可直接加载的数据格式）
- Last verified: `2026-11-17`（联络连连看；其它流程见既有验证记录）
- Scope: 供人类和 AI 作者整理研究逻辑，并据此编写知识数据与玩家文案。
- Code anchors: `ProjectDefinition`、`ProjectAccess`、`ProjectRequirement`、`StageDefinition`；字段入口见[作者指南](authoring-guide.md)。
- 填写时删除方括号提示；这份简报不是游戏内文案。
- 编写前先读[编写研究内容](authoring-guide.md)和[知识定义](definitions.md)。

## 项目概况

- 命名空间与项目 ID：`[namespace:project_id]`
- 所属系统/玩法：`[系统名；关联配方、物品、方块或研究 ID]`
- 期望成果：`[结果 ID；会开放什么实际效果或权限]`
- 可复制的现有项目：`[链接；或说明为什么没有合适范例]`
- 证据边界：`[哪些内容已经由当前源码/数据支持；哪些是设计假设]`

## 研究逻辑

按阶段填写。单阶段项目也使用一个阶段条目。

### 阶段 `[stage_id]`

- 研究目标：`[本阶段要回答的问题或达成的目的]`
- 方法：`[研究者如何获取证据、观察或进行操作]`
- 判据：`[什么结果算完成；应能映射到实际知识条件或任务]`
- 结论：`[完成后可得出的结论；避免超出证据]`
- 必需任务：`[任务 ID、任务类型、目标与成功条件；没有则写无]`
- 可选任务：`[任务 ID、为何可选、完成后影响什么；没有则写无]`
- 路径参考：`[进入该阶段时已掌握的知识如何改变提示/减少任务；或写无]`
- 阶段推进：`[任务就绪后由玩家手动推进；说明阶段顺序和末阶段成果]`
- 成本：`[材料、设备、时间；在哪个操作消耗，失败时是否退还]`
- 失败与补做：`[如何辨认失败、如何重试；原型或样品丢失如何补做；已完成的独立任务不重复]`

任务类型、观察字段和阶段字段须选用[当前实现](definitions.md)中存在的格式。标记可选任务时，要配置阶段任务的 `optional: true`；若某变体隐藏它，还须在该变体 `omit_tasks` 中引用任务 ID。不能只靠自然语言把任务变成可选。

## 五种知识角色

每条知识逐环节填写。写“无”表示该知识不参与该环节；不要因某条知识出现在一个环节，就默认它也在其他环节生效。

| 知识 ID / 条件 | 发现入口 | 行为触发 | 联络 | 开始研究 | 阶段路径参考 |
|---|---|---|---|---|---|
| `[kind + ID 或 KnowledgeCondition]` | `[access.discover_any / 由 start_all 中的想法发现 / 无]` | `[acquisition.required 必需；optional 增加概率；triggers 事件和 subject；现有发射点 / 需 Java 接点 / 无]` | `[桌面 inputs；required_knowledge；optional_knowledge 每缺一项增加一级连连看难度，齐全为0级 / 无]` | `[access.start_all 条件名 / 无]` | `[阶段 ID、variant.when.knowledge_all / 无]` |

普通发现、联络、开始与路径前置都要求知识已在队伍档案中学会。若只希望玩家在当前 run 中做出一次观察即可完成任务，应配置 `type: "observation"` 任务，不要把它误写成永久知识前置。

进入阶段前补齐参考知识，仍参与该阶段的路径选择；已经进入的阶段不重新选路。不同路径可以改变提示或任务，但最终成果一致。

## 任务观察或实物提交

- 任务是否要求直接观察：`[否 / 是，描述观察对象及匹配条件]`
- 观察是否限定当前 run：`[是 / 否；若是配置 observation.team_current_run]`
- 观察是否限定实验：`[实验 ID / 无]`
- 观察是否要写入档案：`[任务观察默认不自动入档；如需永久知识，另设普通学习路径]`
- 是否真实消耗物品：`[否 / 是，列出 item 和 experiment]`

只有物品会在任务提交时实际被消耗，才使用 `type: "sample"`。现场观察可直接完成观察任务，不需要设置消耗实物的 sample 任务；若限定本次实验，设备仍须支持相应试样绑定，也不会自动产生永久档案记录。

土制炉配比观察的正式约定：烧后物品字段 `item.trial_kiln_variant` 取 `clay_rich`、`sand_rich` 或 `balanced`；试验 ID 为 `frostedresearch:trial_kiln/<variant>`，绑定当前队伍 run。三种结果作为观察任务判定，不消耗烧后物品、不自动入档。

## 数据与实现需求

- 可由现有数据定义的部分：`[项目、想法、成果、联络、观察条件、任务、阶段、语言键等]`
- 需复用的现有服务端事件或接点：`[事件 ID、发射位置、调用方；没有则写无]`
- 需要新增的 Java 接点：`[行为检测、观察值写入或任务提交；没有则写无]`
- 需要新增的机制：`[新任务类型、试验、权限或界面交互；没有则写无]`
- 数据示例与准确锚点：`[现有 JSON 路径、注册 ID、配方 ID、代码类/方法]`
- 不支持项或待确认项：`[列出，并标明由谁/如何确认]`
- 获取路线：`[设备、原型、材料在开始该任务之前如何获得；检查是否依赖本项目尚未解锁的配方]`

自定义 trigger 的 `event` 只是匹配已发出的事件。当前没有服务端代码调用 `IdeaAcquisitionService.emit` 时，单独增加事件名不会发生行为监听。自定义观察字段也必须由观察采集端实际写入。能力划分及真实字段见[作者指南的系统能力参考](authoring-guide.md#系统能力参考)。

## 玩家文案草稿

- 项目标题与简介：`[自然语言；不暴露未披露的条件]`
- 阶段标题与目标：`[让玩家知道研究方向]`
- 每项任务标题和方法：`[使用JEI可搜索的实际物品名；配比、制作与操作提示写入阶段/任务method，无需验证的准备步骤不额外设任务]`
- 阶段结论：`[与实际判据一致，像研究者的记录]`
- 对应语言键和中英文：`[language key；中文；英文]`

玩家文案可以自然表达目标、方法与结论，不要求出现“目标/方法/判据/结论”四个栏目。简报用于开发核对，游戏文案服务于玩家阅读。

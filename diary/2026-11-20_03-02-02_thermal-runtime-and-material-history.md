## 热模拟驻地时效与几何分批的 CPU 对照

- 时间　2026-11-19 17:55:04 +0800
- 作者　OpenAI Codex，定向实验由 Terra 6.1 max 执行
- 状态　已完成历史测量对齐和控制实验。百人测量的函数级差额仍待归因。
- 范围　`ThermalDimensionEngine.FixedGeometry`、`TopologyInbox.freeze`、`AirRouteCompiler.Component`、`ThermalNetworkLoadServer`

### 百人服实测

复用 G1、H1、H2 的 8,000 tick 测量，每个版本各有 34,600 次驻地查询。及时要求能读取当前位置、几何版本有效，且读数年龄最多 40 tick。

| 测量 | G1 | H1 | H2 |
|---|---:|---:|---:|
| 及时 / 过期 / 缺失 | 32,404 / 767 / 1,429 | 31,961 / 1,116 / 1,523 | 31,969 / 1,150 / 1,481 |
| 热工作线程累计 CPU，ms | 17,500 | 16,500 | 18,218.75 |
| 热工作线程分配，十进制 GB | 4.040 | 3.749 | 3.218 |

G1、H1 每个基地在全部 40 个测量帧的查询次数相同。H1 在前 1,400 tick 已少 556 次及时读数，此后追回 113 次。第 1,340 tick，H1 的 36 次过期读数都有当前几何，读数年龄均为 43 tick。紧随其后的工作线程快照中，有 18 人所在区域在等热源输入，另 18 人所在区域可推进。该帧另有 20 次缺失，读位置的几何版本与已发布温度不符。六次现场快照只解释采到的事件。

H2 比 H1 多用 1,718.75 ms 工作线程 CPU。前 1,400 tick 少用 312.5 ms，后 6,600 tick 多用 2,031.25 ms。8 个几何提交数相同的 200-tick 窗口仍累计多用 765.625 ms。第 3,400 至 3,600 tick 两版各有 250 次改墙、70 次几何提交、60 次连续同序号同时刻提交、13,250 个累计边界 Section、140 次温度发布和 2,250 个已发布 Tile。H1 的工作线程 CPU 为 343.75 ms，H2 为 703.125 ms。两者都采到 160 次主线程检查点快照，期间热预算延迟事件数为 0。GC 暂停分别为 102.77 和 72.14 ms（墙钟）。该段工作线程 Java 执行栈只采到 37 和 32 个样本。

H2 结束时输出的 JFR 文件为零字节。保留的四个原始 JFR 分块覆盖 8,000 tick 测量，分块内 JFR 数据丢失事件数为 0。用 40 个计数帧和含游戏时刻的主线程事件对齐。H1、H2 的执行栈含 `AirRouteCompiler$Component` 的分别有 7/1,915、10/1,853 个，组件内都未采到 `rehash`。按线程负载事件约 10 秒的周期积分，工作线程用户态约为 16.27 和 17.90 秒，内核态约为 0.12 和 0.20 秒。H2 的恢复逐帧记录到 560/600 tick，完整恢复和进程退出回执缺失。

### 对同一组编辑改变输入到达时机

H2 的 Forge 定向实验给同一批三个相互分离的区域各改一个格子。两组都交付同一条热源窗口，唯一操控的是先交付还是后交付。晚到时有一个编辑区及其相邻区域在提交编辑时仍在 tick 20，另外两个编辑区在 tick 40。全部就绪时一次发布三处，晚到时先发布两处，再发布余下一处。32 组详细记录都分别处理了 3 个片段，边界规模从一次 81 变成 54 加 27，两个集合互不重合。每组在同一物理时刻核对 256 格的温度、焓、材料、分支和总能量，差异均为零。

另用只累加整数的观察者计量 32 组配对。用 `QueryThreadCycleTime` 测调用实际 `processWorkRound` 的同一线程。涉及几何的轮次累计从 56,870,984 增至 68,102,216 cycles（+19.7%），其中 29/32 对增加，每对差值中位数为 482,444 cycles。连续读计数器的中位差为 4,854 cycles，原始数保留此开销。计量覆盖整轮准备、执行及发布，局部案例的 cycles 不外推为百人线程的毫秒。

### 通风组件单独对照

同一 JVM 调用已编译的 `Component` 创建与收尾路径。旧 `Component` 用先前保留的字节码，该类内部源码截至 H1 相同，其余运行类取 H2。每种输入每版累计 400,000 个组件，核对出口、面及边的结果。表中为当前线程的累计数除以组件数量。

| 输入 | 旧 cycles/件 | H2 cycles/件 | 旧分配 B/件 | H2 分配 B/件 |
|---|---:|---:|---:|---:|
| 无出口 | 887 | 403 | 4,760 | 1,592 |
| 通往同一区域的八个出口 | 1,474 | 780 | 5,666 | 2,320 |
| 多区域并包含连接边 | 2,648 | 2,527 | 9,600 | 7,704 |

三种输入的输出一致。百人服的 24,362 对可用、同点、同物理时刻温度，H1 与 H2 的最大差为 0.861°C，全部在既有容差内。容差取 1°C 与 H1 温度相对自然温度偏移的 5% 两者之大。分配收益有局部和全服记录，整场多出的 CPU 尚缺逐笔几何准备、求解、发布的 CPU 计数。

### 决定与产物

保留 H2 现场以及现有的逐格覆盖、时间推进和读数判定。此次新增诊断与验证记录，游戏系统合同无需修订。下一次给几何路径做性能对照时，应分别记每批实际参与的 Page、发布范围和各阶段线程成本，同时记录 40 tick 内的读数。提交次数单独无法衡量成本。

本机生成目录 `build/thermal-ab-20261118/` 下保留 `cpu-diagnosis/window-report.json`、提取和对齐脚本、`cpu-diagnosis/H2-recording/` 的原始分块、`readiness-probe/results-cycles.json` 的完整事务清单、`readiness-probe/results-minimal.json` 的低开销周期计量和 `readiness-probe/route-finish/results.json` 的组件对照。时效逐段数据在 `H1/why-443.json`，各版本的原始驻地计数在对应 `metrics.jsonl`。

### 补充分段计量

在同一组件对照中预先构造并填充 10,000 件，再单独计量 `finish`、读取计数和清理索引。多区域四条边的 6 个配对中 H2 均多用周期，旧代码每件平均 2,968 cycles，H2 为 7,223 cycles。连续创建即完成与预先成批创建的对象寿命和缓存条件不同。实际百人负载中两种时序的比例没有记录。原始分段与连续测量见 `readiness-probe/route-finish/REPORT.md`。

`FixedGeometry.beginGeometryValues` 把已知边界传给 `TiledThermalField.begin`。当前 `begin` 遍历已分配 Tile 的有序目录，按边界选出本次参与者。分成两笔时该选择过程会执行两次，这是可以直接核数的额外工作，现有周期数据只量到包含它的整轮。

## 热模拟按变更 Brick 交付方块签名

- 时间　2026-11-19 18:34:24 +0800
- 作者　OpenAI Codex。Terra 6.1 max 完成独立 JVM 微测。
- 状态　已应用在 H3 工作区。投影局部验证通过。百人测量的及时读数和温差仍未达到原目标。
- 范围　`PageSignatures.copyBricksTo`、`ThermalDimensionEngine.FixedGeometry.prepareField`、`ThermalGeometryPreparationGameTests.sparsePageProjectionWritesOnlySelectedCells`。

### 实现与系统文档

Page 对应一个 16×16×16 的世界 Section。几何发布已经携带 `capturedBricks()` 和 `changedBricks()`。H2 在 `prepareField` 对每个待写 Page 解包全部 4,096 个方块签名。三处各改一个 Brick 的已有场景因此解包 12,288 格，三个实际变更的 Brick 一共只有 192 格。

H3 用 `addedBricks | (changedBricks & capturedBricks)` 选择签名，按 Brick 读取已有的均一值、紧凑数组或宽数组，写回 Section 缓冲中的原有坐标。新建或替换生命周期后首次接纳的 Tile 读取全部已捕获 Brick。`grow` 为新分配的 Brick 读取初始签名，旧覆盖撤出后使用 `UNRESOLVED`。退出的格子也继续经历原有的材料转换和热量处理。系统文档新增[空间单元与交付方式](../docs/climate/thermal-runtime-control.md#pagebrick-与-tile)。

### 验证

- Forge 正常入口 `runGameTestServer` 一次运行几何准备、几何提交、数值发布和驻留时效四组，32/32 通过。新增用例比较稀疏、高位、满页和空掩码写入，检查复用缓冲内其余位置。
- 同一 JVM 比较原来的 4,096 次 `PageSignatures.get` 与新投影。8 份页数据各测 69 种掩码。100,352 个选中格逐项相同，2,160,640 个未选中格保留哨兵，重复使用已填充缓冲的 8,192 项也都正确。混合编码下，只交付一个 Brick 时每次平均线程周期从 14,321 降到 138，4 个从 14,288 降到 501，满页从 14,325 降到 7,488。两边都复用缓冲，计量循环的线程分配均为 0 B。
- 一次新百人服运行对照已有 H2。100 个客户端、25 个基地、1,600 个热源，8,000 个混合负载 tick 加 600 个恢复 tick。两版从同一世界时刻开始测量，每个基地在 40 个统计帧中的驻地查询次数完全相同。H3 服务端与客户端退出码均为 0。

| 8,000 tick | H2 | H3 |
|---|---:|---:|
| 热工作线程 CPU，ms | 18,218.750 | 15,328.125 |
| 热工作线程 CPU / 及时读数，ms | 0.570 | 0.502 |
| 主线程 / 进程 CPU，s | 82.547 / 319.062 | 70.500 / 272.500 |
| 热工作线程分配，十进制 GB | 3.218 | 3.230 |
| 及时 / 过期 / 缺失 | 31,969 / 1,150 / 1,481 | 30,517 / 2,114 / 1,969 |
| 几何提交 / 发布温度块累计数 | 2,865 / 82,913 | 2,734 / 83,266 |

实服观察的热工作线程 CPU 减少 2,890.625 ms（15.9%）。在单独运行的两个 JVM 上，实际发布和卸载的时序存在差异。微测说明签名投影本身节省周期，跨进程总差额包含其他工作。

### 及时读数与温差

H3 的 1,452 次及时读数净损失中，前 1,400 tick 已经少 1,353 次，之后少 99 次。第 600 到 1,000 tick，两版驻地查询都为 1,600 次，及时读数分别为 1,536 和 792。JFR 中工作线程请求预算延迟的区间在该段覆盖约 0.016% 和 40.68% 的墙钟时间。覆盖率按延迟请求区间取并集。在第 600 tick 的另一组固定探针上，H3 有 66 个可读位置停在 43 tick 以前，H2 的 75 个可读位置年龄均不超过 23 tick。H3 的恢复阶段共有 2,900 次驻地读数，全部及时。

按工作负载时刻、位置和真正采样时刻配对的 H2/H3 温度共 21,960 个。26 个超出原容差，最大温差 1.115°C。原容差取 1°C 与该处 H2 温度相对自然温度偏移的 5% 两者之大。核对这些探针所在的实际 Chunk，26 次都落在最近一次卸载保存时刻不同的组中。两边均有保存且最近一次保存的 Page 数和采样时刻范围相同的 4,339 对全部在容差内。两边测量中均未观察到卸载保存的 3,282 对也全部在容差内。以基地 1 的第一个点为例，离开后 H2 保存到世界 tick 13,520，H3 保存到 13,619。在第 2,720 测量 tick 回到该处，两版读数年龄同为 3 tick，温度分别为 −3.732°C 和 −2.635°C。该事件证明输入历史存在差异，单次跨进程记录不足以量化每项原因。

### 剩余工作与产物

变化签名的映射已通过正确性和局部耗时对照。工作区保留此候选供后续验证。整体玩法验收仍需解释工作线程的启动期预算延迟及基地卸载时刻差异，签名投影的成绩不能取代及时性和温度对照。

## 热模拟普通任务为何在启动期延迟

- 时间　2026-11-19 19:51:02 +08:00
- 作者　OpenAI Codex。Terra 6.1 max 执行独立 JVM 停顿对照。
- 状态　确认普通数值工作超过共享额度会推迟更新，且任务内暂停会放大延期。已完成四组前 1,400 tick 的真实服对照。
- 范围　`ThermalWorkerPool.serviceReadyAt`、`chargeService`、`TiledThermalField.advance`、驻地查询的 40 tick 及时标准。

### 决定、验证与文档

保留 H3 现场做诊断。用已编译游戏和临时观测器交叉比较两种读取方式与两档额度，核对客户端、每基地每个统计窗口的尝试数、任务计费与 JFR。按 Brick 读取时，同样 6,000 次查询，放宽诊断服额度使及时数从 4,144 增至 5,478，预算延期请求从 3,819 降至零。整页读取也复现。此前执行停顿的解释只覆盖部分峰值，剔除 GC、几何和页读取后，短时间集中的温场推进已超过原额度。

历史全程的 CPU 下降 15.9% 应解读为 Windows 线程 CPU 计数器的读数差。按 Brick 读取的局部收益有独立周期测量。本轮新增[启动期延迟验证记录](../docs/climate/validation/thermal-validation-reports-2026-11-19-to-20.md#thermal-service-delay-2026-11-19)，其中列出生产计费公式、一个真实延期事件、两种读法的四组对照、窗口计算方法和原始产物入口。本轮的文档影响限于验证证据与本日记。

### 验证边界

历史 8,000 tick 对照每种读法各有一次。晚发布的具体次序只能追到已有记录的时间和空间粒度。此次短测用同一存档的工作负载前缀解释延期机制，历史长测与本轮估算保持各自的计量范围。

<a name="thermal-face-sweep-cpu"></a>

## 减少百人服温场邻面换热的重复计算

- 时间　2026-11-19 20:55:12 +0800
- 作者　OpenAI Codex。Terra 6.1 max 执行固定输入正确性与 CPU 周期对照。
- 状态　已应用。Forge 34/34、固定输入逐项比较与百人短测完成。
- 范围　`TiledThermalField.begin`、`sweepNextCells`、`positiveFace`、`negativeBoundary`、`ThermalExchangeKernel.applyPairWeight`。

### 选择依据与实现

为已编译 H3 加入测试服阶段观察器，沿温场实际阶段改变的时刻归集经过时间。在原额度 250 ms/s 下，正反两遍邻格换热用 8.544 秒，占温场推进 9.083 秒的 94.1%。开始事务、领取输入和筛选输入槽合计 0.154 秒。974 次成功开始在共计 181,296 个目录项中选择 40,698 个 Tile。领取检查了 271,854 条流，215,201 条通过范围筛选。输入缓冲访问 1,297,840 个槽，选中 213,386 个。结束前取消的 127 次正时长事务在温场推进内已用 1.064 秒。

## 材料两层接触与边界候选验证

- 时间　2026-11-20 02:40:29 +08:00
- 作者　OpenAI Codex
- 状态　两层规则与局部失效修复完成；定向回归及同构建内核筛查通过；全服最优性未验证。
- 范围　`MaterialContactPolicy`、`TiledThermalField`、`WorkerPageStore`、拓扑/风道依赖、篝火驻留与 Forge 验证。

### 约束与决定

用户澄清“两层”指实体传播深度，不是 1°C / 0.5°C 温差迟滞。起始固定核未使用旧表层/唯一内层规则，驻留厚墙可继续向深处传热。取消无界扩张候选，恢复同一约束到实际换热和边界请求。篝火（包括熄灭后有余温的本体）具有表层资格，直接邻接内层只能和自己的唯一表层交换；归属沿用最小 signed packed BlockPos。部分形状继续按 `contactFraction` 接触。

正式求解每 Brick 增加三个 long 的正向面许可，24 字节数组载荷。几何提交后重建，扩缩容按 Brick 身份复制；稳态换热只查位。篝火六邻强制 seed 移除，仅保留正功率端口目标，再按材料温差纳入边界。1 K / 0.5 K 门槛及材料自然初始化平台参照保持。

### 发现与验证

首轮 7 项通过。新增三轴 Section 角点检查实际发现缓存漏更新；补齐八角依赖。路由可以改变远处的表层身份，因此通路发现完成后另一次性加入 dirty Brick 的面邻/棱邻。最终夹具在 Y/Z Section 边界放置半砖通路，并开关远处空气入口，逐面比较已安装掩码与即时策略。

最终 Java 17 / Forge 的 28 项必需测试全部通过，日志 `build/material-frontier-validation/final-routes.log`，Gradle 成功。覆盖六面真实篝火、第三层隔离、唯一归属、形状接触、正负迟滞、自然相变、替换、收缩、存档、通风、熄灭与余温。前一轮 `final.log` 也为 28/28；不将这些重复执行累计成更多独立用例。

同一构建比较直接扫描、边界候选缓存和最终 Accepted 合并扫描。2,048 格 / 32 Brick / 16 本体场景，四轮预热、九轮轮换计量。Windows CPU 纳秒中位数多为零，使用单独记录的线程周期判断相对成本，不把 cycles 换算成秒。接触许可缓存较直接策略减少约 56.9% 的检查周期；额外边界缓存在热场景减少约 28.4%，冷场景增加约 4.5%。合并摘要没有稳定优势，两个边界候选均留在 GameTest，不加入生产状态。完整数据与方法见[验证记录](../docs/climate/validation/thermal-validation-reports-2026-11-19-to-20.md#thermal-material-frontier-2026-11-20)。

## 取消材料第三层断热限制

- 时间　2026-11-20 02:56:40 +08:00
- 作者　OpenAI Codex
- 状态　已实现；42 项 Forge GameTest 必需用例全部通过。
- 范围　材料实际换热、跨 Brick 扩张、层数缓存与拓扑依赖清理、篝火驻留说明。

### 用户要求与实现

用户明确要求取消“第三层不传热”，并询问六向换热是否仍需要强制驻留。核对 `PhysicalSourceSpatialIndex.refreshTargets`：上一轮已经去掉六邻 seed，仅保留正功率端口目标；篝火是本体与上方出热口，去重后最多两个 Brick。本轮不恢复六邻强制驻留。

固定求解器 `TiledThermalField.conductance` 和参考编译器 `BrickTopologyCompiler.connectFace` 仅按接触面积与材料导热率传热；第三层及更深材料、两侧表层之间的内部材料都可以交换。移除 `MaterialContactPolicy`、每 Brick 三个 long 的层数接触许可及其内存预算、复制和重建流程，删除表层资格接口及 `BlockBrickLayout.airContactBlocks`。仅用于层数归属的额外邻域、八角和远端风道依赖也已删除，普通相邻面/路由更新继续使用原路径。

`WorkerPageStore.collectMaterialFrontier` 改用已有 `materialNodeMask`。静态 `MATERIAL_FRONTIER_BLOCKS` 仅选 4×4×4 Brick 的六个面，排除中央八格；每个候选仅检查实际朝外方向。完全埋藏的材料同样按最终 Accepted 温度请求下一相邻 Brick，保留进入 1 K、保持 0.5 K 的正负对称迟滞及材料自然初始化相变背景。没有引入新的候选缓存或温度摘要。

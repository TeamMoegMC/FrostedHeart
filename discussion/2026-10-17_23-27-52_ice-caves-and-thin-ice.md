## 首轮待讨论事项

| 议题 | 选项 | 当前建议及理由 |
| --- | --- | --- |
| 离开薄冰后 | 继续破裂；暂停；逐渐恢复 | 触发后继续，提供清晰撤退窗口，危险结果容易理解。具体规则尚未逐项确认。 |
| 厚度与耐久 | 所有厚度一致；越薄越快 | 越薄越快，让现有层数具有玩法意义；完整薄冰与满层薄冰应一致。 |
| 单层如何踩踏 | 修改碰撞；保留无碰撞并做接触检测 | 先验证实际站立和通行体验，再决定；不能仅添加普通踩踏回调就假定有效。 |
| 潜行与跳跃 | 无区别；潜行延缓；潜行豁免；落地加速 | 原型先用统一规则，确认基础体验后再决定是否增加差异。 |
| 哪些实体触发 | 玩家；玩家和生物；按实体分类 | 倾向玩家和生物，明确排除物品等无关实体；不先引入重量系统。 |
| 裂纹预警 | 只有声音；声音与分阶段纹理 | 两者结合；已有随机纹理不是裂纹阶段，需要覆盖分层外观。 |
| 机械破碎结果 | 空气；水；依场景处理 | 悬空处留下空气，已有流体按实际环境处理；与温度融化和挖掘区分。 |
| 掉落 | 不掉落；冰屑；与挖掘相同 | 倾向机械破碎不掉落，减少反复触发的杂物；普通挖掘与精准采集另行保留其规则。 |
| 连锁破裂 | 仅被踩方块；向邻近传播 | 首个原型仅被踩方块，先校准撤退时间。连锁坍塌尚无用户要求。 |
| 开裂时增加层数 | 保留裂纹；重置；修复部分裂纹 | 倾向保留裂纹，避免无意把堆叠变成即时修复；需测试层数变化后的剩余时间。 |
| 蓝冰接水生成薄冰 | 直接复制；接入 FH 相变；暂不做 | 后续接入 FH 温度/相变，首个踩踏原型暂不包含。 |

表中“当前建议”均是讨论起点；实现者应记录最终采用的规则与理由。具体开裂时长尚无定案，先通过快速跨越、持续站立和不同厚度的试玩确定。

### 2026-10-18 — OpenAI Codex：完整薄冰的用户设计修订

本轮只讨论与核对实现条件，未继续修改代码、制作模型或运行构建。以下明确要求针对完整薄冰块 `frostedheart:thin_ice`；不能自动推广到分层薄冰。用户表示认同此前大部分内容，但没有逐项确认其余所有建议。

**用户本轮确认的规则：**

| 项目 | 已确认方向 |
| --- | --- |
| 开裂机制 | 每个阶段向下一阶段以一定概率推进；“快慢”表现为概率差异，不采用固定倒计时。具体阶段数、概率和抽样间隔未定。 |
| 潜行 | 原地潜行和潜行移动都很慢地破碎，不完全豁免。 |
| 静止站立 | 缓慢破碎，比潜行更容易推进。 |
| 正常行走 | 一般速度破碎，比静止站立更容易推进。 |
| 跑步 | 快速破碎，比行走更容易推进。 |
| 跳跃、坠落 | 很快破碎，破碎速度与坠落高度正相关。具体冲击概率曲线未定。 |
| 完全破碎 | 六个面相邻（含上、下）任意有水方块，则原位变为水源；否则变为空气。替代此前草稿的“一律空气、不主动生水”。 |
| 离开后 | 停止踩踏导致的推进，保留已有裂纹。用户已在补充问题中明确确认；替代此前的“离开后仍持续直至碎裂”。 |
| 恢复 | 离开后，气温满足水结冰条件且六面相邻有水方块，才能通过相变恢复完好；条件不足时不能恢复。 |
| 温度加速 | 气温严格高于 0°C 时开裂加快。 |
| 自行开裂 | 气温严格高于 0°C 时有概率自行开裂；该项以性能可接受为前提。 |

**源码核对事实与实现边界：**

- `WorldTemperature.WATER_FREEZES` 为 -5°C；水源配方 `state_transition/minecraft/water_level_0.json` 的冷却阈值同为 -5°C，目标已是完整薄冰。这是当前项目阈值，不应擅自替换成现实水的 0°C；用户明确指定的 0°C 是开裂加速与自行开裂的分界。
- 现有水源回冻还受材料热学推进、生物群系排除和水平流体边界条件影响，不能承诺“只要气温低于 -5°C 就立即结冰”。现有边界条件也不等同于本轮要求的六面邻水。
- 现有完整薄冰冷却边是 -20°C 变普通冰，加热边是 9°C 变水。给开裂薄冰增加回冻修复时，需要明确与这两条相变边的关系；不能简单覆盖已有冷却规则，或用气温检查直接重置裂纹冒充材料相变。
- `WorldTemperature.air` 是现有气温入口，其自然回退带 0.3°C 高斯噪声。设计实现需明确采样位置、频率和噪声策略，避免同次判定多次读温度得出互相矛盾的结果。
- 当前行为草稿仍为统一触发、固定计时、离开后继续和破碎为空气，不符合本轮设计，尚未改写或验证。源码草稿不是本轮设计已经实现的证据。

**代理建议，尚未确认为规则：**

- 踩踏以统一时间间隔抽样，把“姿态/运动状态、裂纹阶段、温度”映射为推进概率；同一判定最多推进一个阶段，声音只在实际变更阶段时播放。这样站立回调频率或多个回调不会无意改变概率单位。
- 跳跃和坠落用落地事件读取实际坠落距离，单独作冲击判定；不让只是从空中经过的实体触发脚下薄冰。落地后再回到当时的站立/移动规则，避免把一次坠落永久当成高负载。
- 高温自行开裂使用现有随机刻抽样，不对全部冰块逐 tick 查温度；邻水检查最多六个位置，不为此加载邻区块。不增加每块冰的方块实体或全世界扫描。此为可控制检查量的方案，尚无性能实测；随机刻推进与踩踏推进的抽样频率需分别校准。
- 回冻以现有热学/相变路径为基础。仍有裂纹的薄冰修复、已经破碎成水源后的普通结冰，是两个需要分别定义的过程；是否逐阶段修复、回冻时间与已有低温变普通冰的优先关系尚待设计。

**试玩反馈：尚无。** 旧草稿的单层 0.75 秒、完整块 3 秒不再是完整薄冰的候选固定时长，不能沿用为本轮定值。下一步先定推进概率、落地冲击与回冻过程，再修改行为草稿和制作表现。

### 2026-10-18 — OpenAI Codex：原版碎冰实际检测方式

用户询问原版是否每 tick 检查冰块上方有无玩家。本轮直接读取 Mojang 版本清单并检查 `26.4-snapshot-4` 官方 client JAR 的字节码；没有继续开发 FH 实现。

- `Entity.applyEffectsFromBlocks` 在实体接地且受方块影响时读取脚下方块，调用 `Block.stepOn`。无位移时也有对应处理，所以站立不动同样能触发；不需要每块冰主动搜寻上方玩家。
- `BrittleIceBlock.stepOn` 只在服务端处理活体，排除 `#does_not_break_brittle_ice` 标签实体；若该位置已有 scheduled tick，则跳过。允许处理时调用 `slightlyMelt` 推进一级，并排定 24 ticks 的更新。
- **这里的 scheduled tick 充当冷却门槛，不是自动持续开裂的计时器。** `BrittleIceBlock`、`CrackingIceBlock`、`IceBlock` 均没有重写 scheduled `tick`，继承的 `BlockBehaviour.tick` 是空方法。到期后需要再次踩踏回调才继续；踩踏路径不会在离开后自行连续推进。
- `CrackingIceBlock.slightlyMelt` 将 `age=0→1→2→3`，再次推进时破碎。碎冰踩踏路径没有概率判断，没有潜行、跑步或坠落高度倍率。
- 原版破碎还通过 `propagateMelting` 推进六面邻接同类冰裂纹；这不是 FH 已确认的规则。继承自冰的光照随机融化也是独立路径，不能把“无人踩踏停止”解释为原版任何环境下都永不变化。

对 FH 的建议：可沿用实体脚下回调和方块冷却门槛的结构，增加已讨论的姿态、温度与冲击概率；没有必要对所有薄冰逐 tick 扫描实体。具体抽样与多人同时踩踏规则仍待定。

来源：[Mojang 官方 client JAR](https://piston-data.mojang.com/v1/objects/ac783fa45b137dd545c7ffb76bbd595ea85fda0a/client.jar)、[官方快照说明](https://www.minecraft.net/en-us/article/minecraft-26-4-snapshot-4)。本地检查记录在 `build/vanilla-inspection/26.4-snapshot-4/`；可由对应官方 JAR 用 `javap -c -p` 重新查看。调查记录见[日记](../diary/2026-10-18_11-54-07_vanilla-brittle-ice-tick-inspection.md)。

### 2026-10-18 12:01 — OpenAI Codex：用户确定概率与冷却共同控制速度

本轮继续确定完整薄冰规则，尚未更新行为代码、模型或测试。以下为用户明确给出的设计：

- 普通踩踏开裂同时受每 tick 推进概率和冷却时间控制。
- 以正常静止站立为锚点：未处于冷却时，每 game tick 有 `1/24` 概率推进一级裂纹；开裂成功后进入 `24 game ticks` 冷却。失败不进入冷却，否则不符合未冷却期间逐 tick 抽样的要求。正常 20 TPS 下，24 ticks 为 1.2 秒。
- 冷却期间不作普通踩踏推进；冷却到期不会自动推进，仍需实体接触并通过概率判定。
- 跳跃和落地按冲击处理，类似耕地踩踏；冲击不受当前冷却限制，一次冲击允许推进多级裂纹，达到破碎所需进度时直接执行最终破碎结果。“多层”在此指裂纹级数，不是分层薄冰的厚度层数。
- 冲击强弱随坠落高度增加的方向沿用此前用户要求。离开后停止踩踏推进、低温邻水回冻、邻水破碎成水源及高温影响等已确认规则继续保留。

**节奏推导（不是固定时长，也不是试玩反馈）：**

在持续正常站立、无温度倍率、无冲击或修复干扰的条件下，未冷却时首次成功等待服从概率 `p=1/24` 的几何分布，平均需要 24 次抽样（约 1.2 秒）。一次成功与下一次成功之间还包括约 24 ticks 冷却，因此平均间隔约 48 ticks（2.4 秒）；实际调度边界可能相差 1 tick。随机性意味着没有固定必碎时刻。

若沿用当前草稿的 `crack=0→1→2→3→破碎`，从完好到破碎需要 4 次成功推进：首次约 24 ticks，其后 3 次各约 48 ticks，总平均约 168 ticks（8.4 秒）。这里使用四次推进仅为评估现有阶段结构的推导，不额外宣称用户本轮已经确认阶段数。

**代理建议与仍未确定的参数：**

- 可以给普通动作定义一个时间参数 `N`（单位 ticks）：`p=1/N`、冷却 `N ticks`，站立为 `N=24`，潜行取更大的 N，走路/跑步取更小的 N；温度影响也可映射到 N。此为保持参数简单的建议，其他动作是否严格使用这组互为倒数的映射及具体数值尚未确认。
- 普通概率应明确以方块每 tick 为抽样单位，避免同一 tick 的重复回调意外多抽；多人踩踏如何合并负载尚未确定。
- 冲击仍需确定起跳是否单独判定、落地高度到推进级数/概率的映射，以及冲击发生后是否重设普通踩踏冷却；本轮只确认冲击能绕过已有冷却，不替用户决定冷却重设方式。

#### 机制比较：固定冷却＋逐 tick 概率，与一次抽取延时

以下为代理分析与建议，不是用户新增决定。

- 薄冰的固定冷却加逐 tick 概率适合持续承重：玩家运动状态变化可改变下一次推进机会，离开后停止踩踏推进；每次冷却提供最短阶段间隔，但后续随机等待没有有限的必成功上限。
- 冰锥进入碎裂后一次抽取 4–32 秒延时，适合“失稳—预警—断裂”：在正常推进且未被其他机制提前移除时，预警后有明确的最短、最长等待窗口。无需在整个等待期反复抽样；可考虑一次 scheduled tick，持续粒子作为表现单独处理，不为此每 tick 扫描冰锥。
- 冰锥的整体启动时间仍由随机刻及小概率控制，没有“开始受热后必定在 32 秒内断裂”的保证；4–32 秒只描述进入碎裂状态后的计时。
- 若选择区间均匀抽样，平均延时为 18 秒；均匀分布只是建议，不是已确认参数。若按 20 TPS 的游戏时间解释，范围为 80–640 game ticks，服务器低 TPS 会拉长现实等待时间。游戏时间还是现实时间、区块卸载和重载时如何延续尚待明确。
- 建议冰锥采用本轮一次随机延时，薄冰保留其接触概率机制。二者服务不同交互，不需要为了统一而引入共同框架；具体性能未实测，不宣称已验证提升。

#### 待决关系与建议

1. **融化与碎裂竞争：** 大于 9°C 同时满足大于 5°C。末端如果已经碎裂，是否还能在倒计时结束前完成融化？代理倾向允许相变先完成并移除该段，避免裂纹反而阻止融化；代价是 4 秒不再是所有消失原因的最低预警时间。中段热裂仍可按倒计时造成下段坠落。此项需用户决定。
2. **融化采样位置：** 倾向仅检查末端自身材料温度是否大于 5°C；不是任意上段受热都远程使冷尖端融化。用户原话尚需明确这一点。
3. **预警期间降温：** 用户明确计时结束立即破碎，但未单独规定降温后的恢复。代理倾向既已失稳就不自动恢复，计时不因后来降温或新随机刻而重置；若希望回冻救回，则需另定暂停/修复过程。
4. **生长条件：** 群系限制确定，水源是否必要未定。可以选择群系代表供水条件而不实际寻水，或群系限制之外继续要求局部供水；二者都无需完整洞穴湿度模拟。生长温度、速率和最大长度仍待定。
5. **热预算：** 暂记 `Q_冰锥融化 ≈ Q_薄冰融化 / 3`；是否明确以完整薄冰为基准、精确比例及对粗细分段的处理待定，不把历史配方数值写死。预算为 1/3 不等于融化时间为 1/3，实际还取决于热交换。
6. **顶部支撑丢失：** 下段失去连接后坠落已确认；对最顶部外部支撑被移除的情况，建议统一为整根坠落，此具体情形仍单列待确认，避免把此前未确认建议默认为额外定案。

**用户新增确认：**

**用户询问方块温度与环境温度，本轮源码核对结果：**

- 环境温度代表周围的热环境；材料温度代表方块本体当前的热状态。热交换改变材料储存的焓（能量），所以环境变暖不代表冰立刻达到同样温度。
- `WorldTemperature.block` 名字容易产生歧义：其源码注释明确说明它是作物/机器使用的局部环境温度，不是材料本体温度；`WorldTemperature.air` 也是环境入口，两者自然背景公式不同。不能把调用 `block()` 当作读到了冰块的真实材料温度。
- 通用材料相变使用 `MaterialThermalLaw` 的焓与相变分支。`temperatureC` 根据能量和热容计算材料温度，相变潜热区间则固定返回相变温度；`Transition.complete` 根据能量是否抵达目标端点判定完成。`PhaseTransitionRuntime` 和 `MinecraftPhaseController` 都有该完成判定，因此不是简单读取气温超过阈值就替换方块。世界条件仍可能限制相变应用。
- `MaterialEnthalpyExchange` 推进活跃材料热交换；`DormantThermalCooling.project` 用简化环境热浴推进休眠记录，也沿用材料焓和潜热平台。材料状态不应被解释成每个普通方块都必须常驻独立计时器。
- 薄冰新增的热裂/回冻修复是另一路：`ThinIcePhaseData.air` 查询冰面上方不带随机采样噪声的合成空气环境，按环境温差推进独立工作预算；普通融化仍由材料热学 runtime 负责。不能用薄冰热裂的气温判断代表所有方块相变。

**对冰锥设计的影响（说明与建议，非用户改案）：**

若把 5°C 定义为材料相变温度，正常吸热路径会先升至 5°C，再在 5°C 平台吸收融化预算，完成后变空气；不是先让材料温度严格超过 5°C 才开始累计潜热。因此需要在后续将“>5°C”明确为外界加热条件，或者将表述收敛为“材料在 5°C 发生吸热相变”。本轮不擅自替用户改变阈值语义。

同理，带 5°C 融化平台的末端通常会在材料达到 9°C 之前融掉，不能保证自身还会触发“材料温度>9°C”的热裂预警。若只有末端具有可用的融化过程，中上段受热仍可能进入 9°C 热裂；如何让非末端材料能够升过 5°C，而不是被一个不可应用的融化分支卡在平台，需要后续实施设计验证。用户若希望高温环境让包括末端在内的冰锥都有机会先热裂，可另选环境温度作为热裂门槛，但这尚未确认。

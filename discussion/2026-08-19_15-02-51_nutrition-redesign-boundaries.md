# 玩家与居民营养系统下一步如何重设计？

- Time: `2026-08-19 15:02:51 +0800`
- Author: `Codex; OpenAI GPT-5; design discussion collaborator`
- Status: `open`
- Related: [玩家与居民营养系统现状](../docs/nutrition/nutrition-player-resident.md), `NutritionCapability`, `ResidentNutrition`, `NutritionRecipe`, `TownHousingMealService`

## 讨论目的

当前营养实现已经足够复杂，继续直接调公式或补配置，可能只会让两套模型更难解释。本帖希望先确定系统边界和数据语义，再决定哪些现有机制保留、合并或删除。

本帖不是实施计划。下文的“工作假设”只是讨论起点，不代表已经接受的设计。

## 已核实的事实基线

完整事实与公式见关联的现状文档。与本次设计最相关的结论是：

1. 玩家和居民拥有同名的脂肪、碳水、蛋白质、蔬菜四项状态，但玩家主要使用 `0..10000` 刻度，居民使用 `0..100` 刻度。
2. 两者共享 `frostedheart:diet_override` 静态食谱，却赋予食谱值不同含义：玩家按饥饿点即时增加，居民按每日个人配餐转换为储备。
3. 玩家查询会经过 `GatherFoodNutritionEvent`，居民直接读取静态食谱；Caupona 等动态食物可能在两侧得到不同结果。
4. 玩家后果仍是部分实现：四通道惩罚不对称，数值上限、界面刻度和命令刻度不一致，过量进食还会衰减已有营养。
5. 居民四通道储备已接入每日衰减、个人配餐、健康/精神恢复、成长、照护优先级和历史统计。
6. 居民侧同时保留个人四通道储备和住宅聚合 `nutritionQuality`；后者仍显示在住宅界面，但不再决定个人恢复。
7. 居民源码默认平衡在当前狩猎肉食基线下不可持续；成功的模拟实验参数尚未成为玩法默认。
8. 代码支持五级居民食物，附带整合包目前只定义了等级 `0`。

## 当前问题的性质

这不只是“数值没调好”，而是四种不同问题叠在了一起：

- **语义问题**：一个食谱数字究竟代表单件绝对摄入、每饥饿点密度，还是长期维持目标？
- **架构问题**：玩家、居民和动态食物是否应该经过同一营养解析入口？
- **玩法问题**：营养应该主要奖励均衡、惩罚缺乏，还是允许囤积并提供持续正收益？
- **表现问题**：玩家和城镇界面应该用什么可理解的指标说明“今天吃得怎么样”和“长期储备如何”？

在这些问题没有明确答案之前，把 `7000` 改成 `200` 或增加更多食物 Tag 只能缓解个别模拟结果，不能降低系统复杂度。

## 工作假设：统一食物语义，不强行统一时间尺度

一个可能的简化方向是：

1. 玩家和居民共享同一个“食物营养画像”与查询 API。
2. 食物画像明确区分热量/食物量与四类营养，不再让一个数字同时承担两种含义。
3. 玩家仍按实际进食和生存消耗更新，居民仍按城镇日结算；两者不必使用同一个 tick 模型。
4. 两侧状态都采用容易解释的标准化刻度，例如 `0..100`，但允许不同的衰减速度和后果公式。
5. 动态汤品、静态物品和数据包覆盖最终都解析为同一种食物画像。

这个方向的目标不是让玩家等于居民，而是让“一块牛排包含什么”只有一个答案，让“这个答案如何影响不同主体”分别由玩家和居民模型负责。

## 需要比较的主要方案

### 方案 A：完全统一状态模型

玩家和居民使用同一范围、同一衰减、同一餐食换算和同一阈值，只改变结算频率。

优点：概念最少，数据和测试最容易共享。

风险：玩家的实时生存节奏与居民的每日批量结算差异很大，强行共用公式可能产生大量特殊参数。

### 方案 B：共享食物画像，保留两套消费者

统一食物数据和解析入口；玩家与居民保留各自状态更新、节奏和玩法后果。

优点：消除食物数据分叉，同时保留两类玩法的差异；迁移范围相对可控。

风险：如果没有严格定义共同输入，两套消费者仍可能逐渐产生新的隐含语义。

### 方案 C：继续完全分离

玩家和居民各自拥有独立食物数据、公式与平衡，只在内容制作流程上提供转换工具。

优点：设计自由度最高，修改一侧不影响另一侧。

风险：内容维护量翻倍，动态食物、数据包兼容和玩家认知仍会分叉。

当前工作假设倾向 **方案 B**，但需要先确认产品目标是否真的要求玩家与居民感知同一种“营养事实”。

## 食物数据语义的候选

需要为 `diet_override` 或其替代格式选择唯一、可解释的含义：

### 候选 1：单件绝对摄入

每件食物直接记录四项绝对摄入；原版饥饿值和饱和度只描述能量与耐饿程度。

这最适合容器、汤品和大小不同的食物，也最容易回答“吃一份获得多少”。缺点是需要重新标定 110 项数据，物品份量变化时也要同步调整。

### 候选 2：每食物单位营养密度

食谱记录每一点食物资源单位的四项密度，实际摄入再乘以物品提供的食物单位。

这能自然适配玩家饥饿值和居民食物单位，但会把原版食物属性变成营养总量的一部分；修改饱和度可能意外改变居民营养。

### 候选 3：四项构成比例加独立总量

食谱分别记录总营养量与四项比例，动态食物先合成总量和比例，再交给消费者。

这最接近当前 Excel 的 `Base + 四项权重`，也便于界面展示；代价是数据格式比单纯四个数字更明确但稍复杂。

无论选择哪种，都应停止使用无法从字段名判断的隐式归一化，并让数据生成、Tooltip、居民配餐和模拟器读取同一含义。

## 玩家营养后果需要单独选择

玩家侧至少有三种不同的玩法方向：

1. **缺乏为主**：健康区间内没有奖励，长期缺某一类才逐步出现可预测的问题；过量最多造成轻微或特定风险。
2. **最佳区间**：过低和过高都会受罚，鼓励维持区间；需要可靠界面和可控食物来源，否则容易变成微操负担。
3. **储备成长**：高储备提供正收益，缺乏提供负收益；本质上会把营养变成第二套可刷属性资源，需要明确上限和衰减目的。

当前实现混合了第 2、3 种：中间区间中性，高值增加最大生命值，部分高值又触发贫血计分。这种混合是否是设计目标，需要先明确。

## 居民侧建议优先讨论的删减

### 1. 住宅聚合 `nutritionQuality`

它与个人储备同时展示，却不再驱动个人恢复。候选处理方式：

- 删除该字段和界面；
- 改成“昨日餐食覆盖率”，明确只描述当天食物；
- 改成四通道餐食摘要，不再压成单一标量；
- 保留但重新接回恢复公式，这会再次与个人储备重叠。

初始倾向是删除，或改成纯观测的四通道餐食摘要。

### 2. 五级居民食物

如果食物等级表示玩家制定的供应优先级，应提供明确的数据定义和管理界面；如果它只是历史遗留的品质概念，个人营养效用已经可以完成选餐，可以考虑简化为单一“居民可食用”Tag。

### 3. 每餐八次贪心选择

八块选择能针对个人缺口配餐，但也使结果难以解释。需要比较：

- 保留分块选择；
- 按整餐目标求一次组合；
- 城镇先形成公共菜单，再按照护需求分配；
- 只按最缺通道选择一种主食，接受较粗的模拟。

这里应以玩家能否理解和干预为标准，而不只是优化器能否得到更高数值。

## 迁移与兼容约束

后续方案至少需要说明：

- 旧玩家 `NutritionCapability` 的 `0..100000` 数据如何迁移；
- 旧居民 `ResidentNutrition` 是否保持可读；
- 现有 110 个 `diet_override` 如何转换或提供兼容别名；
- Caupona 汤等动态食物如何在无玩家上下文时为居民解析；
- 数据包作者看到的字段、单位、范围和默认值；
- 玩家 Tooltip、健康界面、居民详情和城镇统计如何使用同一术语；
- 模拟器如何继续复用玩法公式，而不是维护另一份近似模型。

## 希望本次讨论先达成的决定

建议先回答以下问题，暂时不讨论具体数值：

1. 选择完全统一、共享食物画像或完全分离中的哪一种边界？
2. 食物营养数据采用单件绝对量、每食物单位密度，还是“总量 + 构成比例”？
3. 玩家营养后果采用缺乏为主、最佳区间，还是储备成长？
4. 居民是否继续保留个人四通道储备？
5. 住宅聚合 `nutritionQuality` 删除、重定义还是重新参与结算？
6. 五级居民食物是否保留？
7. 玩家与居民是否必须对动态食物得到完全一致的营养画像？

这些边界确定后，再为数据迁移、公式、平衡目标、UI 和验证场景分别建立实施计划。

## 2026-08-19 19:52:32 +0800 - 实施结果

- Author: `Codex; OpenAI implementation collaborator`
- Status: `resolved`

本轮采用方案 B：玩家与居民共享唯一的食物营养画像和 `FoodNutritionResolver`，但保留各自的实时/每日消费者模型。现有 `diet_override` 原始数据保持不变，四通道公开语义统一为 `clamp(raw / 400, 0, 100)`，动态 Caupona 食物也按实际 `ItemStack` 走同一入口。

已接受并实现的其他边界如下：

- 玩家与居民状态均以 `0..100` 表达；玩家只按实际恢复的 hunger 获得营养，并按 hunger 损失固定扣除。
- 居民保留个人四通道储备，删除住宅 `nutritionQuality` 决策与显示，不增加昨日覆盖率。
- 保留五级食物绝对优先级，改为全镇八片段公共菜单；居民共享食物构成，只按已确定额度缩放总量。
- 当前与长期营养分别决定恢复、成长效率、力量/智力营养上限；训练或实际工作才产生成人成长，营养不会永久降低智力。
- 生产、岗位评分和模拟预测使用有效智力，界面通过持久结算快照解释潜力、上限、成长和主要限制。

实现与公式见[已完成计划](../plans/2026-08-19_18-23-50_nutrition-resident-attribute-redesign.md)和[当前营养文档](../docs/nutrition/nutrition-player-resident.md)。新默认每日需求 `20` 下，`50 residents x 120 days x 100 trials` 的旧狩猎闭环不再自给：纯狩猎食物方案 P50 自给率约 `0.615`、生存率 `0`；每日补充 `6.25` 个烤马铃薯后 P50 自给率约 `0.651`、生存率 `0.06`。这被记录为后续粮食生产平衡输入，不作为本次模型重构失败条件。

## 2026-08-20 17:51:21 +0800 - 居民属性模型再次简化

- Author: `Codex; OpenAI implementation collaborator`
- Status: `resolved`

后续讨论确认长期满足度 EMA、UUID 个人潜力、营养属性上限和有效智力没有提供足够独立的玩家语义，却显著增加了状态、持久化和每日顺序的复杂度，因此本轮全部删除。旧 `nutritionDevelopment` 存档字段被忽略，已有营养、力量和智力原样保留。

力量与智力现在只读取餐后当前支持度，统一按“正向成长 - 营养不足衰减 - 老年基础衰退”每日结算。年龄提供 `1.0/0.7/0.3/0.1` 的基础活动，实际工作补足剩余活动；营养低于力量/智力维护线 `0.40/0.30` 后按 `D^1.5` 开启永久衰减。老人仍能通过良好营养和劳动/学习抵消固定衰退，不再有力量下限。力量权重改为蛋白/脂质/蔬果/碳水 `0.75/0.08/0.03/0.14`。

生产、岗位评分和模拟预测重新直接使用存储智力。游戏和 Stage 3/4 共同调用 `ResidentAttributeModel.settleDailyAttribute`；持久快照只解释昨日活动、恢复、成长、营养衰减、年龄衰退和净变化，不参与以后计算。实现方案见[居民营养与属性成长模型简化重构](../plans/2026-08-20_17-31-55_resident-nutrition-attribute-simplification.md)，当前公式见[营养 living doc](../docs/nutrition/nutrition-player-resident.md)。

## 2026-08-20 21:10:39 +0800 - 公共菜单改为住宅优先菜单

- Author: `wyc; system designer`, `Codex; OpenAI implementation collaborator`
- Status: `resolved`

全镇单一构成与住宅法律的原始目的冲突：住宅法律先把需要照护的人安排进高优先级住宅，高优先级住宅也应当先取得更好的实际食物。因此保留全镇集中口粮额度计算，但把菜单改为按 `TownHousingPlan` 顺序逐栋生成。

- 第一轮住宅保障和第二轮全镇等额分享继续决定每名居民吃多少；
- 食物等级与剩余库存决定每栋住宅吃什么，高优先级住宅先选并占用库存；
- 同一住宅的居民共享菜品构成，仅按各自额度缩放总量；不同住宅可以获得不同等级和构成；
- 每栋住宅的营养评分只聚合本住宅居民的四通道缺口，不恢复逐居民贪心，也不恢复 `nutritionQuality`；
- `HouseBuilding.DailyReport` 保存最近结算日实际扣除的物品 ID/NBT 和小数数量，住宅“今日餐食”页直接显示这些 `ItemStack`；
- 菜单快照以资源执行器实际 `modifiedAmount` 为准，未结算与已结算但未出餐是两个不同状态。

实现和验证见[住宅优先供餐与今日餐食展示计划](../plans/2026-08-20_20-56-26_house-priority-meals-and-menu-ui.md)及[当前营养文档](../docs/nutrition/nutrition-player-resident.md)。

我想在Minecraft游戏（我在开发的冬季救援自研模组）中设计一套研究系统，我的设计哲学在于每一项研究首先要有一个“想法”来开启——这个想法可能是偶然发现的现象，其他研究产生的未解决问题，或是和游戏中的难民NPC交流讨论产生的，或是来自NPC的知识传播——这比较符合现实。开启研究的不一定是一个具体的问题，而只需一个想法。这个过程要体现出研究问题那种非线性的涌现的感觉。

具体开启一项研究之后，分为理论和实验相互交迭的步骤，理论需要提出思考，计算，验证，最终提出假设，并提出实验计划和所需材料；实验目的是通过实验材料和实验本身验证理论假设，需要真正在游戏中搭建具体的看见摸得着的东西，控制变量，发现现象。最终理论和实验吻合，假设被证明，产生“发现”。整个过程要充分利用开放和自由性和玩家的能动性，减少靠数值来衡量科研进度的设定，以及我们实现的一套城镇系统——NPC有智力和受教育程度——研究不是单人工程。

具体的我设计的步骤：
收集想法：在世界中探索，搞机器，合成，和难民居民聊天，随时可以触发，记录到研究笔记里。想法收集足够了，开启一个之前隐藏的研究。注意一开始这个研究不应该揭露研究最终结果，而是仅是一个想法。
理论研究：开启研究后，进入理论步骤。通过若干个子步骤的计算（机械计算器，研究所人力计算）和思考（小游戏，研究所高教育等级居民工作）最终提出假设，总结出实验需求。  
实验研究：必须跟随在理论研究之后，通过在世界中建设实验室，投入研究所人力资源，并需要持续材料供给、能量供给、等，以及时间成本；假设可能被验证，或者否认。
这具有概率性。若否认，则需要进入下一轮理论研究。若成功，则研究完成。  如此迭代，直到研究成功。迭代有上限次数，若超过该次数，则意味着研究失败，该想法不成立。

可能还需要引入一个工程原型研究，但我不了解。

你完全可以提出你的想法。思考设计一下。

你的方向很强，而且它真正有机会把“研究”做成一种**认识世界的玩法**，而不是另一种换皮制造系统。

我认为整套系统最关键的一条原则是：

> **被反复迭代的应该是假设、实验方法和问题框架，而不是一个抽象的“研究进度条”。**

实验也不应该通过一次隐藏成功率判定“自然规律是否成立”。世界中的真实规律应当相对稳定；概率主要影响的是测量误差、设备故障、实验污染、NPC失误和结果是否足够清晰。

整套循环可以概括为：

```text
现象、事故、口述、机器异常
        ↓
      研究笔记
        ↓
讨论、联想、知识交叉、发现矛盾
        ↓
       想法
        ↓
提出多个可能解释
        ↓
       假设
        ↓
预测结果、设计实验、确定控制变量
        ↓
在世界中搭建并运行实验
        ↓
支持 / 反驳 / 无法判断 / 意外现象
        ↓
修正假设、改进实验或重新定义问题
        ↺
       发现
        ↓
工程需求 → 原型 → 现场试验 → 标准化技术
```

其中，实验产生的意外现象、原型的故障和现场试验的失败，都可以重新回到最上方，成为新的想法来源。

# 一、把“想法”“假设”“发现”严格区分开

这几个对象最好不要混在一起。

| 对象   | 它代表什么            | 玩家此时应该知道什么       |
| ---- | ---------------- | ---------------- |
| 观察记录 | 某件确实发生过的事情       | 时间、地点、环境、来源、具体表现 |
| 想法   | 某些记录之间可能存在联系     | 一个模糊问题，但不知道最终答案  |
| 研究问题 | 玩家决定从哪个角度理解想法    | 要解释什么现象，暂时忽略什么   |
| 假设   | 对现象的一个可检验解释      | 如果它成立，应该看到什么结果   |
| 证据   | 实验或观察产生的新记录      | 支持、反驳或无法区分哪些假设   |
| 发现   | 在一定适用条件下得到确认的规律  | 规律本身、适用范围和可能用途   |
| 工程技术 | 把规律变成可靠、可复制的解决方案 | 制造方法、维护要求、工作范围   |

例如，玩家看见锅炉在暴风雪中不断熄火。

此时获得的不是“防冻进气技术研究”，而是：

> **想法：风雪似乎正在让炉火窒息。**

它可能由进气口结冰、燃料受潮、烟囱倒灌、气压变化或操作问题造成。玩家此时不应该看到最终解锁物，更不应该看到“研究完成后解锁加热进气口”。

# 二、想法不应通过“收集满五个点数”出现

你提到“想法收集足够了，开启隐藏研究”。这里最好不要表现为纯数量门槛，否则最后仍然会变成：

> 再捡两个研究点，就能解锁下一项科技。

更合适的是让想法由某种**关系结构**触发，而不是由数量触发。

## 1. 矛盾触发

两条记录无法同时用已有知识解释：

* 相同燃料，两个锅炉的热量输出不同；
* 白天正常，湿冷夜晚异常；
* 增加燃料后火势反而更弱。

研究笔记可以提示：

> “这些记录似乎彼此矛盾。”

玩家将它们放在讨论板上，便可能产生想法。

## 2. 重复现象触发

相似现象在不同环境中反复出现：

* 水泵、门轴和发电机都在低温下变得迟钝；
* 三台不同机器都出现润滑部位阻力增加。

这些记录可能共同产生：

> “寒冷似乎改变了某种机器内部共有的东西。”

## 3. 知识迁移触发

一个领域的发现被应用到另一个领域：

* 玩家已经知道空气夹层可以减缓房屋散热；
* 一名居民提到伤员被湿衣服包裹时体温下降更快；
* 由此产生关于湿衣服、空气层和人体保温的想法。

## 4. NPC知识触发

NPC不应只是提供“研究点”，而应带来不同类型的信息：

* 正规教育产生理论语言；
* 工作经历产生经验规律；
* 个人记忆产生案例；
* 故乡技术产生另一种解决路线；
* 怀疑或偏见也可能产生错误线索。

一名受教育程度不高的老锅炉工，可能比一名高智力学者更早注意到火焰颜色、烟道声音或者积霜位置。

## 5. 意外现象触发

实验的目标是研究A，却出现了无法解释的B。

这类记录应直接标记为“异常”，并且是最有价值的想法来源之一。它能让研究网络自然产生分支，而不是由预先画好的科技树向下展开。

# 三、让玩家主动“合成想法”，而不是等待随机弹窗

可以在研究所中设置一种实体化的设施，例如：

* 研究墙；
* 讨论桌；
* 档案板；
* 黑板；
* 地图与记录柜。

玩家可以把观察记录、NPC证词、计算结果和旧实验日志钉在同一块板上。

系统识别它们之间的关系后，不是直接给出答案，而是生成若干问题：

> 为什么这两台机器只有其中一台结冰？
> 环境温度和空气湿度，哪一个更重要？
> 进气量下降是原因，还是火焰减弱后的结果？
> 艾琳似乎对烟道结构有相关经验。

这样既保留了涌现感，也不会让玩家因为不知道隐藏配方而盲目试错。

每项研究可以拥有多条开启路线。例如同一个“低温润滑”研究可以由以下任意路线出现：

* 观察到发电机启动困难，并发现油脂凝固；
* 与机械师交谈，同时持有一次车辆故障记录；
* 在材料实验中发现液体流速随温度变化；
* 某个工程原型在寒夜现场试验中卡死。

因此它在数据层面仍然是被设计过的研究内容，但在体验上不是固定线性的科技树。

---

# 四、理论研究不应该是“投入聪明居民，等待进度完成”

理论阶段必须要求玩家形成一个**可以被实验推翻的说法**。

一个完整假设至少应包含：

```text
在保持哪些条件不变时，
改变什么因素，
应该导致什么可观察结果；
出现什么结果时，该假设应被否定。
```

例如：

> 如果锅炉熄火是进气口结冰造成的，那么在燃料、炉体、烟道和负载相同时，防止进气口结冰的锅炉应保持更稳定的空气流量和热量输出。

这比“研究进度达到100%，提出假设”更具体。

## 理论页面可以由六个部分组成

| 部分   | 玩家要完成的内容            |
| ---- | ------------------- |
| 已知现象 | 选择哪些记录确实需要解释        |
| 工作假设 | 选择或组合可能的因果解释        |
| 必要假定 | 哪些条件被暂时视为相同或无关      |
| 预测   | 假设成立时会看到什么          |
| 反证条件 | 看到什么便说明假设有问题        |
| 实验方案 | 操纵变量、测量对象、对照条件和运行时间 |

理论不会显示“63%完成”，而是显示具体缺口：

* 尚未提出可以区分两个假设的预测；
* 缺少环境温度记录；
* 燃料湿度可能构成混杂变量；
* 计算结果与假设不一致；
* 当前仪器无法测量需要观察的量。

# 五、计算器的作用应是解决具体问题，而不是生产研究点

机械计算器、研究所人力计算和高教育居民都可以参与，但它们应该提供不同能力。

例如：

* 根据管道直径计算理论空气流量；
* 根据炉体表面积估算散热；
* 比较两组测量是否差异明显；
* 计算实验需要的材料数量和安全范围；
* 检查假设是否违背已有发现；
* 推导一个可观察的预测。

高智力和高教育不应该简单地提高“每天研究点产量”。

更好的影响方式是：

* **智力**：能处理更复杂的因果关系，发现跨领域联系；
* **教育程度**：能使用正式计算、实验方法和专业仪器；
* **领域经验**：能提出特定领域的假设和操作方法；
* **实践技能**：能可靠地搭建、校准和维护装置；
* **怀疑精神**：更容易发现实验漏洞；
* **沟通能力**：更容易让知识在居民之间传播；
* **好奇心**：更容易记录异常现象。

建议至少增加一个“领域知识或经历”维度，否则所有高智力、高教育NPC最终会变得彼此可替代。

# 六、实验不应是“投入材料后进行一次成功率判定”

这是我最建议修改的部分。

自然规律本身不应该因为一次随机数而改变。假设是真是假，应由世界的隐藏因果关系决定。概率应当影响的是玩家能否获得**清晰而可靠的证据**。

可以使用这样的内部逻辑：

```text
实验信息量
= 假设区分力
× 控制变量质量
× 仪器可靠性
× 执行完整度
× 重复程度
```

这些数值可以存在于后台，但不必直接显示。玩家看到的应是具体状态：

* 对照组缺失；
* 两组燃料并非同一批次；
* 温度在实验中发生明显波动；
* 仪器未校准；
* NPC中途离岗；
* 能量供应中断；
* 只运行了一次，无法判断是否为偶发现象；
* 两个假设预测了相同结果，因此此实验无法区分它们。

实验结果分成四类会比较合适。

## 1. 支持假设

观察结果符合预测，并且足以排除主要替代解释。

这并不意味着“永远绝对正确”，而是形成一个带适用条件的发现：

> 在高湿度且环境温度低于某范围时，进气格栅积冰会显著降低锅炉空气流量。

## 2. 反驳假设

实验条件有效，但结果与预测相反。

这不是研究失败，而是排除了一条解释路线。

## 3. 无法判断

可能是实验设计不具区分力，也可能是过程中出现污染、停电、温度变化或仪器损坏。

此时应回到实验方案，而不是完全重做理论。

## 4. 出现异常

主要问题可能得到回答，但又产生新的现象：

* 防冰装置解决了进气问题，却导致烟道冷凝；
* 两组锅炉流量相同，但其中一组仍然熄火；
* 低温不是关键，湿度才是关键；
* 装置在实验室正常，现场暴风雪中失效。

异常应该自动成为新的笔记，并可能产生旁支研究。

# 七、实验装置应使用“功能要求”，不要使用唯一多方块结构

为了利用Minecraft的开放性，实验计划不应给玩家一张必须逐格照抄的建筑蓝图。

系统可以检查装置是否具有必要功能：

```text
变量操纵设备
→ 实验对象
→ 测量设备
→ 数据记录设备

同时还需要：
对照对象
稳定供能
材料供给
环境控制
操作人员
安全设施
```

例如实验计划要求：

> 两个相同燃烧室使用相同批次燃料，在相同负载和相同烟道条件下运行。其中一个进气口受到防冰处理。连续记录空气流量、炉温和燃料消耗。

玩家可以：

* 把装置建在露天；
* 建造低温实验室；
* 利用自然暴风雪；
* 使用不同型号的传感器；
* 用机械记录器或安排NPC人工抄录；
* 建造两个完整锅炉，也可以做缩小的实验炉。

不同方案的成本、稳定性和证据质量不同，但都可以成立。

实验过程中应该有可见现象：

* 管道逐渐积霜；
* 指针开始下降；
* 火焰颜色改变；
* 蒸汽冷凝；
* 机器振动；
* 实验材料开裂；
* NPC发现气味或声音异常。

玩家应当能够站在实验室里，根据装置表现提前猜到结果，而不是等待界面弹出“实验成功”。

# 八、可以存在三类不同实验

你目前规定“实验必须跟在理论之后”，对验证性实验是正确的，但不宜禁止所有前置试验。

## 探索性试验

没有成熟假设，只是主动制造条件、寻找现象。

例如把不同材料放到室外严寒中，观察哪些会破裂。它通常产生想法，但不直接完成研究。

## 验证性实验

必须有明确假设、预测、控制变量和反证条件。

这是确认发现的主要途径。

## 工程测试

它测试的不是自然规律是否成立，而是装置能否满足要求：

* 是否足够可靠；
* 是否容易维护；
* 是否消耗过多能源；
* 是否能由普通居民操作；
* 是否能在暴风雪中连续工作。

把三者分开后，玩家就可以先摆弄机器、偶然发现现象，再进入正式研究，同时又不会破坏你希望存在的“理论—实验”结构。

# 九、不要让迭代上限直接判定“想法不成立”

“连续失败四次，因此该想法永远错误”会产生两个问题。

第一，玩家可能觉得只是连续暗骰失败。
第二，实验失败并不能证明最初的想法毫无价值。

应该区分三种失败。

| 失败类型   | 实际含义      | 下一步          |
| ------ | --------- | ------------ |
| 假设被反驳  | 一个解释错误    | 排除假设，修正理论    |
| 实验无效   | 方法或执行出了问题 | 改进装置、仪器或控制条件 |
| 问题框架崩溃 | 玩家可能问错了问题 | 重新定义问题，产生新想法 |

例如玩家一直研究“低温为什么让锅炉燃料燃烧不充分”，最终发现低温并不是直接原因，真正原因是湿雪堵塞进气口。

此时不是“想法失败”，而是：

> 原始问题把温度当成了原因，但温度只是与积雪同时出现的条件。

这本身就是一个发现。

为了防止玩家无限蛮力尝试，可以设置“研究停滞”，而不是永久失败：

* 团队认为当前证据不足以继续；
* 必须获得新类型的观察；
* 必须换用更好的仪器；
* 必须邀请具有相关领域知识的NPC；
* 必须等待不同环境条件；
* 暂时归档，之后可以重新开启。

真正得到大量高质量反证后，也可以产生一种“否定性发现”：

> 在已测试的温度范围内，单纯加热燃料并不能改善燃烧稳定性。

否定性发现仍然有价值，因为它能阻止城镇浪费资源走错误的工程路线。

# 十、让玩家决定何时接受结论

冬季救援背景中，科研往往伴随紧迫需求。你可以让玩家在证据尚不完全时提前采取行动。

例如一次实验初步支持防冰进气口，但尚未重复验证。玩家有两个选择：

* 继续重复实验，等待更可靠的结论；
* 宣布“暂定结论”，立即投入原型制造。

后者可以更快解决供暖危机，但原型可能存在尚未发现的限制。NPC中的怀疑者可能提出反对，城镇管理者可能要求立即使用。

这样，“科研概率”就从被动暗骰变成了玩家主动承担的不确定性。

结论状态可以使用文字而不是数值：

* 初步迹象；
* 暂定结论；
* 已重复验证；
* 适用范围已确认；
* 存在未解释异常。

---

# 十一、研究必须是团队活动，而不是把NPC变成人形计时器

研究所可以围绕四种活动运转。

## 讨论

NPC提出解释、关联旧知识、分享个人经历。不同背景的人会产生不同假设。

## 计算与整理

居民处理测量记录、检查理论一致性、绘制图表、计算设备规格。

## 实验值班

居民加料、保持温度、记录数据、校准设备、发现故障。

## 评审与教学

实验完成后，团队讨论结果；已经掌握知识的居民将知识教给其他居民。

这里可以引入“个人知识”和“城镇公共知识”的区别。

一名新来的难民工程师可能掌握某种技术，但在他把知识写入档案、完成教学或参与标准化之前，这仍然只是他的个人知识。若他离开、死亡或长期无法工作，城镇就会失去部分能力。

实验日志、研究论文、工程图纸和操作手册，可以把个人经验转化为制度化知识。

这会使研究所、学校、档案室和NPC教育系统自然连接起来。

# 十二、工程原型阶段非常值得加入

科学研究和工程开发解决的是两个不同问题：

> 科学研究问：“它为什么会这样？”
> 工程开发问：“怎样利用这个规律，在现实限制下稳定工作？”

完成“发现”后，最好不要立刻解锁最终配方，而是先解锁一种**设计原则**。

例如发现：

> 进气口积冰会降低燃烧稳定性。

这项发现可以提供：

* 防冰；
* 排水；
* 进气加热；
* 增大有效截面；
* 过滤湿雪；
* 监测空气流量。

但它不直接决定最终设备应该长什么样。

工程流程可以是：

```text
提出需求
→ 选择设计方案
→ 制造一次性原型
→ 实验室测试
→ 真实环境现场试验
→ 记录故障
→ 修改设计
→ 标准化
```

## 1. 提出需求

城镇不是抽象地要求“解锁高级锅炉”，而是提出具体指标：

* 能改装现有锅炉；
* 在暴风雪中持续运行；
* 电力消耗不能太高；
* 普通居民可以维护；
* 不能使用稀缺合金。

## 2. 设计取舍

玩家选择不同方案：

* 电加热进气口：可靠，但消耗电力；
* 机械刮冰：低耗能，但需要维护；
* 大型遮雪罩：便宜，但占空间；
* 热废气回流：节能，但可能产生冷凝和烟气风险。

没有唯一正确答案，而是不同的城镇和资源条件适合不同设计。

## 3. 一次性原型

原型可以是玩家自由搭建的模块化机器，不要求已经拥有标准配方。

它可能昂贵、笨重、不稳定，只能由高技能NPC操作。

## 4. 现场试验

实验室通过不代表工程成功。原型必须在真实庇护所、矿场、运输队或暴风雪中运行。

现场试验可能发现：

* 供电能力不足；
* 普通居民不会维护；
* 雪水进入电气结构；
* 某种材料在反复冷热循环中开裂；
* 装置有效，但噪音导致居民无法休息。

这些故障报告又会产生新的想法和研究。

## 5. 标准化

标准化完成后才真正解锁：

* 稳定配方；
* 批量制造；
* 操作手册；
* NPC自动维护；
* 更低故障率；
* 普通工人培训。

于是“发现”和“科技解锁”之间就有了真正的工程过程。

# 十三、一个完整实例：风雪中的炉火

## 观察阶段

玩家获得以下记录：

* 暴风雪夜，东侧锅炉热量输出下降；
* 炉火在打开炉门后短暂恢复；
* 进气格栅上有明显积冰；
* 相同燃料在室内小炉中燃烧正常；
* 锅炉工NPC说：“以前湿雪天也发生过，但我一直以为是煤受潮。”

系统不显示任何解锁奖励，只产生想法：

> **风雪中的炉火为什么会窒息？**

## 理论阶段

讨论后出现三个工作假设：

* 燃料温度太低，无法充分燃烧；
* 进气格栅积冰，减少空气流量；
* 烟囱在强风下发生倒灌。

机械师倾向于进气问题，锅炉工怀疑燃料，受教育较高的居民提出需要区分空气流量和烟道压力。

玩家选择研究“进气结冰假设”。

团队提出预测：

> 若积冰是原因，则防止进气格栅结冰后，空气流量和热量输出应保持稳定。

## 实验计划

玩家需要准备：

* 两个相同小型燃烧室；
* 同批燃料；
* 相同烟道长度；
* 相同热负载；
* 空气流量计；
* 炉温计；
* 一个经过防冰处理的进气口；
* 一个未经处理的对照进气口；
* 低温环境；
* 连续记录人员或机械记录器。

## 世界实验

玩家可以在室外暴风雪中运行，也可以建立低温实验室。

实验进行时，未经处理的格栅逐渐结冰，流量计指针下降，火焰开始变暗；防冰组保持稳定。

但是如果实验中一组燃料受潮，日志会记录：

> “两组燃料状态不同，本次结果无法单独判断进气作用。”

这次实验是无效实验，而不是随机研究失败。

## 发现

经过有效重复后得到：

> 在湿冷环境下，进气结构积冰会降低燃烧空气流量，并造成锅炉输出不稳定。

同时出现新问题：

> 防冰加热装置是否会消耗过多电力？
> 烟道中的水汽会不会在其他位置重新凝结？

## 工程阶段

玩家设计三种原型：

* 电热格栅；
* 机械除冰格栅；
* 带排水结构的遮雪进气罩。

经过现场试验，其中一种成为城镇的标准冬季锅炉进气组件。另一种原型虽然失败，却产生了“烟道冷凝”的新研究想法。

# 十四、研究界面应展示“研究状态”，而不是进度百分比

一本研究笔记可以包含六个页面：

1. **记录板**：现象、NPC证词、事故日志、旧实验结果；
2. **问题页**：当前想法、已知与未知；
3. **理论页**：假设、假定、预测、反证条件；
4. **实验计划**：变量、对照、仪器、材料、人员和安全要求；
5. **实验日志**：运行曲线、环境变化、设备故障、NPC备注；
6. **结论页**：支持与反对证据、适用条件、未解决异常。

它应该不断告诉玩家：

* “缺少什么”；
* “什么互相矛盾”；
* “哪名居民可能有帮助”；
* “这个实验能够排除什么”；
* “当前结论为什么还不可靠”。

而不是只告诉玩家：

> 理论研究：72%。

# 十五、底层最好是一张“证据与知识图谱”

系统存档的核心不应是：

```text
research_progress = 72
```

而应该是：

```text
观察A 支持 假设1
观察B 反驳 假设1
发现C 可用于 测量技术D
实验E 产生 异常F
NPC甲 掌握 知识C
城镇档案 已记录 知识C
原型G 依赖 发现C和材料知识H
```

研究项目只是这张图谱上的一个临时工作区域。

这样自然会形成：

* 研究之间的交叉；
* 旧发现被新问题重新利用；
* 实验异常产生旁支；
* 工程故障返回基础研究；
* NPC知识传播改变可用路线；
* 同一个问题存在多种开启方式；
* 多项发现共同支持一种工程技术。

# 十六、适合第一版实现的范围

第一版不必尝试完全程序生成科学内容。更可靠的方式是采用“手工研究谜题 + 通用研究框架”的混合设计。

每个研究只需手工定义：

* 多条想法触发路线；
* 一个不泄露答案的问题描述；
* 两到四个合理假设；
* 每个假设的预测；
* 一到两种实验功能需求；
* 支持、反驳、无效和异常结果；
* 最终发现及适用条件；
* 会产生的新问题；
* 可进入的工程应用。

通用系统负责：

* 笔记和关系；
* NPC讨论；
* 理论画布；
* 实验装置检测；
* 控制变量判断；
* 运行日志；
* 证据质量；
* 原型和现场试验；
* 知识传播。

这种设计既可控，又能让玩家感到研究是自己从世界中推导出来的。

最终的核心体验不应是：

> 我投入了三百研究点，所以获得了一台新机器。

而应当是：

> 我们发现了一个反复出现却解释不了的现象；不同居民提出了不同解释；我搭建了一个能够区分这些解释的装置；第一次实验因为供能波动而作废；第二次结果推翻了原假设；第三次出现的新现象让我们重新定义了问题；最后我们不只知道该怎样解决故障，还理解了它为什么发生，并把这种理解变成了一套全城都能制造、操作和维护的技术。

我觉得你的想法非常牛逼。底层最好是一张“证据与知识图谱”这个我尤其是觉得非常重要。我认为我们光靠人力去设计每一个研究的所有途径是不可能的。我们应该做的是一种底层数据结构驱动的工作，这也非常具有扩展性。但我对这个可能的结构是如何自然形成的东西，以及它本身更确切的数学/算法上的定义还是不确定。包括研究的流程本身，我认为你的思路是对的，它只会是底层知识图谱的一个临时工作区域探索，但是玩家在研究过程中，我们要生成出一种线性的流程呈现给玩家。毕竟我们最终要设计成代码，还要反馈给玩家让玩家理解。


你现在抓到的是这套系统真正的“骨架”：

> **研究项目不应该是底层数据。研究项目应该是从当前知识状态中，临时编译出来的一段探索流程。**

更准确地说，底层不只是普通“知识图谱”，而应该是：

> **类型化、带上下文、带来源、允许相互矛盾的认识论超图**
> ＋
> **隐藏的世界因果模型**
> ＋
> **一条按时间排列的研究事件日志**
> ＋
> **把图编译成玩家当前研究步骤的工作流编译器**

整体关系可以表示为：

```text
隐藏世界因果模型 M
        │
        │ 产生真实现象
        ▼
玩家 / NPC / 仪器观察
        │
        ▼
研究事件日志 L：先发生了什么，后发生了什么
        │
        │ Fold / Reduce
        ▼
城镇认识图 K：目前知道什么，为什么相信，存在什么争议
        │
        │ 发现知识缺口、矛盾、异常
        ▼
想法与研究问题 Q
        │
        │ 局部投影
        ▼
研究工作区 R
        │
        │ 工作流编译
        ▼
当前呈现给玩家的线性步骤
        │
        │ 玩家行动产生新事件
        └──────────────────↺
```

这里最重要的是：

* **图负责语义关系**
* **事件日志负责线性历史**
* **工作流编译器负责下一步引导**
* **隐藏世界模型负责实验真实结果**

这样，非线性知识与线性游戏体验并不矛盾。

# 一、不要让“一项研究”成为固定的数据对象

传统科技树可能这样定义：

```json
{
  "research": "heated_air_intake",
  "prerequisites": ["basic_thermodynamics"],
  "theory_points": 300,
  "experiment_items": ["iron_plate", "heater"],
  "result": "heated_air_intake_recipe"
}
```

这种结构的问题是，一切路线都必须事先写好。

你真正需要定义的不是“研究项目”，而是下面这些底层内容：

| 人工定义       | 系统运行时生成 |
| ---------- | ------- |
| 世界变量与概念    | 观察记录    |
| 世界因果机制     | 想法      |
| 可观察方式      | 研究问题    |
| 可干预方式      | 候选假设    |
| 通用推理规则     | 预测      |
| 仪器和机器能力    | 实验需求    |
| 语言模板       | 研究笔记文本  |
| 技术解锁所需知识条件 | 实际研究路线  |

于是，“风雪中的炉火为什么会熄灭”并不是一个预先注册的研究ID。

它可能是运行时生成的一个研究工作区：

```text
问题：
为什么东侧锅炉只在湿雪暴风中出现燃烧不稳定？

相关观察：
- 炉温下降
- 进气口积冰
- 打开炉门后短暂恢复
- 相同燃料在室内炉中正常燃烧

候选解释：
- 燃料受潮
- 进气受阻
- 烟囱倒灌
```

这个工作区完成或关闭之后可以消失，但其中产生的观察、假设、实验记录和发现会永久留在知识图中。

# 二、底层不是普通图，而是“主张—证据图”

最容易犯的错误是直接储存：

```text
积冰 --导致--> 空气流量下降
```

这看起来像知识图谱，但它无法表达：

* 这是谁提出的；
* 它是观察、假设还是已确认发现；
* 它只在什么条件下成立；
* 有哪些证据支持；
* 有哪些实验反驳；
* 这个结论是不是从其他结论推导出来的；
* 不同NPC是否相信它。

因此，“事实”不应该直接作为边，而应该被实体化为一个**主张节点 Claim**。

例如：

```text
Claim H17
────────────────────────────────
谓词：DECREASES

原因：
进气口积冰量

结果：
空气流量

作用范围：
环境温度 < 0°C
空气中存在较高湿度
对象属于开放式锅炉进气结构

认识状态：
假设
```

然后，证据再连接到这个主张：

```text
实验记录 E42
    └── 支持 ──> Claim H17

锅炉工证词 E51
    └── 弱支持 ──> Claim H17

实验记录 E63
    └── 反驳 ──> Claim H17
```

这才允许系统表示争议与修正。

# 三、一个较严格的数学定义

可以先定义一套静态语义模式：

[
\Sigma=(T,P,S)
]

其中：

* (T)：类型集合，例如锅炉、燃料、温度、流量、居民、仪器；
* (P)：谓词集合，例如增加、减少、导致、测量、依赖、相似；
* (S)：规则与机制模式，例如“阻塞降低流量”“温度可能导致相变”。

玩家或城镇当前的知识状态可以定义为：

[
K_t=(V,C,J)
]

其中：

* (V)：实体、概念、实验、数据集、程序等节点；
* (C)：主张节点；
* (J)：依据或论证关系。

一个主张可以表示为：

[
c=\langle p,\vec{a},\kappa\rangle
]

其中：

* (p) 是谓词；
* (\vec{a}) 是带角色的参数；
* (\kappa) 是上下文和适用范围。

例如：

```text
p = DECREASES

arguments:
  cause = intake.ice_mass
  effect = boiler.airflow

scope:
  ambient_temperature < 0
  humidity > 0.75
```

一个论证关系可以表示为：

[
j=\langle Premises,Conclusion,Rule,Polarity,Quality,Provenance\rangle
]

其中：

* `Premises`：哪些记录或主张是前提；
* `Conclusion`：它支持或反驳哪个主张；
* `Rule`：使用了什么推理规则；
* `Polarity`：支持还是反驳；
* `Quality`：证据质量；
* `Provenance`：来源、时间、NPC、仪器、实验批次。

因为一个推理可能同时需要多个前提，所以它本质上是一个**超边**：

```text
观察A ─┐
观察B ─┼── 通过推理规则R ──> 假设H
计算C ─┘
```

代码里不需要真的使用超图数据库。把“论证”作为对象，其中存放一个前提列表即可。

# 四、必须区分“世界真相”和“玩家认知”

底层实际上需要两个不同的模型。

## 1. 隐藏世界因果模型

它决定Minecraft世界实际发生什么。

可以抽象为：

[
x_{t+1}=F(x_t,i_t,\epsilon_t)
]

其中：

* (x_t)：当前世界状态；
* (i_t)：玩家或机器的干预；
* (\epsilon_t)：明确存在的噪声或随机扰动；
* (F)：世界机制。

例如：

```text
低温 + 空气水分
    → 进气口积冰增加

积冰增加
    → 有效进气面积减少

有效面积减少
    → 空气流量降低

空气流量降低
    → 燃烧不稳定
```

这些机制可以直接连接现有游戏模拟代码。

## 2. 玩家认识图

玩家一开始不知道上述因果链。

玩家认识图中可能同时存在：

```text
假设A：低温煤炭本身难以燃烧
假设B：湿煤导致燃烧不完全
假设C：进气口积冰降低空气流量
假设D：暴风导致烟囱倒灌
```

候选假设生成器**不能直接读取隐藏世界真相**，否则它会泄露答案。

隐藏模型只负责：

* 实验实际会发生什么；
* 玩家改变变量之后世界如何响应；
* 仪器读数是什么；
* 未控制因素如何干扰结果。

玩家的假设只能来自：

* 已有知识；
* 通用机制模式；
* NPC经验；
* 当前观察；
* 类比和推理。

这是整个系统公平性的关键。

---

# 五、知识图不会“自己神奇地形成”，它需要语义接口

这里必须明确一个现实边界：

> 系统无法从任意Minecraft机器代码里自动理解“这段代码代表空气流量”“这个变量是湿度”“这个状态可以成为实验变量”。

每个世界系统需要提供一层**研究语义接口**。

例如一个锅炉组件要注册：

```text
可观察变量：
- 炉温
- 燃料消耗速度
- 空气流量
- 烟道压力
- 进气口积冰量

可干预变量：
- 燃料种类
- 燃料湿度
- 进气加热
- 烟囱结构
- 炉门开启状态

隐藏机制：
- 空气流量影响燃烧
- 湿度与低温导致积冰
- 积冰降低有效进气面积
```

一个温度计则注册：

```text
能力：
MEASURE(temperature)

范围：
-50°C ~ 100°C

精度：
±1°C

采样周期：
20 ticks
```

作者工作量从：

> 为每项研究写十几条触发路线、实验路线和失败路线

变成：

> 为每种世界机制定义变量、可观察性、可干预性和因果语义

这是完全不同的复杂度。

一个机制定义完成之后，可以参与许多研究：

* 锅炉积冰；
* 管道堵塞；
* 门锁冻结；
* 水泵失效；
* 风力机叶片积冰；
* 食物冷冻保存；
* 人体冻伤。

# 六、“想法”可以严格定义成知识图中的一个缺口

你最初提出的“想法”非常适合定义成：

> **一个由若干观察锚定、但尚未被当前知识解释的查询。**

形式上可以写成：

[
Idea=\langle Q,A,G,S\rangle
]

其中：

* (Q)：一个尚未回答的问题；
* (A)：产生这个问题的锚点观察；
* (G)：知识缺口类型；
* (S)：显著性信息。

例如：

```text
Q：
什么因素导致了锅炉输出下降？

A：
- 暴风雪时输出下降
- 平静天气正常
- 进气口存在积冰
- 开炉门后暂时恢复

G：
未解释的条件性异常

S：
- 多次出现
- 影响城镇供暖
- 有多名NPC注意到
```

所以，想法不是“收集五点之后解锁”，而是图中出现了某种结构性缺口。

# 七、通过“图模式规则”自动产生想法

系统可以定义一组通用的图模式，而不是每项研究单独定义触发。

## 1. 对比异常规则

```text
同一对象
在上下文C1中出现结果Y1
在上下文C2中出现结果Y2
Y1与Y2明显不同
C1和C2之间存在少量关键差异
当前没有已接受解释

→ 产生问题：
这些上下文差异中的什么因素影响了Y？
```

伪规则：

```text
Observation(subject, variable, value1, context1)
Observation(subject, variable, value2, context2)
Incompatible(value1, value2)
ContextDifference(context1, context2, factor)
NoAcceptedExplanation(variable, factor)

=> Idea: Does factor influence variable?
```

## 2. 重复共现规则

```text
现象A与现象B多次同时出现
但当前知识图中没有二者之间的解释关系

→ 产生问题：
A与B是否有关？
```

这只能产生想法，不能产生因果发现。

## 3. 预测偏差规则

```text
已有理论预测结果Y
实际观察结果明显偏离Y

→ 产生问题：
当前模型漏掉了什么因素？
```

## 4. 证词冲突规则

```text
NPC甲认为原因是A
NPC乙认为原因是B
二者预测不同结果

→ 产生争议型研究问题
```

## 5. 类比迁移规则

```text
已知：
冰会堵塞水管并降低流量

新观察：
锅炉进气口积冰且火焰变弱

→ 产生类比问题：
进气口积冰是否同样降低了空气流量？
```

## 6. 目标缺口规则

```text
城镇有一个必须满足的需求
现有设备无法满足
当前知识中存在可能相关的发现

→ 产生工程型研究问题
```

例如：

```text
需求：
锅炉必须在暴风雪中连续运行12小时

已知：
加热可以融化积冰
已知：
积冰降低流量

→ 工程想法：
能否持续防止进气结构结冰？
```

# 八、图模式规则本质上是一种“图重写系统”

每条规则可以定义为：

```text
Rule:
  匹配模式 Pattern
  条件 Guard
  生成内容 Emit
  去重键 DeduplicationKey
  文本解释 Explanation
```

数学上，可以理解为找到一个映射：

[
\mu:P\rightarrow K
]

其中 (P) 是规则要求的模式，(K) 是当前知识图。

当匹配成功时，系统向图中加入新的节点和关系：

[
K\rightarrow K\cup{Idea(Q)}
]

例如：

```text
规则：
CONTRASTIVE_ANOMALY

匹配：
- 同一锅炉
- 两次不同输出
- 两次上下文不同
- 没有已有解释

生成：
- 想法节点
- 想法与两次观察的来源关系
- 一段说明“为什么这个想法出现”
```

这样每个想法都有完整的解释路径。

玩家看到：

> “这个问题出现，是因为东侧锅炉在三次湿雪天气中输出下降，但在低温干燥天气中表现正常。”

这句话可以直接根据图匹配结果生成，而不需要手写。

# 九、用事件溯源同时解决“图”和“线性流程”

这是我认为最适合你这个系统的架构。

不要只保存当前图，还要保存一条只追加、不修改的事件日志：

```text
ResearchEvent 001
玩家记录：东侧锅炉炉温异常下降

ResearchEvent 002
NPC罗伯特报告：进气格栅上有积冰

ResearchEvent 003
系统识别：两次记录可能有关

ResearchEvent 004
研究团队提出：进气受阻假设

ResearchEvent 005
计算完成：正常流量应为某范围

ResearchEvent 006
实验计划建立

ResearchEvent 007
实验因燃料湿度不一致而无效

ResearchEvent 008
实验计划修改

ResearchEvent 009
第二次实验支持进气受阻假设
```

令事件日志为：

[
L_t=(e_1,e_2,\dots,e_t)
]

当前知识图是事件日志折叠后的结果：

[
K_t=Fold(Apply,K_0,L_t)
]

这带来几个巨大好处。

### 第一，研究历史天然是线性的

玩家的研究笔记可以直接按照事件顺序显示。

### 第二，图可以反复重建

便于存档迁移、调试和修复。

### 第三，每个结论都有来源

点击发现，可以沿事件和论证关系回溯：

```text
发现
→ 支持实验
→ 实验数据
→ 实验装置
→ 原始想法
→ 最初观察
```

### 第四，旧理论被推翻时不必删除历史

它仍然存在于事件日志中，只是当前状态变成：

```text
已反驳
已被更准确理论取代
仅在较窄范围内成立
```

因此：

> **事件日志给玩家提供一条故事线，知识图则提供当前认知结构。**

# 十、研究工作区是知识图的局部投影

一项研究可以定义为：

[
R=\langle Q,A,H,E,P,\Omega\rangle
]

其中：

* (Q)：当前问题；
* (A)：相关观察锚点；
* (H)：候选假设集合；
* (E)：已收集证据；
* (P)：实验计划；
* (\Omega)：尚未完成的研究义务。

研究工作区并不复制整个知识图，而是提取与问题有关的局部子图：

```text
当前问题
  ├── 直接相关观察
  ├── 候选原因
  ├── 已知背景规律
  ├── NPC证词
  ├── 计算与推导
  ├── 当前实验
  └── 支持和反对证据
```

玩家不需要面对完整知识网络。

界面可以只显示：

* 当前问题；
* 三到五条关键观察；
* 当前候选解释；
* 当前最关键的缺口；
* 当前可以采取的行动；
* 已完成研究历史。

其余知识折叠成：

> “引用了3项旧发现”
> “存在2条未解决反证”
> “艾琳掌握可能相关的材料知识”

# 十一、假设生成应该使用“溯因搜索”

假设生成的目标不是寻找一定正确的答案，而是寻找：

> 哪些小型因果结构能够解释当前观察？

这属于溯因推理。

形式上可以寻找若干个候选 (H)，使得：

[
K\cup H\models A
]

其中：

* (K) 是当前已有知识；
* (A) 是需要解释的观察；
* (H) 是补充进去之后可以解释观察的假设。

但系统不应无限组合所有节点，而应从一组**机制模式**中实例化。

例如通用机制模式：

```text
阻塞物增加
→ 有效截面积下降
→ 流量下降

温度下降
→ 液体黏度增加
→ 机械阻力增加

材料含水量增加
→ 燃烧效率下降

外部压力变化
→ 流动方向变化
```

锅炉研究中，系统可能实例化出：

```text
积冰
→ 进气截面积下降
→ 空气流量下降
→ 炉温下降
```

或者：

```text
燃料受潮
→ 燃烧效率下降
→ 炉温下降
```

候选生成器只使用：

* 研究团队已知概念；
* 团队掌握的机制模式；
* 当前上下文中变化的变量；
* NPC提出的说法；
* 与旧发现相似的结构。

它不读取真实答案。

---

# 十二、限制假设搜索，避免组合爆炸

任意图上的解释搜索会迅速爆炸，所以需要明确限制。

建议采用：

```text
最大机制链长度：2～4
每轮候选假设：3～6个
只搜索当前问题附近的局部图
只使用类型匹配的机制
优先使用当前观察中实际变化的变量
优先使用研究团队已知的概念
优先使用具有来源解释的候选
```

候选假设可以按照以下因素排序：

[
Score(H)=
Coverage(H)
-\lambda Complexity(H)
+Prior(H)
+Relevance(H)
]

其中：

* `Coverage`：能解释多少观察；
* `Complexity`：需要引入多少新假定；
* `Prior`：团队是否有相关知识或经验；
* `Relevance`：是否与当前环境变化相符。

这个分数可以只用于排序，不应该显示成“假设正确率”。

# 十三、理论研究应该产生“研究义务”

理论阶段不要定义为：

```text
理论进度 = 0 / 100
```

而应定义为一组当前尚未满足的结构化义务。

例如：

```text
尚未明确需要解释的现象
尚未把“燃烧变差”转换成可测量变量
只有一个解释，缺乏替代假设
当前两个假设预测了相同结果
缺少可以区分假设的实验
缺少必要的计算参数
尚未识别可能的混杂因素
```

一个研究义务可以定义为：

```text
ResearchObligation
────────────────────────
类型：
DERIVE_DISCRIMINATING_PREDICTION

目标：
区分“燃料受潮”和“进气结冰”

完成条件：
存在一个实验条件，使两个假设预测不同结果

可能行动：
- 研究空气流量测量
- 咨询锅炉工
- 使用机械计算器
- 查阅旧实验记录
```

计算器和高教育NPC的作用，就是完成这些具体义务。

例如：

```text
当前缺口：
不知道在正常烟道压力下，理论空气流量应是多少。

可执行任务：
- 机械计算器：根据管径和压力计算
- 高教育居民：进行人工估算
- 搭建标定实验：直接测量
```

时间和人力负责执行这些行为，但不是抽象地生成研究点。

---

# 十四、实验计划可以从候选假设自动生成

假设集合为：

[
H={h_1,h_2,\dots,h_n}
]

一个实验动作 (a) 包含：

[
a=\langle do(X=x),Controls,Measures,Duration\rangle
]

也就是：

* 主动改变什么；
* 保持什么不变；
* 测量什么；
* 持续多久。

每个假设都应该能够对实验产生预测：

[
P(o\mid h,a)
]

例如：

| 实验操作     | 燃料受潮假设 | 进气结冰假设 | 烟囱倒灌假设 |
| -------- | -----: | -----: | -----: |
| 加热进气口    |  无明显改善 |   明显改善 |  无明显改善 |
| 烘干燃料     |   明显改善 |  无明显改善 |  无明显改善 |
| 改变烟囱挡风结构 |  无明显改善 |  无明显改善 |   明显改善 |

系统要寻找的是：

> 哪个可执行实验能够让不同假设产生不同预测？

理论上可以使用信息增益：

[
a^*=\arg\max_a
\left[
IG(a;H)-\lambda Cost(a)-\mu Risk(a)
\right]
]

但第一版不需要完整概率模型。

只需计算：

* 这个实验能否把候选假设分成不同结果组；
* 它能区分多少对假设；
* 当前城镇能否完成；
* 成本和危险是否可接受。

---

# 十五、控制变量可以从“竞争假设”中自动得到

这是数据驱动实验设计中很关键的一点。

假设：

```text
H1：燃料湿度导致炉温下降
H2：进气结冰导致炉温下降
H3：烟囱压力导致炉温下降
```

玩家要验证H2。

那么H1和H3本身就告诉系统应该控制什么：

```text
保持燃料湿度一致
保持烟囱结构一致
记录烟道压力
保持燃料投入速度一致
保持锅炉负载一致
```

换言之：

> **竞争假设就是控制变量需求的来源。**

实验设计不需要作者预先写：

```text
这个实验必须控制燃料湿度、烟道压力、锅炉负载……
```

而是根据当前候选因果模型动态推导。

一般算法可以是：

1. 确定要主动改变的变量 (X)；
2. 确定要观察的结果 (Y)；
3. 找到其他假设中同样可能影响 (Y) 的变量；
4. 将这些变量加入控制或测量列表；
5. 检查是否存在共同原因；
6. 检查目前仪器能否观察这些变量。

# 十六、实验装置应当是一个“能力约束问题”

实验计划不应该要求唯一多方块结构，而应该生成一组能力需求。

例如：

```text
实验需求：
- 能主动加热一个进气口
- 能测量空气流量
- 能测量炉温
- 能让两个燃烧室使用相同燃料
- 能保持相同负载
- 能持续记录六小时
- 能提供低温高湿环境
```

形式上：

[
RequiredCapabilities=
{
Manipulate(X),
Measure(Y),
Hold(C_1),
Hold(C_2),
Log(T),
Replicate(N)
}
]

世界中的方块、NPC和房间提供能力：

```text
温度计：
MEASURE(temperature)

机械流量计：
MEASURE(airflow)

电热器：
MANIPULATE(surface_temperature)

密封燃料仓：
HOLD(fuel_moisture)

低温实验室：
HOLD(ambient_temperature)
HOLD(humidity)

研究员：
LOG_MANUALLY(variable, interval)
```

玩家搭建的实验装置只需满足这些约束。

本质上它是一个约束满足问题：

[
Capabilities(Apparatus)\supseteq RequiredCapabilities
]

这样玩家仍然拥有Minecraft式自由搭建。

# 十七、实验结果不是“成功/失败”，而是新的图结构

一次实验运行应该生成：

```text
ExperimentRun
────────────────────────
实验计划
实际操作轨迹
能量供应轨迹
材料供应轨迹
环境变化
仪器读数
NPC操作日志
故障事件
```

然后验证器判断：

```text
干预是否真的生效
控制变量是否保持稳定
仪器是否在有效范围
数据是否有缺失
两组实验是否可比较
结果是否符合某个假设预测
```

最后增加证据关系：

```text
Run #2
  ├── 强支持 H2
  ├── 反驳 H1
  ├── 对H3无区分力
  └── 产生异常：烟道冷凝增加
```

注意，同一个实验不一定对所有假设都有判断力。

可能出现：

```text
支持H2
但不能排除H3
```

或者：

```text
反驳H1
但无法判断H2与H3
```

这会自然生成下一项研究义务。

# 十八、使用论证结构作为主体，概率作为辅助

系统内部可以给证据记录：

* 有效性；
* 可靠性；
* 区分力；
* 独立性；
* 来源质量。

如果需要，可以进行贝叶斯式更新：

[
\log Odds(H\mid E)
==================

\log Odds(H)
+
\sum_i
\log
\frac{P(E_i\mid H)}
{P(E_i\mid\neg H)}
]

但是不建议用这个概率直接决定：

> 研究进度达到100%，发现完成。

概率更适合：

* 排序候选假设；
* 决定NPC更倾向于支持什么；
* 估计是否值得继续实验；
* 给研究团队生成建议。

真正的发现完成条件应是结构化的。

例如一项因果发现要求：

```text
至少有一次有效的区分性实验
主要竞争假设已经得到处理
不存在未解决的严重控制问题
至少完成一次重复验证
适用范围已经明确
```

一项工程结论则要求：

```text
原型满足性能要求
通过指定环境测试
维护要求可接受
普通居民能够操作
没有未解决的严重安全故障
```

# 十九、线性研究流程不是预先存储的，而是实时编译的

这是回答你“怎样把图呈现成线性流程”的核心。

系统每次图发生变化后，都重新生成当前未满足的研究义务：

```text
Compile(Inquiry, KnowledgeGraph, TownCapabilities)
    → ObligationGraph
```

这些义务之间有依赖关系：

```text
明确问题
    ↓
提出候选假设
    ↓
推导可区分预测
    ↓
确定控制变量
    ↓
准备实验能力
    ↓
运行实验
    ↓
解释结果
    ↓
处理剩余竞争解释
    ↓
形成发现
```

义务本身构成一个小型有向无环图。

工作流编译器执行：

```text
1. 生成所有当前未满足义务
2. 建立义务依赖关系
3. 找到前置条件已经完成的义务
4. 排除当前无法执行的义务
5. 按紧迫性、成本、玩家选择排序
6. 向玩家呈现一个主步骤和少量可选步骤
```

伪代码：

```java
List<Obligation> compile(Inquiry inquiry, KnowledgeGraph graph) {
    List<Obligation> all = obligationRules.stream()
        .flatMap(rule -> rule.generate(inquiry, graph))
        .filter(obligation -> !obligation.isSatisfied(graph))
        .toList();

    DependencyGraph dependencyGraph =
        buildDependencies(all);

    return dependencyGraph.frontier().stream()
        .filter(obligation -> obligation.isCurrentlyFeasible(graph))
        .sorted(byPriorityAndPlayerPreference())
        .toList();
}
```

玩家看到的“当前阶段”只是最前方义务的分类：

```text
当前缺少问题定义
→ 想法阶段

当前缺少可检验假设
→ 理论阶段

当前缺少区分性实验
→ 实验设计阶段

实验已经准备好
→ 实验阶段

数据存在但尚未解释
→ 分析阶段

竞争假设仍未排除
→ 修正阶段

所有接受条件满足
→ 发现阶段
```

因此不要把：

```text
stage = THEORY
```

作为真正数据。

更合理的是：

```text
stage = classify(currentFrontierObligation)
```

阶段是计算结果，不是底层真相。

# 二十、为什么这仍然会给玩家一种清楚的线性体验

因为玩家实际需要的不是一条永远不变的线，而是：

> 我目前为什么卡住，以及下一步可以做什么。

研究笔记可以显示：

```text
第1轮：提出问题
第2轮：形成两个解释
第3轮：发现当前实验无法区分两个解释
第4轮：加入空气流量测量
第5轮：第一次实验因燃料湿度变化而作废
第6轮：修改燃料供应结构
第7轮：实验反驳燃料受潮假设
第8轮：重复实验支持进气结冰假设
第9轮：形成暂定发现
```

这个历史是严格线性的，因为事件发生的时间天然是线性的。

与此同时，当前页面可以显示：

```text
当前工作：
确认这个规律是否也适用于大型锅炉

为什么：
现有证据只来自小型实验炉

可执行方式：
- 在东侧锅炉进行现场测试
- 建造第二个大型对照锅炉
- 收集其他城镇锅炉记录
```

这比“研究进度84%”更清楚。

# 二十一、NPC系统可以直接映射成图搜索能力

NPC不应只是提供研究速度加成。

每名NPC可以拥有：

```text
已知主张集合
可理解概念集合
可使用推理规则集合
领域经验
观察能力
计算能力
怀疑标准
工作记忆和搜索预算
```

不一定要为每个NPC复制整个图。实现上可以使用：

```text
KnownBy(NPC, Claim)
UnderstoodBy(NPC, Concept)
CanApply(NPC, Rule)
```

NPC属性可以映射成算法能力：

| NPC属性 | 算法影响                   |
| ----- | ---------------------- |
| 智力    | 图搜索深度、同时考虑的变量数量、候选假设数量 |
| 教育    | 可使用的正式推理规则、统计方法和测量概念   |
| 领域经验  | 特定机制模式、异常识别、候选假设先验     |
| 实践技能  | 仪器校准、实验执行、设备故障识别       |
| 怀疑精神  | 更容易生成替代假设和控制变量要求       |
| 沟通能力  | 知识传播速度和表达损失            |
| 好奇心   | 记录异常现象和产生想法的概率         |

例如一个老锅炉工可能没有形式教育，但拥有：

```text
火焰颜色变化 → 空气供应异常
烟囱低鸣 → 可能存在倒灌
炉门打开后恢复 → 可能缺乏进气
```

一个学者可能知道：

```text
必须区分燃料湿度、空气流量和烟道压力
需要对照组
需要计算预期流量
```

两者合作才会形成完整实验。

研究团队的能力等于：

> 团队成员所掌握概念、规则、经验与实验能力的组合。

# 二十二、知识传播也可以直接作用于图

NPC说出的不是“研究点”，而是带来源的主张。

例如：

```text
Claim T17：
“湿雪天气中锅炉更容易熄火。”

来源：
NPC罗伯特的经验

证据类型：
个人回忆

可靠性问题：
- 没有仪器记录
- 可能混淆低温与湿度
- 覆盖多个冬季
```

当另一个NPC听到之后：

```text
KnownBy(艾琳, T17)
```

但并不代表：

```text
AcceptedBy(艾琳, T17)
```

知识可以有多个状态：

```text
听说过
理解
相信
能够应用
能够教授
已记录进城镇档案
```

研究所和学校的作用，就是把零散个人知识转换成可追踪、可复制的公共知识。

# 二十三、技术解锁也不应该依赖“研究ID”

传统方式：

```text
完成 research_heated_intake
→ 解锁 heated_intake_recipe
```

数据驱动方式应该是：

```text
当知识图满足某个模式时
→ 允许进入某种工程设计空间
```

例如：

```text
UnlockRequirement:
  Accepted(
    DECREASES(
      intake_icing,
      airflow
    )
  )

  AND Accepted(
    INCREASES(
      surface_heating,
      ice_melting
    )
  )

  AND PrototypeStandardized(
    heated_air_intake
  )
```

于是，玩家可以通过完全不同的研究路线满足这些知识条件。

技术本身依赖的是：

> 城镇已经掌握了哪些规律和程序。

而不是：

> 玩家是否勾选了某个研究节点。

这会极大增强扩展性。

# 二十四、工程原型可以复用同一套架构

科学研究中的核心主张是：

```text
X在条件C下导致Y
```

工程开发中的核心主张是：

```text
设计D在条件C下满足需求R
```

因此工程研究不需要另一套完全独立系统。

工程问题可以表示为：

```text
Question:
存在什么设计D，使其满足：

- 暴风雪中保持空气流量
- 电力消耗低于某值
- 普通居民可以维护
- 不使用稀缺材料
```

候选不再是因果假设，而是设计方案：

```text
D1：电热格栅
D2：机械刮冰器
D3：大型遮雪罩
D4：废热回流
```

实验变成原型测试。

证据关系变成：

```text
测试Run17
  ├── 支持 D1满足可靠性要求
  ├── 反驳 D1满足低功耗要求
  └── 暴露新问题：电气结构进水
```

最终不是找到唯一“正确答案”，而是在多目标约束下找到可接受设计。

可以维护一个帕累托式设计集合：

```text
高可靠、高耗电
低成本、维护频繁
节能、制造复杂
```

由玩家决定城镇采用哪条路线。

# 二十五、锅炉例子的完整数据流

## 1. 世界事件

```text
StormEvent:
  temperature = -18°C
  humidity = 0.91
  snow_type = WET_SNOW
```

隐藏机制使锅炉进气口积冰，空气流量下降。

## 2. 观察事件

```text
O1：
东侧锅炉炉温下降

O2：
进气格栅积冰

O3：
打开炉门后炉火短暂恢复

O4：
室内小炉使用相同燃料但燃烧正常
```

## 3. 图规则匹配

系统发现：

```text
炉温下降与湿雪天气重复共现
积冰与炉温下降共现
打开炉门这一干预使炉火恢复
现有知识没有解释
```

生成：

```text
Idea Q1：
什么因素导致湿雪天气中的锅炉燃烧不稳定？
```

## 4. 候选假设

```text
H1：
燃料湿度增加
→ 燃烧效率下降

H2：
进气口积冰
→ 空气流量下降
→ 燃烧不稳定

H3：
暴风造成烟囱倒灌
→ 排烟受阻
→ 燃烧不稳定
```

## 5. 工作流编译

系统发现：

```text
当前三个假设都能解释炉温下降。
当前缺口是：没有能区分它们的预测。
```

生成当前任务：

> 找到一种只影响其中一个解释的干预方式。

## 6. 推导实验

```text
加热进气口：
H1预测无明显改变
H2预测空气流量恢复
H3预测无明显改变
```

于是生成能力需求：

```text
MANIPULATE(intake_temperature)
MEASURE(airflow)
MEASURE(boiler_temperature)
HOLD(fuel_moisture)
HOLD(chimney_configuration)
HOLD(load)
```

## 7. 第一次实验

玩家没有保持燃料湿度稳定。

结果：

```text
进气加热组燃料更干燥
对照组燃料更潮湿

→ 无法判断改善来自进气除冰还是燃料差异
```

图中增加：

```text
Run1
  └── 无法为H1与H2提供有效区分
```

工作流重新编译：

```text
当前任务：
消除燃料湿度差异。

建议：
使用同一批密封燃料仓供料。
```

## 8. 第二次实验

结果：

```text
进气加热
→ 积冰量下降
→ 空气流量先恢复
→ 炉温随后恢复
```

系统增加：

```text
Run2 强支持 H2
Run2 反驳 H1作为主要解释
Run2 对H3提供中等反证
```

## 9. 发现

```text
Finding F1：

在低温高湿、开放式进气结构中，
进气口积冰会降低空气流量，
并导致锅炉燃烧输出不稳定。
```

注意，这个发现具有明确作用范围。

它不是：

> 积冰永远会让所有锅炉熄灭。

# 二十八、实现时最重要的五个限制

## 1. 不要记录世界中的一切

否则图会爆炸。

只有以下内容进入研究系统：

* 玩家主动记录；
* NPC注意到；
* 专门传感器正在监测；
* 与当前研究有关；
* 达到异常阈值；
* 造成事故或显著结果。

“注意力”本身就是数据入口。

## 2. 不要全图搜索

每次只处理新加入节点附近的局部区域。

```text
新观察加入
→ 查找与其相同对象、变量、上下文的邻域
→ 运行相关规则
→ 更新活跃研究
```

不要每个tick重新扫描全部知识。

## 3. 每个生成结果必须有解释路径

系统生成假设时，必须能够回答：

> 为什么会提出这个假设？

例如：

```text
因为：
- 打开炉门后火焰恢复；
- 已知开门会增加空气供应；
- 进气口存在积冰；
- 已知阻塞可能降低流量。
```

无法解释来源的自动生成内容应当直接丢弃。

## 4. 不要删除被反驳的知识

被反驳的假设是重要的负知识。

后续NPC可以知道：

> “我们已经测试过加热燃料，不能解决这个问题。”

## 5. 使用真值维护，而不是直接覆盖状态

每个推导结论都保存它依赖的前提。

当一个前提被推翻时，系统可以重新计算依赖它的结论：

```text
发现A依赖假设H
假设H后来被反驳
→ 发现A变成“失去支持”
→ 依赖发现A的工程技术被标记为需要复查
```

第一版可以实现一个轻量级的真值维护系统：

```text
主张有若干Justification
只要存在有效Justification，就保持支持
所有Justification失效，则变为无支持
出现强反证，则变为争议或反驳
```

不要一开始试图做“全领域自动科研”。

# 三十、最终可以把整个架构概括为一句话

> **世界机制产生现象；观察把现象写入事件日志；事件日志构建带来源的主张—证据图；图中的矛盾、异常和缺口生成问题；问题通过溯因搜索生成候选假设；假设之间的预测差异生成实验需求；实验结果回写为证据；工作流编译器每次从当前知识状态中选出下一项未满足的研究义务，并将整个非线性探索呈现为一条不断修正、但始终清楚的线性研究历程。**

真正值得优先落地的核心名称可以定为：

```text
EpistemicGraph
ResearchEventLog
InquiryWorkspace
ResearchGrammar
ObligationCompiler
ExperimentCapabilitySystem
```

2. **研究流程必须由当前未满足的认识义务编译产生，而不是预先写成状态机。**

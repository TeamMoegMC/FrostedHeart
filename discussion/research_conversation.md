我想在Minecraft游戏（我在开发的冬季救援自研模组）中设计一套研究系统，我的设计哲学在于每一项研究首先要有一个“想法”来开启——这个想法可能是偶然发现的现象，其他研究产生的未解决问题，或是和游戏中的难民NPC交流讨论产生的，或是来自NPC的知识传播——这比较符合现实。开启研究的不一定是一个具体的问题，而只需一个想法。这个过程要体现出研究问题那种非线性的涌现的感觉。

具体开启一项研究之后，分为理论和实验相互交迭的步骤，理论需要提出思考，计算，验证，最终提出假设，并提出实验计划和所需材料；实验目的是通过实验材料和实验本身验证理论假设，需要真正在游戏中搭建具体的看见摸得着的东西，控制变量，发现现象。最终理论和实验吻合，假设被证明，产生“发现”。整个过程要充分利用开放和自由性和玩家的能动性，减少靠数值来衡量科研进度的设定，以及我们实现的一套城镇系统——NPC有智力和受教育程度——研究不是单人工程。

具体的我设计的步骤：
收集想法：在世界中探索，搞机器，合成，和难民居民聊天，随时可以触发，记录到研究笔记里。想法收集足够了，开启一个之前隐藏的研究。注意一开始这个研究不应该揭露研究最终结果，而是仅是一个想法。
理论研究：开启研究后，进入理论步骤。通过若干个子步骤的计算（机械计算器，研究所人力计算）和思考（小游戏，研究所高教育等级居民工作）最终提出假设，总结出实验需求。  
实验研究：必须跟随在理论研究之后，通过在世界中建设实验室，投入研究所人力资源，并需要持续材料供给、能量供给、等，以及时间成本；假设可能被验证，或者否认。
这具有概率性。若否认，则需要进入下一轮理论研究。若成功，则研究完成。  如此迭代，直到研究成功。迭代有上限次数，若超过该次数，则意味着研究失败，该想法不成立。

可能还需要引入一个工程原型研究，但我不了解。

你完全可以提出你的想法。思考设计一下。

你的方向很强，而且它真正有机会把“研究”做成一种**认识世界的玩法**，而不是另一种换皮制造系统。

我认为整套系统最关键的一条原则是：

> **被反复迭代的应该是假设、实验方法和问题框架，而不是一个抽象的“研究进度条”。**

实验也不应该通过一次隐藏成功率判定“自然规律是否成立”。世界中的真实规律应当相对稳定；概率主要影响的是测量误差、设备故障、实验污染、NPC失误和结果是否足够清晰。

整套循环可以概括为：

```text
现象、事故、口述、机器异常
        ↓
      研究笔记
        ↓
讨论、联想、知识交叉、发现矛盾
        ↓
       想法
        ↓
提出多个可能解释
        ↓
       假设
        ↓
预测结果、设计实验、确定控制变量
        ↓
在世界中搭建并运行实验
        ↓
支持 / 反驳 / 无法判断 / 意外现象
        ↓
修正假设、改进实验或重新定义问题
        ↺
       发现
        ↓
工程需求 → 原型 → 现场试验 → 标准化技术
```

其中，实验产生的意外现象、原型的故障和现场试验的失败，都可以重新回到最上方，成为新的想法来源。

# 一、把“想法”“假设”“发现”严格区分开

这几个对象最好不要混在一起。

| 对象   | 它代表什么            | 玩家此时应该知道什么       |
| ---- | ---------------- | ---------------- |
| 观察记录 | 某件确实发生过的事情       | 时间、地点、环境、来源、具体表现 |
| 想法   | 某些记录之间可能存在联系     | 一个模糊问题，但不知道最终答案  |
| 研究问题 | 玩家决定从哪个角度理解想法    | 要解释什么现象，暂时忽略什么   |
| 假设   | 对现象的一个可检验解释      | 如果它成立，应该看到什么结果   |
| 证据   | 实验或观察产生的新记录      | 支持、反驳或无法区分哪些假设   |
| 发现   | 在一定适用条件下得到确认的规律  | 规律本身、适用范围和可能用途   |
| 工程技术 | 把规律变成可靠、可复制的解决方案 | 制造方法、维护要求、工作范围   |

例如，玩家看见锅炉在暴风雪中不断熄火。

此时获得的不是“防冻进气技术研究”，而是：

> **想法：风雪似乎正在让炉火窒息。**

它可能由进气口结冰、燃料受潮、烟囱倒灌、气压变化或操作问题造成。玩家此时不应该看到最终解锁物，更不应该看到“研究完成后解锁加热进气口”。

# 二、想法不应通过“收集满五个点数”出现

你提到“想法收集足够了，开启隐藏研究”。这里最好不要表现为纯数量门槛，否则最后仍然会变成：

> 再捡两个研究点，就能解锁下一项科技。

更合适的是让想法由某种**关系结构**触发，而不是由数量触发。

## 1. 矛盾触发

两条记录无法同时用已有知识解释：

* 相同燃料，两个锅炉的热量输出不同；
* 白天正常，湿冷夜晚异常；
* 增加燃料后火势反而更弱。

研究笔记可以提示：

> “这些记录似乎彼此矛盾。”

玩家将它们放在讨论板上，便可能产生想法。

## 2. 重复现象触发

相似现象在不同环境中反复出现：

* 水泵、门轴和发电机都在低温下变得迟钝；
* 三台不同机器都出现润滑部位阻力增加。

这些记录可能共同产生：

> “寒冷似乎改变了某种机器内部共有的东西。”

## 3. 知识迁移触发

一个领域的发现被应用到另一个领域：

* 玩家已经知道空气夹层可以减缓房屋散热；
* 一名居民提到伤员被湿衣服包裹时体温下降更快；
* 由此产生关于湿衣服、空气层和人体保温的想法。

## 4. NPC知识触发

NPC不应只是提供“研究点”，而应带来不同类型的信息：

* 正规教育产生理论语言；
* 工作经历产生经验规律；
* 个人记忆产生案例；
* 故乡技术产生另一种解决路线；
* 怀疑或偏见也可能产生错误线索。

一名受教育程度不高的老锅炉工，可能比一名高智力学者更早注意到火焰颜色、烟道声音或者积霜位置。

## 5. 意外现象触发

实验的目标是研究A，却出现了无法解释的B。

这类记录应直接标记为“异常”，并且是最有价值的想法来源之一。它能让研究网络自然产生分支，而不是由预先画好的科技树向下展开。

# 三、让玩家主动“合成想法”，而不是等待随机弹窗

可以在研究所中设置一种实体化的设施，例如：

* 研究墙；
* 讨论桌；
* 档案板；
* 黑板；
* 地图与记录柜。

玩家可以把观察记录、NPC证词、计算结果和旧实验日志钉在同一块板上。

系统识别它们之间的关系后，不是直接给出答案，而是生成若干问题：

> 为什么这两台机器只有其中一台结冰？
> 环境温度和空气湿度，哪一个更重要？
> 进气量下降是原因，还是火焰减弱后的结果？
> 艾琳似乎对烟道结构有相关经验。

这样既保留了涌现感，也不会让玩家因为不知道隐藏配方而盲目试错。

每项研究可以拥有多条开启路线。例如同一个“低温润滑”研究可以由以下任意路线出现：

* 观察到发电机启动困难，并发现油脂凝固；
* 与机械师交谈，同时持有一次车辆故障记录；
* 在材料实验中发现液体流速随温度变化；
* 某个工程原型在寒夜现场试验中卡死。

因此它在数据层面仍然是被设计过的研究内容，但在体验上不是固定线性的科技树。

---

# 四、理论研究不应该是“投入聪明居民，等待进度完成”

理论阶段必须要求玩家形成一个**可以被实验推翻的说法**。

一个完整假设至少应包含：

```text
在保持哪些条件不变时，
改变什么因素，
应该导致什么可观察结果；
出现什么结果时，该假设应被否定。
```

例如：

> 如果锅炉熄火是进气口结冰造成的，那么在燃料、炉体、烟道和负载相同时，防止进气口结冰的锅炉应保持更稳定的空气流量和热量输出。

这比“研究进度达到100%，提出假设”更具体。

## 理论页面可以由六个部分组成

| 部分   | 玩家要完成的内容            |
| ---- | ------------------- |
| 已知现象 | 选择哪些记录确实需要解释        |
| 工作假设 | 选择或组合可能的因果解释        |
| 必要假定 | 哪些条件被暂时视为相同或无关      |
| 预测   | 假设成立时会看到什么          |
| 反证条件 | 看到什么便说明假设有问题        |
| 实验方案 | 操纵变量、测量对象、对照条件和运行时间 |

理论不会显示“63%完成”，而是显示具体缺口：

* 尚未提出可以区分两个假设的预测；
* 缺少环境温度记录；
* 燃料湿度可能构成混杂变量；
* 计算结果与假设不一致；
* 当前仪器无法测量需要观察的量。

# 五、计算器的作用应是解决具体问题，而不是生产研究点

机械计算器、研究所人力计算和高教育居民都可以参与，但它们应该提供不同能力。

例如：

* 根据管道直径计算理论空气流量；
* 根据炉体表面积估算散热；
* 比较两组测量是否差异明显；
* 计算实验需要的材料数量和安全范围；
* 检查假设是否违背已有发现；
* 推导一个可观察的预测。

高智力和高教育不应该简单地提高“每天研究点产量”。

更好的影响方式是：

* **智力**：能处理更复杂的因果关系，发现跨领域联系；
* **教育程度**：能使用正式计算、实验方法和专业仪器；
* **领域经验**：能提出特定领域的假设和操作方法；
* **实践技能**：能可靠地搭建、校准和维护装置；
* **怀疑精神**：更容易发现实验漏洞；
* **沟通能力**：更容易让知识在居民之间传播；
* **好奇心**：更容易记录异常现象。

建议至少增加一个“领域知识或经历”维度，否则所有高智力、高教育NPC最终会变得彼此可替代。

# 六、实验不应是“投入材料后进行一次成功率判定”

这是我最建议修改的部分。

自然规律本身不应该因为一次随机数而改变。假设是真是假，应由世界的隐藏因果关系决定。概率应当影响的是玩家能否获得**清晰而可靠的证据**。

可以使用这样的内部逻辑：

```text
实验信息量
= 假设区分力
× 控制变量质量
× 仪器可靠性
× 执行完整度
× 重复程度
```

这些数值可以存在于后台，但不必直接显示。玩家看到的应是具体状态：

* 对照组缺失；
* 两组燃料并非同一批次；
* 温度在实验中发生明显波动；
* 仪器未校准；
* NPC中途离岗；
* 能量供应中断；
* 只运行了一次，无法判断是否为偶发现象；
* 两个假设预测了相同结果，因此此实验无法区分它们。

实验结果分成四类会比较合适。

## 1. 支持假设

观察结果符合预测，并且足以排除主要替代解释。

这并不意味着“永远绝对正确”，而是形成一个带适用条件的发现：

> 在高湿度且环境温度低于某范围时，进气格栅积冰会显著降低锅炉空气流量。

## 2. 反驳假设

实验条件有效，但结果与预测相反。

这不是研究失败，而是排除了一条解释路线。

## 3. 无法判断

可能是实验设计不具区分力，也可能是过程中出现污染、停电、温度变化或仪器损坏。

此时应回到实验方案，而不是完全重做理论。

## 4. 出现异常

主要问题可能得到回答，但又产生新的现象：

* 防冰装置解决了进气问题，却导致烟道冷凝；
* 两组锅炉流量相同，但其中一组仍然熄火；
* 低温不是关键，湿度才是关键；
* 装置在实验室正常，现场暴风雪中失效。

异常应该自动成为新的笔记，并可能产生旁支研究。

# 七、实验装置应使用“功能要求”，不要使用唯一多方块结构

为了利用Minecraft的开放性，实验计划不应给玩家一张必须逐格照抄的建筑蓝图。

系统可以检查装置是否具有必要功能：

```text
变量操纵设备
→ 实验对象
→ 测量设备
→ 数据记录设备

同时还需要：
对照对象
稳定供能
材料供给
环境控制
操作人员
安全设施
```

例如实验计划要求：

> 两个相同燃烧室使用相同批次燃料，在相同负载和相同烟道条件下运行。其中一个进气口受到防冰处理。连续记录空气流量、炉温和燃料消耗。

玩家可以：

* 把装置建在露天；
* 建造低温实验室；
* 利用自然暴风雪；
* 使用不同型号的传感器；
* 用机械记录器或安排NPC人工抄录；
* 建造两个完整锅炉，也可以做缩小的实验炉。

不同方案的成本、稳定性和证据质量不同，但都可以成立。

实验过程中应该有可见现象：

* 管道逐渐积霜；
* 指针开始下降；
* 火焰颜色改变；
* 蒸汽冷凝；
* 机器振动；
* 实验材料开裂；
* NPC发现气味或声音异常。

玩家应当能够站在实验室里，根据装置表现提前猜到结果，而不是等待界面弹出“实验成功”。

# 八、可以存在三类不同实验

你目前规定“实验必须跟在理论之后”，对验证性实验是正确的，但不宜禁止所有前置试验。

## 探索性试验

没有成熟假设，只是主动制造条件、寻找现象。

例如把不同材料放到室外严寒中，观察哪些会破裂。它通常产生想法，但不直接完成研究。

## 验证性实验

必须有明确假设、预测、控制变量和反证条件。

这是确认发现的主要途径。

## 工程测试

它测试的不是自然规律是否成立，而是装置能否满足要求：

* 是否足够可靠；
* 是否容易维护；
* 是否消耗过多能源；
* 是否能由普通居民操作；
* 是否能在暴风雪中连续工作。

把三者分开后，玩家就可以先摆弄机器、偶然发现现象，再进入正式研究，同时又不会破坏你希望存在的“理论—实验”结构。

# 九、不要让迭代上限直接判定“想法不成立”

“连续失败四次，因此该想法永远错误”会产生两个问题。

第一，玩家可能觉得只是连续暗骰失败。
第二，实验失败并不能证明最初的想法毫无价值。

应该区分三种失败。

| 失败类型   | 实际含义      | 下一步          |
| ------ | --------- | ------------ |
| 假设被反驳  | 一个解释错误    | 排除假设，修正理论    |
| 实验无效   | 方法或执行出了问题 | 改进装置、仪器或控制条件 |
| 问题框架崩溃 | 玩家可能问错了问题 | 重新定义问题，产生新想法 |

例如玩家一直研究“低温为什么让锅炉燃料燃烧不充分”，最终发现低温并不是直接原因，真正原因是湿雪堵塞进气口。

此时不是“想法失败”，而是：

> 原始问题把温度当成了原因，但温度只是与积雪同时出现的条件。

这本身就是一个发现。

为了防止玩家无限蛮力尝试，可以设置“研究停滞”，而不是永久失败：

* 团队认为当前证据不足以继续；
* 必须获得新类型的观察；
* 必须换用更好的仪器；
* 必须邀请具有相关领域知识的NPC；
* 必须等待不同环境条件；
* 暂时归档，之后可以重新开启。

真正得到大量高质量反证后，也可以产生一种“否定性发现”：

> 在已测试的温度范围内，单纯加热燃料并不能改善燃烧稳定性。

否定性发现仍然有价值，因为它能阻止城镇浪费资源走错误的工程路线。

# 十、让玩家决定何时接受结论

冬季救援背景中，科研往往伴随紧迫需求。你可以让玩家在证据尚不完全时提前采取行动。

例如一次实验初步支持防冰进气口，但尚未重复验证。玩家有两个选择：

* 继续重复实验，等待更可靠的结论；
* 宣布“暂定结论”，立即投入原型制造。

后者可以更快解决供暖危机，但原型可能存在尚未发现的限制。NPC中的怀疑者可能提出反对，城镇管理者可能要求立即使用。

这样，“科研概率”就从被动暗骰变成了玩家主动承担的不确定性。

结论状态可以使用文字而不是数值：

* 初步迹象；
* 暂定结论；
* 已重复验证；
* 适用范围已确认；
* 存在未解释异常。

---

# 十一、研究必须是团队活动，而不是把NPC变成人形计时器

研究所可以围绕四种活动运转。

## 讨论

NPC提出解释、关联旧知识、分享个人经历。不同背景的人会产生不同假设。

## 计算与整理

居民处理测量记录、检查理论一致性、绘制图表、计算设备规格。

## 实验值班

居民加料、保持温度、记录数据、校准设备、发现故障。

## 评审与教学

实验完成后，团队讨论结果；已经掌握知识的居民将知识教给其他居民。

这里可以引入“个人知识”和“城镇公共知识”的区别。

一名新来的难民工程师可能掌握某种技术，但在他把知识写入档案、完成教学或参与标准化之前，这仍然只是他的个人知识。若他离开、死亡或长期无法工作，城镇就会失去部分能力。

实验日志、研究论文、工程图纸和操作手册，可以把个人经验转化为制度化知识。

这会使研究所、学校、档案室和NPC教育系统自然连接起来。

# 十二、工程原型阶段非常值得加入

科学研究和工程开发解决的是两个不同问题：

> 科学研究问：“它为什么会这样？”
> 工程开发问：“怎样利用这个规律，在现实限制下稳定工作？”

完成“发现”后，最好不要立刻解锁最终配方，而是先解锁一种**设计原则**。

例如发现：

> 进气口积冰会降低燃烧稳定性。

这项发现可以提供：

* 防冰；
* 排水；
* 进气加热；
* 增大有效截面；
* 过滤湿雪；
* 监测空气流量。

但它不直接决定最终设备应该长什么样。

工程流程可以是：

```text
提出需求
→ 选择设计方案
→ 制造一次性原型
→ 实验室测试
→ 真实环境现场试验
→ 记录故障
→ 修改设计
→ 标准化
```

## 1. 提出需求

城镇不是抽象地要求“解锁高级锅炉”，而是提出具体指标：

* 能改装现有锅炉；
* 在暴风雪中持续运行；
* 电力消耗不能太高；
* 普通居民可以维护；
* 不能使用稀缺合金。

## 2. 设计取舍

玩家选择不同方案：

* 电加热进气口：可靠，但消耗电力；
* 机械刮冰：低耗能，但需要维护；
* 大型遮雪罩：便宜，但占空间；
* 热废气回流：节能，但可能产生冷凝和烟气风险。

没有唯一正确答案，而是不同的城镇和资源条件适合不同设计。

## 3. 一次性原型

原型可以是玩家自由搭建的模块化机器，不要求已经拥有标准配方。

它可能昂贵、笨重、不稳定，只能由高技能NPC操作。

## 4. 现场试验

实验室通过不代表工程成功。原型必须在真实庇护所、矿场、运输队或暴风雪中运行。

现场试验可能发现：

* 供电能力不足；
* 普通居民不会维护；
* 雪水进入电气结构；
* 某种材料在反复冷热循环中开裂；
* 装置有效，但噪音导致居民无法休息。

这些故障报告又会产生新的想法和研究。

## 5. 标准化

标准化完成后才真正解锁：

* 稳定配方；
* 批量制造；
* 操作手册；
* NPC自动维护；
* 更低故障率；
* 普通工人培训。

于是“发现”和“科技解锁”之间就有了真正的工程过程。

# 十三、一个完整实例：风雪中的炉火

## 观察阶段

玩家获得以下记录：

* 暴风雪夜，东侧锅炉热量输出下降；
* 炉火在打开炉门后短暂恢复；
* 进气格栅上有明显积冰；
* 相同燃料在室内小炉中燃烧正常；
* 锅炉工NPC说：“以前湿雪天也发生过，但我一直以为是煤受潮。”

系统不显示任何解锁奖励，只产生想法：

> **风雪中的炉火为什么会窒息？**

## 理论阶段

讨论后出现三个工作假设：

* 燃料温度太低，无法充分燃烧；
* 进气格栅积冰，减少空气流量；
* 烟囱在强风下发生倒灌。

机械师倾向于进气问题，锅炉工怀疑燃料，受教育较高的居民提出需要区分空气流量和烟道压力。

玩家选择研究“进气结冰假设”。

团队提出预测：

> 若积冰是原因，则防止进气格栅结冰后，空气流量和热量输出应保持稳定。

## 实验计划

玩家需要准备：

* 两个相同小型燃烧室；
* 同批燃料；
* 相同烟道长度；
* 相同热负载；
* 空气流量计；
* 炉温计；
* 一个经过防冰处理的进气口；
* 一个未经处理的对照进气口；
* 低温环境；
* 连续记录人员或机械记录器。

## 世界实验

玩家可以在室外暴风雪中运行，也可以建立低温实验室。

实验进行时，未经处理的格栅逐渐结冰，流量计指针下降，火焰开始变暗；防冰组保持稳定。

但是如果实验中一组燃料受潮，日志会记录：

> “两组燃料状态不同，本次结果无法单独判断进气作用。”

这次实验是无效实验，而不是随机研究失败。

## 发现

经过有效重复后得到：

> 在湿冷环境下，进气结构积冰会降低燃烧空气流量，并造成锅炉输出不稳定。

同时出现新问题：

> 防冰加热装置是否会消耗过多电力？
> 烟道中的水汽会不会在其他位置重新凝结？

## 工程阶段

玩家设计三种原型：

* 电热格栅；
* 机械除冰格栅；
* 带排水结构的遮雪进气罩。

经过现场试验，其中一种成为城镇的标准冬季锅炉进气组件。另一种原型虽然失败，却产生了“烟道冷凝”的新研究想法。

# 十四、研究界面应展示“研究状态”，而不是进度百分比

一本研究笔记可以包含六个页面：

1. **记录板**：现象、NPC证词、事故日志、旧实验结果；
2. **问题页**：当前想法、已知与未知；
3. **理论页**：假设、假定、预测、反证条件；
4. **实验计划**：变量、对照、仪器、材料、人员和安全要求；
5. **实验日志**：运行曲线、环境变化、设备故障、NPC备注；
6. **结论页**：支持与反对证据、适用条件、未解决异常。

它应该不断告诉玩家：

* “缺少什么”；
* “什么互相矛盾”；
* “哪名居民可能有帮助”；
* “这个实验能够排除什么”；
* “当前结论为什么还不可靠”。

而不是只告诉玩家：

> 理论研究：72%。

# 十五、底层最好是一张“证据与知识图谱”

系统存档的核心不应是：

```text
research_progress = 72
```

而应该是：

```text
观察A 支持 假设1
观察B 反驳 假设1
发现C 可用于 测量技术D
实验E 产生 异常F
NPC甲 掌握 知识C
城镇档案 已记录 知识C
原型G 依赖 发现C和材料知识H
```

研究项目只是这张图谱上的一个临时工作区域。

这样自然会形成：

* 研究之间的交叉；
* 旧发现被新问题重新利用；
* 实验异常产生旁支；
* 工程故障返回基础研究；
* NPC知识传播改变可用路线；
* 同一个问题存在多种开启方式；
* 多项发现共同支持一种工程技术。

# 十六、适合第一版实现的范围

第一版不必尝试完全程序生成科学内容。更可靠的方式是采用“手工研究谜题 + 通用研究框架”的混合设计。

每个研究只需手工定义：

* 多条想法触发路线；
* 一个不泄露答案的问题描述；
* 两到四个合理假设；
* 每个假设的预测；
* 一到两种实验功能需求；
* 支持、反驳、无效和异常结果；
* 最终发现及适用条件；
* 会产生的新问题；
* 可进入的工程应用。

通用系统负责：

* 笔记和关系；
* NPC讨论；
* 理论画布；
* 实验装置检测；
* 控制变量判断；
* 运行日志；
* 证据质量；
* 原型和现场试验；
* 知识传播。

这种设计既可控，又能让玩家感到研究是自己从世界中推导出来的。

最终的核心体验不应是：

> 我投入了三百研究点，所以获得了一台新机器。

而应当是：

> 我们发现了一个反复出现却解释不了的现象；不同居民提出了不同解释；我搭建了一个能够区分这些解释的装置；第一次实验因为供能波动而作废；第二次结果推翻了原假设；第三次出现的新现象让我们重新定义了问题；最后我们不只知道该怎样解决故障，还理解了它为什么发生，并把这种理解变成了一套全城都能制造、操作和维护的技术。

我觉得你的想法非常牛逼。底层最好是一张“证据与知识图谱”这个我尤其是觉得非常重要。我认为我们光靠人力去设计每一个研究的所有途径是不可能的。我们应该做的是一种底层数据结构驱动的工作，这也非常具有扩展性。但我对这个可能的结构是如何自然形成的东西，以及它本身更确切的数学/算法上的定义还是不确定。包括研究的流程本身，我认为你的思路是对的，它只会是底层知识图谱的一个临时工作区域探索，但是玩家在研究过程中，我们要生成出一种线性的流程呈现给玩家。毕竟我们最终要设计成代码，还要反馈给玩家让玩家理解。


你现在抓到的是这套系统真正的“骨架”：

> **研究项目不应该是底层数据。研究项目应该是从当前知识状态中，临时编译出来的一段探索流程。**

更准确地说，底层不只是普通“知识图谱”，而应该是：

> **类型化、带上下文、带来源、允许相互矛盾的认识论超图**
> ＋
> **隐藏的世界因果模型**
> ＋
> **一条按时间排列的研究事件日志**
> ＋
> **把图编译成玩家当前研究步骤的工作流编译器**

整体关系可以表示为：

```text
隐藏世界因果模型 M
        │
        │ 产生真实现象
        ▼
玩家 / NPC / 仪器观察
        │
        ▼
研究事件日志 L：先发生了什么，后发生了什么
        │
        │ Fold / Reduce
        ▼
城镇认识图 K：目前知道什么，为什么相信，存在什么争议
        │
        │ 发现知识缺口、矛盾、异常
        ▼
想法与研究问题 Q
        │
        │ 局部投影
        ▼
研究工作区 R
        │
        │ 工作流编译
        ▼
当前呈现给玩家的线性步骤
        │
        │ 玩家行动产生新事件
        └──────────────────↺
```

这里最重要的是：

* **图负责语义关系**
* **事件日志负责线性历史**
* **工作流编译器负责下一步引导**
* **隐藏世界模型负责实验真实结果**

这样，非线性知识与线性游戏体验并不矛盾。

# 一、不要让“一项研究”成为固定的数据对象

传统科技树可能这样定义：

```json
{
  "research": "heated_air_intake",
  "prerequisites": ["basic_thermodynamics"],
  "theory_points": 300,
  "experiment_items": ["iron_plate", "heater"],
  "result": "heated_air_intake_recipe"
}
```

这种结构的问题是，一切路线都必须事先写好。

你真正需要定义的不是“研究项目”，而是下面这些底层内容：

| 人工定义       | 系统运行时生成 |
| ---------- | ------- |
| 世界变量与概念    | 观察记录    |
| 世界因果机制     | 想法      |
| 可观察方式      | 研究问题    |
| 可干预方式      | 候选假设    |
| 通用推理规则     | 预测      |
| 仪器和机器能力    | 实验需求    |
| 语言模板       | 研究笔记文本  |
| 技术解锁所需知识条件 | 实际研究路线  |

于是，“风雪中的炉火为什么会熄灭”并不是一个预先注册的研究ID。

它可能是运行时生成的一个研究工作区：

```text
问题：
为什么东侧锅炉只在湿雪暴风中出现燃烧不稳定？

相关观察：
- 炉温下降
- 进气口积冰
- 打开炉门后短暂恢复
- 相同燃料在室内炉中正常燃烧

候选解释：
- 燃料受潮
- 进气受阻
- 烟囱倒灌
```

这个工作区完成或关闭之后可以消失，但其中产生的观察、假设、实验记录和发现会永久留在知识图中。

# 二、底层不是普通图，而是“主张—证据图”

最容易犯的错误是直接储存：

```text
积冰 --导致--> 空气流量下降
```

这看起来像知识图谱，但它无法表达：

* 这是谁提出的；
* 它是观察、假设还是已确认发现；
* 它只在什么条件下成立；
* 有哪些证据支持；
* 有哪些实验反驳；
* 这个结论是不是从其他结论推导出来的；
* 不同NPC是否相信它。

因此，“事实”不应该直接作为边，而应该被实体化为一个**主张节点 Claim**。

例如：

```text
Claim H17
────────────────────────────────
谓词：DECREASES

原因：
进气口积冰量

结果：
空气流量

作用范围：
环境温度 < 0°C
空气中存在较高湿度
对象属于开放式锅炉进气结构

认识状态：
假设
```

然后，证据再连接到这个主张：

```text
实验记录 E42
    └── 支持 ──> Claim H17

锅炉工证词 E51
    └── 弱支持 ──> Claim H17

实验记录 E63
    └── 反驳 ──> Claim H17
```

这才允许系统表示争议与修正。

# 三、一个较严格的数学定义

可以先定义一套静态语义模式：

[
\Sigma=(T,P,S)
]

其中：

* (T)：类型集合，例如锅炉、燃料、温度、流量、居民、仪器；
* (P)：谓词集合，例如增加、减少、导致、测量、依赖、相似；
* (S)：规则与机制模式，例如“阻塞降低流量”“温度可能导致相变”。

玩家或城镇当前的知识状态可以定义为：

[
K_t=(V,C,J)
]

其中：

* (V)：实体、概念、实验、数据集、程序等节点；
* (C)：主张节点；
* (J)：依据或论证关系。

一个主张可以表示为：

[
c=\langle p,\vec{a},\kappa\rangle
]

其中：

* (p) 是谓词；
* (\vec{a}) 是带角色的参数；
* (\kappa) 是上下文和适用范围。

例如：

```text
p = DECREASES

arguments:
  cause = intake.ice_mass
  effect = boiler.airflow

scope:
  ambient_temperature < 0
  humidity > 0.75
```

一个论证关系可以表示为：

[
j=\langle Premises,Conclusion,Rule,Polarity,Quality,Provenance\rangle
]

其中：

* `Premises`：哪些记录或主张是前提；
* `Conclusion`：它支持或反驳哪个主张；
* `Rule`：使用了什么推理规则；
* `Polarity`：支持还是反驳；
* `Quality`：证据质量；
* `Provenance`：来源、时间、NPC、仪器、实验批次。

因为一个推理可能同时需要多个前提，所以它本质上是一个**超边**：

```text
观察A ─┐
观察B ─┼── 通过推理规则R ──> 假设H
计算C ─┘
```

代码里不需要真的使用超图数据库。把“论证”作为对象，其中存放一个前提列表即可。

# 四、必须区分“世界真相”和“玩家认知”

底层实际上需要两个不同的模型。

## 1. 隐藏世界因果模型

它决定Minecraft世界实际发生什么。

可以抽象为：

[
x_{t+1}=F(x_t,i_t,\epsilon_t)
]

其中：

* (x_t)：当前世界状态；
* (i_t)：玩家或机器的干预；
* (\epsilon_t)：明确存在的噪声或随机扰动；
* (F)：世界机制。

例如：

```text
低温 + 空气水分
    → 进气口积冰增加

积冰增加
    → 有效进气面积减少

有效面积减少
    → 空气流量降低

空气流量降低
    → 燃烧不稳定
```

这些机制可以直接连接现有游戏模拟代码。

## 2. 玩家认识图

玩家一开始不知道上述因果链。

玩家认识图中可能同时存在：

```text
假设A：低温煤炭本身难以燃烧
假设B：湿煤导致燃烧不完全
假设C：进气口积冰降低空气流量
假设D：暴风导致烟囱倒灌
```

候选假设生成器**不能直接读取隐藏世界真相**，否则它会泄露答案。

隐藏模型只负责：

* 实验实际会发生什么；
* 玩家改变变量之后世界如何响应；
* 仪器读数是什么；
* 未控制因素如何干扰结果。

玩家的假设只能来自：

* 已有知识；
* 通用机制模式；
* NPC经验；
* 当前观察；
* 类比和推理。

这是整个系统公平性的关键。

---

# 五、知识图不会“自己神奇地形成”，它需要语义接口

这里必须明确一个现实边界：

> 系统无法从任意Minecraft机器代码里自动理解“这段代码代表空气流量”“这个变量是湿度”“这个状态可以成为实验变量”。

每个世界系统需要提供一层**研究语义接口**。

例如一个锅炉组件要注册：

```text
可观察变量：
- 炉温
- 燃料消耗速度
- 空气流量
- 烟道压力
- 进气口积冰量

可干预变量：
- 燃料种类
- 燃料湿度
- 进气加热
- 烟囱结构
- 炉门开启状态

隐藏机制：
- 空气流量影响燃烧
- 湿度与低温导致积冰
- 积冰降低有效进气面积
```

一个温度计则注册：

```text
能力：
MEASURE(temperature)

范围：
-50°C ~ 100°C

精度：
±1°C

采样周期：
20 ticks
```

作者工作量从：

> 为每项研究写十几条触发路线、实验路线和失败路线

变成：

> 为每种世界机制定义变量、可观察性、可干预性和因果语义

这是完全不同的复杂度。

一个机制定义完成之后，可以参与许多研究：

* 锅炉积冰；
* 管道堵塞；
* 门锁冻结；
* 水泵失效；
* 风力机叶片积冰；
* 食物冷冻保存；
* 人体冻伤。

# 六、“想法”可以严格定义成知识图中的一个缺口

你最初提出的“想法”非常适合定义成：

> **一个由若干观察锚定、但尚未被当前知识解释的查询。**

形式上可以写成：

[
Idea=\langle Q,A,G,S\rangle
]

其中：

* (Q)：一个尚未回答的问题；
* (A)：产生这个问题的锚点观察；
* (G)：知识缺口类型；
* (S)：显著性信息。

例如：

```text
Q：
什么因素导致了锅炉输出下降？

A：
- 暴风雪时输出下降
- 平静天气正常
- 进气口存在积冰
- 开炉门后暂时恢复

G：
未解释的条件性异常

S：
- 多次出现
- 影响城镇供暖
- 有多名NPC注意到
```

所以，想法不是“收集五点之后解锁”，而是图中出现了某种结构性缺口。

# 七、通过“图模式规则”自动产生想法

系统可以定义一组通用的图模式，而不是每项研究单独定义触发。

## 1. 对比异常规则

```text
同一对象
在上下文C1中出现结果Y1
在上下文C2中出现结果Y2
Y1与Y2明显不同
C1和C2之间存在少量关键差异
当前没有已接受解释

→ 产生问题：
这些上下文差异中的什么因素影响了Y？
```

伪规则：

```text
Observation(subject, variable, value1, context1)
Observation(subject, variable, value2, context2)
Incompatible(value1, value2)
ContextDifference(context1, context2, factor)
NoAcceptedExplanation(variable, factor)

=> Idea: Does factor influence variable?
```

## 2. 重复共现规则

```text
现象A与现象B多次同时出现
但当前知识图中没有二者之间的解释关系

→ 产生问题：
A与B是否有关？
```

这只能产生想法，不能产生因果发现。

## 3. 预测偏差规则

```text
已有理论预测结果Y
实际观察结果明显偏离Y

→ 产生问题：
当前模型漏掉了什么因素？
```

## 4. 证词冲突规则

```text
NPC甲认为原因是A
NPC乙认为原因是B
二者预测不同结果

→ 产生争议型研究问题
```

## 5. 类比迁移规则

```text
已知：
冰会堵塞水管并降低流量

新观察：
锅炉进气口积冰且火焰变弱

→ 产生类比问题：
进气口积冰是否同样降低了空气流量？
```

## 6. 目标缺口规则

```text
城镇有一个必须满足的需求
现有设备无法满足
当前知识中存在可能相关的发现

→ 产生工程型研究问题
```

例如：

```text
需求：
锅炉必须在暴风雪中连续运行12小时

已知：
加热可以融化积冰
已知：
积冰降低流量

→ 工程想法：
能否持续防止进气结构结冰？
```

# 八、图模式规则本质上是一种“图重写系统”

每条规则可以定义为：

```text
Rule:
  匹配模式 Pattern
  条件 Guard
  生成内容 Emit
  去重键 DeduplicationKey
  文本解释 Explanation
```

数学上，可以理解为找到一个映射：

[
\mu:P\rightarrow K
]

其中 (P) 是规则要求的模式，(K) 是当前知识图。

当匹配成功时，系统向图中加入新的节点和关系：

[
K\rightarrow K\cup{Idea(Q)}
]

例如：

```text
规则：
CONTRASTIVE_ANOMALY

匹配：
- 同一锅炉
- 两次不同输出
- 两次上下文不同
- 没有已有解释

生成：
- 想法节点
- 想法与两次观察的来源关系
- 一段说明“为什么这个想法出现”
```

这样每个想法都有完整的解释路径。

玩家看到：

> “这个问题出现，是因为东侧锅炉在三次湿雪天气中输出下降，但在低温干燥天气中表现正常。”

这句话可以直接根据图匹配结果生成，而不需要手写。

# 九、用事件溯源同时解决“图”和“线性流程”

这是我认为最适合你这个系统的架构。

不要只保存当前图，还要保存一条只追加、不修改的事件日志：

```text
ResearchEvent 001
玩家记录：东侧锅炉炉温异常下降

ResearchEvent 002
NPC罗伯特报告：进气格栅上有积冰

ResearchEvent 003
系统识别：两次记录可能有关

ResearchEvent 004
研究团队提出：进气受阻假设

ResearchEvent 005
计算完成：正常流量应为某范围

ResearchEvent 006
实验计划建立

ResearchEvent 007
实验因燃料湿度不一致而无效

ResearchEvent 008
实验计划修改

ResearchEvent 009
第二次实验支持进气受阻假设
```

令事件日志为：

[
L_t=(e_1,e_2,\dots,e_t)
]

当前知识图是事件日志折叠后的结果：

[
K_t=Fold(Apply,K_0,L_t)
]

这带来几个巨大好处。

### 第一，研究历史天然是线性的

玩家的研究笔记可以直接按照事件顺序显示。

### 第二，图可以反复重建

便于存档迁移、调试和修复。

### 第三，每个结论都有来源

点击发现，可以沿事件和论证关系回溯：

```text
发现
→ 支持实验
→ 实验数据
→ 实验装置
→ 原始想法
→ 最初观察
```

### 第四，旧理论被推翻时不必删除历史

它仍然存在于事件日志中，只是当前状态变成：

```text
已反驳
已被更准确理论取代
仅在较窄范围内成立
```

因此：

> **事件日志给玩家提供一条故事线，知识图则提供当前认知结构。**

# 十、研究工作区是知识图的局部投影

一项研究可以定义为：

[
R=\langle Q,A,H,E,P,\Omega\rangle
]

其中：

* (Q)：当前问题；
* (A)：相关观察锚点；
* (H)：候选假设集合；
* (E)：已收集证据；
* (P)：实验计划；
* (\Omega)：尚未完成的研究义务。

研究工作区并不复制整个知识图，而是提取与问题有关的局部子图：

```text
当前问题
  ├── 直接相关观察
  ├── 候选原因
  ├── 已知背景规律
  ├── NPC证词
  ├── 计算与推导
  ├── 当前实验
  └── 支持和反对证据
```

玩家不需要面对完整知识网络。

界面可以只显示：

* 当前问题；
* 三到五条关键观察；
* 当前候选解释；
* 当前最关键的缺口；
* 当前可以采取的行动；
* 已完成研究历史。

其余知识折叠成：

> “引用了3项旧发现”
> “存在2条未解决反证”
> “艾琳掌握可能相关的材料知识”

# 十一、假设生成应该使用“溯因搜索”

假设生成的目标不是寻找一定正确的答案，而是寻找：

> 哪些小型因果结构能够解释当前观察？

这属于溯因推理。

形式上可以寻找若干个候选 (H)，使得：

[
K\cup H\models A
]

其中：

* (K) 是当前已有知识；
* (A) 是需要解释的观察；
* (H) 是补充进去之后可以解释观察的假设。

但系统不应无限组合所有节点，而应从一组**机制模式**中实例化。

例如通用机制模式：

```text
阻塞物增加
→ 有效截面积下降
→ 流量下降

温度下降
→ 液体黏度增加
→ 机械阻力增加

材料含水量增加
→ 燃烧效率下降

外部压力变化
→ 流动方向变化
```

锅炉研究中，系统可能实例化出：

```text
积冰
→ 进气截面积下降
→ 空气流量下降
→ 炉温下降
```

或者：

```text
燃料受潮
→ 燃烧效率下降
→ 炉温下降
```

候选生成器只使用：

* 研究团队已知概念；
* 团队掌握的机制模式；
* 当前上下文中变化的变量；
* NPC提出的说法；
* 与旧发现相似的结构。

它不读取真实答案。

---

# 十二、限制假设搜索，避免组合爆炸

任意图上的解释搜索会迅速爆炸，所以需要明确限制。

建议采用：

```text
最大机制链长度：2～4
每轮候选假设：3～6个
只搜索当前问题附近的局部图
只使用类型匹配的机制
优先使用当前观察中实际变化的变量
优先使用研究团队已知的概念
优先使用具有来源解释的候选
```

候选假设可以按照以下因素排序：

[
Score(H)=
Coverage(H)
-\lambda Complexity(H)
+Prior(H)
+Relevance(H)
]

其中：

* `Coverage`：能解释多少观察；
* `Complexity`：需要引入多少新假定；
* `Prior`：团队是否有相关知识或经验；
* `Relevance`：是否与当前环境变化相符。

这个分数可以只用于排序，不应该显示成“假设正确率”。

# 十三、理论研究应该产生“研究义务”

理论阶段不要定义为：

```text
理论进度 = 0 / 100
```

而应定义为一组当前尚未满足的结构化义务。

例如：

```text
尚未明确需要解释的现象
尚未把“燃烧变差”转换成可测量变量
只有一个解释，缺乏替代假设
当前两个假设预测了相同结果
缺少可以区分假设的实验
缺少必要的计算参数
尚未识别可能的混杂因素
```

一个研究义务可以定义为：

```text
ResearchObligation
────────────────────────
类型：
DERIVE_DISCRIMINATING_PREDICTION

目标：
区分“燃料受潮”和“进气结冰”

完成条件：
存在一个实验条件，使两个假设预测不同结果

可能行动：
- 研究空气流量测量
- 咨询锅炉工
- 使用机械计算器
- 查阅旧实验记录
```

计算器和高教育NPC的作用，就是完成这些具体义务。

例如：

```text
当前缺口：
不知道在正常烟道压力下，理论空气流量应是多少。

可执行任务：
- 机械计算器：根据管径和压力计算
- 高教育居民：进行人工估算
- 搭建标定实验：直接测量
```

时间和人力负责执行这些行为，但不是抽象地生成研究点。

---

# 十四、实验计划可以从候选假设自动生成

假设集合为：

[
H={h_1,h_2,\dots,h_n}
]

一个实验动作 (a) 包含：

[
a=\langle do(X=x),Controls,Measures,Duration\rangle
]

也就是：

* 主动改变什么；
* 保持什么不变；
* 测量什么；
* 持续多久。

每个假设都应该能够对实验产生预测：

[
P(o\mid h,a)
]

例如：

| 实验操作     | 燃料受潮假设 | 进气结冰假设 | 烟囱倒灌假设 |
| -------- | -----: | -----: | -----: |
| 加热进气口    |  无明显改善 |   明显改善 |  无明显改善 |
| 烘干燃料     |   明显改善 |  无明显改善 |  无明显改善 |
| 改变烟囱挡风结构 |  无明显改善 |  无明显改善 |   明显改善 |

系统要寻找的是：

> 哪个可执行实验能够让不同假设产生不同预测？

理论上可以使用信息增益：

[
a^*=\arg\max_a
\left[
IG(a;H)-\lambda Cost(a)-\mu Risk(a)
\right]
]

但第一版不需要完整概率模型。

只需计算：

* 这个实验能否把候选假设分成不同结果组；
* 它能区分多少对假设；
* 当前城镇能否完成；
* 成本和危险是否可接受。

---

# 十五、控制变量可以从“竞争假设”中自动得到

这是数据驱动实验设计中很关键的一点。

假设：

```text
H1：燃料湿度导致炉温下降
H2：进气结冰导致炉温下降
H3：烟囱压力导致炉温下降
```

玩家要验证H2。

那么H1和H3本身就告诉系统应该控制什么：

```text
保持燃料湿度一致
保持烟囱结构一致
记录烟道压力
保持燃料投入速度一致
保持锅炉负载一致
```

换言之：

> **竞争假设就是控制变量需求的来源。**

实验设计不需要作者预先写：

```text
这个实验必须控制燃料湿度、烟道压力、锅炉负载……
```

而是根据当前候选因果模型动态推导。

一般算法可以是：

1. 确定要主动改变的变量 (X)；
2. 确定要观察的结果 (Y)；
3. 找到其他假设中同样可能影响 (Y) 的变量；
4. 将这些变量加入控制或测量列表；
5. 检查是否存在共同原因；
6. 检查目前仪器能否观察这些变量。

# 十六、实验装置应当是一个“能力约束问题”

实验计划不应该要求唯一多方块结构，而应该生成一组能力需求。

例如：

```text
实验需求：
- 能主动加热一个进气口
- 能测量空气流量
- 能测量炉温
- 能让两个燃烧室使用相同燃料
- 能保持相同负载
- 能持续记录六小时
- 能提供低温高湿环境
```

形式上：

[
RequiredCapabilities=
{
Manipulate(X),
Measure(Y),
Hold(C_1),
Hold(C_2),
Log(T),
Replicate(N)
}
]

世界中的方块、NPC和房间提供能力：

```text
温度计：
MEASURE(temperature)

机械流量计：
MEASURE(airflow)

电热器：
MANIPULATE(surface_temperature)

密封燃料仓：
HOLD(fuel_moisture)

低温实验室：
HOLD(ambient_temperature)
HOLD(humidity)

研究员：
LOG_MANUALLY(variable, interval)
```

玩家搭建的实验装置只需满足这些约束。

本质上它是一个约束满足问题：

[
Capabilities(Apparatus)\supseteq RequiredCapabilities
]

这样玩家仍然拥有Minecraft式自由搭建。

# 十七、实验结果不是“成功/失败”，而是新的图结构

一次实验运行应该生成：

```text
ExperimentRun
────────────────────────
实验计划
实际操作轨迹
能量供应轨迹
材料供应轨迹
环境变化
仪器读数
NPC操作日志
故障事件
```

然后验证器判断：

```text
干预是否真的生效
控制变量是否保持稳定
仪器是否在有效范围
数据是否有缺失
两组实验是否可比较
结果是否符合某个假设预测
```

最后增加证据关系：

```text
Run #2
  ├── 强支持 H2
  ├── 反驳 H1
  ├── 对H3无区分力
  └── 产生异常：烟道冷凝增加
```

注意，同一个实验不一定对所有假设都有判断力。

可能出现：

```text
支持H2
但不能排除H3
```

或者：

```text
反驳H1
但无法判断H2与H3
```

这会自然生成下一项研究义务。

# 十八、使用论证结构作为主体，概率作为辅助

系统内部可以给证据记录：

* 有效性；
* 可靠性；
* 区分力；
* 独立性；
* 来源质量。

如果需要，可以进行贝叶斯式更新：

[
\log Odds(H\mid E)
==================

\log Odds(H)
+
\sum_i
\log
\frac{P(E_i\mid H)}
{P(E_i\mid\neg H)}
]

但是不建议用这个概率直接决定：

> 研究进度达到100%，发现完成。

概率更适合：

* 排序候选假设；
* 决定NPC更倾向于支持什么；
* 估计是否值得继续实验；
* 给研究团队生成建议。

真正的发现完成条件应是结构化的。

例如一项因果发现要求：

```text
至少有一次有效的区分性实验
主要竞争假设已经得到处理
不存在未解决的严重控制问题
至少完成一次重复验证
适用范围已经明确
```

一项工程结论则要求：

```text
原型满足性能要求
通过指定环境测试
维护要求可接受
普通居民能够操作
没有未解决的严重安全故障
```

# 十九、线性研究流程不是预先存储的，而是实时编译的

这是回答你“怎样把图呈现成线性流程”的核心。

系统每次图发生变化后，都重新生成当前未满足的研究义务：

```text
Compile(Inquiry, KnowledgeGraph, TownCapabilities)
    → ObligationGraph
```

这些义务之间有依赖关系：

```text
明确问题
    ↓
提出候选假设
    ↓
推导可区分预测
    ↓
确定控制变量
    ↓
准备实验能力
    ↓
运行实验
    ↓
解释结果
    ↓
处理剩余竞争解释
    ↓
形成发现
```

义务本身构成一个小型有向无环图。

工作流编译器执行：

```text
1. 生成所有当前未满足义务
2. 建立义务依赖关系
3. 找到前置条件已经完成的义务
4. 排除当前无法执行的义务
5. 按紧迫性、成本、玩家选择排序
6. 向玩家呈现一个主步骤和少量可选步骤
```

伪代码：

```java
List<Obligation> compile(Inquiry inquiry, KnowledgeGraph graph) {
    List<Obligation> all = obligationRules.stream()
        .flatMap(rule -> rule.generate(inquiry, graph))
        .filter(obligation -> !obligation.isSatisfied(graph))
        .toList();

    DependencyGraph dependencyGraph =
        buildDependencies(all);

    return dependencyGraph.frontier().stream()
        .filter(obligation -> obligation.isCurrentlyFeasible(graph))
        .sorted(byPriorityAndPlayerPreference())
        .toList();
}
```

玩家看到的“当前阶段”只是最前方义务的分类：

```text
当前缺少问题定义
→ 想法阶段

当前缺少可检验假设
→ 理论阶段

当前缺少区分性实验
→ 实验设计阶段

实验已经准备好
→ 实验阶段

数据存在但尚未解释
→ 分析阶段

竞争假设仍未排除
→ 修正阶段

所有接受条件满足
→ 发现阶段
```

因此不要把：

```text
stage = THEORY
```

作为真正数据。

更合理的是：

```text
stage = classify(currentFrontierObligation)
```

阶段是计算结果，不是底层真相。

# 二十、为什么这仍然会给玩家一种清楚的线性体验

因为玩家实际需要的不是一条永远不变的线，而是：

> 我目前为什么卡住，以及下一步可以做什么。

研究笔记可以显示：

```text
第1轮：提出问题
第2轮：形成两个解释
第3轮：发现当前实验无法区分两个解释
第4轮：加入空气流量测量
第5轮：第一次实验因燃料湿度变化而作废
第6轮：修改燃料供应结构
第7轮：实验反驳燃料受潮假设
第8轮：重复实验支持进气结冰假设
第9轮：形成暂定发现
```

这个历史是严格线性的，因为事件发生的时间天然是线性的。

与此同时，当前页面可以显示：

```text
当前工作：
确认这个规律是否也适用于大型锅炉

为什么：
现有证据只来自小型实验炉

可执行方式：
- 在东侧锅炉进行现场测试
- 建造第二个大型对照锅炉
- 收集其他城镇锅炉记录
```

这比“研究进度84%”更清楚。

# 二十一、NPC系统可以直接映射成图搜索能力

NPC不应只是提供研究速度加成。

每名NPC可以拥有：

```text
已知主张集合
可理解概念集合
可使用推理规则集合
领域经验
观察能力
计算能力
怀疑标准
工作记忆和搜索预算
```

不一定要为每个NPC复制整个图。实现上可以使用：

```text
KnownBy(NPC, Claim)
UnderstoodBy(NPC, Concept)
CanApply(NPC, Rule)
```

NPC属性可以映射成算法能力：

| NPC属性 | 算法影响                   |
| ----- | ---------------------- |
| 智力    | 图搜索深度、同时考虑的变量数量、候选假设数量 |
| 教育    | 可使用的正式推理规则、统计方法和测量概念   |
| 领域经验  | 特定机制模式、异常识别、候选假设先验     |
| 实践技能  | 仪器校准、实验执行、设备故障识别       |
| 怀疑精神  | 更容易生成替代假设和控制变量要求       |
| 沟通能力  | 知识传播速度和表达损失            |
| 好奇心   | 记录异常现象和产生想法的概率         |

例如一个老锅炉工可能没有形式教育，但拥有：

```text
火焰颜色变化 → 空气供应异常
烟囱低鸣 → 可能存在倒灌
炉门打开后恢复 → 可能缺乏进气
```

一个学者可能知道：

```text
必须区分燃料湿度、空气流量和烟道压力
需要对照组
需要计算预期流量
```

两者合作才会形成完整实验。

研究团队的能力等于：

> 团队成员所掌握概念、规则、经验与实验能力的组合。

# 二十二、知识传播也可以直接作用于图

NPC说出的不是“研究点”，而是带来源的主张。

例如：

```text
Claim T17：
“湿雪天气中锅炉更容易熄火。”

来源：
NPC罗伯特的经验

证据类型：
个人回忆

可靠性问题：
- 没有仪器记录
- 可能混淆低温与湿度
- 覆盖多个冬季
```

当另一个NPC听到之后：

```text
KnownBy(艾琳, T17)
```

但并不代表：

```text
AcceptedBy(艾琳, T17)
```

知识可以有多个状态：

```text
听说过
理解
相信
能够应用
能够教授
已记录进城镇档案
```

研究所和学校的作用，就是把零散个人知识转换成可追踪、可复制的公共知识。

# 二十三、技术解锁也不应该依赖“研究ID”

传统方式：

```text
完成 research_heated_intake
→ 解锁 heated_intake_recipe
```

数据驱动方式应该是：

```text
当知识图满足某个模式时
→ 允许进入某种工程设计空间
```

例如：

```text
UnlockRequirement:
  Accepted(
    DECREASES(
      intake_icing,
      airflow
    )
  )

  AND Accepted(
    INCREASES(
      surface_heating,
      ice_melting
    )
  )

  AND PrototypeStandardized(
    heated_air_intake
  )
```

于是，玩家可以通过完全不同的研究路线满足这些知识条件。

技术本身依赖的是：

> 城镇已经掌握了哪些规律和程序。

而不是：

> 玩家是否勾选了某个研究节点。

这会极大增强扩展性。

# 二十四、工程原型可以复用同一套架构

科学研究中的核心主张是：

```text
X在条件C下导致Y
```

工程开发中的核心主张是：

```text
设计D在条件C下满足需求R
```

因此工程研究不需要另一套完全独立系统。

工程问题可以表示为：

```text
Question:
存在什么设计D，使其满足：

- 暴风雪中保持空气流量
- 电力消耗低于某值
- 普通居民可以维护
- 不使用稀缺材料
```

候选不再是因果假设，而是设计方案：

```text
D1：电热格栅
D2：机械刮冰器
D3：大型遮雪罩
D4：废热回流
```

实验变成原型测试。

证据关系变成：

```text
测试Run17
  ├── 支持 D1满足可靠性要求
  ├── 反驳 D1满足低功耗要求
  └── 暴露新问题：电气结构进水
```

最终不是找到唯一“正确答案”，而是在多目标约束下找到可接受设计。

可以维护一个帕累托式设计集合：

```text
高可靠、高耗电
低成本、维护频繁
节能、制造复杂
```

由玩家决定城镇采用哪条路线。

# 二十五、锅炉例子的完整数据流

## 1. 世界事件

```text
StormEvent:
  temperature = -18°C
  humidity = 0.91
  snow_type = WET_SNOW
```

隐藏机制使锅炉进气口积冰，空气流量下降。

## 2. 观察事件

```text
O1：
东侧锅炉炉温下降

O2：
进气格栅积冰

O3：
打开炉门后炉火短暂恢复

O4：
室内小炉使用相同燃料但燃烧正常
```

## 3. 图规则匹配

系统发现：

```text
炉温下降与湿雪天气重复共现
积冰与炉温下降共现
打开炉门这一干预使炉火恢复
现有知识没有解释
```

生成：

```text
Idea Q1：
什么因素导致湿雪天气中的锅炉燃烧不稳定？
```

## 4. 候选假设

```text
H1：
燃料湿度增加
→ 燃烧效率下降

H2：
进气口积冰
→ 空气流量下降
→ 燃烧不稳定

H3：
暴风造成烟囱倒灌
→ 排烟受阻
→ 燃烧不稳定
```

## 5. 工作流编译

系统发现：

```text
当前三个假设都能解释炉温下降。
当前缺口是：没有能区分它们的预测。
```

生成当前任务：

> 找到一种只影响其中一个解释的干预方式。

## 6. 推导实验

```text
加热进气口：
H1预测无明显改变
H2预测空气流量恢复
H3预测无明显改变
```

于是生成能力需求：

```text
MANIPULATE(intake_temperature)
MEASURE(airflow)
MEASURE(boiler_temperature)
HOLD(fuel_moisture)
HOLD(chimney_configuration)
HOLD(load)
```

## 7. 第一次实验

玩家没有保持燃料湿度稳定。

结果：

```text
进气加热组燃料更干燥
对照组燃料更潮湿

→ 无法判断改善来自进气除冰还是燃料差异
```

图中增加：

```text
Run1
  └── 无法为H1与H2提供有效区分
```

工作流重新编译：

```text
当前任务：
消除燃料湿度差异。

建议：
使用同一批密封燃料仓供料。
```

## 8. 第二次实验

结果：

```text
进气加热
→ 积冰量下降
→ 空气流量先恢复
→ 炉温随后恢复
```

系统增加：

```text
Run2 强支持 H2
Run2 反驳 H1作为主要解释
Run2 对H3提供中等反证
```

## 9. 发现

```text
Finding F1：

在低温高湿、开放式进气结构中，
进气口积冰会降低空气流量，
并导致锅炉燃烧输出不稳定。
```

注意，这个发现具有明确作用范围。

它不是：

> 积冰永远会让所有锅炉熄灭。

# 二十八、实现时最重要的五个限制

## 1. 不要记录世界中的一切

否则图会爆炸。

只有以下内容进入研究系统：

* 玩家主动记录；
* NPC注意到；
* 专门传感器正在监测；
* 与当前研究有关；
* 达到异常阈值；
* 造成事故或显著结果。

“注意力”本身就是数据入口。

## 2. 不要全图搜索

每次只处理新加入节点附近的局部区域。

```text
新观察加入
→ 查找与其相同对象、变量、上下文的邻域
→ 运行相关规则
→ 更新活跃研究
```

不要每个tick重新扫描全部知识。

## 3. 每个生成结果必须有解释路径

系统生成假设时，必须能够回答：

> 为什么会提出这个假设？

例如：

```text
因为：
- 打开炉门后火焰恢复；
- 已知开门会增加空气供应；
- 进气口存在积冰；
- 已知阻塞可能降低流量。
```

无法解释来源的自动生成内容应当直接丢弃。

## 4. 不要删除被反驳的知识

被反驳的假设是重要的负知识。

后续NPC可以知道：

> “我们已经测试过加热燃料，不能解决这个问题。”

## 5. 使用真值维护，而不是直接覆盖状态

每个推导结论都保存它依赖的前提。

当一个前提被推翻时，系统可以重新计算依赖它的结论：

```text
发现A依赖假设H
假设H后来被反驳
→ 发现A变成“失去支持”
→ 依赖发现A的工程技术被标记为需要复查
```

第一版可以实现一个轻量级的真值维护系统：

```text
主张有若干Justification
只要存在有效Justification，就保持支持
所有Justification失效，则变为无支持
出现强反证，则变为争议或反驳
```

不要一开始试图做“全领域自动科研”。

# 三十、最终可以把整个架构概括为一句话

> **世界机制产生现象；观察把现象写入事件日志；事件日志构建带来源的主张—证据图；图中的矛盾、异常和缺口生成问题；问题通过溯因搜索生成候选假设；假设之间的预测差异生成实验需求；实验结果回写为证据；工作流编译器每次从当前知识状态中选出下一项未满足的研究义务，并将整个非线性探索呈现为一条不断修正、但始终清楚的线性研究历程。**

真正值得优先落地的核心名称可以定为：

```text
EpistemicGraph
ResearchEventLog
InquiryWorkspace
ResearchGrammar
ObligationCompiler
ExperimentCapabilitySystem
```

其中最关键的并不是图数据库，而是两件事：

1. **主张必须是一等对象，证据必须连接到主张，而不是直接修改真假值。**
2. **研究流程必须由当前未满足的认识义务编译产生，而不是预先写成状态机。**


你目前这套系统距离在具体的Minecraft里面实现还差很多更具体的东西，游戏里我们整合包主要有一个能获取指定位置方块温度的API，背后是一套世界内的温度缓存系统，你不需要在乎细节。然后城镇系统主要是由城镇方块来处理，都是基于team的虚拟towndata，背后按照需要的时间尺度走tick，然后城镇数据里还有resident居民数据，有力量、智力、教育等级等属性（也可以加新的），然后每天会分配居民到各个城镇方块对应的建筑（玩家自己搭建，我们有一套封闭空间检测系统，你不需要在乎细节），然后进行工作，产出到仓库（一个特定建筑），然后有住宅建筑，会从仓库消耗，大概就是这样，然后会有随机属性难民刷新，玩家可以选择招募，这个你可以考虑是知识传播的重点因素，因为难民刷新是唯一的产生新随机性的地方，我们的设定里难民肯定携带者很多知识，另外就是难民在各种地方工作的时候肯定也会产生你说的各种观察，目前我们工作比较少，主要是狩猎建筑，矿场建筑，还有货运站（负责物流）。其实物流的倒是很有用因为物流的居民会和玩家工厂交互很多，虽然他们不是真的交互（只是类似AE2那样，和仓库通讯，有接口和p2p等），但是依旧是观察机器等的主要来源。当然狩猎和矿场也是，是外出探索，肯定会发现新东西和现象。然后是科技方块主要是基于机械动力的机器（这些都可以被抽象为BlockEntity），还有沉浸工程的多方块设备（内部有state和logic，可理解为多方块的BE)，以及虚拟化的用于加热的能量塔设备、城镇建筑（可理解为更加自由的多方块BE），这三类东西其实本质上都可以理解为“机器”，这些主要分为供能（应力或者电，机械动力主要是应力能量，沉浸工程是电力能量，城镇建筑是连着的虚拟居民和一个物资存储系统的）和消耗能量。目前某种意义上我们所有的研究在游戏中的完成之后，都可被想象成为了实现很多Effect，第一类effect是使用禁止性的。比如研究完成之前禁止合成某东西，禁止使用某方块。第二类effect更自由，可以叫stats effect，背后是我们为每个玩家队伍/城镇存储的是一系列key-value数据，叫variants，存储的数据可以被stats effect更新，数据本身可以是数字，也可以是boolean等，也可以更复杂，但游戏中其他系统如上面说的能量塔设备背后其实也是一个teamdata，它就可以从team调取这个背后的variant，然后取值。举个例子一个能量塔热效率研究就可以更新这个效率variant数值从0到0.1，然后能量塔的logic部分就可以具体去用这个新的variant真正实现这个效率升级。这个只是例子，其他的比如说你说的燃烧室什么的，本质上也都是BE，所以也可以implement一个IOwnerTile接口，用于获取team，然后就能被研究上锁或者获取variant。然后多方块MB的话就可以实现IOwnerState之类的，本质上都是获取team。

当然了我所说的这一切都可以尝试修改，而且目前的研究系统非常原始，每个effect都是绑定一个具体的research，这和我们的设想完全不同，我只是提供一些context，以及具体游戏中的应用场景。你接下来思考的时候也一定要开始思考具体的架构。

开始思考。


你给出的这些现有系统，已经足以把研究系统从抽象设计推进到一套具体架构。现在最需要做的，不是先实现一个“万能知识图数据库”，而是先建立一条稳定的数据管线：

> **机器、城镇建筑和居民产生结构化信号；观察者把其中一部分信号转化为观察；观察进入队伍知识图；知识图生成研究问题与研究义务；玩家完成义务后形成发现或工程标准；最后再把这些知识成果投影成现有的使用限制和 variants。**

我建议把整体拆成六层：

```text
┌────────────────────────────────────────────┐
│ 1. 世界运行层                               │
│ BE、IE多方块、能量塔、城镇建筑、居民工作     │
└──────────────────┬─────────────────────────┘
                   │ 产生结构化运行信号
                   ▼
┌────────────────────────────────────────────┐
│ 2. 观察层                                   │
│ 居民观察、物流检查、仪器记录、实验监控       │
└──────────────────┬─────────────────────────┘
                   │ 生成Observation
                   ▼
┌────────────────────────────────────────────┐
│ 3. 队伍认识层                               │
│ Claim、Evidence、Idea、Hypothesis、Finding  │
└──────────────────┬─────────────────────────┘
                   │ 编译当前知识缺口
                   ▼
┌────────────────────────────────────────────┐
│ 4. 研究工作流层                             │
│ 当前问题、研究义务、实验计划、线性时间线     │
└──────────────────┬─────────────────────────┘
                   │ 形成稳定知识资产
                   ▼
┌────────────────────────────────────────────┐
│ 5. 知识成果层                               │
│ Finding、Procedure、DesignStandard          │
└──────────────────┬─────────────────────────┘
                   │ 投影
                   ▼
┌────────────────────────────────────────────┐
│ 6. 游戏效果层                               │
│ 禁止/允许使用、配方解锁、variant贡献         │
└────────────────────────────────────────────┘
```

这里有一个必须先明确的边界：

> 我们可以不再手写“研究路线”，但仍然需要给世界系统做一次性的“研究语义标注”。

系统不可能自动从一个陌生BlockEntity的Java代码中理解：

* 哪个字段代表输入；
* 哪个字段代表产出；
* 哪个字段代表电力或应力供应；
* 哪些状态能被观察；
* 哪些变量可以被玩家主动改变；
* 哪些变化具有研究意义。

但我们不需要为每项研究写路线。我们只需要为每类机器声明一次它拥有哪些语义变量和能力，之后许多研究都可以围绕这些变量自动产生。

# 一、首先建立统一的“研究对象”抽象

你描述的三类系统：

* 机械动力BlockEntity；
* 沉浸工程多方块的state或logic；
* 虚拟能量塔和城镇建筑；

从研究系统的角度确实应该统一视为一种东西：

> **能够接收输入、依赖支持条件、产生输出、具有运行状态，并处于某种环境中的研究对象。**

可以定义统一引用：

```java
public sealed interface ResearchSubjectRef
        permits BlockSubjectRef,
                MultiblockSubjectRef,
                TownBuildingSubjectRef {

    TeamId owner();
    ResourceLocation profileId();
}
```

具体类型：

```java
public record BlockSubjectRef(
        TeamId owner,
        ResourceKey<Level> dimension,
        BlockPos pos,
        UUID instanceId,
        ResourceLocation profileId
) implements ResearchSubjectRef {
}

public record MultiblockSubjectRef(
        TeamId owner,
        ResourceKey<Level> dimension,
        BlockPos masterPos,
        UUID instanceId,
        ResourceLocation profileId
) implements ResearchSubjectRef {
}

public record TownBuildingSubjectRef(
        TeamId owner,
        UUID buildingId,
        ResourceLocation profileId
) implements ResearchSubjectRef {
}
```

这里最好给BE和多方块实例一个持久化UUID。仅使用坐标不够，因为玩家拆掉机器后在同一位置重新放置，它在纵向研究记录中应当是一个新实例。

## 不要求所有第三方BE直接实现接口

自己的BE可以实现：

```java
public interface IOwnedResearchSubject extends IOwnerTile {
    ResearchSubjectRef getResearchSubjectRef();
}
```

但对于机械动力和沉浸工程，不建议到处Mixin接口。更适合使用适配器注册表：

```java
public interface ResearchSubjectAdapter<T> {

    ResourceLocation profileId();

    boolean supports(T subject);

    ResearchSubjectRef getSubjectRef(T subject);

    TeamId getOwner(T subject);

    void collectSignals(
            T subject,
            ObservationRequest request,
            ResearchSignalSink sink
    );

    Set<ResearchCapability> getCapabilities(T subject);
}
```

注册方式可以是：

```java
ResearchSubjectAdapters.register(
        someCreateBlockEntityType,
        new CreateMachineResearchAdapter()
);

ResearchSubjectAdapters.register(
        someIEMultiblockDefinition,
        new IEMultiblockResearchAdapter()
);
```

自研的能量塔和城镇建筑则直接提供适配器。

这样研究系统永远不直接依赖具体机器类，只依赖：

```text
ResearchSubjectRef
ResearchSubjectProfile
ResearchSubjectAdapter
```

# 二、所有机器统一暴露“过程语义”

机器差异很大，但运行过程大体都可以抽象成：

```text
输入
  ├── 材料
  ├── 电力
  ├── 应力
  ├── 劳动力
  └── 时间

支持条件
  ├── 温度
  ├── 房间环境
  ├── 维护状态
  ├── 物流可用性
  └── 操作者能力

运行状态
  ├── 正常
  ├── 空闲
  ├── 缺料
  ├── 能量不足
  ├── 堵塞
  └── 故障

输出
  ├── 物品
  ├── 热量
  ├── 服务
  ├── 运输能力
  └── 副产物
```

为每类机器定义一个研究档案：

```java
public record ResearchSubjectProfile(
        ResourceLocation id,
        Set<VariableDefinition<?>> observableVariables,
        Set<VariableDefinition<?>> controllableVariables,
        Set<CapabilityKey> capabilities,
        Set<OperationalChannelDefinition> channels,
        Set<ResourceLocation> tags
) {
}
```

例如机械动力机器可以暴露：

```text
输入：
- item_input_rate
- rotational_speed
- stress_capacity
- stress_consumption

输出：
- item_output_rate

状态：
- running
- overstressed
- stalled
- recipe_active

环境：
- ambient_temperature
```

沉浸工程机器可以暴露：

```text
输入：
- electric_input
- material_input

输出：
- material_output
- heat_output

状态：
- active
- recipe_progress
- internal_energy
- failure_state
```

城镇建筑可以暴露：

```text
输入：
- assigned_residents
- labor_strength
- material_input
- warehouse_availability

输出：
- daily_production
- injury_count
- trip_duration

环境：
- building_temperature
- exterior_temperature
```

这让许多通用研究规则可以跨系统工作。例如：

```text
支持条件不变，但产出下降
→ 产生性能异常想法

温度下降与故障重复共现
→ 产生低温相关想法

投入相同，但不同建筑产出不同
→ 产生差异原因问题

材料充足但机器持续空闲
→ 产生物流、能量或控制异常问题
```

# 三、温度API应成为通用上下文，而不是某个研究专用接口

你们已经有指定方块位置温度API，这非常适合成为研究系统最早落地的环境变量。

不要让每个BE自己调用温度API。可以统一做一个上下文增强器：

```java
public interface ResearchContextEnricher {
    void enrich(
            ResearchSubjectRef subject,
            MutableResearchContext context
    );
}
```

其中一个实现：

```java
public final class SpatialTemperatureEnricher
        implements ResearchContextEnricher {

    @Override
    public void enrich(
            ResearchSubjectRef subject,
            MutableResearchContext context
    ) {
        subject.anchorPosition().ifPresent(anchor -> {
            double temperature =
                    temperatureApi.getTemperature(
                            anchor.level(),
                            anchor.pos()
                    );

            context.put(
                    ResearchVariables.AMBIENT_TEMPERATURE,
                    temperature
            );
        });
    }
}
```

于是所有有空间位置的研究对象，自动携带：

```text
ambient_temperature
dimension
position
room_id
building_id
time_of_day
weather_context
```

城镇建筑可以定义多个采样点：

* 建筑中心；
* 工作区；
* 外墙附近；
* 室外入口。

第一版只取建筑锚点即可，不必一开始就做复杂空间平均。

# 四、机器不能直接写入知识图，而应先产生“研究信号”

这是非常重要的架构约束。

错误方式是：

```java
if (temperature < -10 && efficiency < 0.7) {
    teamResearchGraph.addIdea(...);
}
```

这样每个机器都在实现自己的研究逻辑，最终又会回到手写路线。

正确方式是机器只报告：

```text
我现在输入了多少；
我现在产出了多少；
我的能量供应是什么；
我的运行状态是什么；
我所在位置温度是多少。
```

统一信号结构：

```java
public record ResearchSignal(
        ResearchSubjectRef subject,
        long gameTime,
        SignalSource source,
        Map<VariableKey<?>, SampleValue<?>> values,
        Set<ResourceLocation> eventTags
) {
}
```

例如能量塔一天结束时发出：

```text
subject = 热能塔#17
input_fuel = 120
heat_output = 8400
operating_hours = 20
ambient_temperature = -22
state = ACTIVE
```

机械动力机器可能发出：

```text
subject = 粉碎机#4
rotational_speed = 64
stress_capacity = 1024
stress_consumption = 512
input_count = 64
output_count = 48
stall_count = 3
ambient_temperature = -18
```

这只是**潜在可观察信号**，并不等于城镇已经知道这些信息。

# 五、在“机器信号”和“知识观察”之间增加观察门

如果所有机器信息自动进入知识图，居民、物流、仪器和实验室都失去意义。

所以数据流应该是：

```text
机器运行信号
    ↓
ObservationGate
    ↓
真正被观察到的记录
```

观察来源可以分为：

```java
public enum ObservationChannel {
    INCIDENT,               // 明显事故
    RESIDENT_WORK_REPORT,   // 普通工作报告
    LOGISTICS_INSPECTION,   // 物流居民检查
    MANUAL_PLAYER_RECORD,   // 玩家手动记录
    SENSOR_MONITORING,      // 仪器监测
    EXPERIMENT_TRACE        // 正式实验
}
```

同一个机器信号，通过不同渠道会产生不同质量的观察。

例如：

| 渠道     | 玩家得到的信息             |
| ------ | ------------------- |
| 普通工人报告 | “这台机器今天经常卡住。”       |
| 物流居民检查 | “输入供应正常，但产出低于平日。”   |
| 受教育技术员 | “应力供应稳定，机器仍出现三次停转。” |
| 仪器监测   | 完整转速、应力、温度和产出时间序列   |
| 正式实验   | 带控制组、干预记录和有效性判断的数据  |

观察记录：

```java
public record ObservationRecord(
        ObservationId id,
        ResearchSubjectRef subject,
        long startTime,
        long endTime,
        ObservationChannel channel,
        Optional<ResidentId> observer,
        Map<VariableKey<?>, ObservedValue<?>> values,
        ResearchContext context,
        ObservationQuality quality,
        Provenance provenance
) {
}
```

质量不应只是一个总百分比，可以拆成：

```java
public record ObservationQuality(
        PrecisionLevel precision,
        CompletenessLevel completeness,
        ReliabilityLevel reliability,
        boolean instrumented,
        boolean continuous
) {
}
```

# 六、物流建筑会成为机器观察系统的核心

你提到物流居民虽然不真正跑到机器旁边，但会通过类似AE2的接口、仓库通讯和P2P与玩家工厂交互。

这反而非常适合研究系统。

物流建筑可以把连接的机器接口视为它的“观察范围”：

```text
物流建筑
  ├── 连接机器A
  ├── 连接机器B
  ├── 连接仓库C
  └── 连接能量塔D
```

每日物流工作结束时，物流建筑可以生成一个虚拟工作报告：

```java
public interface JobObservationProvider {

    void generateWorkObservations(
            WorkShiftContext context,
            ObservationSink sink
    );
}
```

物流建筑的实现可以分析：

```text
机器请求了什么；
实际供应了多少；
机器输出了多少；
机器是否因为输入不足停机；
机器是否在供应充足时仍然低产；
不同时间段输入输出是否异常；
接口是否重复堵塞；
机器所在位置温度如何。
```

由此可以产生非常有价值的观察：

```text
“粉碎机的原料供应一直充足，但近三天产量下降。”

“南侧机器收到的应力供应没有变化，但停转次数增加。”

“两个相同机器使用同一仓库供料，室外机器效率明显更低。”

“能量塔燃料消耗保持不变，但热量输出在低温天气下降。”
```

物流居民的属性可以影响他们能看到什么：

* 智力高：能发现多变量之间的关联；
* 教育高：能产生定量报告；
* 相关经验：能识别特定机器异常；
* 观察力高：能发现不明显的反复故障；
* 沟通能力高：报告更完整。

物流建筑不需要真的模拟居民访问每台机器，只需要：

```text
物流接口连接关系
＋
机器适配器提供的数据
＋
居民工作上下文
```

# 七、狩猎和矿场应当产出“现场观察”，而不只是资源

狩猎和矿场本身就是野外研究入口。

每日工作结果除了物资产出，还可以生成一份 `ExpeditionReport`：

```java
public record ExpeditionReport(
        ResourceLocation expeditionType,
        List<ResidentId> residents,
        ResearchContext environment,
        Map<ResourceLocation, Integer> yields,
        List<FieldIncident> incidents,
        List<FieldObservation> observations
) {
}
```

狩猎可以产生：

```text
低温下动物活动减少；
某种动物更常出现在热源附近；
猎物脂肪厚度变化；
工具在极寒中更容易损坏；
居民在某类衣物下受伤更少；
某个区域存在异常温度。
```

矿场可以产生：

```text
某种矿层温度异常；
低温时工具损耗增加；
某种材料在冷热变化后开裂；
矿井深度与温度变化；
运输时间与矿物损耗关系；
某种设备在地下运行更稳定。
```

这些报告首先是观察，不直接解锁研究。

# 八、居民属性应当影响“能做什么”，而不是研究点速度

现有属性可以这样使用：

| 属性   | 研究系统中的作用                  |
| ---- | ------------------------- |
| 智力   | 假设搜索深度、能同时处理的变量数量、跨观察关联能力 |
| 教育等级 | 定量表达、正式实验设计、计算方法和仪器使用     |
| 力量   | 搭建重型装置、危险现场实验、长时间野外工作     |
| 工作岗位 | 决定能接触哪些对象和观察渠道            |

建议额外增加的不是一堆数值条，而是两个数值和一组标签。

## 1. 观察力

决定居民能否把潜在信号注意为观察。

```java
int observation;
```

## 2. 沟通能力

决定私人知识和工作经验能否被完整地表达给团队。

```java
int communication;
```

## 3. 经历标签

比单纯的“机械知识等级37”更适合难民系统。

```text
former_machinist
former_miner
railway_dispatcher
field_medic
teacher
boiler_operator
electrician
hunter
warehouse_clerk
```

经历标签负责授予特定知识包和识别规则。

# 九、难民应携带“私人知识包”，而不是直接携带科技解锁

难民是整个系统中最适合承担知识随机性的部分。

每次难民生成时，从其背景原型中生成若干私人知识包：

```java
public record ResidentKnowledgePacket(
        ResourceLocation id,
        Set<ConceptKey> knownConcepts,
        Set<MechanismSchemaKey> mechanismSchemas,
        Set<ProcedureKey> knownProcedures,
        Set<RecognitionRuleKey> recognitionRules,
        List<TestimonyTemplate> testimonies
) {
}
```

知识包可以分成五类。

## 概念知识

居民知道某种概念存在：

```text
空气流量
润滑黏度
烟囱倒灌
材料疲劳
控制变量
热交换
```

## 机制模式

居民知道一种通用解释方式：

```text
温度下降
→ 液体黏度增加
→ 机械阻力增加

堵塞增加
→ 有效截面积减少
→ 流量下降
```

## 程序知识

居民知道如何做某件事：

```text
校准流量计
检查轴承
设计对照实验
记录燃料批次
维护高压设备
```

## 案例记忆

居民曾经见过某种现象：

```text
“以前铁路转辙器在湿雪天会冻住。”

“旧工厂的锅炉开门后火焰会恢复。”

“某些油在严寒中会变得像蜡。”
```

这些是带来源的证词，不是已确认发现。

## 工程设计模式

居民知道一种可能的解决路线：

```text
加热进气格栅
机械刮冰
废热回流
双层保温
旁路阀
```

同样不能直接解锁最终机器，只能提供原型候选。

# 十、私人知识不会自动成为城镇知识

难民加入后，应当拥有：

```java
ResidentKnowledgeState privateKnowledge;
```

队伍拥有：

```java
TeamEpistemicState publicKnowledge;
```

两者不能直接合并。

私人知识通过以下行为外部化：

```text
与玩家交谈；
在相关建筑中工作；
在研究所参与讨论；
看到能够唤起其经验的异常；
教授其他居民；
撰写记录；
参加实验设计。
```

例如一个前锅炉工在物流站看到：

```text
机器输入正常；
产出下降；
打开维护门后短暂恢复；
温度很低。
```

他的私人知识包中有：

```text
“开门恢复可能意味着进气不足。”
```

于是产生：

```text
TestimonyEvidence：
罗伯特认为机器可能缺乏空气供应。

CandidateHypothesis：
进气受阻导致输出下降。
```

如果他从未参与相关工作，也没有被安排到研究所，这个知识可能永远不会被团队发现。

这样难民就不是随机属性劳动力，而是真正改变研究空间的人。

# 十一、建议让研究系统本身尽量确定性

你说难民刷新是主要的新随机性来源，这非常适合这套设计。

可以让：

```text
难民携带什么知识
→ 随机

世界里实际发生了什么
→ 由模拟决定

居民在已知信息下能否识别现象
→ 由属性和规则决定

系统生成哪些想法
→ 由图模式确定

实验结果
→ 由世界状态决定

结论如何更新
→ 由证据规则确定
```

研究中尽量不要使用：

```text
本次实验有35%概率成功。
```

而应使用：

```text
居民教育不足，因此无法形成定量方案；
缺少流量计，因此只能观察火焰状态；
供能中断，因此实验数据无效；
控制组燃料来源不同，因此无法区分解释。
```

即使需要轻微随机性，也可以使用居民和日期种子保证可重现，而不是暗骰科研结果。

# 十三、知识图中的核心不是“事实”，而是主张

```java
public record ClaimKey(
        PredicateKey predicate,
        Map<RoleKey, TermRef> arguments,
        Scope scope

}
```

例如：

```text
predicate:
DECREASES

arguments:
cause = intake_icing
effect = airflow

scope:
ambient_temperature < 0
humidity = HIGH
subject_profile = open_air_intake
```

运行时记录：

```java
public final class ClaimRecord {

    private final ClaimId id;
    private final ClaimKey key;

    private ClaimKind kind;
    private ClaimStatus status;

    private final Set<JustificationId> supporting;
    private final Set<JustificationId> attacking;
```

状态可以是：

```java
public enum ClaimStatus {

    CONTESTED,

    REJECTED,
    SUSPENDED
}
```

它不能只是一个概率数字。

# 十四、观察如何自然变成“想法”

完整处理链建议是：

```text
ResearchSignal
    ↓
ObservationGate
    ↓
ObservationRecord
    ↓
ObservationAggregator
    ↓
PhenomenonSummary
    ↓
IdeaRuleEngine
    ↓
IdeaCandidate
```

## ObservationAggregator

不要把机器每tick的数据永久存入图。

普通观察只保留聚合结果：

```java
public record PhenomenonSummary(
        ResourceLocation subjectProfile,
        VariableKey<?> targetVariable,
        ContextBucket context,
        int sampleCount,
        SummaryStatistics statistics,
        Set<ObservationId> representativeObservations
) {
}
```

例如：

```text
能量塔
温度区间：-25到-15
平均燃料输入：120
平均热量输出：8300
样本数：5天
```

以及：

```text
能量塔
温度区间：0到10
平均燃料输入：121
平均热量输出：9500
样本数：6天
```

然后通用规则发现：

```text
输入基本一致；
产出显著不同；
主要上下文差异是温度；
当前没有已接受解释。
```

生成：

```text
Idea：
环境温度是否影响能量塔的热量输出？
```

## 变量需要声明比较语义

每个变量定义：

```java
public record VariableDefinition<T>(
        VariableKey<T> key,
        Codec<T> codec,
        ValueComparator<T> comparator,
        ValueBucketer<T> bucketer,
        Tolerance<T> meaningfulDifference
) {
}
```

否则系统不知道：

```text
温度差1度是否重要；
产量差1个是否重要；
运行状态之间如何比较；
两个物品类型是否相同。
```

# 十五、想法生成规则应当是通用图规则

第一版只需要少量强规则。

## 性能异常

```text
输入和支持条件基本相同；
输出明显变化；
存在一个或少数上下文差异；
没有已有解释。
```

生成：

```text
什么因素导致了输出变化？
```

## 环境相关性

```text
某故障在特定温度区间反复出现；
在其他温度区间很少出现。
```

生成：

```text
温度是否与该故障有关？
```

## 同型对象差异

```text
两个同类型机器；
输入相同；
一个正常，一个异常。
```

生成：

```text
两台机器之间的什么差异造成了结果不同？
```

## 预测偏差

```text
已有知识预测产量X；
实际结果明显偏离。
```

生成：

```text
当前模型漏掉了什么因素？
```

## 证词冲突

```text
两个居民对同一现象提出不同解释。
```

生成争议研究。

## 城镇目标缺口

```text
城镇需要某性能；
现有机器无法满足；
存在可能相关的知识。
```

生成工程研究。

规则接口：

```java
public interface IdeaGenerationRule {

    Stream<IdeaCandidate> evaluate(
            GraphDelta delta,
            TeamResearchContext context
    );
}
```

每次只处理新增数据附近的局部图，不扫描全图。

# 十六、假设生成依赖“机制模式库”

系统不能从一句“输出降低”凭空生成合理因果解释。

它需要一套通用机制模式：

```java
public record MechanismSchema(
        MechanismSchemaKey key,
        TypedGraphPattern pattern,
        Set<ConceptKey> requiredConcepts,
        Set<ProcedureKey> requiredProcedures,
        PredictionGenerator predictionGenerator
) {
}
```

例如：

```text
阻塞机制：
阻塞量增加
→ 有效通道面积减少
→ 流量下降
```

```text
资源不足机制：
输入供应下降
→ 运行时间下降
→ 产出下降
```

```text
热损失机制：
内外温差增加
＋ 保温不足
→ 热损失增加
→ 有效热输出下降
```

```text
技能不足机制：
操作者能力不足
→ 错误率增加
→ 产出或可靠性下降
```

当当前问题是：

```text
为什么低温时热输出下降？
```

系统会在团队目前可用的机制模式中搜索：

* 外部热损失；
* 燃料状态变化；
* 管道结冰；
* 物流供应不足；
* 测量误差；
* 操作人员低温影响。

其中一些可能是真的，一些可能是错误解释。

候选假设生成器不能读取隐藏世界机制，只能使用：

```text
团队已知概念；
居民携带的机制模式；
已有观察；
机器公开的可观察变量；
相关旧发现。
```

# 十七、研究流程具体表现为“研究义务”

底层不要保存：

```java
stage = THEORY;
progress = 0.73;
```

而要保存：

```java
public record ResearchObligation(
        ObligationId id,
        ObligationType type,
        RequirementExpression completionCondition,
        Set<ObligationId> dependencies,
        List<ResearchActionOption> availableActions,
        String reasonTemplate
) {
}
```

义务类型可以包括：

```java
public enum ObligationType {
    CHARACTERIZE_PHENOMENON,
    FORMALIZE_VARIABLE,
    GENERATE_ALTERNATIVE_HYPOTHESES,
    DERIVE_PREDICTION,
    IDENTIFY_CONFOUNDERS,
    ACQUIRE_MEASUREMENT_CAPABILITY,
    DESIGN_EXPERIMENT,
    PREPARE_APPARATUS,
    ASSIGN_RESEARCHERS,
    RUN_EXPERIMENT,
    ANALYZE_RESULT,
    REPLICATE_RESULT,
    DEFINE_SCOPE,
    REVIEW_FINDING,
    BUILD_PROTOTYPE,
    FIELD_TEST_PROTOTYPE,
    STANDARDIZE_DESIGN
}
```

每当知识图变化，工作流编译器重新计算：

```java
List<ResearchObligation> obligations =
        workflowCompiler.compile(
                inquiry,
                teamResearchData,
                townCapabilities
        );
```

然后取当前依赖已满足的最前沿义务：

```text
当前主要任务：
排除“燃料供应不足”这一替代解释。

原因：
物流记录显示总供应量正常，但尚未确认实验期间持续稳定。

可用行动：
- 安排物流居民进行专门监控；
- 安装持续输入记录器；
- 从仓库预留固定批次燃料。
```

玩家看到的线性阶段由当前义务分类：

```text
当前义务是提出假设
→ 理论阶段

当前义务是准备装置
→ 实验准备阶段

当前义务是解释结果
→ 分析阶段

当前义务是现场测试
→ 工程原型阶段
```

因此“阶段”是界面投影，不是底层状态机。

# 十八、研究所中的居民执行具体任务，而不是产生研究点

研究所可以是现有城镇建筑体系中的一种建筑。

每天分配居民后，研究所获得的是一组可执行劳动能力：

```text
理论讨论；
档案整理；
定量计算；
实验设计；
实验值班；
结果复核；
知识教学。
```

具体任务例如：

```java
public record ResearchTask(
        ResourceLocation type,
        InquiryId inquiry,
        Set<ResidentRequirement> residentRequirements,
        Set<FacilityRequirement> facilityRequirements,
        Duration workDuration,
        ResearchTaskResultGenerator resultGenerator
) {
}
```

例如“把观察正式定义成热效率”：

```text
要求：
教育等级达到某阈值；
知道输入能量和输出热量概念；
拥有计算设施。

结果：
生成变量定义：
thermal_efficiency = heat_output / fuel_input
```

“提出替代假设”：

```text
要求：
至少一名高智力居民；
团队拥有两个以上相关机制模式；
进行一次研究讨论。

结果：
生成若干候选假设。
```

“复核实验”：

```text
要求：
另一名未参与原实验的受教育居民；
完整实验日志；
研究所档案设施。

结果：
识别遗漏控制变量，或者提高证据可靠性。
```

这些任务可以需要一天或数天，但其结果是明确结构，而不是加进度条。

# 二十一、实验装置检查是“能力约束”，不是蓝图检查

系统生成：

```text
需要：
- 两个同类热能塔或两个可比较运行阶段；
- 能改变其中一组保温状态；
- 能测量燃料输入；
- 能测量热量输出；
- 能记录环境温度；
- 能保持相同负载；
- 能保证燃料供应不中断；
- 至少一名实验值班居民。
```

世界中的设施提供能力：

```java
public record ResearchCapability(
        CapabilityKey key,
        Optional<VariableKey<?>> variable,
        CapabilityQuality quality
) {
}
```

例如：

```text
能量塔适配器：
MEASURE(fuel_input)
MEASURE(heat_output)
CONTROL(insulation_mode)

温度API采样点：
MEASURE(ambient_temperature)

仓库接口：
HOLD(material_supply)

物流居民：
MONITOR(material_flow)

研究居民：
LOG_EXPERIMENT
```

只要：

```text
装置能力集合 ⊇ 实验需求能力集合
```

实验就能开始。

玩家如何搭建、机器放在哪里、使用哪种物流线路，都由玩家决定。

# 二十二、实验结果由实际运行轨迹决定

实验开始后，只对被链接对象进行高频记录。

```java
public record ExperimentRun(
        ExperimentRunId id,
        ExperimentPlanId plan,
        long startTime,
        long endTime,
        Map<ExperimentalGroupId, GroupTrace> traces,
        List<ExperimentIncident> incidents,
        ExperimentValidity validity
) {
}
```

有效性检查：

```text
干预是否真的达到目标；
输入是否持续稳定；
应力或电力是否中断；
温度是否超出计划范围；
居民是否完成值班；
测量是否缺失；
实验组与控制组是否可比较；
是否发生非计划故障。
```

输出不是：

```text
实验失败。
```

而是：

```text
本次实验不能区分两种假设。

原因：
控制组燃料供应在第3小时中断；
实验组运行时间比控制组少17分钟；
环境温度在实验中升高8度。
```

或者：

```text
结果支持“外部热损失”假设。

依据：
实验组增加保温后，
燃料输入基本不变，
热量输出提高，
且变化发生在保温干预之后。
```

这些结果被写回知识图，成为新的证据。

# 二十三、发现和工程成果必须分开

建议定义三种稳定成果。

## Finding：发现

表示城镇接受了某种规律：

```text
低温环境下，能量塔外壳热损失增加。
```

## Procedure：程序知识

表示城镇掌握了方法：

```text
如何测量热能塔输入输出；
如何校准热量记录器；
如何进行对照运行。
```

## DesignStandard：工程标准

表示某种设计已经通过原型和现场验证：

```text
热能塔双层保温结构V1。
```

只有工程标准应该直接产生大部分机器效率加成和正式使用解锁。

合理流程是：

```text
发现热损失规律
    ↓
允许设计保温原型
    ↓
在实验环境测试
    ↓
在真实城镇现场运行
    ↓
形成标准化设计
    ↓
正式应用variant效果
```

这样科研不会直接魔法式提高机器效率。

# 二十四、最终效果不能再绑定研究ID

当前系统可能是：

```text
Research A完成
→ Effect A执行
```

应该改成：

```text
知识图满足某个条件
→ 生成稳定知识资产
→ 知识资产触发效果规则
```

需要一个中间层：

```java
public record KnowledgeAsset(
        KnowledgeAssetKey key,
        KnowledgeAssetType type,
        Provenance provenance
) {
}
```

类型：

```java
public enum KnowledgeAssetType {
    FINDING,
    PROCEDURE,
    DESIGN_STANDARD
}
```

这些资产拥有稳定ID，例如：

```text
winterrescue:finding/external_temperature_increases_heat_loss
winterrescue:procedure/controlled_thermal_test
winterrescue:design/heat_tower_insulation_v1
```

这看上去也有ID，但它和旧research ID有本质区别：

```text
旧Research ID：
代表一条固定路线。

KnowledgeAsset ID：
代表一个稳定语义结果。
```

任意研究问题、任意观察路线、任意假设迭代，只要最终形成相同结果，都可以生成同一个KnowledgeAsset。

一项研究也可能生成多个资产。

# 二十五、用“发现解析器”把开放图谱转成稳定资产

机器代码不能直接查询一整张开放知识图。所以需要解析器：

```java
public interface KnowledgeAssetResolver {

    Stream<KnowledgeAsset> resolve(
            GraphDelta delta,
            TeamEpistemicState state
    );
}
```

例如：

```text
匹配条件：
存在一个已接受主张：

外部温差增加
→ 热量损失增加

作用对象：
热能塔外壳

证据条件：
至少一次有效干预实验；
至少一次重复验证；
不存在未解决的强反证。

输出：
FindingAsset:
external_temperature_increases_heat_loss
```

这样最终效果仍然是可控的，但通往它的路线不是固定的。

# 二十六、将现有variants升级成类型安全的“效果投影”

你们已经有team级key-value variants，这很适合作为下游投影，不需要推翻。

但最好从任意字符串和强制类型转换，升级为：

```java
public final class VariantKey<T> {

    private final ResourceLocation id;
    private final Codec<T> codec;
    private final T defaultValue;
    private final VariantAggregator<T> aggregator;
}
```

例如：

```java
public static final VariantKey<Double> HEAT_TOWER_EFFICIENCY =
        VariantKey.doubleKey(
                id("heat_tower_efficiency"),
                0.0,
                DoubleAggregator.ADDITIVE
        );
```

效果不要直接修改一次数值，而是增加一个带来源的贡献：

```java
public record VariantContribution<T>(
        ResourceLocation contributionId,
        KnowledgeAssetKey source,
        VariantKey<T> target,
        VariantOperation operation,
        T value
) {
}
```

例如：

```text
contributionId:
winterrescue:heat_tower_insulation_v1_efficiency

source:
winterrescue:design/heat_tower_insulation_v1

target:
winterrescue:heat_tower_efficiency

operation:
ADD

value:
0.10
```

最终值：

```text
基础值
＋ 所有ADD贡献
× 所有MULTIPLY贡献
再进行clamp
```

这样效果是幂等的，不会因为加载存档、重复解析图谱而多加一次。

# 二十七、BE只访问编译后的队伍投影

不要让每台机器每tick查询知识图。

图变化后，生成一个缓存：

```java
public final class TeamResearchProjection {

    private final Set<ActionKey> unlockedActions;
    private final Set<KnowledgeAssetKey> assets;
    private final Map<VariantKey<?>, Object> resolvedVariants;
}
```

机器运行时只做O(1)查询：

```java
TeamResearchProjection projection =
        researchService.getProjection(teamId);

double bonus =
        projection.getVariant(
                ResearchVariants.HEAT_TOWER_EFFICIENCY
        );
```

使用限制：

```java
if (!projection.can(
        ResearchActions.USE_ADVANCED_HEAT_EXCHANGER
)) {
    return AccessResult.DENIED;
}
```

这适用于：

* 合成配方；
* 方块交互；
* 多方块启动；
* 特殊维护功能；
* 原型模式；
* stats读取。

# 二十八、使用权限建议分成三档

科学发现不应立刻允许无限批量制造。

```java
public enum TechnologyAccess {
    FORBIDDEN,
    PROTOTYPE_ONLY,
    STANDARDIZED
}
```

## FORBIDDEN

尚未掌握必要知识，不能制造或使用。

## PROTOTYPE_ONLY

已经掌握原理，可以在以下情况下使用：

```text
位于研究实验；
被实验控制台链接；
数量受限；
需要高教育居民；
维护成本高；
可能产生故障。
```

## STANDARDIZED

完成现场试验和标准化后：

```text
普通合成解锁；
正常使用；
居民可以自动维护；
正式variant效果生效。
```

这正好把你之前不确定的工程原型阶段嵌入现有禁止性Effect体系。

# 二十九、具体例子：能量塔热效率研究

假设能量塔适配器暴露：

```text
fuel_input
heat_output
operating_time
load
maintenance_state
ambient_temperature
```

物流建筑连接到能量塔。

## 第一天到第五天

物流居民产生报告：

```text
燃料供应稳定；
负载基本相同；
严寒日的热输出低于普通天气。
```

观察聚合器发现：

```text
输入近似相同；
输出差异明显；
温度是主要上下文差异。
```

生成想法：

> 为什么低温天气中能量塔消耗相同燃料，却输出更少热量？

## 候选假设

团队已有知识和难民知识生成：

```text
H1：低温改变了燃料状态。
H2：内外温差增加了外壳热损失。
H3：低温导致物流供应出现间歇中断。
H4：热量记录方式在低温下存在误差。
```

其中一个新难民拥有：

```text
former_heating_engineer
heat_transfer_schema
insulation_procedure
```

他在研究讨论中提出H2。

## 当前义务

工作流编译器发现：

```text
尚未证明燃料供应在整个运行期间持续稳定。
```

显示：

> 安排物流居民连续监控能量塔燃料输入。

完成后排除H3。

下一项义务：

> 设计能够区分燃料状态变化和外壳热损失的实验。

## 实验方案

系统生成需求：

```text
保持相同燃料来源；
保持相同负载；
记录环境温度；
记录燃料输入；
记录热量输出；
改变外壳保温条件；
连续运行指定时间。
```

玩家可以：

* 建两个可比较的能量塔；
* 或让同一个塔在两个相近天气阶段运行；
* 给其中一组增加临时保温原型。

## 实验结果

若保温组在相同输入下输出提高：

```text
支持H2；
反驳H1作为主要解释；
产生新问题：保温材料长期耐久性如何？
```

形成：

```text
Finding：
较大内外温差会增加能量塔外壳热损失。
```

随后开放保温原型。

现场测试验证：

```text
提高热输出；
未造成过热；
维护成本可接受；
普通居民可以维护。
```

最终形成：

```text
DesignStandard：
heat_tower_insulation_v1
```

效果规则：

```text
heat_tower_efficiency += 0.10
```

能量塔logic继续按照你们现有方式读取team variant。

# 三十、一个必须避免的设计问题

假如当前能量塔逻辑是：

```text
基础效率固定；
研究完成后variant直接从0变成0.1；
此前世界中完全没有温度相关热损失。
```

那么它不能被包装成“玩家发现低温热损失”，因为世界此前没有这个现象。

这种情况应该被定义成纯工程研究：

```text
城镇提出提高热效率需求；
团队使用已有热学知识设计改进；
制造保温原型；
测试后形成标准。
```

而真正的科学发现必须对应世界中已经存在、可以观察和干预的机制。

因此研究可以分为：

```text
发现型：
世界里已经存在机制，玩家逐渐认识它。

工程型：
玩家根据已有发现设计尚不存在的解决方案。

混合型：
发现一个机制，然后围绕它进行工程开发。
```

这一区分会决定整套系统是否真实可信。

# 三十一、tick与性能架构

不要让知识图每tick扫描所有机器。

建议的调度：

```text
每tick：
只记录正在运行的正式实验对象。

每20tick或操作周期：
机器适配器刷新短期运行窗口。

每游戏小时：
压缩普通机器运行摘要。

每工作班次或每日：
生成物流、矿场、狩猎和城镇建筑报告；
运行居民知识识别；
执行研究任务；
处理知识传播。

每次新增重要Observation或Claim：
局部运行图规则；
重新编译受影响的Inquiry；
重新计算知识资产与效果投影。
```

普通机器运行记录只保留聚合值。

正式实验保留完整时间序列，实验完成后再压缩为：

```text
数据摘要；
有效性结果；
代表性曲线；
原始数据哈希或归档引用。
```

# 三十四、最适合的第一条垂直切片

第一版不要同时接入所有机器。

我建议只贯通这五样东西：

```text
温度API
＋
一个虚拟能量塔
＋
物流建筑
＋
一个携带热学知识的难民
＋
热效率variant
```

完整目标是：

1. 能量塔适配器产生输入、输出、温度信号；
2. 物流居民每天形成观察；
3. 不同温度下的异常自动产生想法；
4. 难民知识包提供一个新的机制假设；
5. 研究所生成具体研究义务；
6. 玩家用实验控制台链接能量塔；
7. 实验记录实际运行条件；
8. 证据支持或反驳假设；
9. 形成Finding；
10. 解锁原型；
11. 现场测试形成DesignStandard；
12. DesignStandard触发`heat_efficiency += 0.1`；
13. 能量塔logic继续读取原有team variant。

这条链一旦打通，就证明：

* 世界能够产生观察；
* 难民能够传播知识；
* 图谱能够形成研究问题；
* 非线性数据能够编译成线性任务；
* 实验能够在Minecraft世界内运行；
* 最终成果能够作用到现有机器系统；
* effect已经不再依赖固定research ID。

# 三十五、这版架构最核心的七条原则

1. **所有研究数据属于team，居民拥有私人知识覆盖层。**
2. **机器只产生语义信号，不直接产生研究或知识。**
3. **没有居民、仪器或实验，就没有正式观察，避免全知视角。**
4. **研究路线运行时生成，但变量、机制模式和最终效果端点需要一次性定义。**
5. **研究项目是知识图的临时工作区，研究阶段是当前义务的界面投影。**
6. **发现、程序和工程标准是稳定知识资产；游戏系统只依赖这些资产和编译后的variants。**
7. **科学发现改变玩家认知，工程标准才通常改变机器性能。**

从工程优先级上看，最先应该实现的不是假设生成器，而是这四个底座：

```text
统一ResearchSubject适配层
ResearchSignal → Observation管线
TeamResearchData与事件日志
KnowledgeAsset → Effect/Variant投影
```

这四块一旦稳定，上层的想法、假设、实验和NPC知识传播才能真正落在现有Minecraft系统上，而不会再次退化成另一套固定研究树。

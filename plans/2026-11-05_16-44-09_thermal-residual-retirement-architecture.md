## 目标和已确定的取舍

用户要求完整回收、低复杂度和高性能，明确拒绝把 0.0625°C 当作余温退休目标，以及普通余温拖到几十分钟的处理。采用现有的 1°C 进入/0.5°C 退出尺度；先在真实生命周期出口消除普通尾部，只有仍有有效状态的已加载休眠 Chunk 才进入轻量维护。

架构选择为：一份共享退出规则、现有在线所有者、现有 Chunk 存档所有者、一个服务器主线程的有限轮转表。普通查询维持按需投影；退休不依赖有人使用红外。没有逐方块定时器、预测到期堆、后台线程、磁盘定期扫描或新的热量权威副本。

以下为拟实施合同。当前源码行为见下一节；参数候选、工作预算和验收目标均不代表已经实现或已经测得。

## 1. 状态归属：Page 是计算结构，Chunk 是保存位置

以下状态是每个 Brick/材料记录的逻辑归属，不新增一套持久化状态机。一块 Chunk 可以同时有 live Brick 和 dormant Brick。

| 逻辑状态 | 数值权威 | 允许的工作 | 离开条件 |
|---|---|---|---|
| 无额外状态 | 各消费者既有自然背景/无材料读数合同 | 普通公式查询 | 真实热源、输入或相邻传播要求建立状态 |
| 在线 | 已提交区域帧及其材料 H/branch；输入归现有 Store | 现有 solver、发布和活动维护 | 冷退役，或实际卸载交接成功 |
| 已加载休眠 | Chunk 的不可变 Air/Material checkpoint | 按需投影、有限清理、已存材料的相变完成 | 有效余温耗尽，重新获得在线所有者，或 Chunk 卸载 |
| 已卸载 | 原版磁盘 NBT | 无运行任务 | 原版加载后再按时间处理 |

普通 SAVE 会存在在线数据的磁盘镜像，镜像不构成第二份可消费的能量。清理器排除当前 live/captured Brick、在途恢复和正在封存的范围；不得因镜像冷而删除当前计算状态。

旧读者仍借用的帧按现有 lease 生命周期释放。逻辑退休可以先完成，物理数组要等最后读者退出，不能在这里增加强制回收或复制温场。

## 2. 一份保留政策，明确 0.5°C 的含义

拟设纯规则类型 `ThermalRetentionPolicy`，只含阈值和纯判定函数。进入保持 `>= 1.0°C`；退出使用 `< 0.5°C`，等于 0.5°C 时保留。退出数值是本次允许的局部普通温差截断，不是整个温度模型的误差保证，也不是未来累计误差保证。

普通数据可丢弃须同时满足：相关范围没有维持它的源/邻区/路由依赖；没有未消费输入或恢复责任；没有潜热进度、未确认相变或材料布局交接；最大绝对扰动低于门槛。冷热扰动对称处理。细网格检查所有相关节点，粗档检查其现有表示的界；不能用平均值抵消一冷一热的热点。

背景选择随已有语义明确：

- 在线 Air 退休使用 `componentPerturbationC` 所代表的同一背景场，不能在主线程再次用 Section 中心绝对温度替代它。
- 在线材料沿当前自然基准与相变判定。退休确认使用同一已提交帧/对应环境，而非一个过时的 desired mask。
- 休眠普通数据按现有休眠自然浴投影，然后检查残余。一次维护切片固定其游戏 tick、自然值、材料配置 epoch；提交前核对这些依赖仍成立。
- 冷退役捕获的原因与普通卸载不同：已由在线判定可释放的范围直接移除，不能又用另一背景把它保存成“新余温”。UNLOAD 仍保存有意义的真实历史。

这统一的是保留政策，不擅自合并 `naturalAir`、`naturalBlock`、区域无源背景和红外占位。背景高差/气候漂移导致的现有查询差异，必须在温度比较中单列；0.5°C 不能被宣传为所有 UI 读数的最大跳变。

相变记录需要看 H/branch 和真实进度，不能只看温差。已完成但尚未改变世界的相变仍要完成现有业务交接；尚有潜热且正好处于平台平衡的记录可以继续存在，这是必要状态。没有潜热进度且没有待办的可相变材料，允许按普通规则回收，不能仅因配方定义过相变就永久保留。

`pending`、`coldPending` 和 producer/Store 的未消费 J 不由温差过滤删除。它们继续通过既有消费、恢复和损耗账目闭合。状态 `isEmpty()` 同时检查这些责任。

## 3. 把主要回收放进现有交接

### 冷退役和缩小

1. 继续由 `WorkerPageStore` 给出希望保留的 Brick 范围，保留邻区、source、route、phase 的依赖判定。
2. `MinecraftPageManager` 复用 `mayWithdrawThermalChunk` 和现有捕获 cursor 取得可用 cut，针对实际退出的 `removedMask` 核对状态。新的输入/热帧不能被旧退出通知覆盖。
3. 已可释放的普通范围不创建 Air/Material 数组；合并时以 `sampledBricks = removedMask` 加空结果，明确删除旧 checkpoint 中的同一范围。空捕获是删除，不能被解释为“没有更新”。
4. 有必要保留的状态先交给 Chunk；捕获暂时失败时，保持 Page/Brick 所有权并加入现有 `withdrawals` 或 `shrinkQueue`，后续继续。不得先执行 `discardLifecycle`。
5. 交接成功后提交现有 retirement/residency，释放输入 credit、halo/environment 跟踪和 Page 句柄。缩小只更新退出范围，不重新捕获剩余 Page。

`captureDormantPage` 可继续用 boolean 表示“本次交接完成，包括成功得到空结果”。将过滤/移除 mask 作为现有捕获参数；无需新 Future 或多层提交协议。若当前 cut 已出现重新发热，保留 Page 并让现有维护刷新决定，不伪造 geometry revision。

### 普通保存、实际卸载和取消

| 事件 | 必须遵守的顺序 |
|---|---|
| 普通 SAVE | 封存现有 Accepted → 构造保存镜像并过滤镜像中的无意义余温 → 序列化 → 解除快照；在线 H/J 所有权继续存在 |
| 实际 UNLOAD | 封存值与剩余 J → 构造/合并快照 → `write(true)` → 现有 `finish(true)` 导出确认 → 原版卸载 → 解除 Page 和维护引用 |
| 取消 UNLOAD | `finish(false)` → 释放准备快照与 producer 临时持有 → 原版保留 Chunk，继续在线推进；准备副本不得作为新权威覆盖它 |
| 准备后几何改变 | 沿现有 native retry 重新准备同一 holder；旧快照只释放，不应用其清理结果 |
| 保存过程中发生新输入 | 复用当前 checkpoint 的额外输入收集与收据；回收不自行“清空队列” |

原版卸载回调可能已经无法通过 `getChunkNow` 找到该 Chunk。回收/捕获使用回调提供的真实 Chunk 或当前 `NativeUnloadCheckpoint` 已持有的实例，不能把 lookup 为空解释成“余温不存在”。实际卸载遇到未完成交接，应在原版准备/重排阶段处理完，不能依赖卸载后重试。

普通保存中的过滤只作用保存镜像，不能额外重置幸存条目的 H/tick。序列化期间不重复 `setUnsaved(true)`，避免当前已有的 flush 保存循环问题；自然维护删除真实 dormant 状态时才按正常变更标脏。

## 4. 重载和已加载休眠维护

### 重载顺序

NBT decode 仍只读当前 v6 格式和原始数据，保持逐 component/材料 sampleTick、H、branch、BlockState 和待消费 J。世界自然温度可用后，加载流程登记轻量维护；恢复构建先按当前规则投影和过滤，再消费有效记录。普通查询保持只读，在清理正式提交前仍可读到正常衰减的旧记录。

已冷普通记录不能因为旧 mask 还在就种下 restoration seed 或重建 Page。确有待消费 J 时仍走现有 `advanceColdRestores`，清理器不抢它的责任。加载钩子不强制遍历世界方块或同步压缩整块密集历史；局部恢复在既有分片构建中完成筛选，剩余物理压缩交给维护。

只有几何准备而未发布的 live Brick 仍由现有 owner/capturedMask 判断占用；不能将准备中的范围当作自由 dormant 数据处理。

### 唯一新增的调度容器

拟设 `DormantThermalMaintenance`，由当前服务器主线程独占，复用 `MinecraftThermalEvents` 生命周期。它使用一个已加载 Chunk 的有序集合/轮转表，每个 Chunk 最多一项；初始可直接使用 fastutil 的对象有序集合，Chunk 实例身份就是本次加载身份，不另造 generation。

- 登记只来自加载、Page 交接、保存状态替换和已存材料变化等已知事件。
- 每个候选只附少量游标/下次检查 tick；采用约 5 游戏秒的粗检查间隔，无逐条到期时间或预测堆。
- 服务器 END tick 统一给予约 0.2ms 的软维护预算，额外限制每 tick 至多 64 个候选检查、512 个记录检查；每 32 个记录检查一次时间。数值为初始测量起点，实际尾延迟须实测。
- 工作单位为一个 Section 的一次筛选，跨 tick 使用一个可复用 scratch 和 cursor；处理完一个 Section 就轮转，避免一块密集 Chunk 长期独占。检查标记与候选集合本身不分配逐记录对象。
- 移除/压缩前核对原快照身份、配置、范围 ownership 以及实际自然基准是否变化。若变化，丢弃本次删除标记，保留新数据，下次重新检查；不复制旧快照覆盖新状态。
- 没有物理 runtime 时，这个小维护器仍可运行；不能为了清理存档启动 solver/worker/Page。
- 实际 Chunk 卸载立即注销它及正在使用的 cursor；Level 卸载移除该 Level 条目；server stop 清空全部引用。热 profile 重载重置受影响摘要/切片并重排，不能把仍加载的 dormant 数据漏出维护。

这选择有限轮转而不选到期堆：普通冷退役已直接消失，余项数量远小于所有历史方块；天气、BlockState、重载、再次供热本就使预测到期失效。轮转只有增删与游标，不需要堆下标、重复任务去重、取消墓碑及预测时间重算。若实测剩余候选扫描仍是主要成本，再按证据替换；不提前同时维护两套索引。

5 秒是检查间隔，不是任何规模下的回收期限。积压时按预算继续前进，并记录最老待处理时间；提交前查询继续按当前 tick 投影余温，提交后一起结束对应历史覆盖。支持容量必须通过实际记录数和最坏清理延迟给出，不能声称负载多大都瞬时清完。

## 5. 批量删除与摘要

`MaterialSectionState` 增加一次筛选/一次压缩的出口。全部保留返回原对象；全部退出返回 null；部分退出一次性构造紧凑位置/H/branch/palette/tick 数组。不得循环调用 `Editor.remove()` 后反复 `snapshot()`，也不为每个删除位置构造对象。

`AirFieldCheckpoint` 按现有 component/Brick 过滤，保留 surviving component 的原 sampleTick，重建目录时复用未变化数组。当前单格数据可由节点极值得到界；读取到带局部函数的 v6 数据时必须计入对应形状幅值，不能仅检查 8 个 coarse 值漏掉内部冷热峰。

捕获/解码/合并已有遍历中顺手记录普通数据的温度上下界、最晚 sampleTick，以及是否有相变/特殊状态。优先只做 Section 级摘要；不默认增加每格缓存或 64 份定时 metadata。可变 editor 更新摘要时允许保守扩大，压缩时重新收紧；旧摘要不能低估新温差。

当所有普通记录采用同一休眠速率、当前自然浴为 B 时，以下界可快速证明整段已经冷却：

    residualUpper(t) = max(abs(Tmin - B), abs(Tmax - B))
                       * exp(-rate * max(0, t - latestSampleTick) / 20)

这里 Tmin/Tmax 是普通记录原始温度范围，单位 °C；latestSampleTick 取最晚而非最早采样 tick。因为更早记录冷却得更多，该界可以保守跳过细查。相变条目不适用此显热界。自然值或热 profile 改变后重新计算，不能凭固定过期时间删除。

只读查询的临时投影不重写原状态，也不独立决定某条记录从此消失。一次 Section 筛选在主线程原子安装结果并推进现有材料 revision；查询、红外、恢复与保存从此看到同一删除结果。旧不可变数组由既有读者持有到释放为止。

采用这一点是为了避免额外的“已逻辑删除”位图和消费规则：如果查询先把余温判为无效、原记录仍在，而天气在压缩前改变，重新投影可能让它又出现。统一提交消除此接缝，也避免一个玩家的读取顺序改变其他玩家结果。正常冷退休同步于现有交接，只有少数加载休眠候选承担有限维护延迟。

## 6. 相变和未消费能量的收尾

对已存相变材料，维护复用 `DormantThermalCooling.project` 的 H/branch 计算。完成的相变在主线程通过已有 `MinecraftPhaseController.applyDormantTransition` 提交；沿用实际配方条件、世界 mutation、材料身份更新和残余焓转移。只处理已经存在的热记录，不扫描全世界寻找新冰/水任务。

相变提交会同步修改存档/BlockState，调用后结束或重取该 Section 的维护视图，不能继续沿旧数组下标删除。条件暂不允许转换时保留责任，后续在同一有限轮转中再检查；不创建新的相变重试队列。潜热反向退回零进度后，再按普通规则判断。

pending 只有现有输入所有者完成交接/消费才消失。改变休眠半衰期也会影响 `PendingHeatCheckpoint.restore` 的既有冷却损耗，需随当前账目核对正负 J、一次恢复、取消再恢复和跨进程保存；不能把这部分当成无关配置值。

## 7. 红外、温度计和自然回退

服务端回收后使用现有 material revision / Chunk materialRevision；最后一份材料也移除时仍保留“发生删除”的版本可见性。`InfraredCapture` 遍历当前与客户端已知范围的并集，输出已消失 Brick 的 `INVALID_TEMPERATURE`。Section 的 presence 清零本身不擦客户端纹理，必须实际编码删除。

部分回收时，将本 Section 的变化交给当前增量协议即可，初版允许按现有 Section revision 重发相关 Page；不为每个玩家另建删除历史。仍有 live 材料或解析场时，按既有顺序重新合成，而非整页抹除。两个玩家各自确认自己的 baseline；完整响应仅在 LAST 提交。

维护尚未提交时，红外继续显示现有记录按当前 tick 投影的值；维护提交后，由 revision 触发实际 INVALID 编码。删除不依赖温度量化是否变化：即使删除前后最后一次温度落在同一 0.25°C 档，旧 texel 也必须被覆盖。这样查询路径不承担压缩、持久化或额外的退休标记。

本次保留当前缺失显示合同：红外无数据为蓝色占位，材料温度计返回不可用，空气/环境调用恢复各自已有自然/解析场合成。回收后视觉覆盖会结束，但蓝色不表示实际 -20°C。若要让所有自然方块也始终显示真实温度，须另行设计自然背景显示，不能通过永久保留历史材料来实现。此项也不能被写成“退休时所有显示连续”的承诺。

## 8. 散热尺度与玩法校准

普通冷退役已低于 0.5°C 时直接结束，因此不再进入 1800 秒半衰期尾部。对于真正有明显余温的休眠保存，将 `dormantTemperatureHalfLifeSeconds` 的默认候选改为 30 游戏秒。它是短时近似的起点，不宣称与在线空间传热严格等价。

普通显热、自然值固定时：

    deltaT(t) = deltaT0 * 2^(-t / halfLifeSeconds)
    tToExit = halfLifeSeconds * log2(abs(deltaT0) / 0.5)

其中 t 是游戏秒（20 tick）；正负温差相同；低于门槛直接退出。30 秒半衰期下，2°C 约 60 秒、10°C 约 130 秒、20°C 约 160 秒到达门槛。相变不使用这张时间表。

在线仍由现有容量、材料接触和环境边界散热；调整候选值时必须同时检查在线曲线。常规单篝火场景的拟验收目标是熄火后约 1–3 分钟结束主要供暖和普通余温；并非给所有大体积蓄热/密闭空间设定统一倒计时。

用同样点火史的持续在线与卸载返回场景对照。若 30 秒导致明显的离开加速冷却，优先用已有空气/材料容量和换热系数校准正常响应，并同时测燃烧时升温、供暖范围及稳态收益。未通过这组对照前，30 秒不能作为最终通过值；不另叠一套只在“火灭了”时启用的强制清零方程。生命周期正确性不依赖最终选定的半衰期。

当前默认值、开发配置和实际整合包配置需分别处理。只改 Java 默认不会覆盖旧文件中的 1800。实施部署时定位配套仓库并读取其 AGENTS.md，明确更新已发布默认配置，单独报告用户自定义值；不要默默覆盖无法识别来源的自定义配置。停服现实时间仍不计入游戏 tick 冷却。

## 9. 复杂度和预期成本

设 K 为当前已加载且有有效 dormant 状态的 Chunk 数，R 为到期检查所触及的记录数，N 为一个被修改 Section 的记录数。

| 操作 | 目标成本 | 说明 |
|---|---|---|
| 没有 dormant 数据 | O(1)，不分配 | 空集合检查后返回 |
| 普通 Page 冷退休 | 并入已有检查与 mask 合并 | 可释放范围不再分配完整存档数组 |
| 已加载维护 | 每 tick 受预算限制；整轮 O(K + R) | 一个候选/Chunk，一个共享切片 scratch |
| 部分数组压缩 | O(N)，每次发布一次 | 保留未变数组；全空直接解除引用 |
| 卸载后的历史 | 0 CPU、0 维护条目 | 磁盘标签在下一次自然加载/保存时消除 |
| 多玩家读取同一区域 | 共用一次回收结果 | 不增加“玩家数 × 清理扫描” |

软时间预算不保证每次恰好停在 0.2ms 内，尤其数组发布、原版方块相变和 GC；记录真实最大耗时。按记录分片、先看摘要、减少数组复制，才是控制尖峰的主要办法。

不宣称理论上的全局最快。选择该架构是因为它让常规退休、卸载后的历史和空闲期都退出维护成本，并把少数余项交给一个有限容器；是否需要更复杂索引由实际 profile 决定。

## 10. 实施边界和验收

拟新增至多两个职责类型：纯 `ThermalRetentionPolicy` 与主线程 `DormantThermalMaintenance`。数组筛选留在 `MaterialSectionState` / `AirFieldCheckpoint`，归属更新留在 `DormantChunkThermalState`，交接留在 `MinecraftPageManager` / `MinecraftThermalInput`。不建立通用 GC 框架、任务总线或第二套保存状态机。

实现顺序：先纯规则与批量筛选；再补冷退役/缩小、空捕获覆盖和 native 保存交接；再接重载与有限轮转、相变和关闭清理；再核对红外删除；最后同批校准散热并统一编译、运行必要 Forge 场景。保留当前 v6 数值含义，新增摘要只在内存生成，不另写缓存字段进 NBT。

必须覆盖的具体行为：

1. 正负温差、阈值等号、内部峰值与冷热抵消；冷 Air/材料确实删除，部分删除保留邻近热点和原 H/branch/tick。
2. Page 全退役和部分 shrink；捕获第一次读不到一致帧、之后恢复；新热源/输入赶在退出通知之后到达。旧 generation 不能删除新 Page。
3. 真实卸载、准备后取消、准备后施工、立即返回，以及无 runtime 的休眠 Chunk；最后一个材料/最后一个 Section 删除后附件和维护条目为空。
4. 普通保存、再次保存、新进程重启；冷记录不复活，有效余温仍可读，未消费 J 不丢失、不重放。保存取消不延长半衰期。
5. 潜热进度、反向回退、已完成待转换以及转换条件受阻；回收不抹掉相变，世界转换后保留正确残余焓。
6. 两个独立红外 baseline、整页/部分删除、解析场重叠、关开视野、最后一项删除。复现夹具中的“所有材料永久可读”不能作为新合同，须区分有意义余温保留和合法退休。
7. 活动期间热配置重载、Level 卸载、停服与 Chunk 同坐标新实例；释放旧游标/引用，没有后台任务把 Chunk 留在内存。
8. 真实一篝火露天/普通房间、混合材料和相变负载的在线/离开返回曲线；同时观察升温、供暖和玩家效果，不能用改参数后的计算公式替代场景结果。

性能负载至少包括空闲、密集基地持续燃烧、同 tick 大批灭火、分散 Chunk 的连续卸载返回，以及同一区域多个红外消费者。记录主线程维护/捕获的 P95/P99/max、分配、存活记录数、集合峰值/归零、最老清理延迟、NBT 大小和增量包量。普通冷退役循环的存活数据应回到基线；有效潜热/其他活跃源单独计数。

沿用真实 Forge GameTest、实际客户端红外及独立进程保存重启。使用当前产物取得基线，不复制或重编历史源码，不采用路径敏感 hash；不使用已知低计的 Windows ThreadMXBean 秒数单独宣称速度提升。与本次变更无关的全套矩阵不作为前置。

## Outcome

用户已授权统一实施并运行真实 Forge 验证。当前实现采用30秒休眠半衰期、0.5°C保留规则和有限轮转；普通空气捕获原0.0625°C阈值已统一。露天稀疏上边界修复一并进入本批。

真实测试修正了本计划的两项预期：封闭/通风房间仍存在显著余热时不能按固定1–3分钟清空；地面相变也不保证在90秒内转入STORED，现已直接观察到熄火后LIVE泥土焓继续下降。用于尝试缩短时间的全局热容量修改，以及未被生产证据支持的材料连接性重构，均已撤回。在线热容保持原值，现有潜热活动规则保持。

## 1. 本版交付与最新约束

完成一种可辨认、尺寸受控、可以探索和采矿的地下热液矿床：一条含水主裂隙连接两至三个洞厅，配有沉淀水盆、矿化侧壁、少量喷口外观和停止活动的支区。群系、水盆和矿物共同服从同一份地点布局。

用户明确要求热量守恒。本版将“热液”用于描述景观和成矿形态，**不固定指定高水温、不按位置给水补热、不新增喷口供热、不新增热量求解或热源实体**。粒子只是视觉表现，不能声称它向空气、水或玩家输入了热量。

现有 `frostedheart:biome_temp` 的热液群系 `40.0` 修正，以及当前玩家接触水的温度规则，属于已经存在的温度系统。本轮不改变其公式或数值，也不把这些规则解释成守恒地热实现。群系空间分布改变后，受既有群系温度规则影响的位置也会改变；这是新分布的兼容影响，不能声称温度分布完全不变。

第一版包含实际群系归属、洞形、水盆、围岩、矿脉、干燥通路、局部视觉效果、生成工具同步及真实生成验证。其质量目标是“能看出这是一个完整地质地点”；算法和持续运行成本均有明确上限。

## 4. 固定候选单元：直接解决最小规模与相互裁切

首版使用 `512×512` 格候选单元，每格最多一处矿床。候选中心相对单元中心在 X/Z 各偏移最多 `80` 格。包含主体、蚀变带、群系缓冲及细节的总外接半径硬上限为 `160` 格。

因此：中心离单元边界至少 `256−80=176` 格；所有内容离单元边界至少 `176−160=16` 格。相邻单元候选中心最小间距 `512−2×80=352` 格，两处最大包络之间至少剩 `352−2×160=32` 格。斜向相邻单元距离更大。这个限制直接排除了本版矿床之间的重叠，不需要优先级争夺、Voronoi 图或跨区域冲突求解。

查询位置使用 `Math.floorDiv(x,512)` 和 `Math.floorDiv(z,512)`，包含负坐标。由于范围完全装在自己的单元内，只查当前位置所属单元即可；本版没有邻近九格或二十五格搜索。

选址按固定顺序处理：位置哈希 → `placement_chance` → 气候适宜性 → 少量地形检查 → 生成不可变布局。随机源由世界种子、单元坐标及固定 salt 派生，不消费调用者共享 RNG，不依赖区块生成顺序。

初始 `placement_chance=0.75`，表示每个气候适宜候选有 75% 概率使用，**不表示世界 75% 的面积属于热液群系**。实施时测量旧版分布与新地点密度，按找到矿床的平均距离校准此值。

适宜性从当前三条记录提取忽略 depth 后的两种条件：`C∈[-1.2,-1.05] 且 H∈[-1,0.3]`，或 `C∈[-1.05,-0.19] 且 T∈[0.55,0.85]`。C 为大陆性、H 为湿度、T 为温度气候坐标，均不是摄氏度。每候选先采 C，再采必要的 H 或 T，最多两类气候函数；不为它计算 depth。

地形检查只使用不加载区块的基础地形查询，在主洞厅中心及四个外围检查点核对预期顶盖。发现明显露头或空间高度不足时整处不采用；不缩小必有核心。五个点只能筛掉明显不适合的地点，不构成任意地形下的完整顶盖证明。主体生成时仍构造可靠的水盆壳；干燥上层与已有洞穴相通可以接受，主池排空不能接受。

代价是存在最低间距、单元内单点上限和一定规则性；中心扰动、随机方向与内部变化负责降低重复感。首版为节省复杂度接受这个取舍。

## 5. 边缘过渡：布局包络内直接求权重

所有洞室、裂隙和装饰都限制在地点自己的包络内。将 X/Z 转为地点的局部 u/v 坐标，内椭圆半轴为 a/b，外椭圆半轴为 a+16/b+16。计算：

```text
qi = (u/a)^2 + (v/b)^2
qo = (u/(a+16))^2 + (v/(b+16))^2
qi <= 1：w=1；qo >= 1：w=0
中间区域：t=(qi-1)/(qi-qo)，w=1-3*t*t+2*t*t*t
```

权重只决定围岩替换概率、细脉密度、小裂隙宽度和局部细节数量。矿脉向外变细、围岩恢复原岩；采样哈希固定，所以生成顺序不会改变纹理。Y 方向以独立上下界及短过渡控制，不追加六维群系选择器。

这是内外椭圆之间的形态权重，不是任意群系边界的精确欧氏距离。每个 X/Z 柱可复用一次结果；不建立全区域距离场、像素图或寻路网格。必有核心完全处于 w=1 的内部。

蓄水池用明确的池底、池壁与水位闭合。渐变控制周边地质表现；水盆封闭层有确定厚度，不采用随机概率变薄。

## 6. 实际群系接入与上下文所有权

增加一个只服务本版矿床的轻量 `HydrothermalBiomeSource`，内部仍使用现有 `MultiNoiseBiomeSource` 处理其余群系。实际 quart 位置进入地点包络与独立 Y 范围时返回热液群系，否则返回普通来源。`collectPossibleBiomes` 必须同时包含热液群系和普通来源。

这样 BIOMES 填充、结构候选、群系定位和其他直接使用 BiomeSource 的调用得到同一套规则。只改区块 biome 容器、另留一套来源查询的方案不进入实现。

上下文附着到 `RandomState` 所持有的 `Climate.Sampler`，通过一个很小的 sampler 访问接口取得。初始化接点选择 `ChunkGenerator.createState` 开头：它同时接收完整世界种子和 `RandomState`，此时也能取得当前 generator，提供不加载区块的基础高度查询。原版 `ChunkMap` 在创建 `RandomState` 后调用此方法，再进入结构状态准备，因此应在结构的群系查询之前完成绑定。

这样每次群系查询通过原有 sampler 参数访问本维度上下文，避免静态的“世界名→种子”目录，也避免共享预设对象互相覆盖运行时种子。普通来源不分配矿床缓存；启用本包装来源才创建上下文。上下文包含种子、配置、必要的基础高度查询入口和固定容量缓存，不保存整个 ServerLevel。实施前用真实 Forge 启动确认相关 Mixin 的加载、绑定顺序和高度查询没有递归群系规划。无运行上下文的离线来源查询使用普通来源，不拿隐式种子零构造地点。

一次区块填充先拿到本块候选及相交情况。普通来源继续交给 `ColumnCachingBiomeResolver`；其结果外层再应用地点归属。修改现有 `instanceof MultiNoiseBiomeSource` 接线以识别包装内的普通来源，不能让整个世界失去原有列缓存。

第一版只注册热液规则，不建立通用特殊群系插件系统、扩展调度器或地区类型继承体系。

## 7. 地质体生成：一次按柱处理，限制在当前区块

在 CARVERS 完成后、常规装饰前，为实际相交区块调用 `HydrothermalGenerator`。先做 Y 和 X/Z 包围盒排除，再按 16×16 柱计算裂隙和洞厅的垂直区间。少量区间合并后，写入空腔、水体、封闭层、围岩和固定细节。

每柱最多投影到八个裂隙段、检查三个洞厅；洞厅椭圆截面需要的平方根每柱复用。逐 Y 写入阶段只做区间与材料判断，不重复计算气候、曲线距离或群系最近邻。只写确实变化的方块，复用可变坐标与小型暂存数组。

所有写入限定在当前目标区块。跨块洞厅、矿脉和水位从同一不可变布局重算。直接使用生成阶段的方块写入与高度图/流体后处理接口，保留 Minecraft 所需的 bookkeeping；首版不引入另一套裸写 Section 引擎。

保护水盆使用一个普通静态封闭层方块，复用现有岩石贴图，正常可挖掘，无 BE、无随机 tick。将它排除出矿石/雕刻替换集合，并加入 `minecraft:features_cannot_replace` 与 `minecraft:lava_pool_stone_cannot_replace`。原版 Lake 的挖空与屏障替换走不同检查，两处都需要覆盖。外表可覆一层方解石、石灰岩或凝灰岩，内部保持二至三格可靠池壁/池底。

同时精简热液群系自己的后续装饰。相邻群系的 feature 仍可能跨界，因此必须用真实顺序和反向顺序检验封闭层，重点检查 Lake、Geode、矿石替换和会改写地面的 feature。遇到某个已注册 feature 无视这些材料约束时，只给该入口增加针对保留水盆范围的相交排除；不在全世界每次 `setBlock` 上加通用拦截。

既有洞穴从干燥侧壁接入可接受；封闭层之外的背景矿石和细节可以自然变化。必有主池、主洞厅和干燥通路属于明确保留的结构。

## 8. 水体、喷口外观与资源

主池和相通的下部裂隙共用水位。上部浅池通过岩坎分隔，只有少量明确的短溢流；避免生成大量长瀑布与开放水边。世界生成直接形成普通静水，初始流体安定过程要计入测试。

第一版复用普通水、凝灰岩、方解石、石灰岩、玄武岩及现有矿石。新增可见资产限于静态封闭层及无 BE 的喷口外观；喷口模型可复用已有模型资源。喷口没有热量输出、矿物增长或周期性方块变化。大面积岩浆、岩浆块气泡柱不作为本群系标志，以避免与岩浆矿床混同，也避免引入其冷却与气泡更新成本。

矿化分带用来提高找矿的可读性，不声称是所有真实矿床共有的固定顺序：主裂隙以黄铁矿/铜建立连续走向；支裂隙安排锌、铅、银富集；外围以贫矿细脉和沉淀岩收尾；镍作为少量局部变体。

每个地点先确定有限的矿脉段和矿包，再按预定材料比例写入。大多数围岩仍是贫矿岩体；目标是沿线索找到富集段。基于旧版实际生成量统计每种矿物的有效方块/掉落期望，新版首轮目标保持在旧版同等矿床体积的 `±10%` 内。可见富集需要相应减少背景随机矿，不能在原产量上直接叠加整面富矿墙。

保留 `the_winter_rescue:hydrothermal_deposits` ID，现有群系采矿配方继续引用它；矿物块与原料 ID 不另建一套。既有城镇群系采矿表本轮不随可视矿脉自动增产。

## 9. 局部表现与持续运行成本

水下发射点使用少量局部矿物悬浮粒子，池缘发射点使用薄水雾。优先复用原版粒子，必要的方向和寿命在单个发射点限制，不增加专用渲染通道、shader 或透明体积雾。群系全域白灰粒子删除或显著降低，以真实客户端观察后选择。

喷口方块使用客户端原有 `animateTick` 机会，在近处产生少量粒子/偶发声音。每次最多产生一至两个粒子，初始寿命二十至四十 tick；发射点总数上限六。具体可见粒子峰值需要测量，超过预算先减发射概率和寿命。

服务端没有新增逐矿床任务、喷口 BE tick、方块实体、定时矿物生长、热源注册或流体热计算。地图上的静态矿床不因为存在而持续工作。原版流体在邻居变化、玩家破坏后的正常更新仍然存在，不能把整个场景的持续成本宣称为绝对零。

## 10. 旧 feature 与工具的具体调整

| 现有内容 | 第一版处理 |
|---|---|
| `hydrothermal_lake`、`hydrothermal_delta` | 从本群系随机大景观入口移除；由共同布局的池体和沉淀台地替代，解除错误的扫描后重采样 Y 组合 |
| `hydrothermal_geode` | 主要产量并入裂隙矿化；如保留，作为低频停止活动支区，使用地点已经给定的位置 |
| `hydrothermal_magma`、本群系岩浆湖/岩浆泉 | 从核心景观移除；以静态沉淀柱、深色矿化岩承担辨识度 |
| 高密度闪长岩团、方解石散斑 | 主要分布并入共享围岩与蚀变带；不继续叠加原次数 |
| 藤蔓 | 少量放在较干燥、停止活动的边区；活跃水盆核心不铺满植物 |
| 特有矿石 placed features | 重新分配为沿裂隙矿化与较少背景矿，并校准每种矿物产量 |
| 原版普通矿、地牢、泉水等 | 逐项检查对主池和路线的影响；保留无冲突背景内容，侵入核心的入口做局部排除 |

为热液规则增加一份小型工具配置，作为该规则的唯一手写来源；候选条件、布局参数和 salt 由生成工具导出到 biome source 的配置字段。运行时不读取 Python 文件，也不再复制一套独立的气候阈值。

当前 `normal.json` 的三条热液输出从普通 multi-noise 表移出，转作新布局的选址条件。普通表的其余记录逐项保留。现有 notebook 与保存 JSON 曾出现群系记录不同步，因此不盲目整表重新生成：先核对、保留已保存的深层冰霜记录，再让 notebook/实际导出入口读取共享热液规则。最终重新导出必须能得到审阅过的运行数据。

已有五维 spline 选择器的公共项提取、缓存和冰霜输出保留。热液地质体使用地点查询；气候适宜性预览不能冒充新热液群系的真实空间遮罩。明确标注旧实验脚本与当前生产导出入口，不重构所有历史工具。

## 11. 代码与数据边界

| 责任 | 最小实现 |
|---|---|
| 选址、形状参数、缓存 | `HydrothermalRegions`，内部使用小型不可变 Plan/配置记录；专门处理一种矿床 |
| 实际群系来源 | `HydrothermalBiomeSource` 及其 Codec 注册，委托现有普通来源 |
| 世界种子与上下文接线 | `ChunkGenerator.createState` 初始化及 sampler 的小型访问接点；每维度独立，随其对象释放 |
| 地质体与材料写入 | `HydrothermalGenerator`，一次按柱计算，固定数量裂隙/洞厅/水盆 |
| 局部视觉 | 一个无 BE 的喷口方块；一个普通封闭层方块，复用材质 |
| Python/数据 | 一个共享热液配置、现有生产导出入口、热液 biome feature 列表和 normal 的包装接线 |

不引入新的后台线程池、网络协议、存档地区数据库、通用图编辑器或可扩展地质模拟框架。客户端仅接收 Minecraft 原本的方块与粒子表现；服务器种子和完整布局无需同步给客户端。

现有运行时文件、其他生成规则和用户当前未提交改动均须按原内容保留。实施完成后为新行为补充 living docs，并按仓库格式追加 diary；本设计稿不充当“已经实现”的系统文档。

## 12. 成本上限与优化顺序

| 成本 | 本版限制与验证方式 |
|---|---|
| 地点查询 | 所属单元定位、一个候选缓存项、包围盒/形状判断；块内结果复用 |
| 候选气候采样 | 哈希通过后最多两类气候函数；负结果同样缓存 |
| 地形选址探针 | 每个采用候选最多五个不加载区块的基础高度查询；单独测冷规划峰值 |
| 布局缓存 | 每维度最多 `64` 项，包含正负结果；不可变条目、固定容量替换，允许确定性重算；目标总保留量 `≤256 KiB`，实施后实测对象大小 |
| 每柱形状计算 | 最多八条线段投影、三个洞厅截面；不逐方块重算 |
| 地质写入垂直范围 | 主体最多 56 格，加上下各 8 格蚀变，最多 72 格；完整 16×16 覆盖时至多 `18,432` 个候选方块位置，实际先按柱剔除 |
| 临时内存 | 每个生成任务目标 `≤16 KiB` 的地点专用暂存；不保存全区块三维距离数组 |
| 普通区块 | 先做区域/高度排除，保持原有列缓存和 FastNoiseEngine；不向原 density 树添加热液遮罩 |
| 长期运行 | 无新增服务端周期任务；仅使用原版流体更新和有限客户端视觉机会 |

这些是设计的结构上限和目标，不是已经测得的运行时间或内存值。方块替换、流体安定、光照、缓存未命中和对象头均需要实际统计。

首轮计时目标：普通区块的均值和 P95 不出现可重复超过 `3%` 的回退；热液区块完整生成均值/P95 争取不高于当前版，出现超过 `5%` 的稳定回退先定位热点再交付；全路线按实际地点频率加权的生成耗时争取不增加。以上比例是待审核验收目标，不是性能承诺。

优化顺序为：确认有没有丢失现有列缓存 → 消除重复候选扫描 → 复用按柱结果 → 减少重复读写 → 调整可选小细节。只实现这一条简单路径，基于实测热点继续优化；若为达标必须损失主池或必有通路等核心行为，回报具体差额供审核，不默默牺牲设计目标。

## 13. 实施顺序与真实验收

用户审核本稿后，按以下顺序完成实现和验证；各步是同一项已批准工作的内部顺序。

1. 固化热液现状和源表差异，生成当前版对照数据；建立共享工具配置，保留全部无关群系记录。
2. 完成有上限的区域规划、真实 biome source 与种子上下文接线；先验证普通列缓存、负坐标、查找命令和多维度隔离。
3. 完成两个必有洞厅、主池、通路和封闭层，跑实际 CARVERS/FEATURES/流体/光照流程；再加入矿化、第三侧厅与少量局部视觉。
4. 以当前版、新版仅主体、新版完整内容做同机器同配置对照。测试先用专用新世界；默认 normal 与其工具导出在验证通过后统一接入。
5. 完成完整矿床截图、剖面、分布及矿量表、计时与持续运行报告；更新实现文档和 diary，保留复现入口。

至少覆盖八个固定种子、三十二处采用地点、三十二个被拒绝的候选单元，以及单元边界和负坐标。既要完整生成所有相交区块，也要改变区块顺序、四线程并发生成、卸载后重开；缓存顺序改变不能改变布局或必有结构。

正确性检查包括：候选总包络不越单元；主洞厅尺寸达标；两个必有洞厅间存在可行走的干燥路径；主池水位一致且无非设计出口；邻块后续装饰不会打穿池壁；普通来源没有遗留独立热液碎片；没有热液方块写入地点范围以外。

实际运行还要在生成安定后观察至少十分钟，区分新产生的流体安定成本与静态场景持续成本；玩家挖开池壁后的流动属于正常行为。真实客户端固定视角比较粒子数、透明层开销和帧时间，不能只拿服务端生成计时说明显示性能。

计时采用固定区块、交替版本与多轮样本，同时报告冷规划、暖缓存、均值、P95、CPU、临时分配及配置；不能只选暖缓存和最好的一轮。使用真实 Forge 生成与现有运行时验证入口，不建立镜像实现的 JUnit 套件。原有峡谷独立实验只能提供方法参考，不能替代本版完整世界生成验收。

## 14. 用户审核时需要确认的设计取舍

- 接受固定候选单元与地点最小间距，换取确定尺寸、无相互裁切和常数范围查询。
- 接受两个必有洞厅加一个可选侧厅、至多四池六个视觉发射点，用空间组织建立特点。
- 接受热液首先是可探索的静态地貌与成矿表现，本版不增加任何固定高水温或喷口热量输出。
- 接受实际群系分布由地点布局决定，旧的三条热液气候输出转为选址条件，其余群系数据保留。
- 接受先在新测试世界验收；旧世界已生成区块不重写，新旧地区可能出现接缝，且现有 FH 读档行为会应用当前 biome source。
- 接受上述性能比例作为首轮验收目标。若实测显示简单实现不能满足，同时提交具体场景、热点和可选减法，保持性能代价可审核。

## 16. 2026-10-24 修订结果

用户后续批准了初版编码，又明确要求热液与后续矿床均不得新增 Mixin。已撤销本轮两个新增 Mixin、自定义 BiomeSource、原生成 Mixin 中的热液接线及入口注册，保留此前原有列缓存与 FastNoiseEngine。地质体算法文件暂留为未接入草稿，不作为已实现功能。运行中的 normal.json 仍为原有 multi_noise，未进行群系记录迁移。

后续应先围绕现有 configured_feature / placed_feature 解释所需能力；现成原版 feature 与新增 Java Feature 采用同一世界生成机制，不能因为更换术语就默认需要扩展。首要约束为无新增 Mixin、自然随机形态、共享可复用逻辑和无新增供热。实际群系边界继续由原气候表决定，地貌可以跨过原群系边界；此变更放弃本稿中的群系与矿床范围强制一致要求。

后续架构已整理在 [无新增 Mixin 的共享矿床生成架构](2026-10-24_03-16-48_deposit-feature-architecture.md)。新稿明确共享入口、配置内有限缓存、跨块写入、自然几何与统一验收；旧稿不作为实施接线依据。

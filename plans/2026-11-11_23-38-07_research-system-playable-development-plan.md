## 1. 最终交付目标

玩家在正常生存游戏中，能够发现研究、理解缺少的知识、完成实际实验，并使用研究解锁的配方或设备。整个流程不依赖管理员指令、创造模式发物品或手工安装示例数据包。

完成标准包括：

- 想法可以由行为或联络获得；主线项目也能由已有观察、成果承接，不必先有想法。
- 项目有清楚的发现、补齐知识、开始、执行和完成过程，未知内容按设计逐步披露。
- 单阶段研究、多阶段研究、可选任务和知识影响后续路径均能实际运行。
- 土制冶炼炉、冶铁炉、耐火砖三个项目具有完整内容、可操作设备、反馈和有效解锁。
- 保存、重登、服务器重启、区块卸载、组队协作及研究重开不会使流程卡死。
- 正式整合包的每项旧研究都有去向；替换、沿用和取消研究限制后的进度都能继续游玩。
- 玩家能在游戏内找到下一步要做什么；开发者能依据文档增加项目和常规事件条件。

**三个项目可玩是中期里程碑；正式整合包衔接、存档处理和完整游玩验收完成，才算本计划交付。**

保温杯改版、城镇研究所/研究室、联络小游戏留在后续扩展。当前先完成玩家亲自研究的流程；保温杯原有内容仍需在旧研究清单中妥善处理。

## 3. 实施时遵守的规则

1. **知识条件看学习入档后的有效知识。** 收到来件本身不算掌握；保留现有自动学习途径，不把所有入口改成必须手动点击。观察、通气、烧制等任务动作单独判定。
2. **想法获取与学习条件分开。** 必要前置仅限制行为触发与联络，不能顺手加到所有外部授予途径上。现有 `understanding` 是学习条件，不直接拿来代替行为触发条件。
3. **行为概率与联络代价分开。** 非必要知识提高行为触发概率；合法联络不随机失败，等待基准暂定 10 秒。概率、时间减免和实验数值在对应内容实施时配置。
4. **项目发现与开始分开。** 开始需要全部项目知识；项目可以包含多个想法及其前置，也允许作者省略其中部分前置。共享条件合并，不能把作者独立配置的项目要求强制改成自动展开全部想法。
5. **分支条件不混入开始条件。** 中途补齐的知识参与后续分支；已进入的分支固定，重新开始才重新选择。不同路径最终成果相同。
6. **先完成具体项目，再提取确有复用的能力。** 第一项只需单阶段时，不先实现任意流程图、通用脚本语言或材料模拟系统。
7. **两仓分工。** FH 实现通用机制、物品方块和界面；TWR 提供正式项目、材料集合、配方与进度安排。每步分别记录两仓改动和验证。

## 4. 开发顺序与里程碑

| 步骤 | 交付内容 | 玩家可见的结果 | 依赖 |
|---|---|---|---|
| M0 | 运行基线、三项目内容卡、旧研究清单 | 确定材料和工具在正常进度可获得 | 无 |
| M1 | 知识条件、项目发现和开始 | 能看到已知缺项；主线可不经过想法 | M0 |
| M2 | 行为想法与 10 秒联络 | 从实际探索发现项目，补齐知识开始研究 | M1 |
| M3 | 小号实验炉、样品提交、正式解锁 | **土制冶炼炉完整可玩** | M1、M2 |
| M4 | 多阶段、风道游戏、临时配方和原型转化 | **冶铁炉完整可玩** | M3 |
| M5 | 控温实验炉、结果观察、条件路径 | **耐火砖完整可玩，并验证分支规则** | M4 |
| M6 | 正式研究目录替换、权限与存档迁移 | 整合包前后进度接通，旧世界可继续 | 清单从 M0 开始；按 M3–M5 逐项推进 |
| M7 | 完整引导、多人/存档/性能及生存游玩验收 | **一套正式可玩的研究系统** | M1–M6 |

每一步都包含对应 UI、存档和测试。M7 是整体验收，不是到最后才做界面或保存进度。开发按里程碑完成情况推进，不在内容和第三方接口尚未核实前承诺日历工期。

## 5. M0：建立可开发、可游玩的基线

2026-11-12 实际进展（partial）：[内容卡与基线](2026-11-12_12-36-00_research-m0-content-baseline.md)、[81项旧目录](2026-11-12_12-34-00_research-m0-legacy-catalog.md)、[验证与交接](../diary/2026-11-12_12-40-00_research-m0-baseline-handoff.md)。完整 GameTest 源集编译、正式目录 preflight 与6项研究相关必需测试通过；未据此宣布正常生存可玩。用户明确决定原型鼓风口独立接受风箱试吹，M4 不提前要求建成冶铁炉。

### 要做的事

- 用当前 Java 17 环境复核生产编译、研究相关 GameTest 和客户端入口。重现此前的测试编译问题并处理其实际原因；临时排除测试仅能作为定向诊断，不能成为最终验收方式。
- 检查 `runClient` 当前加载的模组、数据与正式包差异，明确开发世界、正式包测试世界各自用途。测试世界、日志和截图留在生成目录。
- 为三个项目各写一张内容卡：触发入口、必要/非必要知识、开始知识、阶段任务、需要材料/工具、实验反馈、最终解锁和正常获取路线。
- 建立 81 项旧研究处置表：旧 ID、上下游、解锁效果、保留/改版/取消限制、目标项目/成果、旧存档处理、验收状态。先登记全量，再按三项目及其直接上下游细化。
- 验证第三方接点：IE 合金炉成型、Charcoal Pit 风箱实际供气和鼓风口替换、现有耐火砖烧成途径。必要时阅读依赖源码或做一个小型接入验证。

### 首先消除的进度循环

- 小号实验炉不能要求先获得最终炉砖或先建好正式合金炉。
- 绘图台、记录材料、观察入口和第一项研究所需材料必须能在研究开始前取得。放大镜是辅助工具，普通观察键也能完成必需观察。
- 风箱、原型鼓风口材料必须在冶铁炉解锁前可得；不能让“研究冶铁”反过来要求先完成同一项冶铁研究。
- 控温实验炉与砖坯必须在耐火砖研究前或研究期间可获得，不能依赖该研究尚未解锁的耐火砖。
- 最终成果的学习条件也必须可达，避免做完研究却只能把成果留在来件、始终无法获得对应配方；不能让成果的理解条件反过来要求先使用自己的解锁物。

**完成条件：** 三项目各有从现有生存进度进入的材料路线；基本编译/测试入口可用；第三方设备接口的可行性有源码或实际验证依据。尚待细化的参数列在内容卡上，不用占位指令冒充获取路线。

## 6. M1：知识条件、项目发现与开始

2026-11-12：[接口决定与验收](2026-11-12_13-02-00_research-m1-interface-decisions.md)已落实；[M1-B 实现交接](../diary/2026-11-12_13-29-45_research-m1-access-origins-handoff.md)记录了11项必需测试通过及尚缺的客户端/多人/独立进程重启验证。对话、回退点与后续进度见[开发协调记录](2026-11-12_13-00-00_research-development-coordination.md)。

### 数据与判定

- 增加可复用的知识条件：想法和成果按定义 ID 查询；观察按物品/方块/实体、标签及必要字段匹配，不把某次观察的 UUID 写成项目的固定前置。
- 分开表示“哪些知识让项目可见”和“开始研究必须有哪些知识”；支持观察、想法、成果，以及多个前置的全部满足。
- 保留要求的披露来源：同一个条件可以对应多个想法，获得其中任意一个即可披露；只属于未获想法的内容仍显示未知占位。
- 项目开始不再依赖唯一的起源想法。研究记录、图谱和命令同步改为能够记录多个来源或成果来源。
- 把新增的前置、可选知识、触发和阶段任务中的观察条件纳入观察用途与差异判定，包含尚未解锁的后续阶段用途。否则会出现“项目需要观察，却不允许这份观察入档”。

### 界面

- 项目页区分未开始、可开始、进行中、可完成、已完成；开始按钮说明当前缺项。
- 已披露要求显示名称、是否掌握和寻找方向；未知要求显示占位及作者允许的方向提示。
- 档案/来件状态明确区分。已经收到但尚未学会的知识，能够引导玩家去学习。
- 主线成果也能连到后续项目；界面不再假定每个项目都必须挂在一个想法下面。

### 验收

1. 项目要求 I、J 两个想法，分别关联 A/B、B/C：仅有 I 时公开 A/B，J/C 保留未知，B 只显示一次；未集齐不能开始。
2. 知识只在来件时不满足开始条件，入档后立即更新；自动学会的知识同样有效。
3. 只有成果前置的主线项目能够发现并开始，不必人为生成占位想法。
4. 仅用于新前置或后续分支的观察能够正常入档，已有观察去重和独立证据规则仍成立。

## 7. M2：行为获得想法与联络代价

2026-11-12：[M2 实现交接](../diary/2026-11-12_14-07-13_research-m2-behavior-contact-handoff.md)记录了17项必需测试通过；随后[手动回环更正](../diary/2026-11-12_14-18-30_research-m2-manual-loop-compatibility.md)恢复已知想法的另一条联络历史，并通过7项M2定向测试。自动行为仍去重，客户端实际体验待后续综合验收。

### 行为入口

- 提供按事件 ID 和条件分派的入口，先接入物品获得、物品使用、方块交互、观察完成、知识学会。一个想法可配置多个入口；命中任意一个就独立评估。
- “获得物品”覆盖拾取、合成、烧炼取出和容器取出等实际获取路径；移动背包槽位不重复当成获得。具体第三方获取方式通过同一入口补充。
- 先检查必要知识，再计算非必要知识的概率加成；成功后走现有知识产出与通知流程。已有想法不重复刷来件和通知。
- 给其他模组或 KubeJS 留可调用的自定义事件入口，携带玩家/队伍、事件 ID 和必要上下文；普通项目作者通过数据配置，不要求每项研究新增监听类。
- 事件“成功发生一次”与概率“尝试一次”的对应关系写进文档，处理主副手回调、持续使用及同一次操作的重复通知。

### 联络

- 选择成立的候选后开始计时，显示进度与取消操作，结束时产出想法。默认等待 10 秒；相关知识的减免参数集中配置。
- 必要前置和可选加成分开查询；建议可选加成读取已学档案，不强迫全部塞进桌面选择槽。
- 处理旧规则的 2–5 输入限制。对已经提供的候选想法，满足必要前置即可联络，必要知识为零或一项时也适用；不能因为 UI 要求两张札记而额外增加门槛。旧的多份观察比较规则如何兼容到候选发现过程，在本阶段定下。
- 明确零/单必要知识时的联络入口与候选披露方式，避免直接把所有未知想法列成目录。候选怎样被发现与取得候选后是否满足联络条件分别设计，见第 12 节。
- 行为触发前置不移到通用授予入口；外部获得想法仍能按原本途径进入来件或档案。

### 验收

- 同一想法能分别由两个不同事件触发；缺少必要知识只阻断行为与联络，外部获取不受这道门槛影响。
- 非必要知识改变配置中的行为概率/联络时间，合法联络完成后不会随机失败。
- 联络重复点击、关闭界面、退出和重登的处理一致，不重复产出。
- 土制冶炼炉和冶铁炉的触发范围符合内容集合；不会只在一种拾取路径下生效。

## 8. M3：先让土制冶炼炉完整可玩

2026-11-12：设备与实物提交节点 M3-A 已实现，完整21项必需测试通过，见[交接](../diary/2026-11-12_14-53-36_research-m3a-trial-kiln-sample-handoff.md)。下一步 M3-B 接入正式项目、两类成果和旧进度；客户端/正式包生存仍待验证，不能把机制示例当作正式项目交付。

这一阶段交付第一条正式流程：**获得可冶炼矿物 → 发现想法/项目 → 补齐观察知识 → 制作并试烧小炉 → 提交完好炉 → 建造和使用正式炉。**

### 实施内容

- TWR 配置可用该炉冶炼的矿物集合、粘土/沙子物品观察、想法、项目和成果。矿物集合要跟实际配方对应，不能只硬编码当前碰巧找到的两种矿物。
- 为三种小号实验炉提供配方、模型、名称和操作说明。建议先用同一套方块/物品逻辑表达三种配比及状态，避免复制三套设备代码。
- 试烧具有可见的进行中、完好和损坏状态。配比决定结果，两种错误成分损坏；时长、点火/供热和损坏说明在内容卡中定值。设备保存进度，并明确拆除时材料、烧制状态和产物如何处理。
- 将制作、试烧结果和实物提交接到当前研究记录。提交操作显示将消耗什么，服务端完成扣除与任务更新；损坏样品不能算完好样品。
- 为后续设备建立最小的任务完成入口：队伍、研究记录、任务、实际结果。先服务当前项目，后续再增加事件类型。
- 成果接通 `immersiveengineering:alloybrick` 配方，并承接 `immersiveengineering:multiblocks/alloy_smelter` 成型权限。玩家应确实能造出和使用这台炉。
- 对 `alloy_kiln` 做第一项新旧映射，更新相关配方和引导，验证新旧入口不会让玩家做两遍同一研究。

三种炉都要有完整制作和试烧体验；是否把“三种均试烧”设成硬性完成条件，仍需在本阶段内容卡里明确。当前确定的最终提交是完好的那一个，不要求提交两个坏炉。

### 完成条件

普通生存流程从触发到使用正式炉全程可玩；过程退出重进可继续；同队两人可分工制作和提交；一份样品不会重复扣除或反复完成任务。完成后依据实际代码补齐数据定义与玩家路线文档。

**到这里先安排一次完整试玩，再决定哪些操作确实需要抽象成通用机制。**

## 9. M4：用冶铁炉落实阶段、小游戏和原型

### 多阶段基础

- 项目加入有稳定 ID 的阶段、任务、说明、完成结论和阶段产出；简单项目按单阶段运行。
- 研究记录保存当前阶段、任务进度和阶段产出记录；阶段推进与产出一次完成，重登或多人同时操作不重复发放。
- 旧平铺 `requirements` 兼容为单阶段，现有证据、纸牌计算、实验台需求继续可用。
- 阶段页明确“现在做什么、在哪里做、完成后进入哪里”，保留已完成阶段结论。建议由玩家确认进入下一阶段；必需任务完成后仍可补知识或做可选任务，在确认进入时才选择分支。

### 第一阶段：风道小游戏

- 实现表达风道连通的简单游戏：有起点、出口、可操作区域和明确通关条件；地图、操作方式、失败重试在内容卡中定稿。
- 复用绘图台的研究任务定位和完成回调接法，游戏本身单独实现，不把现有纸牌游戏改名代替风道游戏。
- 支持开始、退出、重试和结果反馈。首版只看通关；解法、步数或表现不改变原型质量和最终成果。
- 通关后记录阶段完成，开放鼓风口原型配方，并说明如何制作和安装。

### 第二阶段：原型通气与观察

- 原型能作为实验对象放置并接收 Charcoal Pit 风箱的实际供气。首次有效供气转为正常鼓风口，保留正确朝向及继续使用所需状态。
- 观察转化后的对象才能完成对应任务。普通鼓风口的观察可以作为知识，但不能独自替代本次原型通气过程。
- 只保存判定需要的实验状态和对象关联；观察不为此复制整个 BlockEntity 内部数据。
- 原型丢失可以通过仍有效的原型配方重新制作，已有通关记录不要求反复重做小游戏；此为建议默认处理，见第 12 节。

### 临时配方与最终成果

- 在现有技术权限汇总中增加“进行中的研究阶段提供的临时配方”，与永久成果权限分开。
- 从小游戏完成持续到研究完成或放弃；关闭界面、换维度和重登不撤销。完成后由正式成果承接，放弃时移除对应临时来源。
- 暂时权限按研究记录来源合并：结束一个项目不能撤掉另一个项目或永久成果提供的同一权限。
- 更新 `charcoal_pit:sandy_tuyere` 现有正式配方的解锁安排；最终同时解锁鼓风口和 `charcoal_pit:main_bloomery`。
- 实际合成、JEI 展示和相关机器配方消费采用一致状态，不能只在研究页显示“已解锁”。

### 完成条件

小游戏通关 → 重登后仍可制作原型 → 风箱供气 → 原型转化 → 观察验证 → 正式配方解锁，整条路线可玩。中途离开界面、丢失原型、重复供气、放弃重开均有明确且可继续的结果。

## 10. M5：用耐火砖落实控温实验和研究路径

### 控温实验炉与烧制

- 新增控温实验炉方块、物品、配方、界面和使用说明；确定可获得的供热方式、温度范围、烧制时间和炉子自身的前置。
- 玩家能够设定温度，并看到设定值、烧制状态和产物。若采用升温过程，必须区分实际温度与设定温度，明确何时开始有效烧制计时。
- 砖坯配方与已有耐火材料链衔接。合适温度产出完好耐火砖，不合适温度产出碎裂耐火砖；需要时分别说明未烧足或烧坏。
- 确定中途调温、燃料中断、输出格满和卸载区块的行为，保存设备过程。参数按具体玩法设定，不扩展成所有材料共用的热化学模拟。
- 成功烧制与观察验证属于同一项研究的连续任务；用必要的样品状态或实验记录关联区分实验成果与随手取得的现成砖。
- **观察成功样品即可完成实验，不增加提交步骤，也不强制先失败一次或试遍全部温度。**

### 想法触发与观察用途

- 配置观察任意耐火砖，以及观察制作原料含耐火砖的方块/物品两个入口；两者都只提供想法获取机会。
- 确定“原料含耐火砖”是直接配方关系还是递归关系。建议首版用直接配方关系，特殊机器配方由适配器或内容标签补全，在配方重载后建立索引，观察时直接查询。
- 补齐内容卡中的其他触发入口和开始知识，让没有现成耐火砖的玩家也能走到实验。之前讨论的原料获取入口可以作为候选，尚不能当作已确认设计。
- 新物品/样品字段接入观察采样与用途判断；成功、失败、现成参考物的记录不会因过度去重而混成同一类。

### 第一例条件路径

建议用“准备分析 → 烧制验证”验证路径能力：观察过现成耐火砖类方块，或完成指定可选参考任务，可在进入烧制阶段时获得更具体的温度提示。普通路径也提供可操作的试验指导，最终目标保持相同。具体说明由项目内容卡确定。

- 进入下一阶段时读取当时的已学知识和已完成可选任务，选定任务/提示变体，并保存选择。
- 可选任务不阻止当前阶段完成；用于分支的参考知识不放进项目开始必需清单。
- 多个分支条件同时满足时使用作者明确的优先顺序，并有默认路径；不枚举所有知识排列组合。
- 新知识在进入分支前取得，和早已取得时效果一致；进入后补齐不会改变当前阶段，后续阶段仍可利用。
- 第一例可只改变提示。另用针对性测试验证“下一阶段任务集合减少”这一能力，确保通用规则确实支持用户提出的任务变化，不给正式项目硬加无关实验。

### 完成条件

两条路径均能烧成、观察并完成研究，获得相同成果。现成砖观察能触发想法或提供参考，但不能跳过本次烧制实验。已经进入的路径经重登、重启和补知识后保持固定；重开可以按新知识选择。

## 11. M6：正式内容、旧研究与存档衔接

### 正式内容落地

- 将正式项目、想法、成果、观察条件和必要标签放进 TWR 随整合包加载的数据中，建议使用现有 `kubejs/data/<namespace>/frostedresearch/knowledge/` 路径；在开发环境和发布包分别验证实际加载。
- 三项目之外的旧研究逐项决定：改为新项目、沿用并调整，或取消研究限制。沿用可以先保持简单任务，不要求每项都增加小游戏和新方块。
- 按生产链顺序迁移，保持每批上下游可玩；主线通过成果衔接，旁支通过适合其内容的想法入口发现。
- 每项同时核对配方、设备使用、多方块成型、任务书、语言与其他旧效果。不能只迁配方而漏掉能力或后继入口。
- 取消研究限制时，同时移除其残留锁定和前置引用；原有配方材料、设备条件继续存在。
- 升级实际服务器时处理 `config/fhresearches/` 中已迁出的旧文件，避免仓库删除了条目、服务器残留配置却仍被加载。以运行时目录和权限结果验收。
- 将主线前后衔接与多想法项目纳入正式内容；若尚无合适内容承载某条通用规则，至少提供独立验收数据，明确不是正式剧情。

### 两类迁移分别处理

**已有知识系统存档：** 从当前 `KnowledgeState` schema 2 升级，旧研究记录转成单阶段记录，保留已有完成、放弃和成果历史；没有起源想法的新记录可以正常序列化。阶段、任务和分支使用稳定 ID，重排界面不改变进度。

**旧研究系统存档：** `legacyIds` 只处理旧标识重命名，不能直接把旧研究变成新知识。按处置表建立旧完成项/已授予效果到新成果的映射，并标记已经迁移，重复登录或重载不重复发物品奖励。

建议优先保留玩家已获得的使用权限和已经完成的成果。旧研究的部分进度只在语义对应时转换，无法对应的条目列出具体处理方案；不把旧进度百分比机械换算成新的实物实验完成。

### 状态与恢复

- 保存当前阶段、已进入分支、任务进度、临时配方来源、实验设备局部进度；从保存状态恢复，不在登录时重新选择分支。
- 内容更新造成任务改名或移除时，提供明确的旧 ID 映射和进度承接；暂时缺少定义时保留原记录，恢复定义后可继续。
- 队伍合并出现同项目多个进行中记录时，制定合并/保留规则；不能覆盖掉另一份进度或重复发成果。
- 验证新建世界、已有旧研究进度世界、已有知识示例进度世界。迁移测试使用存档副本，结果写明实际迁移了哪些状态。

**完成条件：** 81 项处置表每项都有已实施去向及验证记录。允许有意保留的旧项目继续运行，但不能要求玩家为同一权限重复研究，也不能存在未处理的旧研究锁或断开的下游。

## 14. M7：验证、引导和发布准备

### 自动验证

使用当前 [Forge GameTest 体系](../src/gametest/README.md)，继续维护相关现有测试，不重新引入已移除的 JUnit。

重点新增行为测试：

- 已知/未知要求、任意类型前置、入档口径与观察用途。
- 多事件触发、必要知识限制范围、概率参数、联络完成/中断。
- 单阶段兼容、多阶段推进、可选任务、分支固定与中途补知识。
- 三种小炉试烧、提交消耗；风道通关、原型通气与转化；控温烧制与观察验证。
- 临时权限和永久权限相互承接，同队协作、队伍变化及重复完成处理。
- 实验台既有计时/暂停路线的回归；新增研究、设备和权限经保存重载后保持一致。
- 两类存档迁移、取消研究限制后的实际可用性、正式定义的引用与上下游衔接。

实现过程中使用 `compileJava`、`compileGameTestJava`、`runGameTestServer -PgameTestNamespaces=...` 运行相关检查；新增测试 namespace 后写进测试 README。旧目录仍使用 `validateResearchCatalog -PresearchCatalogDir=<TWR 的 config/fhresearches 路径>`，新定义同时验证正式加载与配方/成果引用。检查通过后随改动范围推进，不无理由重复全量构建。

### 客户端与玩家验收

- 复用 `runObservationUiClient` 做观察回归；现有 `runResearchUiClient` 主要覆盖旧图谱，需另补新项目页面与执行流程的客户端检查。
- 在实际客户端检查缺项提示、未知占位、任务说明、阶段结论、联络计时、小游戏、设备菜单、JEI 和成果通知；覆盖常用 GUI 缩放与长文本。
- 复核手持观察遮罩、背包/容器操作和放大镜视觉；真实键鼠操作单独确认，不以模拟回调代替手感验收。
- 在正常整合包新世界中从材料获取玩通三项目，随后继续至少一段下游生产链；无管理员完成指令、无创造发放关键材料。

- 中途遗失原型、调错温度、丢弃样品或忘记下一步时，游戏内有可理解的反馈和继续路线。
- 在正式研究目录规模下检查事件处理、知识页刷新、图谱、存档和同步表现。关注是否出现整页反复重建、全量扫描或可感知停顿，有证据再做针对性优化。

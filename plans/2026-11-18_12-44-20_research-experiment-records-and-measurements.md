## 目标与范围

让研究能够使用肉眼可见的现象、仪器测得的数值，以及设备保存的实验过程结果。玩家通过观察、操作仪器或读取报告获得相应知识，研究按内容需要使用这些知识。

本轮讨论已明确：

- 鼓风口、土制炉现有流程通过 BlockState、物品类型或已有样品信息即可表达，保持简单。
- 精确温度、电压、频率等数据需要明确的测量来源；直接观察可以记录外观变化、异响等定性现象。
- 实验记录继续属于观察知识；取得它的交互可以是观察、测量或读取报告。
- 当前读数与历史过程分开。冷却后测温得到当前温度；烧制温度、保温时长来自实验时保存的记录。
- 控温实验炉是通用设备。烧制记录也应供多种材料、多个研究使用。

首版完成烧制记录这一条可玩的闭环，不扩展电学或声学模拟，不要求给所有设备添加专用仪表。

## 已核对的现状

| 代码锚点 | 现状及实现影响 |
|---|---|
| `ObservationSampling.block/entity` | 自动采集环境和方块状态；没有通用 BlockEntity / 多方块数据采集器。 |
| `Observation`、`ObservationFields` | 观察为 UUID 标识的不可变快照。`context.*` 字符串、`field.*` 数值只适用于方块/实体；物品观察不能直接使用这些字段。 |
| `ItemRetrieval.registerField` | 物品可注册 `item.*` 字符串采集器；没有通用的物品数值测量接口。 |
| `KnowledgeCondition`、`FieldCondition` | 现有条件可以匹配有类型字段；需要将新增实验数据接入同一查询和用途判定。 |
| `ObservationSessions`、`KnowledgeService.observeResearchTarget` | 新鲜观察能直接推进当前研究任务，不必先入档；本次实验样品另检查真实物品/方块上的 `ResearchSampleBinding`。读取报告还没有对应入口。 |
| `ControlledFurnaceBlockEntity.start/tick/writeCustomNBT/readCustomNBT` | 已锁定批次温度、时长、产物和实验绑定；目前没有升温曲线。成功试验产物写入绑定，失败品没有有效成功试样绑定。尚无独立烧制报告。 |
| `ObservationPresentation.details` | 普通观察详情会显示环境温度；它来自 `WorldTemperature.block`，不能当作设备内部或试样的测温结果。 |
| `ResearchNotes.canExport` | 普通物品观察不能抄录为笔记。实验报告的传播需要明确接入，不能直接放开全部物品观察。 |

核对日期为 2026-11-18。实施前重查上述接点，尤其注意其他对话可能正在修改知识界面。

## 玩家交互

### 三种获取方式

| 方式 | 玩家动作 | 记录内容 |
|---|---|---|
| 直接观察 | 原观察键或放大镜检视对象 | 外观、结构、可感知现象；有专门定义时生成对应实验观察。 |
| 即时测量 | 操作仪器，读取读数 | 对应目标在测量时刻的数值、单位、仪器来源。首版预留接点。 |
| 读取实验报告 | 在设备中查看已完成实验，选择「记下实验记录」 | 已完成批次的加工条件、持续时间与结果。首版实现。 |

记录正文使用自然语言；对实验有用的数值、单位和来源可以显示。字段名、NBT 路径、内部 UUID 不进入玩家操作文案。

普通检视试样只提供它实际能呈现的信息。历史温度通过明确的「烧制记录」入口读取；如果试样携带了设备记录，显示它的设备来源和记录时间。一次操作相关的信息集中展示，避免连续弹出多张确认页。

获得记录进入现有来件/学习流程；研究现场直接读取记录可以像新鲜观察一样登记任务进度。档案知识用于联络和项目开启时，继续遵循现有「学会才算掌握」规则，不引入自动学习所有读数的例外。

### 首个应用：控温实验炉

建议流程：启动试烧 → 设备记录批次 → 取出试样 → 阅读烧制记录、观察外观 → 按研究要求完成任务。

- 炉内置记录功能，首版不用再制作独立温度计。
- 成功和失败的试烧都留下记录，方便比较；失败记录不因此成为成功实验的证明。
- 炉 GUI 提供最近完成批次的报告；试验样品携带同一份报告快照，取出、换炉或开始下一批后仍可读取。
- 不保存无限炉内历史。炉保留最近报告，已经附到试样、收入札记或抄录的记录独立保存。
- 普通耐火砖当前完成条件保持「观察本次成功试样」。先通过示例任务验证读取温度/时长的能力；是否把正式研究拆成「读记录＋观察外观」两项，见待定项。

## 数据与扩展方式

### 记录模型

推荐给现有观察增加可选的结构化实验载荷，保留 `KnowledgeKey.Kind.OBSERVATION` 和原始记录 UUID。普通观察缺少该载荷时保持原语义。以下是拟议字段，不是已有数据格式：

| 信息 | 含义 |
|---|---|
| 观察主题 ID | 例如「烧制实验记录」，标识模板；不替代每条记录自己的 UUID。 |
| 对象 | 实际被测材料、试样或设备；与来源仪器分别保存。 |
| 获取方式和来源 | 直接观察、即时测量、读取设备报告；说明数值来自哪里。 |
| 有类型的字段 | 字符串、数值及单位/显示规则；例如结果状态、恒温段温度、有效加工时长。 |
| 批次信息 | 同一份报告的稳定批次身份、发生时间，以及存在时的队伍/run/实验关联。 |

实验数值使用独立字段查询入口，拟为 `measurement.<name>`；不把数值全部塞进 `item.*` 字符串，也不更改既有环境 `temperature` 的含义。物品、方块和设备报告都能承载实验载荷。

- 同一原始报告反复读取或转抄保留身份。新的即时测量或实验批次才产生新记录。
- 测量发生时间、读取时间分别处理；后来打开报告不把历史测量变成当前读数。
- 未采集值为未知，不补成 0；旧物品没有报告时展示「未记录」。
- 报告保留少量研究所需事实，不复制整份 BlockEntity NBT。
- 批次身份与知识差异分别判断。新 UUID 不代表一定需要再学一条知识；按研究条件保留有意义的差异。
- 普通知识可以传播；是否满足「本次研究亲自完成的实验」，继续由任务与实际实验关联判断。

### 数据包与 Java 的分工

数据包定义观察主题、名称与正文、目标范围、使用的采集器、字段标签和单位、研究条件。Java 采集器对接设备实际状态、指定 NBT 数据或多方块接口。

首版做一个通用烧制报告采集器；换材料或研究只需改内容数据。复杂设备再补适配器，不要求每个观察主题各写一个 Java 类。

新条件须能用于联络输入、行为想法触发、项目知识条件和阶段任务，并接入已有观察用途/差异索引。作者应能声明「仪器读数为某范围」或「某类设备的烧制报告」，不依赖显示文本。

实验记录经现有知识同步和笔记载体保存；只为符合定义的实验报告接入传播能力。转抄不触发一次新的现场实验，也不修改报告对象、来源或批次。

## 开发步骤

| 阶段 | 工作与交付 | 完成条件 |
|---|---|---|
| M1：最小记录契约 | 确定可选实验载荷、定义加载、类型/单位查询、旧数据读取；提供一份烧制记录示例。 | 普通观察照常解码；物品报告的数值可比较；同一报告保存、同步、重读后身份和内容不变。 |
| M2：取得与使用知识 | 接入读取记录交互、预览/收件、学习、用途/差异、联络和研究条件；复用现场任务处理所需的实验关联。 | 读取报告能产生知识并完成示例任务；仅转抄不算重新做实验，未入档不满足普通项目开启条件。 |
| M3：控温炉批次报告 | 在现有批次结算点生成报告；持久化最近报告和试样携带数据；补 GUI 阅读入口。 | 成败记录可比较；换温度、开始下一批、卸载/重启均不改旧报告；取消不产生完成报告。 |
| M4：内容与兼容 | 用耐火砖场景验收；补通用内容模板、玩家提示与存量数据处理。 | 现有三项研究仍可完成，新增示例能用测量条件推进；无报告的旧物品仍按原规则使用。 |

M1–M3 每步先验证再推进，接口稳定后再展开仪器物品、复杂多方块或其他模组适配。

### 控温炉温度语义

当前 `temperature` 是下一批设定，`locked_temperature` 是本批工艺参数。运行中改设定只影响下一批，报告必须使用本批锁定值。

首版继续采用理想恒温的简化模型，以本批锁定温度表示模型中的恒温段温度，界面明确来源。有效加工时长采用加载状态下实际完成的加工 tick，展示秒数按 20 tick/s 换算；不计离线或区块卸载时间。

不生成当前模型没有测得的升温曲线、试样内外温差、冷却速度。以后有真实温度变化时再扩展最高温度等字段，保留新旧模型来源的区别。

## 验证与兼容

- **数据与知识**：新旧观察读写；数值范围/单位；未知值；重复报告；差异学习；定义重载；联络与开启研究的入档要求；笔记转抄。
- **炉批次**：成功、欠烧、过烧；运行中改温；下一批覆盖炉内最近记录但不改旧试样；取消、拆炉、输出等待及保存/重启。继续覆盖既有一次交付规则。
- **研究现场**：同队读取；本次任务关联；普通成品、外队、旧 run 或转抄报告的各自用途。检查两个任务引用同一批次时不会因先完成一个而丢失另一项所需关联。
- **实际界面**：烧一炉、取样、读记录、观察结果、保存退出重进；确认玩家能分辨设定温度、记录温度、当前环境温度。
- **旧内容回归**：鼓风口、土制炉不改用新机制；普通耐火砖既有进度与已完成成果继续有效。现有批次按原规则结算，不从缺失信息编造报告。

只为上述行为增加有意义的定向测试。编译通过、服务端测试通过、Playtest 部署和实际客户端验收分别记录。修改 TWR 时先读取其适用说明，两个仓库分别检查与提交；不修改无关构建设置。

## 待定的内容选择

1. 耐火砖正式研究是否新增「读取烧制记录」为必需任务，还是先作为辅助信息；框架用示例项目完成验证即可。
2. 普通观察详情中的精确环境温度是否继续直接展示。无论如何，环境温度都不能替代设备/试样的测量结果；已有记录不改写。
3. 后续首个独立仪器选择温度计还是其他设备；电压、声音和复杂多方块的具体玩法另定。

## Frozen Capacity Decisions

以下是从仓库接口讨论中继承的已定基础。若最终拓扑无法直接表达这些规则，必须把冲突重新列为设计决策，不能在
实现中静默改写：

- 运力表示持续占用的服务能力，不是每搬一件就扣除的库存；不跨日囤积。
- 零距离下传输 `1 item/s` 占用 `1` 运力，不引入参考速率 `R_ref`。
- 权威占用保留有限 `double`，不增加 `Q` 或 `ceil(raw / Q) * Q` 量化层；复用前置运力模型的局部 `8 ULP`
  容差比较，不复用 `TeamTownResourceHolder.DELTA`，也不修改权威数值。
- 已绑定设备只保存一个服务端已接受的 `rateItemsPerSecond`；已有连接的玩家上调失败时整条旧预约不变。P2P 初次
  绑定准入失败时保持未绑定且不保存目标，不建立带目标的 `rate=0` 禁用记录。供给短缺不改设置速率，而是统一按全镇
  比例计算有效速率。
- 红石停机不修改服务端已接受的设置速率或绑定，但使受影响连接暂时休眠：有效速率和占用运力均为 `0`。红石恢复
  后按原设置速率恢复预约；若此时全镇运力不足，进入统一的比例短缺，不把设置速率静默降低。
- 端点、区块或维度未加载时只暂停实际物品移动，继续按已接受的设置速率和权威距离占用运力，与仓库接口的未加载
  行为一致。未加载期间实际搬运量为 `0` 且不积累突发额度，但不能像红石停机一样释放预约。
- 同一条 P2P 绑定的两个 `GlobalPos` 固定，其曼哈顿距离不会自行变化，也不需要周期性 metric 刷新。改绑是原子删除
  旧连接并建立一条从新端点位置派生距离的新连接，不是旧连接距离变化。初次绑定和改绑都属于玩家准入操作，语义类似
  玩家放置仓库接口：服务端按新距离和设备设置速率检查所需占用，不能绕过准入直接制造全镇短缺。玩家在菜单中主动
  提高 `rateItemsPerSecond` 同样走玩家上调准入和拒绝合同。
- 非整数 `items/tick` 复用前置计划验证后的小数余数模型，不因设备空闲积累整数突发额度。
- 初次绑定固定使用通用 `TransportConsumerParameters` 提供的默认请求速率执行准入；未绑定终端不提供预先调整
  绑定速率的额外状态。准入成功后才保存已接受速率并允许玩家在发送端菜单调整；改绑沿用旧连接已接受的设置速率。
  默认最大值及配置来源同样优先复用通用参数，P2P 如需不同边界必须给出玩法理由和独立测试。

## Direct-link Formula

同维度、任意一个发送端点直连一个接收端点时，每条有向连接的距离与占用公式冻结为：

```text
manhattanDistance = abs(senderX - receiverX)
                  + abs(senderY - receiverY)
                  + abs(senderZ - receiverZ)
distanceFactor = 1 + 0.05 * manhattanDistance
reservedTransportCapacity = rateItemsPerSecond * distanceFactor
```

这使距离每增加一格只增加基础占用的 `5%`，不会指数增长，也没有参考速率或向上量化。该公式只有在“单条链路、
同维度、两端位置明确”时定义完整。多来源收货端对每条入站连接分别应用公式；双向端互联对两个方向分别应用公式。
跨维度、中继或共享链路必须先确定怎样计距和由谁占用，不能用伪造坐标差静默代替。

T01 的实现把 `0.05` 作为 `TransportConsumerParameters.p2pDistanceCostPerBlock` 的源码默认值，并通过
`FHConfig.SERVER.TOWN.TRANSPORT_CONSUMERS.p2pDistanceCostPerBlock` 提供运行时覆盖；该字段与仓库加权距离系数独立。

### Device forms and names

- 玩家可见名称使用“发货终端”“收货终端”和“双向物流终端”，避免使用视角不明确的“输入端”“输出端”。代码内部
  可以继续使用 input/output 等方向术语，但玩家反馈必须明确写出发送方和接收方。
- 三类终端均表现为一格的复古工业货运设备，共用铆接钢板、线缆盒、仪表和状态灯等基础外观，并符合项目既有的
  `16x16` 像素贴图与沉浸工程式复古未来风格。
- 发货终端使用内凹装货口、汇聚箭头或压入式滚轮表达发送；收货终端使用外凸卸货槽、发散箭头或短传送带表达接收。
  角色差异必须同时依靠轮廓和方向图形，不能只依靠颜色。
- 发货终端和收货终端各有一个明确的库存连接面，分别自动从相邻物品能力取货、向相邻物品能力交货。双向物流终端
  不主动扫描或搬运任何相邻容器，但六个面都向漏斗、管道等外部自动化暴露同一受限物品能力。
- 三类终端可按玩家视线朝向上下东南西北六个方向，不保留固定世界顶面。发货端和收货端的库存连接面始终位于角色
  正面的反面，并使用含边框严格为 `6x6` 像素的凹入开口：发货端为蓝色 `shipping_terminal_port`，收货端为橙色
  `receiving_terminal_port`。其余非功能面使用带信封标识的 `frostedheart:block/transport_station` 货运站材质；双向端
  没有专用开口面。
- 世界中不显示跨越整条链路的永久光束。配对时可以临时显示端点连线；实际传输只在两端播放短暂机械动作、灯光或
  少量粒子。
- 方块状态至少要区分未配对、已配对空闲、正在传输、红石停机、运力短缺、收货端无可用容器和对端未加载；不得用
  笼统的“目标不可用”混合这些不同事实。最终颜色、动画和模型资源在 T07 确定，但角色图形与运行状态图形不得互相替代。
- 发货/收货终端使用端点终端界面，双向物流终端使用带 4+4 缓存区的独立界面；三类标题必须明确显示具体终端类型。
  两种界面顶层都只保留“终端”和“过滤”，双向端在过滤页内再选择“输入过滤”或“输出过滤”。输入过滤对应待发货
  方向的发送过滤，输出过滤对应已接收方向的接收过滤。
- 双向端四格待发送与四格已接收在界面中分组并分别标注“待发货”“已接收”。相关终端行完整显示对端坐标；运力显示
  同时包含剩余值与城镇总值。方向和速率使用完整终端名，并把当前方块写作“本终端”，例如“本终端->收货终端，
  20物品/秒”，不再只显示易混淆的尖括号。双向端的两个方向优先分别使用一行正常字号；单个本地化方向仍过长时，应按
  “来源 ->”与“目标，速率”继续换行，坐标顺延到全部方向行之后，不得缩小或越出面板。菜单首个同步包前使用客户端
  BlockState 状态，不能闪现“未配对”；右上状态
  使用正常字号并与标题互相避让。服务端的打开菜单、调速和过滤授权不得把已绑定终端短暂写成 `UNBOUND`。拥有出站方向的
  终端可在速率框内滚轮调速，步长与仓库接口一致：`1/8/16/64 items/s`。

### Order-independent route-card pairing

- 配对工具暂称“货运路线牌”。路线牌记录两个被玩家分别右击的端点，点击顺序不决定传输方向；方向完全由两端类型
  按下表推导。
- 第一次点击把稳定端点位置和已知类型写入路线牌。第二次点击后，服务端重新读取两个位置并统一验证方块类型、城镇、
  队伍、权限和维度规则，再从权威位置派生距离并建立或原子替换绑定事实；不能信任路线牌保存的类型、距离或占用。
  初次绑定和改绑都按玩家上调语义执行运力准入；只有准入成功才提交新绑定和预约。待选阶段路线牌切换材质，tooltip
  显示所选端点类型、坐标和下一步提示；成功、解绑或清空选择后恢复常规模型。
- 配对成功后清空路线牌的待选端点，并把这次成功连接的稳定标识写回路线牌。路线牌对空气或无关方块右击时解除它
  当前记录的连接；如果该连接已经被后来操作覆盖，旧路线牌只能报告连接已失效，不能误删替代它的新连接。只有一个
  待选端点而尚未形成连接时，对空气或无关方块右击只清除本次选择。
- 配对因事实验证或运力准入失败时不修改任何既有绑定或预约，也不在终端中保存未生效目标；初次绑定保持未绑定，改绑
  保留旧连接继续运行。路线牌可以保留可继续使用的第一次选择以便玩家修正第二端点，同时向玩家说明失败原因，但该
  临时选择不是终端绑定事实。
- 同一个端点不能与自身配对。两个发货终端或两个收货终端互不兼容，服务端必须拒绝建立连接。

| 端点组合 | 建立的方向 |
|---|---|
| 发货终端 + 收货终端 | `发货终端 -> 收货终端` |
| 发货终端 + 双向物流终端 | `发货终端 -> 双向端已接收缓存区` |
| 收货终端 + 双向物流终端 | `双向端待发送缓存区 -> 收货终端` |
| 双向物流终端 + 双向物流终端 | 同时建立两个相反方向 |
| 发货终端 + 发货终端 | 不兼容 |
| 收货终端 + 收货终端 | 不兼容 |

### Binding cardinality and ownership

- 首版中，一个发货终端最多拥有一个目标；改绑属于替换该发货终端的唯一出站连接。不支持广播式一对多传输。
- 一个收货终端可以同时接受多个发货终端。每个发货终端分别拥有自己的连接、设置速率和唯一运力预约；收货终端只
  维护入站连接索引，不为同一传输重复预约。
- 双向物流终端首版最多绑定一个对端，不能同时加入多条连接。该限制避免它同时进入互相冲突的缓存锁定模式，也把
  双向端多对端路由留在后续独立设计中；不影响收货终端已经冻结的多来源汇聚。首版不支持广播。
- `发货终端 -> 收货终端` 和 `发货终端 -> 双向端` 的预约由发货终端拥有；`双向端 -> 收货终端` 的预约由双向端
  拥有。任何拆除、改绑和失效清理都必须由同一个稳定预约键完成，不能由接收方再登记一份占用。
- 一个收货终端存在多个可发送来源时，传输调度必须使用可持久化或可确定恢复的轮询游标，避免端点坐标、区块加载或
  Map 遍历顺序永久偏袒某条连接。
- 收货终端界面必须列出全部来源及各自坐标、设置速率、有效速率和状态，并允许逐条解除；发货终端只显示自己的唯一
  目标。
- 创建、改绑和解除连接的权限属于城镇所属队伍的所有成员，不再额外限定镇长或终端放置者。
- 多人竞争以服务端实际处理顺序为准：最后一个成功通过验证的绑定操作覆盖同一发货端或双向端的旧绑定；验证失败的
  后续操作不得破坏仍有效的旧连接。向同一收货端增加不同来源属于追加，不覆盖其他发货端已有的入站连接。
- 同一对有向端点之间最多存在一条稳定连接。即使玩家用不同路线牌重复绑定同一对端点，服务端后处理且成功的绑定也
  必须原子替换先前连接并使旧路线牌失效，不能追加第二条预约、第二份速率预算或第二次传输调度。
- 双向端的单对端绑定必须在双方保存相互一致的索引。任意一方改绑、主动解绑、被拆除或因生命周期规则失效时，另一
  方同步解除旧索引；双向端互联时还要原子注销两个方向的预约，不能留下单边绑定或幽灵占用。

### Bidirectional-terminal buffer contract

- 双向物流终端有两个彼此独立的四格缓存区，玩家可见名称为“待发送”和“已接收”，总计八个真实物品槽。“待发送”
  在未锁定时只接受玩家或外部物流插入，不允许玩家或外部物流提取；“已接收”在未锁定时只允许玩家或外部物流提取，
  不接受玩家或外部物流插入。
- 远端送达的物品只能进入四格“已接收”缓存区，绝不能重新进入“待发送”或被自动回送。目标不能接受时保留来源侧
  物品并形成背压，不允许因缓存已满复制、吞失或丢出物品。
- 双向端与发货终端绑定时充当接收方并锁定整个“待发送”缓存区；双向端与收货终端绑定时充当发送方并锁定整个
  “已接收”缓存区。即将锁定的缓存区非空不再阻止绑定，已有物品原位保留。
- 锁定缓存区不向外部自动化暴露插入或提取能力，也不参与 P2P 自动发送或接收，但玩家始终可以在终端菜单中手动取出
  其中的遗留物品；锁定状态不允许玩家再手动放入物品。解除连接后恢复该缓存区的正常能力。
- 两个双向端互相绑定时都不锁定缓存区。每一端的四格“待发送”自动传到另一端的四格“已接收”，两端分别相当于
  对方的发货端。
- 双向端互联在权威模型中是两条有向连接，不是一条隐藏的共享带宽。A、B 分别保存自己的出站设置速率并分别拥有
  预约；同距离下总占用为 `(rateA + rateB) * distanceFactor`。任意一端把速率设为 `0` 即可得到实际上的单向传输，
  但不会锁定两个缓存区。

### Redstone, dimensions, menus, and filters

- 首版中，终端收到红石信号时进入停机。发货端暂停唯一出站连接，收货端暂停全部入站连接，双向端暂停与该设备有关
  的所有发送和接收方向；连接和设置速率保留，但这些休眠方向的有效速率和占用运力都是 `0`。
- 首版只允许同维度端点配对。服务端在建立和恢复连接时都要验证双方维度相同；不定义跨维度距离、附加成本或升级。
- 三类终端菜单都增加“相关终端”和“物品过滤”子页面。“相关终端”显示本地全部连接、对端位置、连接状态、速率及
  对端过滤内容，并提供与权限一致的逐条解除操作；收货端在此列出全部来源。
- 发货端配置发送过滤，收货端配置接收过滤，双向端分别配置发送过滤和接收过滤。一件物品只有同时通过该有向连接的
  发送方过滤与接收方过滤才允许移动；对端过滤在“相关终端”中只读展示，修改仍须操作拥有该过滤器的终端。
- 每套过滤器都支持白名单和黑名单模式，默认模式为白名单。没有配置任何过滤条目时无条件放行全部物品，不把空白名单
  解释为拒绝全部；添加第一个条目后才按当前白名单或黑名单模式过滤。
- 过滤器默认使用精确模式，匹配物品种类及物品数据/NBT，忽略堆叠数量；玩家可以为每套过滤器切换模糊模式，只比较
  物品注册种类并忽略数据/NBT。双向端的发送与接收过滤器拥有彼此独立的条目、白/黑名单模式和精确/模糊模式。
- 过滤名单容量、幽灵槽布局和复制操作属于 T07 界面实现细节，不再阻塞 T00 的 ready 决定。

### Network composition boundaries

- 首版不提供设备内部的直接中继。任何终端收到的物品都不会由 P2P 系统自动转入下一条连接；双向端的“已接收”也
  绝不能自动流入自身“待发送”。
- 玩家可以使用箱子、漏斗、管道或其他外部物品能力作为中间缓存，把多个独立 P2P 路段串联为中继。每一跳仍拥有独立
  的稳定连接、过滤、设置速率、距离成本和运力预约，不能被折叠成一条隐藏路径。
- 首版不提供频道号或同频道自动组网；所有 P2P 移动都必须归属于路线牌显式建立的端点连接。
- 由于首版禁止内建中继，发货端不能接收、收货端不能发送，双向端又只有一个对端且“已接收”不会自动进入“待发送”，
  P2P 层自身不能形成物品可连续传播的多跳循环，因此不需要对纯 P2P 连接执行全局有向环检测。
- 玩家可以用箱子、漏斗、管道或其他外部物流把若干独立 P2P 路段接成物品闭环。此类闭环允许存在，也不由 P2P 系统
  跨外部物流检测或禁止；每一段 P2P 仍独立调度和计费，并保证自身受控失败路径中的物品守恒。物品是否持续循环由玩家
  搭建的外部物流、背压、过滤和库存容量决定。
- 双向端互联形成的两个相反方向是明确允许且可审计的连接，不属于需要拒绝的重复链路。重复链路专指相同 sender、
  receiver 有向端点对被登记多次。

### Transfer execution and lifecycle

- 有向连接由发送方主动推送，接收方不主动从来源拉取。发货终端和处于发送模式的双向端都是发送方；收货终端和
  处于接收模式的双向端只接受推送。
- 来源库存按 slot 索引从小到大扫描，选择第一个非空且同时通过发送过滤和接收过滤的物品。这里的“靠前”指最靠前的
  可发送 slot；某个靠前 slot 被过滤器拒绝时可以继续检查后续 slot，不能让一件不合规物品永久堵塞整个来源库存。
- 没有任何可发送物品、双方过滤器没有交集或目标当前不能接收时，本次不移动物品，也不消耗可搬运数量。实现可以在
  证明玩家可见延迟很小且确实降低空转开销后，为该连接加入短暂、有上限的重试冷却；冷却期间不得积累突发额度，相关
  库存、过滤、红石或连接状态变化时应尽量提前唤醒。
- 发货终端相邻的来源容器消失或不再暴露物品能力时，按“没有可发送物品”处理；收货终端相邻的目标容器消失或不再
  暴露物品能力时，按“目标当前不能接收”处理。两种情况都只暂停搬运，保留绑定、设置速率和预约占用；容器或能力恢复
  后自动继续且不产生突发。只有 P2P 终端方块本身被替换才按生命周期规则解绑。
- 多来源收货端不提供玩家可配置的来源优先级或权重。固定公平策略仍使用轮询；发送方负责实际推送，接收端索引或统一
  调度器负责决定当前允许哪个来源提交，不能退化为 tick 顺序永久偏袒。
- 首版传输没有玩家可见的中转缓存或在途动画。一次成功移动在同一次服务端调用中完成，未被目标实际接受的余量必须
  立即留在或退回发送方，不能进入接收方的其他隐藏槽、掉落到世界或计入已移动预算。
- 本计划中原先的“Action 部分成功”来自仓库接口通过 `TownResourceActions.ItemStackAction` 修改城镇虚拟仓库的实现，
  不适用于 P2P 的术语。P2P 对应的边界是目标物品能力在模拟后只实际接受一部分，或提交阶段返回剩余物品；T05 必须以
  目标实际接受量为准扣减来源和速率预算，并把余量恢复到发送方。
- P2P 不强制加载区块或维度。任一端点所在维度或区块未加载时暂停连接并保留绑定，待双方重新加载后继续；暂停期间不
  允许空闲额度累积，并继续占用已接受的预约运力。
- 任一端点位置已被其他方块替换，或两端不再属于同一城镇队伍时，服务端在下次可验证事实时自动解绑，并按同一稳定
  连接 ID 清理双方索引和预约。短暂未加载不能被误判为方块已替换。
- 首版采用常规 Minecraft 生命周期保证，不实现发送方不可见恢复日志或强制同步写盘。完整服务端调用、正常停服、
  区块加载/卸载和目标部分接收必须保证未送达余量仍由发送方持有；JVM、进程或机器在来源提取与目标插入之间突然
  崩溃或断电不属于首版保证范围，文档和测试不得把该硬崩溃窗口描述为已经解决。

## Design Questions to Freeze

### Device and topology

- 无剩余阻塞项；首版不提供来源优先级、权重或广播。

### Capacity ownership

- 单条有向连接只创建一条预约，并继续用发送端的 `TransportEndpointId(GlobalPos)` 作为预约 key；稳定 binding ID、收货端
  入站索引和双方关系由 T03 的城镇级 P2P 状态持有。T01-T03 必须实现独立休眠表达和多预约原子增删。
- 初次绑定、改绑或主动上调速率被拒绝时，菜单和世界反馈如何显示 `requiredAdditionalCapacity`；未绑定状态或已有
  设置速率和旧连接继续运行的权威行为已经冻结，剩余问题只涉及 T07 的具体呈现。

## Proposed State Contract

已经实现且后续任务必须优先复用的通用前置合同：

```text
TransportEndpointId
└─ GlobalPos endpointPos

TransportEndpointRequest
├─ TransportEndpointId endpointId
├─ TransportEndpointKind endpointKind
└─ int rateItemsPerSecond

TransportReservation (persistent authority)
├─ TransportEndpointKind endpointKind
├─ int rateItemsPerSecond
├─ double scaleMetric             // server-derived fact
└─ TransportAdmissionStatus

TransportReservation.SNAPSHOT_CODEC
└─ adds double reservedTransportCapacity

TransportReservationResult
├─ decision
├─ optional reservationAfter
├─ TownTransportSummary townSummaryAfter
└─ requiredAdditionalCapacity

TeamTown
├─ registerOrUpdateTransportEndpoint(...)
├─ refreshTransportEndpointMetric(...)
└─ unregisterTransportEndpoint(...)
```

`TransportEndpointRequest` 是不可信设置输入，不能重新加入距离、对端坐标或占用字段。当前
`registerOrUpdateTransportEndpoint`/`refreshTransportEndpointMetric` 会调用仓库拓扑专用的
`currentWarehouseDistance`，`TeamTownData#refreshWarehouseTopologyIfDirty` 也只批量重算 `WAREHOUSE_INTERFACE`。
因此 P2P 的 `T01/T02` 必须先增加按 `TransportEndpointKind` 选择的服务端事实解析和占用公式；在该边界完成前，不能把
P2P kind 塞进现有入口并误用“接口到全镇仓库的加权距离”。删除连接只按稳定 `TransportEndpointId` 调用
`unregisterTransportEndpoint`；按单仓核心批量注销的 API 已不存在。

P2P 不应在稳态 tick、区块加载变化或普通事实刷新中调用 `refreshTransportEndpointMetric`。直连距离只在建立/改绑、
存档迁移或恢复校验时从绑定双方的固定 `GlobalPos` 派生；端点方块被移动或替换时旧位置的稳定端点失效并按生命周期
规则解绑，不能把新位置当成同一连接的距离变化。

未来 P2P 自身的持久化类型和字段由 T03 确定。其逻辑至少要表达已冻结的有向连接、双向端缓存模式和多来源
收货索引，但不能让客户端提交权威距离或占用：

```text
P2PDirectedBinding
├─ stable binding ID
├─ sender GlobalPos
├─ receiver GlobalPos
├─ rateItemsPerSecond
├─ distanceMetric
├─ active/dormant transport state
└─ admissionStatus

P2PReceiverIndex
└─ incoming sender endpoint IDs

BidirectionalTerminalState
├─ pendingSend ItemStack[4]
├─ received ItemStack[4]
├─ send filter
├─ receive filter
└─ peer endpoint ID

P2PRouteCardState
├─ optional pending first endpoint
└─ optional stable binding ID
```

每条有向连接只由发送端点拥有唯一预约，接收端点不重复预约；双向端互联因此登记两个相反方向的预约。Map 仍属于
具体 `TeamTownData`；绑定双方必须属于同一城镇，且服务端要重新验证端点方块类型和队伍。任何客户端提交的距离或
占用都只能视为请求参数，权威值必须由服务端位置和统一公式生成。

## Validation Outline

- 公式：距离 `0`、相邻、长距离、速率边界、相差 `1/8/9 ULP`、非有限数和乘法溢出。
- 配对：无序点击、重复操作、自环、同端点对后绑定覆盖、目标替换、改绑、路线牌精确解除、旧牌不误删新连接、不同
  队伍、跨维度、队伍外玩家和同 tick 竞争操作；初次绑定使用通用默认速率，成功后才能调整，改绑沿用旧设置速率。
- 生命周期：双方加载/卸载的四种组合、未加载时不强制加载且保留绑定和预约、重新加载后无突发、方块替换自动解绑、
  换队自动解绑、相邻容器或能力消失时保留连接和预约、容器恢复后无突发、重启和存档升级。
- 安全：来源扣除与目标插入的提交边界、模拟后目标只部分接收、余量回到发送方、目标满、异常中断、发送/接收过滤
  交集变化、未配置放行全部、白/黑名单、精确数据/NBT 与模糊物品种类匹配、双向端独立过滤、内建中继被拒绝、外部
  缓存中继逐跳独立，以及外部物流接成闭环时每段 P2P 的背压与物品守恒。
- 双向缓存：待发送/已接收各四格的保存和同步；任一缓存非空时仍可成功切换到锁定模式；锁定后外部自动化和 P2P
  访问被拒绝、玩家只能手动取出不能放入；解除连接后能力恢复且遗留物品不变。
- 吞吐：默认速率、`1280 items/s`、短缺小数比例、多个链路公平性、空闲后恢复无突发；红石停机时连接保留但有效
  速率和占用均为 `0`，恢复后重建占用并正确进入比例短缺；未加载暂停时实际搬运为 `0` 但预约占用不变。
- 容量准入：同一绑定的距离在其生命周期内恒定；初次绑定和改绑都像玩家放置仓库接口一样按新距离和设置速率执行
  玩家准入，不能直接制造比例短缺。拒绝时初次绑定保持未绑定，改绑保留旧连接，终端不保存未生效目标；玩家主动提高
  设置速率遵循相同的原子拒绝合同。
- 同步与反馈：服务端拒绝篡改值，菜单、方块状态和镇长印章描述同一权威状态。
- 性能：大量已加载但空闲设备不持续扫描库存、标脏或发送网络包；若实现重试冷却，验证上限、状态变化提前唤醒和
  冷却期间不积累突发额度。
